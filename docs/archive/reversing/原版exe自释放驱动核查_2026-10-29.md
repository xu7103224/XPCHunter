# 原版 exe 自释放驱动核查（2026-10-29）

> 本文修正先前「原版驱动 = `View++_Driver64.sys`」的假设，并给出一个
> 会影响功能对齐策略的结论。

## 0. 结论摘要

| 问题 | 答案 |
|---|---|
| 原版 exe 会自释放驱动吗？ | **会**。资源类型 `KERNEL`、ID `0xE7`，写到程序目录后注册为服务加载 |
| 我们逆向的 `View++_Driver64.sys` 是它释放的那个吗？ | **不是**。是同一产品线的**另一个版本** |
| 两者功能等价吗？ | **不等价**。exe 释放的 1.0.0.5 只有 197 个命令实现，1.0.6.0 有 248 个 |
| 原版 exe 发的命令在 1.0.0.5 里都能用吗？ | **不能**。260 条里有 74 条落在 1.0.0.5 的空槽位，被静默跳过 |
| 我们的复刻基础还成立吗？ | **成立，而且基础更好**。我们按 1.0.6.0 复刻，是功能超集 |

## 2. 自释放机制（完整调用链）

### 2.1 入口 `sub_1400EE4C0`

```
GetModuleFileNameW(0, path, 0x104)      ; exe 自身路径
wcsrchr(path, '\\')                     ; 截到目录
if (盘符文件数 <= 0x1E)
    wcsncpy(Destination, exe_basename, 0x20)   ; 用 exe 文件名（去扩展名）

GetDriveTypeW("X:\\")
if (类型 != 3 /* 非固定盘 */)
    GetSystemDirectoryW(...); wcsncat("\\drivers")   ; 落到 System32\drivers

for (edi = 0; edi < 0x20; edi++) {
    if (edi)  snwprintf(Buffer, "%s\\%s%s.sys", dir, Destination, "as")
    else      snwprintf(Buffer, "%s\\%s.sys",  dir, Destination)
    if (!sub_1400EEA50(Buffer)) continue;     ; 写出失败换名字
    if (sub_140048FE0(Buffer)) { 成功; break; }
    sub_1400EE9E0(Buffer);                    ; 删除残留
    if ((edi & 1) == 0) sub_1400EE890(Destination);  ; 每两轮换随机名
}
```

第一轮名字是 `PCHunter`（`mov dword ptr [Destination], 430050h` 即 `'P' 'C' 'H' 'u' 't'`）。
之后 `sub_1400EE890` 用 `GetTickCount()` 做种子、`rand() % 26 + 97` 生成
14~17 个小写字母的随机名，并跳过已存在的文件。

### 2.2 写盘 `sub_1400EEA50`

```c
FindResourceW(hMod, (LPCWSTR)0xE7, L"KERNEL")
LockResource(...)
if (目标文件已存在 && memcmp 相同) return 成功;   // 不重写
CreateFileW(..., CREATE_ALWAYS, FILE_ATTRIBUTE_HIDDEN)
SetFileAttributesW(..., attrs | HIDDEN | SYSTEM)
WriteFile(资源内容)
```

### 2.3 注册服务 `sub_140048B20`

```c
GetProcAddress(ntdll, "ZwLoadDriver")
RegCreateKeyW(HKLM, L"System\\CurrentControlSet\\Services\\<name>")
    Type = 1 (SERVICE_KERNEL_DRIVER)
    ErrorControl = 1
    Start = 1
    ImagePath = L"\\??\\<完整路径>"
// 防安全模式清理：
RegCreateKeyW(HKLM, L"...\\Control\\SafeBoot\\Minimal\\<name>.sys")
RegCreateKeyW(HKLM, L"...\\Control\\SafeBoot\\Network\\<name>.sys")
ZwLoadDriver(L"\\Registry\\Machine\\System\\CurrentControlSet\\Services\\<name>")
// 失败则删除 Enum / Security / Services\<name>
```

### 2.4 打开设备 `sub_140048FE0`

```c
wcsrchr(driver_path, '\\')               // 文件名
wcsrchr(name, '.')                       // 去掉 .sys
snwprintf(Destination, L"\\\\.\\%s", name)   // \\.\<驱动文件名>
CreateFileW(Destination, GENERIC_READ, ...)  // 先试直接打开
if (失败) sub_140048B20(...)                 // 再注册服务加载
```

**设备名 = 驱动文件名（去扩展名）。** 因为驱动随机命名，设备名每次运行都不同，
所以 exe 里搜不到任何硬编码的设备名字符串。

## 3. 内嵌资源清单

`KERNEL` 类型下三个 PE，全部是内核驱动（Subsystem=1）：

| 资源 ID | 尺寸 | 架构 | SizeOfImage | EntryPoint |
|---|---|---|---|---|
| 167 | 616,232 | x86 | 0xB2000 | 0xAD000 |
| 178 | 616,744 | x86 | 0xB2000 | 0xAD000 |
| **231 (0xE7)** | **644,888** | **x64** | **0xBC000** | **0xB9000** |

`FindResourceW` 写死 0xE7，因此**只有 231 会被释放**。167/178 供 32 位 exe 使用。

## 4. 命令表逐槽对比（核心发现）

把 1.0.0.5 装进 IDA，用 `mov eax, 8D8h` 特征定位到命令表初始化函数
（RVA `0x72FE0`），与 1.0.6.0 的 `InitCommandHandlerTable` 逐槽对比。

### 4.1 NULL 槽位分布

| | 1.0.0.5 | 1.0.6.0 |
|---|---|---|
| 非 NULL 槽位 | **197** | **248** |
| NULL 槽位 | **86** | **35** |

NULL 区间对比：

```
1.0.0.5: 3, 97-98, 105-110, 114-119, 121-123, 131-138, 158-159,
         165-166, 185-190, 198-224, 237-240, 249-262, 273-276, 282
1.0.6.0: 3, 97-98, 105-110, 114-119, 121-123, 131-138,
         165-166, 185-190, 282
```

两版共有的 NULL 是 35 个；1.0.0.5 另外多出 51 个空槽。

### 4.2 51 个新增槽位（1.0.6.0 相对 1.0.0.5）

单向新增，**没有任何槽位被移除**：

| 区间 | 命令行 | 功能 |
|---|---|---|
| 158–159 | 0x0BE–0x0BF | MiniFilterPreRename / PreVolumeMount |
| 198–224 | 0x0E6–0x100 | SSDT 表读写、导出表修复、Hook 安装、内核内存上下文 |
| 237–240 | 0x10D–0x110 | MiniFilter PreDelete/PreFlush/PreHardLink/PreShutdown |
| 249–262 | 0x119–0x126 | Hook 详情查询、进程/线程上下文（Win7/8/10） |
| 273–276 | 0x131–0x134 | 回调上下文、线程上下文 |

### 4.3 原版 exe 与 1.0.0.5 的错配

原版客户端 exe 发出 **260 条**命令，其中：

| | 数量 |
|---|---|
| 落在 1.0.0.5 空槽位（被 `if (HandlerFunc)` 静默跳过） | **74** |
| 在 1.0.0.5 里有实现 | 186 |

**这 74 条恰好覆盖 SSDT、Hook、内核内存、进程上下文这几类核心 ARK 功能。**
也就是说，原版 exe 配它自己释放的驱动时，这 74 个功能是**点了没反应**的。

其中 49 条属于 1.0.6.0 新增的 51 条；另外 25 条是两版都为 NULL 的槽位
（`3, 97-98, 105-110, 114-119, 122-123, 131, 133-138, 282` 等）。

## 5. 对我们复刻工作的影响

### 5.1 结论：我们做对了，而且比原版更完整

我方驱动按 1.0.6.0 逐槽复刻（283 槽差异 0，248 个实现 + 35 个 NULL），
**这是 1.0.0.5 的功能超集**。原版 exe 能用的 186 条我们都有，
原版 exe 用不了的 74 条我们**也有 49 条**。

所以之前所有基于 1.0.6.0 的复刻工作**没有白做**，方向是对的。

### 5.2 但要修正一个判断

之前认为「219 条真缺口，需要全部补齐」。现在要按「原版实际能达到的能力」分三层：

| 层次 | 命令数 | 说明 |
|---|---|---|
| **A 层**：原版 exe + 1.0.0.5 真正可用的功能 | **186** | 原版用户实际体验到的能力上限 |
| **B 层**：我方驱动多出来的能力 | **49** | 1.0.0.5 空槽位但我方有实现，exe 会发送 |
| **C 层**：两版都空槽 | **25** | 原版也不处理，无需实现 |

186 + 49 + 25 = 260，与原版 exe 发出的命令数吻合。

**做功能对齐时，标杆应该是 A 层 186 条**，而不是 260 条。因为原版界面
在那 49 条对应的功能上，本身就显示不出数据——用户看到的就是空列表。

B 层 49 条是我们可以**做得比原版更好**的地方，属加分项而非对齐项。
它们全部集中在 SSDT/Hook/内核内存/进程上下文，正是 ARK 工具最核心的能力区。

C 层 25 条是两版都空槽（`3, 97-98, 105-110, 114-119, 122-123, 131,
133-138, 282` 等），原版自己也不处理，不必实现。

### 5.3 协议层的结论不变

- exe 侧发送器 `sub_14004DD40` 明文写 `*(_DWORD *)lpInBuffer = 539232272`（= `0x20240810`），
  说明**魔数是客户端决定的**，驱动侧可选校验。
- 我方驱动校验它，与 exe 实际行为匹配，实机验证通过（0x25/0x56/0xC7）。
- 1.0.0.5 里没有这个常量，说明它不校验魔数——不影响我们。
- 260 条命令清单、入参/出参尺寸映射**仍然有效**（从 exe 侧提取，与用哪个 .sys 无关）。

### 5.4 设备名的注意事项

我方驱动硬编码 `\Device\View++ByLinxer`，我方客户端硬编码同名。
若要跑「原版客户端 + 我方驱动」，文件必须命名为 `View++ByLinxer.sys`，
因为原版客户端按**驱动文件名**拼设备名（`\\.\<文件名去.sys>`）。

## 6. 提取脚本

```python
data = open('PCHunter64.exe','rb').read()
bias = 0x7A3A00 - 0x846000            # .rsrc 段 RAW - VA
drva, dsz = 0x97E890, 644888          # 资源树 231/2052 的 DataRVA / Size
blob = data[drva+bias : drva+bias+dsz]
open('PCHunter_embedded_0xE7.sys','wb').write(blob)
```

资源树遍历：从 `.rsrc` 起始偏移读 `IMAGE_RESOURCE_DIRECTORY`，
第一层是类型（命名项 `KERNEL`），第二层是 ID，第三层是语言（2052=简中）。
