# 原版客户端命令清单 —— 全量重提取（2026-10-29）

> 本文修正此前「原版客户端只发 180 条命令」的结论。该结论源于提取脚本只扫描了
> `0x14001F000–0x14002B000` 这一个约 48KB 的区间，而命令发送器 `sub_14004DD40`
> 的真实调用点散布在整个 `.text`（最远到 `0x1400529AB`）。

## 1. 结论先行

| 项目 | 旧结论（错误） | 本次全量重提取 |
|---|---|---|
| 发送器调用点 | 184 | **487**（可解析 448） |
| 不同命令号 | 180 | **260** |
| 覆盖驱动槽位 | — | **260 / 283**（0..282） |
| 我方已接入 | 18 | 18 |
| 真实缺口 | 143 | **235**（另有 25 条原版发往驱动 NULL 槽位） |

关键点：**原版客户端把命令表用到了 260/283，几乎占满**。此前「180 条、缺 143 条」
低估了约 90 条。

## 2. 提取方法（可复现）

1. 用 IDA MCP 取 `sub_14004DD40` 的全部 xref：**490 条**，其中 487 条落在 `.text`。
2. 用 `dumpbin /disasm /range:` 反汇编 `0x14001F337–0x1400529AB`，得 70,216 行。
3. 对每个调用点，向前回溯到最近的 `lea rcx, [frame+disp]` —— 这是请求结构体基址
   （IDA 已注释为 `lpInBuffer`）。
4. 以该基址 + 偏移定位协议字段（字段名与我方 `XPCH_REQUEST` 一致）：

   | 偏移 | 字段 | 说明 |
   |---|---|---|
   | `+0x00` | Magic | 调用方不写，由 `sub_14004DD40` 强制填 `0x20240810` |
   | `+0x04` | **Command** | 命令号，本次提取的目标 |
   | `+0x08` | OutputBuffer | 结果字节指针（1=成功） |
   | `+0x10` | ContextPointer | 入参缓冲 |
   | `+0x18` | ExtraPointer | 出参缓冲 |
   | `+0x20` | OutputSize | 输出缓冲大小 |
   | `+0x24` | ContextSize | 入参缓冲大小 |
   | `+0x28` | Checksum | MD5(前 0x28 字节)[0..3] |
5. 栈偏移归一化：`r11` 需与 `rsp` 视为同一帧（`mov r11, rsp` prologue），
   `push`/`sub rsp` 累加偏移，`lea rbp, [rsp±x]` 建立 rbp 帧基址。

命中率：**448 / 487 = 92%**。

### 未解析的 39 个调用点

全部属于**动态命令号**：命令号来自寄存器（如 `mov [rsp+24h], ebp` 或
`mov [rsp+24h], r8d`），同一条封装函数按参数服务多条命令。典型例子：

```asm
; sub_14001FC63  —— 命令号在 ebp
mov dword ptr [rsp+24h], ebp
mov qword ptr [rsp+38h], rbx        ; OutPtr
mov dword ptr [rsp+44h], 200000h    ; OutSize = 2MB
call sub_14004DD40
```

这类封装是「批量转发器」，实际命令号由上层调用者传入，不影响命令集合的完整性
（其取值必落在已发现的 260 条之内）。

## 3. 协议字段全部在封装函数体内可见

抽样反编译 24 个封装函数，**全部可读**。最简形态只有 7 行：


## 4. 反编译可行性 —— 难度的真实分界

对 351 个不同封装函数按大小分层抽样：

| 函数大小 | 数量 | 反编译结果 |
|---|---|---|
| ≤ 0x600 字节 | **346（99%）** | 全部成功，伪代码可读 |
| > 0x600 字节 | **5（1%）** | 全部失败，需读汇编 |

失败清单（`Decompilation failed`）：

- `0x140039CC0`（7149 字节）
- `0x14003C0D0`（6634 字节）
- `0x140037AA0`（4735 字节）
- `0x14003E7E0`（3113 字节）
- `0x140036F50`（2567 字节）

这 5 个虽然 Hex-Rays 失败，但**汇编仍可读**。实测 `0x140037AA0` 的协议一目了然：

```asm

mov dword ptr [rbp+130h+var_1A8+4], 5Ah     ; 入参: 值名长度

mov dword ptr [rbp+130h+var_138+4], 8       ; OutSize = 8

```

**所以即使最大的 7KB 函数，协议层也能提取，只是慢一些。**

## 5. 原版的两个复用模式（影响工作量估算）

### 5.1 预取 + 按下标取详情

`sub_140024040` 反编译结果：

```c
malloc(0x578);                           // 1400 字节 = 28 × 48 + 8
InBuffer[0] = 0xB600000000LL;            // cmd = 0xB6
InBuffer[4] = 0x57800000000LL;           // OutSize = 0x578
sub_14004DD40(InBuffer);                 // 一次性取回整张表
if (*v4 == 1 && n <= 0x1B)               // 表头标志 + 下标范围
    v5 = &v4[48 * n + 8];                // 第 n 条记录
else if (v4[1] == 1 && n == 28)
    v5 = v4 + 1352;                      // 第 28 条（表尾附加记录）
...
v9 = 183;                                // cmd = 0xB7
v13 = 48;                                // 单个记录 48 字节
```

含义：**一次 `0xB6` 拿回整张表，之后 `0xB7` 只取某条详情**。这类「列表页 + 详情页」
在原版里普遍存在，因此 260 条命令覆盖的界面功能远多于 260 个。

### 5.2 通用读写原语被大量复用

- `cmd=0x62`（98）— **打开对象**，入参是宽字符路径，出参是句柄
- `cmd=0x64`（100）— **查询对象大小**
- `cmd=0x67`（103）— **读取对象内容**

这三条在 `sub_140032290`（导出文件）、`sub_14004BB00`（批量导出）等多处重复出现，
是「路径 → 打开 → 查大小 → 读内容」的通用文件导出管线。已观察到调用点：
`0x62` 6 处、`0x64` 7 处、`0x67` 5 处。

## 7.1 顺带核实的两处事实

**其一：`0x13A` 是原版的死代码路径。**
原版确实在 `sub_14004C240` 里发 `0x13A`（申请 1MB 输出），但驱动 `Table[282]`
是 NULL，`if (HandlerFunc)` 判空后直接返回 result=0，所以原版这个调用**永远失败**。
我方在 282 槽挂了自己的诊断处理器（导出每条命令的调用次数/结果/PID），
因此这条命令在我方是「可用」的，比原版更好用而不是更差。

**其二：`0x13A` 出现在原版里，说明之前的提取器确实漏扫描。**
旧的 48KB 区间提取不到 `0x14004C2C3`（位于 `.text` 偏移 +0x4C 万处），
这正是「180 条」偏低的直接原因之一。

## 8. 对「是否需要逆向 exe」的回答

**需要，而且难度不高。** 依据：

1. **协议层 100% 可提取**。所有封装函数都是「填 5 个字段 + 调一次发送器」，
   99% 的函数 Hex-Rays 可直接给出命名良好的伪代码，剩下 1% 读汇编也能拿到字段。
2. **真正的成本不在破解，在出参结构的语义**。命令号、尺寸、入参布局一眼可见；
   但「这 52 字节记录里第 7 个 DWORD 是什么」需要对照驱动侧实现或界面列标题才能命名。
3. **驱动侧已完全对齐**（283 槽差异 0），所以出参结构可以直接从我们的驱动源码读，
   不需要从 exe 侧反推。这消掉了最难的一半。

工作量的正确估算不是「260 条 × 单条成本」，而是「219 条缺口 × (协议提取 + 界面接线)」，
其中协议提取因为驱动已有实现而大幅简化。

### 8.1 端到端可行性样本

以槽位 11（`CmdReadProcessMemoryBlock`）为例，完整走通一遍：

**exe 侧**（`sub_140035D00`，反编译 18 行）：

```c
_BOOL8 sub_140035D00(__int64 a1, __int64 a2, __int64 a3, int a4)
{
    _QWORD v5[2];
    v5[0] = a1;      // 入参第 1 项
    v5[1] = a2;      // 入参第 2 项
    v7 = 43;         // cmd = 0x2B
    v9 = v5;         // ContextPointer = &v5
    v11 = 16;        // ContextSize = 16（两个 qword）
    v10 = a3;        // ExtraPointer = a3
    v12 = a4;        // OutputSize = a4
    sub_14004DD40(v6);
    return v13 == 1;
}
```

**驱动侧**：`Table[11] = CmdReadProcessMemoryBlock`（槽位 = 0x2B − 0x20 = 11，吻合）。

**结论**：入参 = 两个 64 位值，出参长度由调用方给，成功标志单字节。
实现只需要照着这个签名调用 `XpchInvoke(Client, 0x2B, &in, 16, out, outSize, &res)`，
再按驱动源码解析 `out`。**没有任何需要猜测的地方。**

同样的流程对 219 条缺口逐条重复即可，单条成本主要在「读驱动源码给字段命名」，
而不是「逆向 exe」。
