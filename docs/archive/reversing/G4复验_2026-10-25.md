## 一、发现并修复的三个真实缺陷

本轮 G4 复验的价值不在"确认通过"，而在**暴露了三个会实际影响用户的缺陷**。

### 1.1 `FeCheckKiDebugRoutine` 缓冲区溢出 → 进程被中止

| | |
|---|---|
| 现象 | `--g4-status-cli` 完全无输出；调试器看到 `STATUS_HEAP_CORRUPTION`（`0xC0000374`） |
| 根因 | 该函数写入 176 字符的说明，而 `--g4-status-cli` 与 GUI 状态栏只给 `char detail[160]`。`strcpy_s` 超长时触发 `_invalid_parameter_handler`，默认**中止进程** |
| 修复 | 调用方缓冲 `160 → 512`；`FeCheckKiDebugRoutine` / `FeFindPteHook` 改用 `_snprintf_s(..., _TRUNCATE, ...)`，缓冲不足时截断而非中止 |

### 1.2 `CMD_STAT_EXT_TOTAL_SIZE` 少算 0x11C0 → 内核越界写 BSOD 0x3B

| | |
|---|---|
| 现象 | `--scan` 扫到 0x13A 时 BSOD 0x3B；崩溃指令 `mov qword ptr [rcx+rbx+948h], rax`（`rbx = 0x11B0`） |
| 根因 | 宏只算了「env 块及之后的相对长度」，**漏掉前面「表快照 283×16 + 打开记录 16」= 0x11C0**。Need 只有 0xA40，实际写到 0x1C00，缓冲区之后 0xBC0 字节全部越界 |
| 修复 | 新增 `CMD_STAT_HEAD_SIZE`，`CMD_STAT_EXT_TOTAL_SIZE = HEAD + ALLOCPROC_INENV + 48 = 0x1C00`。实测 0x13A 由 BSOD 变为 `OK / result=1` |

### 1.3 `FeSettingReadObjectTypes` ENV 尺寸不一致 → 堆损坏

| | |
|---|---|
| 现象 | `--setting-cli` 无输出，随后 guest 不可达；`ntdll!RtlReportCriticalFailure`、`rbx=0xC0000374` |
| 根因 | 客户端写 `ENV = 0x320`，驱动实际 `CMD_ENV_SIZE = 0x4A0`，小 0x180；驱动写 `env+0x340` 已越界，后续诊断段整体错位 |
| 修复 | 统一为 `0x4A0`，并按驱动公式补全 `SNAP` / `+48`：`TOTAL = 0x1C00`（与驱动 `CMD_STAT_EXT_TOTAL_SIZE` 完全一致） |
| 修复后实测 | `object types: available`，`PsProcessType = FFFFF8032016F390`、`PsThreadType = FFFFF8032016F3B8`，`extra[3]/[4]` 与 `extra[6]/[7]` 的 RVA/运行期地址成对吻合 |

### 1.4 附带：`--regkey-cli` 未剥离双引号

路径末尾带 `"`，导致 `reg key: HKLM\SOFTWARE\Microsoft" (0 values)`。
已按其它分支的写法剥离引号与行尾空白。
