# 钩子检测能力分析：是否需要逆向、以及误判风险的来源

日期：2026-10-29
问题：进程钩子、驱动钩子检测需要对映射 PE 做二进制比对，经验要求高，
      且容易误判。这部分是否必须逆向实现？

## 0. 结论

**必须逆向，而且误判风险不是来自"经验不足"，而是来自"缺少基线"。**

原版的做法不是"拿内存字节跟磁盘字节比"这么简单。它有一套**三层判定模型**，
每一层解决一类误判：

| 层 | 判据 | 解决的误判 |
|---|---|---|
| 1 | 表项当前值 ≠ 原始值 | 只抓地址重定向，不碰代码 |
| 2 | 内存前 16 字节 ≠ 磁盘前 16 字节 | 抓 inline patch |
| 3 | 双重有效性校验（地址可读 + 逐字节可读） | 排除换页、跨页断裂导致的假差异 |

我方当前实现**只做了第 1 层的一半**，第 2 层的对比源和防护都不完整。

## 1. 原版的真实实现（逆向证据）

### 1.1 `QuerySyscallHookStatus`（`0x140087400`）

```c
char QuerySyscallHookStatus(__int64 SyscallAddress)
{
    if (!GtRead(GtKeRaiseIrql)) ParseSyscallTableExportDir();   // 懒加载基线
    TableEntryCount = GtRead(GtKeRaiseIrql);
    SyscallTable    = GtRead(GtKeLowerIrql);
    if (TableEntryCount && SyscallTable
        && CheckMemoryValid(SyscallTable) == 1
        && CheckMemoryValid(SyscallTable + 55) == 1)
    {
        HookTableBuffer = GtAlloc(8576);          // 4 条记录的基线表
        // 在 4 条记录里找 SyscallAddress
        for (TableIndex = 0; TableIndex < 4; TableIndex++) {
            if (pHookTable[6*TableIndex + 1] == SyscallAddress) break;
        }
        if (TableIndex >= 4) return 0;

        if (LODWORD(pHookTable[6*TableIndex]) == 1) {     // 基线有效
            pTargetEntry = SyscallTable + (TableIndex + 1);
            OriginalAddress = pHookTable[6*TableIndex + 1];
            if (*pTargetEntry != OriginalAddress) {       // ← 第 1 层
                Result = 1;
                WritePhysicalMemoryQword(pTargetEntry, OriginalAddress);  // 顺手恢复
            }
            if (MemoryCompare(pHookTable[6*TableIndex+1],
                              (char*)pHookEntry + 16, 0x10)) {  // ← 第 2 层
                OriginalBytes = *((_OWORD*)pHookEntry + 1);
                return WritePhysicalMemoryBuffer(...) | Result;
            }
        }
    }
}
```

关键点：

1. **基线来自磁盘文件**（`ParseSyscallTableExportDir` 那条链从
   `wdf01000.sys` 的文件映像里解析出两张系统调用表，存进 GT）。
   不是"运行时快照"，是"磁盘上的原始值"。
2. **只比对 16 字节**，不是整个函数。因为 inline hook 只需改前几个字节。
3. **对比前先 `CheckMemoryValid(SyscallTable + 55)`**——检查整段 56 字节可读。
   这是防跨页断裂的护栏。

### 1.2 `ValidateSingleHookEntry`（`0x140085ADC`）—— 误判防护的核心

```c
char ValidateSingleHookEntry(__int64 a1)
{
    v2 = *(_QWORD*)(a1 + 8);                    // 当前地址
    if (!v2) return 1;                          // ← 空条目直接放过
    if (v2 != *(_QWORD*)(a1 + 16))              // 当前 ≠ 原始
        *(_BYTE*)a1 = 1;                        //   标记 addrChanged

    if (CheckMemoryValid((void*)(v2 + 15)) == 1)  {   // ← 关键护栏 1
        if (MemoryCompare(*(_QWORD*)(a1+8), (char*)(a1+24), 0x10)) {
            v3 = *(_BYTE*)a1 == 0;
            *(_BYTE*)(a1+1) = 1;                //   标记 bytesChanged
            if (v3) {
                for (i = 0; i < 0x10; i++)      // ← 关键护栏 2
                    if (!CheckMemoryValid((void*)(*(_QWORD*)(a1+8) + i)))
                        break;
                if (i && ReturnFalseStub() == 1)   // ← 关键护栏 3
                    *(_QWORD*)(a1+16) = v6;
            }
        }
    }
    return 1;
}
```

三层护栏各自防一类误判：

| 护栏 | 代码 | 防什么 |
|---|---|---|
| **1. 尾部有效性** | `CheckMemoryValid(v2 + 15)` | 地址在页尾、+15 越界 → 整条跳过，不做判断 |
| **2. 逐字节有效性** | 循环 `CheckMemoryValid(v2 + i)`，全部通过才继续 | 跨页断裂（前半页映射、后半页未映射） |
| **3. 二次确认** | `ReturnFalseStub()` 返回 1 才写回 | 只对确定可疑的条目回填原始地址 |

**`ReturnFalseStub` 的真相**：它在驱动里只有 2 条指令
（`xor al, al; ret`），即**恒返回 0**。所以这两处调用：

```c
if (i && ReturnFalseStub() == 1)
    *(_QWORD*)(a1 + 16) = v6;          // 永远不会执行
```

是**死代码**。原版在这里留了一个"看起来会回填原始地址"的分支，
但开关永远是关的。实际被采用的判定只有：

```c
if (v2 != *(_QWORD*)(a1 + 16))  *(_BYTE*)a1 = 1;      // addrChanged
if (MemoryCompare(...))         *(_BYTE*)(a1+1) = 1;   // bytesChanged
```

两个标志位就是最终输出，不需要"回填"。这段死代码的意义是：
**保留了回填能力但默认关闭**，因为自动回填风险太高（可能把正常的
系统修补也回滚掉）。

> 注：我方 `SystemInfo.c:12` 的 `ReturnFalseStub` 同样返回 0，
> 与原始驱动 `0x140007AB0` 一致，此处转写正确。

### 1.3 `GetHookEntryInfo`（`0x140086CD4`）—— 每次固定查 4 条

```c
// 固定填 4 条记录，每条 40 字节，共 160 字节（>= 0xA0）
*(_QWORD*)(a3 + 16)  = v9[1];
*(_QWORD*)(a3 + 56)  = v9[2];
*(_QWORD*)(a3 + 96)  = v9[3];
*(_QWORD*)(a3 + 136) = v9[4];
// 再从基线表取 4 条的 {标记, 地址, 原始16字节}
if (基线[0]有效) { *(a3+8)=..., *(a3+24)=16字节 }
if (基线[1]有效) { *(a3+48)=..., *(a3+64)=16字节 }
if (基线[2]有效) { *(a3+88)=..., *(a3+104)=16字节 }
if (基线[3]有效) { *(a3+128)=..., *(a3+144)=16字节 }
// 逐条验证
ValidateSingleHookEntry(a3);       // +0
ValidateSingleHookEntry(a3+40);    // +40
ValidateSingleHookEntry(a3+80);    // +80
ValidateSingleHookEntry(a3+120);   // +120
```

这 4 条对应的是**系统调用入口路径上的 4 个关键跳转点**：
`KiSystemCall64` 链上的 int2e/sysenter → SSDT 的 4 段路径。
不是"所有函数"，而是"必经的 4 个关卡"——这是避免大量误判的关键设计。

## 2. 我方当前实现的差距

### 2.1 驱动侧

| 函数 | 状态 |
|---|---|
| `ValidateSingleHookEntry`（ContextMgmt.c:2518） | ✅ 已按原版转写，三层护栏齐全 |
| `QuerySyscallHookStatus`（TailHelpers.c:3952） | ❌ **实现完全错误**，见下 |
| `CmdCheckBytePattern` | ✅ 已转写 |
| `ParseSyscallTableExportDir` | ⚠️ 已转写，但依赖链上有 6 个下游函数需要验证 |

**`QuerySyscallHookStatus` 的实现错误是本次分析最重要的发现：**

我方版本：
```c
__int64 QuerySyscallHookStatus(__int64 SyscallAddress)
{
    // 只检查首字节是不是 E9 或 FF 25
    UCHAR FirstByte = *(UCHAR*)SyscallAddress;
    if (FirstByte == 0xE9) Result = 1;
    else if (FirstByte == 0xFF && (SecondByte & 0x3F) == 0x25) Result = 1;
    return Result;
}
```

原版版本：查基线表 → 比对地址 → 比对 16 字节 → 三护栏。

**两者语义完全不同。** 我方版本的问题：

1. **只看首字节**。现代 hook 常用 `mov rax, imm64; jmp rax`（12 字节）、
   `push imm; ret`、或 5 字节 `jmp rel32` 前面的 `nop` 填充——全都漏掉。
2. **不比对基线**，所以「首字节恰好是 E9 的正常函数」会被**误报**。
   x64 内核里 `E9` 作为首字节的合法函数不少（长跳转编译产物）。
3. **不做有效性校验**，`SyscallAddress` 无效时会直接读崩（虽然有
   `MmIsAddressValid` 保护，但没有 `+15` 的尾部检查，页尾仍可能失败）。

这是一处**既有漏报又有误报**的实现，必须重写。

### 2.2 一个必须理解的设计：检测即恢复

原版 `QuerySyscallHookStatus` 在发现差异后**直接写回原始值**：

```c
if (*pTargetEntry != OriginalAddress) {
    Result = 1;
    WritePhysicalMemoryQword(pTargetEntry, OriginalAddress);   // 顺手恢复
}
...
if (MemoryCompare(...)) {
    return WritePhysicalMemoryBuffer(addr, &OriginalBytes, 0x10, 0, 0) | Result;
}
```

这带来两个后果：

1. **`0x11A`（QueryHookStatus）是有副作用的只读命令**。
   调用一次就会把检测到的 hook 抹掉，第二次调用返回 0。
   如果按"只读"语义去调它做 UI 刷新，会不知不觉改掉系统状态。

2. **误判的代价从"显示错误"升级为"破坏系统"**。
   如果基线错了（比如基线本身是 hook 后的值），恢复操作会把
   正常的系统修补写坏，可能直接蓝屏。

所以我方当前那个"只看首字节 E9"的实现，虽然是错的，
但至少**没有破坏性**——它只返回标志，不写内存。
重写时必须明确区分两条命令：

| 命令 | 应有行为 |
|---|---|
| `0x11A` QueryHookStatus | **只检测，不恢复**（改进原版） |
| `0x119` GetHookEntryInfo | 只填 4 条记录的标志和字节，不恢复 |
| `0x11B` EnumHookDetail | 只枚举详情 |
| `0x118` CmdCheckBytePattern | **这才是恢复命令** |

原版把恢复混进检测里，是因为它假定基线绝对可信。我方应按
"检测"与"恢复"分离设计，恢复只由 `0x118`（`RestoreSyscallHookByIndex`）
执行——那个函数本来就有完整的恢复逻辑。

### 2.3 客户端侧

`HookViews.c` 的 `FeScanRing3Hooks` 用「IAT 条目是否落在所有已加载模块之外」
作为唯一判据。这个判据的误判来源很多：

| 误判情形 | 说明 | 我方是否处理 |
|---|---|---|
| **延迟加载 / 手工绑定** | IAT 还没填，条目为 0 或指向 stub | 部分（跳过 0 和 <0x10000） |
| **模块枚举不全** | 32/64 位混合、Wow64、内存映射 PE 未列入 | ❌ 未处理 |
| **CFG 跳板** | Control Flow Guard 的 `__guard_dispatch_icall` 跳板在模块外 | ❌ 未处理 |
| **JIT / 动态代码** | .NET JIT、V8 代码页在模块外，但完全合法 | ❌ 未处理 |
| **钩子引擎的 trampoline** | Detours/Microsoft Detours 的跳板页 | ❌ 未处理 |
| **代理 DLL** | 转发导出，目标在另一模块 | ✅ 能正确匹配 |
| **地址对齐/大页** | SizeOfImage 与实际映射不一致 | ❌ 未处理 |

原版有 6 个独立的钩子对话框类，说明它把检测拆成了不同维度：

```
CRing3HookDialog         Ring3 钩子（IAT/EAT/inline）
CHookDialog             通用钩子列表
CCodeHookDialog         代码段 inline patch
CMessageHookDialog      消息钩子（SetWindowsHookEx）
CUserHookDialog         用户态钩子
CObjectTypeHookDialog   对象类型钩子
```

我方目前只有一个 Ring3 扫描，且判据单一。

## 4. 回答"是否需要逆向"

### 4.1 必须逆向，理由有三

**第一，判据本身无法凭经验猜出。**

"拿内存跟磁盘比"是实现细节，但**比哪 16 字节、比之前做哪些有效性检查、
哪些情况要放过**——这些是设计决策，只能从代码读出。
`ValidateSingleHookEntry` 的三层护栏就是典型：少一层就多一类误判，
多一层就漏一类攻击。

**第二，基线的构造方式决定了检测上限。**

原版从 `wdf01000.sys` 的**文件映像**里解析系统调用表描述符
（`ParseSyscallTableExportDir` 那条约 2000 字节的链）。这不是常识能想到的——
为什么是 wdf01000.sys？因为它是少数在 .data 里保留了完整 syscall 表
描述符的驱动之一，且稳定加载。

如果我方自己拍脑袋选基线（比如"用当前内存快照"），就永远检测不出
"从启动时就被 hook"的情况。

**第三，反分析的坑必须知道。**

`ReturnFalseStub()` 这种命名是故意误导。如果按名字理解，会认为
`if (i && ReturnFalseStub() == 1)` 恒假，从而删掉这段——结果就是
少了一层二次确认，误判率上升。这类坑只能靠逆向发现。

### 4.2 但"经验"的作用被高估了

真正的经验价值不在于"凭感觉判断什么是钩子"，而在于**知道有哪些误判来源**，
然后针对性加护栏。原版的做法证明这一点：

- 它不依赖"聪明的人工判断"，而是把判断转化成**可验证的机械检查**
- 每类误判都对应一个具体的护栏（尾部有效、逐字节、二次确认）
- 甚至用 `ReturnFalseStub` 把"是否二次确认"做成编译期开关

所以正确的方法不是"积累经验"，而是**建立误判清单 + 逐项加护栏**。

## 5. 建议的实施顺序

### 阶段 1：修正错误实现（最高优先级）

`QuerySyscallHookStatus`（TailHelpers.c:3952）当前是错的，
既漏报又误报。按原版 `0x140087400` 重写：

- 从基线表按地址查条目
- 比对表项地址（第 1 层）
- 比对 16 字节（第 2 层）
- 加三层有效性护栏
- 顺手恢复（原版行为）

这一条修完，`0x119/0x11A/0x11B` 三个命令才有意义。

### 阶段 2：验证基线链

`ParseSyscallTableExportDir` 依赖 6 个下游函数。需要逐级验证
`g_DiagChainStage` 打到第几级（驱动里已有这套诊断打点）。
当前 Ring0 页显示 blocked，根因就在这里。

### 阶段 3：按原版的 7 类分发表扩展

优先做原版文案里列出的：
- `HalDispatchTable` / `HalPrivateDispatchTable` / `HalAcpiDispatchTable`
- `KiDebugRoutine`
- 文件系统类（FltMgr / NPFS / MSFS）

这几类判据与 SSDT 类似（读表项 + 比对基线），可以复用同一套护栏。

### 阶段 4：Ring3 补齐判据

当前只看"IAT 落在模块外"，需要补：
- CFG 跳板白名单（`__guard_dispatch_icall` 系列）
- JIT 代码页识别（按内存属性 `PAGE_EXECUTE_READWRITE` + 非映像）
- Wow64 / 32 位模块枚举
- inline hook 检测（读模块入口前 16 字节与磁盘比）

## 6. 误判清单（实施时逐项对照）

这是本次分析最有实用价值的产出。每项都对应原版的一个具体处理：

| # | 误判来源 | 原版如何防 | 实施要点 |
|---|---|---|---|
| 1 | 地址在页尾，+15 越界 | `CheckMemoryValid(v2+15)` | 整条跳过，不判断 |
| 2 | 跨页断裂（前半页有映射） | 逐字节 `CheckMemoryValid(v2+i)` | 全通过才继续 |
| 3 | 换页中（页面暂时不在内存） | 同上，逐字节检查会失败即退出 | 标记为"未能判定"，不报可疑 |
| 4 | 正常的长跳转首字节 E9 | 不只查首字节，比 16 字节基线 | 必须有基线 |
| 5 | 系统调用表项本就被修正 | 只比"地址 ≠ 原始" | 需要磁盘基线 |
| 6 | 延迟加载 IAT 未填充 | 跳过 0 和 <0x10000 的值 | 已做 |
| 7 | CFG 跳板在模块外 | （原版未明确处理） | 需加白名单 |
| 8 | JIT 代码页 | （原版未明确处理） | 需按内存属性排除 |
| 9 | 模块枚举不全 | （原版未明确处理） | 需枚举 Wow64 和内存映射 PE |
| 10 | 反分析桩 `ReturnFalseStub` | 保留二次确认 | 不要因为名字而删掉 |
| 11 | 同名函数多个实例 | 按地址精确匹配 | 基线表按地址索引 |
| 12 | 系统刚启动基线未建立 | 懒加载 + 检查 Count 非 0 | 已做 |

## 8. 一句话回答
