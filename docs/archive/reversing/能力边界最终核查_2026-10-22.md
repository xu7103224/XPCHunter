# 剩余 29 项是否是"能力边界"——最终核查（2026-10-22）

## 问题

上一轮我写了「4 项需要内核任意地址读」，但只核对了 0x215/0x217。
本次把命令表里**所有名字指向"读/调用内核内存"的命令**逐条打开伪代码核对，
确认边界是否真实存在。

## 逐条核对结果

| 命令 | 索引 | IDA 地址 | 实际能力 |
| --- | --- | --- | --- |
| 0x001 CmdReadProcessMemory | 0 | 0x14007F384 | `KeStackAttachProcess` 后读**进程**内存 |
| 0x020 CmdReadProcessMemoryBlock | 11 | 0x14004A0B0 | 读进程命令行（解析 PEB） |
| 0x037 CmdReadProcessMemoryEx | 23 | 0x140071470 | `QueryProcessMemoryRegions` 枚举区域 |
| 0x211 CopyKernelArrayToUserBuffer | 208 | 0x14006BC78 | 读**一个固定 GT 槽**指向的数组 |
| 0x214 CopyKernelDualArrayToUserBuffer | 211 | 0x14006BDA4 | 读**一个固定 GT 槽**指向的数组 |
| 0x215 ReadKernelMemoryToUserBuffer | 212 | 0x14006AFEC | 读**一个固定 GT 槽**指向的 QWORD |
| 0x217 CmdReadKernelMemoryRange | 215 | 0x14006BBB8 | 读**一个固定 GT 槽**指向的 QWORD |
| 0x221 CmdCallKernelMemoryFunction | 219 | 0x14006C42C | 调**一个固定 GT 槽**里的函数，参数来自用户 DWORD |
| 0x245 CmdCallSystemRoutine | 225 | 0x1400776D8 | 调**一个固定 GT 槽**里的函数，参数硬编码为 1 |
| 0x040 CmdReadPhysicalMemory | 32 | 0x1400352BC | 输出 7928 字节物理内存**上下文表** |

**10 条命令，没有一条接受"用户指定内核地址"作为输入。**

它们的共同形态是：从 GT 表里取一个**初始化阶段已经解析好的**地址/指针，
再读或调用它。原版能工作，是因为它有一张完整的 GT 描述表，
在 DriverEntry 里把 ntoskrnl 里的各个目标地址逐一解析并写进对应槽。

本复刻没有那张描述表（这是"1:1 复刻 1516 个函数"仍未完成的根本原因），
所以这些槽里的值要么为 0、要么是 RVA 而不是 VA。

## 所以这 4 项为什么做不了

    KiDebugRoutine Hooked     需要读 ntoskrnl 里某个未导出全局
    Find PTE Hook in 0x%p     需要读目标 VA 的自映射 PTE 项
    Find Next ClassInitData   需要读 ntoskrnl 数据段
    Dump Kernel Memory        需要按任意地址转储

这四个动作的第一步都是"读一个我事先不知道地址的内核位置"。
原版靠 GT 描述表预先算好；没有描述表就必须有一个"按地址读"的原语，
而命令表里不存在这个原语。

## 为什么不自己加一条读内存命令

技术上可行（`MmIsAddressValid` + `ProbeForRead` + `memcpy`，几十行），
但**清单的判据不允许**：

> 本文件把「复刻 ARK 前端并接入全部原 ARK 前端功能」这个目标转成可勾选、
> 可验收的条目。……参照物：`docs/reversing/原版前端功能地图.md`

加一条原版没有的命令，等于"我的驱动能做原版做不到的事" —— 那不是复刻，
是新增功能。而且前端将依赖一条原版不存在、因此永远不会被验证的协议路径。

真要让这 4 项工作，正确做法是**补完 GT 描述表**（把 ntoskrnl 的
目标地址按版本解析进对应槽），那才是原版的机制。这是一项独立的、较大的工作
（原版 1516 个函数里相当一部分就是这套解析），不是给 4 个 UI 项打补丁能解决的。

## 那 Network 22 项呢

与上面同源但更彻底：原驱动**连槽位都没有**。命令表 282 槽审计确认
没有任何网络命令。`0x112 CmdEnumAleEndpointLayers` 名字像，
但 `EnumerateAleEndpointLayers` 实际枚举 `\FileSystem\RAW`，
是文件系统过滤层。

原版前端的 Network 页要工作，同样依赖 GT 描述表 + 一批本复刻里
仍为空壳的 NDIS/WFP 解析函数（`FindNdisExportsBySectionScan` 等已实现，
但 `ParseNtKernelDataOffsets` 一类尚未产出）。当前 `ndisRead=0`
（诊断口 env+0x40）就是这条链没通的直接表现。

## 结论

**29 项不是"我还没查清"，也不是"实现不到位"，而是原版机制中的
GT 描述表在本复刻里尚未补完的连带结果。**

能推进的路径只有一条：补完 GT 描述表。
这一条修好，会同时解锁：

- B 类 4 项（KiDebugRoutine / PTE Hook / ClassInitData / Dump Kernel Memory）
- Network 页的 NDIS/WFP 部分（前提是解析函数也补齐）
- Kernel 的 SSDT Restore（`GT[0x802]` 有了值就不再依赖 td.sys）
- 以及清单里其他因槽位为空而返回 0 的命令

这是当前唯一有意义的主攻方向，而不是那 29 个 UI 条目本身。
