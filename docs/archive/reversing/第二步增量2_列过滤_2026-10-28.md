# 第二步增量 2：Process 页列过滤（2026-10-28）

范围：在增量 1 建立的 `g_ProcCache` 上增加列过滤，复用 `ProcRenderRows()`。
不动外观骨架、不动驱动、不动协议。

## 一、实现内容

### 1.1 过滤器（`FeProcPage.c`）

```c
char  g_ProcFilter[128] = "";   /* 空 = 不过滤 */
ULONG g_ProcShown = 0;          /* 过滤后实际渲染行数 */
```

- `ProcFilterMatch(it, acc, filter)`：**任一拍中即保留**，五列都参与
  （PID / Name / Path / EPROCESS / Ring3 状态）；空串恒通过；
- `ProcStrIStr()`：手写大小写无关子串查找（不引 shlwapi）；
- **状态列用 `_stricmp` 精确匹配**——`"accessible"` 是 `"INACCESSIBLE"`
  的子串，用子串匹配会让两个状态互相误命中（这条是自检抓出来的，见 §2.1）；
- `ProcRenderRows()` 改为**先过滤后排序**：只把命中行放进索引数组，
  `qsort` 规模随之缩小，排序与过滤天然可组合；
- `FeProcPageSetFilter()`：写入过滤串并重绘，状态行同步显示
  `Processes: N (filter "xxx" matched M)`；缓存未就绪时只记录，等刷新生效。

### 1.2 UI（`frontend.c`）

- `IDC_PROC_FILTER`(1033) 的 `EDIT` 控件，`EM_SETCUEBANNER` 提示可筛的列；
- `WM_COMMAND` 顶部处理 `EN_CHANGE`（注意：EN_CHANGE 是**通知码**不是命令 ID，
  必须先判 `HIWORD(wParam)`），边打边筛；
- `WM_SIZE` 的 Process 分支把列表高度减去 `filterH=30` 给过滤框让位
  （原实现直接叠在列表底部会压住 26px），过滤框落在列表与状态行之间；
- `FeProcPagePageShow` 控制过滤框只在本页可见；
- 新增 `--filter TEXT` 启动参数（自动化验证用）：写入编辑框并调用
  `FeProcPageSetFilter`，刷新后即生效。

## 二、验收

### 2.1 过滤器自检（`--selftest-filter-cli`，进程内确定性）

10 个用例，覆盖空串 / 大小写 / 五列各自命中 / 状态精确匹配 / 无命中：

```
filter selftest: 4 rows, 5 columns
  filter ""            -> pids=100,200,300,400  OK
  filter "explorer"    -> pids=100              OK
  filter "EXPLORER"    -> pids=100              OK   大小写无关
  filter "svchost"     -> pids=200              OK
  filter "system32"    -> pids=200,300          OK   Path 列
  filter "malware"     -> pids=400              OK   Name 列
  filter "abb"         -> pids=400              OK   EPROCESS 十六进制
  filter "inaccessible"-> pids=200,300          OK   状态列
  filter "accessible"  -> pids=100,400          OK   状态列（精确）
  filter "nomatch-xyz" -> pids=                 OK
filter selftest: PASSED
```

**首轮曾 FAILED**：`"accessible"` 命中了全部 4 行——因为它是 `"INACCESSIBLE"`
的子串。改为状态列精确匹配后通过。这条正是"自检优于肉眼"的例子。

### 2.2 GUI 真实路径双向验证（跨进程）

用 `--filter` 启动 + 计划任务探针读状态行：

| 过滤串 | status 文本 | visible_rows | 判定 |
|---|---|---|---|
| `INACCESSIBLE` | `... (filter "INACCESSIBLE" matched 10)` | **10** | 全中（该 guest 10 个进程全部 Ring3 不可访问）✓ |
| `Windows` | `... (filter "Windows" matched 0)` | **0** | 全不中（0x0E4 在此 guest 返回的 PID 无效，路径全空）✓ |
| `explorer` | `... (filter "explorer" matched 0)` | **0** | 同上 ✓ |

命中 10 与命中 0 两个方向都正确，证明"过滤 → 索引 → 渲染 → 状态行"
整条链路在真实 GUI 里工作。

### 2.3 布局探针

## 三、已知环境限制

本 guest 上 `0x0E4`（CmdEnumProcessListWin10）返回的 10 条记录 PID 全部相同
（`458383552`）且 Name 为空，导致 Path 解析失败、Name 列显示 `(?)`。这是
**既有驱动侧行为**（`docs/reversing/剩余四条命令状态与下一步_2026-10-27.md`
§2 记录 0x0E4 已对齐原版的 664 字节条目布局，原版 `+0x08` 起就是 0），
不是本次过滤改动引入的。过滤的 PID 列与状态列因此成为本 guest 上最有意义
的筛选维度。
