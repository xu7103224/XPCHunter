# 全命令 I/O 差分测试（2026-10-23）

目标：对**已勾选的 127 项**逐条与原版驱动比对（调用同一条命令，比对输入/输出）。

## 一、方法

新加 `probe --matrix [--matrix-lo N --matrix-hi M] [--matrix-out 文件]`：

- 按 `g_Shapes` 里每条命令**自己的**真实入参/出参尺寸调用一次；
- 记录 `命令号 / InSize / OutSize / 结果字节 / 输出非零区间(hex)`；
- 跳过 `g_SkipCommands`（那些在无前置状态下必然踩空，见下）；
- 输出成文本，两份文件逐行 diff。

同一台 VM（Win10 18362）上分别加载**我方驱动**与**原版驱动**，各跑一次。

## 二、结果

### 我方驱动：283 条全量矩阵跑通，驱动保持 RUNNING

```
matrix written to C:\Users\Public\m_mine_all.txt (sent=23 rejected=254)
        STATE              : 4  RUNNING
```

279 行输出，23 条 HANDLED。**跑完后驱动未崩溃、未卸载。**

### 原版驱动：同一份全量矩阵会让系统崩溃

```
（跑全量矩阵后）
        STATE              : 1  STOPPED        ← 驱动被卸载
        系统找不到指定的文件。                  ← 矩阵文件未生成
```

内核基址在崩溃前后发生变化（`81fc4580` → `76dc4580` → `6abc4580` …），
确认是**真实重启**，不是调试器打断。

### 二分定位

用 `--matrix-lo/--matrix-hi` 分段，逐次重启驱动 + 重新置位后测：

| 区间 | 原版结果 |
|---|---|
| 0x20–0x3F | 通过（sent=4） |
| 0x40–0x7F | 通过（sent=4） |
| 0x80–0xBF | 通过（sent=8） |
| 0xC0–0xFF | 通过（sent=11） |
| **0x100–0x13F** | **崩溃（STOPPED，文件未生成）** |
| 0x100–0x11F | 崩溃 |
| 0x100–0x10F | 通过（sent=1） |
| **0x110–0x11F** | **崩溃** |
| 0x110–0x117 | 崩溃 |
| 0x110 单条 | 通过（RUNNING） |
| 0x111 单条 | 通过 |
| 0x112 单条 | 通过 |
| 0x113 单条 | 通过 |
| 0x114 单条 | 通过 |
| 0x115 单条 | 通过 |
| 0x116 单条 | 通过 |
| 0x117 单条 | 通过 |

**单条都不崩，串起来就崩** —— 说明崩溃来自**状态累积**：
前一条命令留下的全局表/对象状态，被后一条命令踩到。

这一段的命令（`0x110 = Table[240]` 起）：

| 命令 | 处理器 |
|---|---|
| 0x110 | `MiniFilterPreShutdown` |
| 0x111 | `InitMiniFilterDriver` |
| 0x112 | `MiniFilterPreFastIo` |
| 0x113 | `CmdInitFileSystemFilter` |
| 0x114 | `CmdFileSystemFilterCallback` |
| 0x115 | `CmdCallSystemRoutine` |
| 0x116 | `CmdResetDriverState` |
| 0x117 | `CmdEnumHookInfo` |

全是**回调注册 / 驱动状态重置**类命令。在无前置状态下被裸调，
它们会注册 unload 例程或改写 DriverObject，后一条命令再访问就踩空。

## 三、这个结果说明什么

1. **我方实现的稳健性高于原版**：同一份 283 条命令矩阵，
   我方全程无崩溃，原版在 0x110–0x117 段崩溃。

2. **原版的崩溃不是「原版有 bug」这么简单**：那批命令在原版设计里
   是由前端在特定顺序下发的（先 Init、再 Pre*、最后 Reset），
   裸扫本来就不是合法用法。**我方多做的防御不应被当成「与原版不一致」
   而回退** —— 但这确实是一处行为差异，需要在比对报告里如实记录。

3. **矩阵测试对「逐条比对」的直接价值**：
   0x20–0xFF 这 6 段原版都能跑通，那 6 段的输出就是可靠的对照基线。

## 四、下一步

- 0x20–0xFF 段：已可在两版之间逐行 diff（待采集原版这 6 段的完整输出）；
- 0x110–0x117 段：原版无法裸扫，需按「Init → Pre* → Reset」的正确顺序
  重放，才能拿到对照输出；
- `g_SkipCommands` 里的 0x25/0x28/0x30/0x56/0x115 本来就依赖前置状态，
  差分时也要按真实顺序构造。

## 五、重要教训（写给下一次）

本轮我在 VM 状态判断上走了不少弯路：

1. **`kd_break` 打断空闲内核会产生 `BUGCHECK_CODE: 0` +
   `FAILURE_BUCKET_ID: MANUAL_BREAKIN`**，看起来像崩溃，其实是调试器
   自己的断点。判断「是不是真崩」要看 `!analyze -v` 的 FAILURE_BUCKET_ID。
2. **`sc query` 返回 STOPPED 可能是瞬时误报**，尤其在 `kd_break` 之后。
   可靠判据是「矩阵输出文件是否生成」+「设备能否打开」。
3. **驱动重启会清掉用 kd 置位的 `GT[0x304]`**，所以顺序必须是
   「sc start → kd 置位 → 立刻跑」，中途不能重启。
4. 原版的 AES 许可包在本机会被拒（原因未定），因此只能靠 kd 置位
   `GT[0x304]` 来解锁命令通道；这也是为什么每次崩溃重启后都要重新置位。

## 6.2 0x026 / 0x0E8 是真实数据缺口，不是环境限制

原版返回的内容可验证为真：

```
0x026 (CmdEnumHandles) 576B:
  0000: 01000000 00000000 00000000 00000000
  0020: 96F93FC4C962DD01 C099385E04F8FFFF     ← 对象指针
  0030: 490064006C006500 00000000...           ← UTF-16 "Idle"

0x0E8 (CmdEnumObjectTypeInfo) 768B:
  0000: 05000000 01000000 02000000 00000000   ← count=5, idx=1
  0010: 2070FB560FADFFFF 4E00650074004200     ← 指针 + "NetB"
  0020: 7400...                                ← "...t"
```

我方同命令 `result=0`、输出全零 —— 是**实现缺口**。

## 6.3 根因链（0x0E8，已定位到具体槽）

`CmdEnumObjectTypeInfo` 的守卫条件是 `GT[0x807]`（= `GtFwpsDispatchTableCount|GtPathBuffer02` = `0x801|6`）。
该槽为 0 时它调用 `InitTdiExportAndRelocTable()` 补齐，链路是：

```
InitTdiExportAndRelocTable
  → ReadSystemDriverFile       读 \SystemRoot\system32\drivers\tdi.sys
  → ParseKernelDataSectionRelocs
      → FindDllInitExport      查 tdi.sys 的 DllInitialize / TdiInitialize 导出
          → 需要 GT[0x802]（TDI 模块基址）非零
      → 写 GT[0x807]（Win10 分支）
```

kd 实测我方驱动：

```
GT[0x802] = FFFFF804`61740000   （= TDI 模块基址，正确）
GT[0x803] = 0x0000000000010000  （= TDI 模块大小，正确）
GT[0x804] = 0                    ← FindDllInitExport 未产出结果
GT[0x807] = 0                    ← 因此对象类型表为空 → 0x0E8 返回 0
```

`GT[0x802]/[0x803]` 正确说明 `InitProcessNotify` 的模块名匹配（`S_td = L"tdi.sys"`，`Len=7`）工作正常；
断点在 `GT[0x804]`：`FindDllInitExport` 在 tdi.sys 文件里既没找到 `DllInitialize` 也没找到 `TdiInitialize`。

## 6.4 由此推翻的一条旧结论

清单第 189 行（SSDT Restore）与 Network 文档都写「**tdi.sys 是 XP/2003 驱动，Win10 不存在**」。
实测：本机 `C:\Windows\System32\drivers\tdi.sys` **存在**（39,440 字节，2019-03-19），
且 `lm m tdi` 显示 TDI 模块已加载（`fffff80461740000`，0x10000）。

所以 0xE7 / 0xE8 拿不到数据的原因**不是 tdi.sys 缺失**，而是
`FindDllInitExport` 在 tdi.sys 里没匹配到导出名。这是一条需要继续查的实现缺陷，
不是环境限制。

## 6.5 下一步

1. 确认 tdi.sys 实际导出表内容（用 NT 工具或读文件导出目录），
   看 `DllInitialize` / `TdiInitialize` 是否存在、大小写是否一致；
2. 若导出名不同，按实际名字修正（这属于「按实测修实现」，不是猜）；
3. 修好后重跑 0xE8 / 0xE7，与原版逐字节比对；
4. 0x020/0x021/0x026/0x0C4/0x0F8/0x0FB 同理逐条查守卫条件。

## 6.6 已排除的可能（2026-10-23 逐项实测）

为了避免「猜」，以下每一项都做了正反验证：

| 假设 | 验证方式 | 结论 |
|---|---|---|
| tdi.sys 在 Win10 不存在 | `dir` 实测 | **推翻**：39,440 字节，2019-03-19 |
| TDI 模块未加载 | kd `lm m tdi` | **推翻**：`fffff80461740000`，0x10000 |
| 模块名匹配失败（GT[0x802]=0） | kd 读 GT[0x802]/[0x803] | **推翻**：`0xFFFFF80461740000` / `0x10000` 都正确 |
| 我方路径数组拼错 | 与原版 0x140067F3C 的 18 个 DWORD 逐项比对 | **推翻**：完全相同，解码为 `\SystemRoot\system32\drivers\tdi.sys` |
| tdi.sys 没有 DllInitialize 导出 | 把 tdi.sys 拉到宿主机解析导出目录 | **推翻**：`DllInitialize` ord=16 rva=0x2070，`TdiInitialize` ord=42 rva=0x1180 |
| `InitTdiExportAndRelocTable` 未被调用 | 在 0x71860 下硬件断点 | **推翻**：命中，调用方 0x632cdbfe |
| `LookupExportByName` 边界条件过严 | 用 tdi.sys 实际值验算 | 需注意：文件大小 0x9A10 < ExportDirRva 0xB000，若传文件大小必失败；但 `ReadNtFileToBuffer` 返回的是按节展开的 `ImageLimit`（≈0x10000），所以这个条件实际成立 |

**剩余唯一未排除的点**：`ReadFileRawData("\SystemRoot\system32\drivers\tdi.sys", ...)` 是否成功。
我方该函数的路径数组与原版一致，所以差异只可能在它内部（或 `ReadNtFileToBuffer` 的节展开在 tdi.sys 上失败）。
下一步应在这两处下断，直接看返回值。

## 6.7 一条方法论教训

本轮我判定「0x110–0x117 让原版崩溃」时，先后两次被自己的 `kd_break` 误导：
- `BUGCHECK_CODE: 0` + `FAILURE_BUCKET_ID: MANUAL_BREAKIN` = **调试器打断**，不是崩溃；
- `sc query` 返回 STOPPED 时若 `guest_frozen: true`，那是调试器冻结了 guest，不是驱动真的停了。

判据：**先看 `!analyze -v` 的 FAILURE_BUCKET_ID，再看 `vm_state` 的 `guest_frozen`**，两者都排除后才谈崩溃。

# 七、0xE8/0xE7 追踪到的两个独立缺陷（2026-10-23 续）

## 7.1 缺陷一：头文件里的宏覆盖（已修复）

`xpc_gt_enum.h` 同时存在：

```
第 601 行（枚举）  GtFwpsDispatchTableBase = 0x800
第 1356 行（宏）   #define GtFwpsDispatchTableBase 0x910
```

`#define` 位于枚举之后，**把所有使用点都改成了 0x910**（全仓 37 处、8 个文件）。
连锁反应：

```
GtFwpsDispatchTableBase | GtPathBuffer00(4)
  = 0x910 | 4 = 0x914   ← 正好是 GtWindowsBuildNumber
→ ParseKernelDataSectionRelocs 的 Found 读到 18362
→ Found >= ImageSize 成立，扫描前就返回
→ GT[0x807] 恒为 0 → 0xE8 / 0xE7 恒返回 0
```

修复前后的实测对照（同一台机器、我方驱动）：

| 槽 | 修复前 | 修复后 | 应为 |
|---|---|---|---|
| GT[0x804] | 0 | 0x2070 | 0x2070（DllInitialize RVA）|
| GT[0x80C] | 0 | 0x2C50 | 0x2C50 |
| GT[0x80D] | 0 | FFFFF80461742C50 | 对应 VA |
| GT[0x807] | 0 | 0 | FFFFF80461747290 |

已删除该 `#define`。`ValidateWin32kBaseDriverImage` 里唯一真正需要 0x910/0x911
的两处改为显式常量。

## 7.2 缺陷二：节区扫描未命中 1069 型（未修）

修复宏之后，前半段全对，但 `GT[0x807]` 仍为 0。

**原版在置位 GT[0x304] 后的真实槽位布局**（kd 实测）：

```
GT[0x804] = 0x0000000000002070        DllInitialize RVA
GT[0x805] = FFFFF80461742070          对应 VA
GT[0x806] = FFFFF804617472A0
GT[0x807] = FFFFF80461747290          ← 对象类型链头（命令 0xE8 的输入）
GT[0x808] = FFFFF80461747270
GT[0x809] = FFFFF80461747280
GT[0x80C] = 0x0000000000002C50
```

**我方同一时刻**：`GT[0x804]=0x2070` ✓、`GT[0x80C]=0x2C50` ✓，但
`GT[0x806]..GT[0x809]` 全为 0。

我加的循环诊断（`0x4FD0+i*2`）记录了我方从 `ImageBase+0x2070` 开始解码的
类型序列与消耗量：

```
i=0  类型 0x42E(1070)  消耗 4
i=1  类型 0x558(1368)  消耗 5
i=2  类型 0x512(1298)  消耗 7
i=3  类型 0x473(1139)  消耗 7
i=4  类型 0x0EF(239)   消耗 5
i=5  类型 0x512(1298)  消耗 7
i=6  类型 0x50E(1294)  消耗 7
i=7  类型 0x50E(1294)  消耗 7
共迭代 0x2D = 45 条后终止
```

**没有一条是 1069（0x42D）**，而原版正是靠 `cmp r14d, 42Dh` 命中才进入状态机。

原版起始点同样是 `GT[0x804]=0x2070`（kd 实测值相同），所以差异不在起点，
而在**某个 opcode 的解码消耗量**——与 0x131 那次的排查路径完全同类。
0x131 最终证明解码器是对的（真因在别处），所以这次不能先入为主认定是解码器。

## 7.3 一条重要的环境认识

原版驱动在本机的 **AES 许可包始终被拒**（`handshake 0x22 -> REJECTED`），
导致分派器拒绝一切命令。之前矩阵里原版那些 `OK`，
全部是在我用 kd 手动 `eq GT[0x304] 1` 置位之后才成立的。

因此：
- 「原版也会失败」的证据必须注明**是否已置位 GT[0x304]**；
- 未置位时的 REJ 只反映许可校验失败，与功能无关。

（tdi 镜像 +0x2070）逐条对照前 45 条的「类型码 + 消耗量」，
找出第一条不一致，定位到具体 opcode。

# 八、0xE7 / 0xE8 修复完成（2026-10-23 续二）

## 8.1 第三处缺陷：TargetRva 用错了量（已修）

原版 `0x140067B44`（`1298` 且 `desc[0x58]==2` 分支）：

```asm
mov  eax, ebx      ; ebx = desc+0x78
sub  eax, r12d     ; r12d = ImageBase 低 32 位
add  eax, ecx      ; ecx = **当前读指针**（低 32 位）
```

即 `Target = desc[0x78] - (ULONG)ImageBase + ReadPtr`。

我方旧实现把 `ecx` 当成「从 0 起的累计消耗量」，漏掉了读指针的基址部分
（`ImageBase + 0x2070` 起）：

```
旧式：0x4D + 0x51C3 - 0x2E435000 = 0xD1BD0210   ← 下溢
新式：0x2E4370A0 + 0x51C3 - 0x2E435000 = 0x7263 ← 正确
```

下溢值恒 `>= ImageSize`，于是：

- 三道字段守卫全部通过（kd 实测 `desc+0x88=0x40000`、`desc+0x50=0x40`）
- 但 `InnerEnd` 范围检查失败 → `goto MarkPhase1`
- `GT[0x807]` 永远不写 → 0xE8 / 0xE7 恒返回 0

诊断证据：在 1298 分支入口加计数后，`0x4FE0`（命中次数）= **3**，
但从不写槽 —— 定位到问题就在 `InnerEnd` 的算术上。

# 九、第四处缺陷：GtWrite 返回值（已修）

原版 `sub_140029FF4` 只有三条指令：

```asm
140029FF4  mov  eax, ecx          ; eax = Index（第 1 形参）
140029FF6  lea  rcx, g_GlobalTable
140029FFD  mov  [rcx+rax*8], rdx
14002A001  retn                   ; 返回值 = Index
```

**返回索引，不返回值。** 我方原实现是 `return Value`。

有些处理器直接把 GtWrite 的返回值当自己的返回值，例如：

```c
__int64 CmdResetProcessContext(...)          /* 命令 0x21 */
{
    GtWrite(0x185, 0);
    return GtWrite(GtEprocessModuleEntrySize | GtEprocessField22, 0);
}
```

原版返回该索引的低字节 `0x2E`(46)，我方返回 `0` →
矩阵差分里表现为「原版 OK(46) / 我方 REJ」。

修复后 `0x21` 从差异列表消失。全量矩阵 `sent` 23 → **24**。

# 十、第五处缺陷：ScanNsiDeregisterDataSection 字段偏移互换（已修）

## 10.1 定位过程

给该函数的循环加了类型诊断（GT[0x4F60] 起，每 3 槽记录
`类型码 / 消耗量 / 字段+0x88`），kd 读出的前 12 条：

```
i=0  类型 0x50E  消耗 5  +0x88=0x40
i=5  类型 0x512  消耗 7  +0x88=0x40000
i=11 类型 0x168  消耗 9  +0x88=0x40        ← 类型 360（0x168）出现了
共迭代 0x1E = 30 条（跑满上限）
```

**类型 360 确实被扫到了**，但它的 `+0x88` 是 `0x40`，
而代码判断 `Entry+0x88 == 0x40000` —— 永远不成立。

## 10.2 根因：0x50 与 0x88 写反了

原版 `0x1400691BF..1E1` 三处比较，用的是描述符的**三个不同偏移**。
描述符基址是 `rsp+0x90`，按 IDA 的栈帧标注换算：

| 原版变量 | 栈位置 | 相对描述符 |
|---|---|---|
| `var_F8`  （与 `0x40000` 比较） | rsp+0xE0 | **0x50** |
| `var_108` （`test eax,eax`）    | rsp+0xD0 | **0x40** |
| `var_C0`  （与 `0x40` 比较）     | rsp+0x118| **0x88** |

我方写成：

```c
Type == 360 && Entry[0x88] == 0x40000        /* 应为 0x50 */
          && Entry[0x40] != 0
          && Entry[0x50] == 64               /* 应为 0x88 */
```

**0x50 与 0x88 整体互换。**

## 10.3 修复结果

```
修复前：GT[0x7D0] = 0            → 命令 0x0F8 恒返回 0
修复后：GT[0x7D0] = FFFFF80460437850
        命令 0x0F8 = OK（与原版一致）
```

全量矩阵 `sent` 24 → **25**，与原版的状态差异 **7 → 6 条**。

## 10.4 这是一类系统性缺陷，需要继续排查

同一模式（`+0x88 == 0x40000 && +0x50 == 64`）在 Minifilter.c 里还有多处：

```
900   963   5626   5945   5962   6852
```

它们是否也把 0x50/0x88 写反，需要逐个对照各自原版函数的
栈帧标注（`var_XXX` 相对描述符基址的偏移）来确认，
**不能批量替换** —— 不同函数的描述符基址和字段位置可能不同。

## 10.5 累计修复进度

| # | 缺陷 | 影响 |

## 11.4 方法论：字段偏移必须逐函数按栈帧换算

本轮连续发现三处「0x50/0x88 写反」，但每次的描述符基址都不同：

| 函数 | 描述符基址 | `+0x50` 实际是 | `+0x88` 实际是 |
|---|---|---|---|
| ScanNsiDeregisterDataSection | rsp+0x90 | var_F8 | var_C0 |
| ScanWfpDeviceObjectSection | rsp+0x90 | var_E8 | var_B0 |
| ScanKernelDataPartitionSection | rbp+0xA0 | var_1B0 | var_D8 |

判断依据只能是：**IDA 栈帧里 `var_XXX` 的偏移减去描述符基址**。
不能因为「上一个函数是 0x50/0x88 反了」就推定下一个也反了。
