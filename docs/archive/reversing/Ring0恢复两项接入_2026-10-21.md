# Ring0 两项恢复操作接入（2026-10-21）

## 一、结论

| 项 | 命令 | 前端入口 | 实机结果 | 勾选 |
| --- | --- | --- | --- | --- |
| `Restore Over. Hooks/Patches` | 0x118 | Ring0 Hooks 页按钮 + `--restorehooks-cli` | `nothing to restore`（908 条 / 0 改写） | ✅ |
| `Restore KernelCallbackTable Replaced` | 0x131 + 0x132 | Ring0 Hooks 页按钮 + `--cbtable-cli` | `callback table not initialized` | ❌ |

**第一项勾选、第二项不勾选**，判断标准与之前一致：入口接好不等于功能完成。
0x131 拿不到任何回调槽（`ready=0`、`slots=0`），"恢复"这个动作无处可证。

## 二、0x118 的语义（按原始反汇编确认）

```c
// CheckBytePatternOperation(0x140086FD0)
if (InputSize != 8) return 0;
v = *(int64*)In;
if ((BYTE)v == 1) {
    for (i = 0; i < 0x200; i++)
        Result |= RestoreSyscallHookByIndex(SBYTE1(v), i);   // 全索引
} else {
    return RestoreSyscallHookByIndex(SBYTE1(v), HIDWORD(v)); // 单条
}
```

`RestoreSyscallHookByIndex(0x1400872C4)` 的恢复条件是**表项当前值 ≠ 磁盘原始值**：

```c
pTargetEntry = SyscallTable + 8*Index;
if (*pTargetEntry != OriginalAddress) {          // ← 只有被改写过才动手
    WritePhysicalMemoryQword(pTargetEntry, OriginalAddress);
}
if (MemoryCompare(OriginalAddress, Entry+16, 0x10))   // 指令也不一致才写指令
    WritePhysicalMemoryBuffer(...);
```

本机 0x117 返回 908 条，两个改写标志 `flagAddr` / `flagBytes` **全为 0**，
即没有任何表项被改写 → 没有可恢复目标 → 返回 0 是**正确行为**。

界面必须把这个状态说成"没有待恢复项"，而不是"失败"，否则会让用户误以为
系统真被 hook 了。实测状态栏：

```
Restore Over. Hooks/Patches: nothing to restore - all 908 hook entries
match their on-disk originals (0 modified, driver result=0)
```

CLI 输出：

```
state        = nothing to restore
driverOk     = 0  resultByte = 0
totalEntries = 908  modified = 0
```

## 三、0x131 / 0x132 的语义与当前状态

### 3.1 0x131 CmdEnumCallbackContext（OutlineSize 必须 == 1352）

```c
memset(out, 0, 0x548);
TableReady = GtRead(2308);                 // GtHookTableCount
if (!TableReady) {
    BuildCallbackContextHookTargets();
    TableReady = GtRead(2308);             // 再取一次
}
if (EnumCallbackContextTable(out + 4) == 1) {
    Result = 1;
    if (TableReady) {
        if (CopyCallbackContextHookTable(out + 4) == 1 &&
            ValidateSsdtHookTargetTable2(out + 4) == 1) {
            *(BYTE*)out = 1;                       // 就绪标志
            *(WORD*)(out + 8) = GtWindowsBuildNumber;
        }
    }
}
```

本机 `GT[2308]` 为 0，调用 `BuildCallbackContextHookTargets()` 后仍为 0，
于是 `EnumCallbackContextTable` 返回 0 → 整条命令返回 0。
**这是环境状态（回调上下文链表未建立），不是参数错误。**

### 3.2 0x132 CmdSetCallbackContext（InSize 必须 == 48）

```c
if (In[24] == 1 && *(QWORD*)(In+8))
    HookResult = InstallCallbackContextHookEntry(In);    // 装 Hook
if (In[25] == 1) {
    target = *(QWORD*)(In+8);
    if (target > MmSystemRangeStart && MmIsAddressValid(target)
        && MmIsAddressValid(target+15))
        PatchResult = WritePhysicalMemoryBuffer(target, In+26, 16, 0, 0);
}
return HookResult & PatchResult;
```

前端 `FeRestoreCallbackSlot` 按此实现：只置 `[25]=1` 走打补丁路径，
`In+8` 放目标地址，`In+26` 起放 16 字节原始指令。由于 0x131 拿不到槽，
这个函数目前没有调用者 —— 保留实现但如实标注。

## 四、前端改动

`XPCHunterUM/src/frontend.c`：

- Ring0 Hooks 页新增两个按钮：
  - `Restore Over. Hooks/Patches`（IDC_HK_RESTORE）
  - `Restore KernelCallbackTable`（IDC_HK_CBTABLE）
- 两个按钮**只在主 Tab 2（Ring0 Hooks）显示**，Ring3 页隐藏
- 新增 CLI：`--restorehooks-cli`、`--cbtable-cli`
- `DoRestoreOverHooks` 按四种状态分别措辞（restored / nothing to restore /
  attempted-no-effect / not connected），绝不把"无待恢复项"显示成失败

`XPCHunterUM/src/KernelHookViews.c` 新增：

- `FeRestoreOverHooks()` —— 打包 0x118 的 8 字节入参，并在返回 0 时
  回查 0x117 的 `ModifiedCount` 区分两种含义
- `FeLoadCallbackTable()` —— 0x131 枚举
- `FeRestoreCallbackSlot()` —— 0x132 打补丁（当前无调用者，待 0x131 可枚举后启用）
- `FeHookRestoreStateText()` / `FeCbStateText()` —— 状态文案

## 五、过程中发现并修掉的一个自身缺陷

`FeLoadCallbackTable` 初版在 `ok == FALSE` 时把 State 设成 `FE_CB_REJECTED`
并返回 FALSE，导致 CLI 打印 "query failed" —— 这让"回调链未初始化"
看起来像"查询出错"。已改为：查询本身完成即返回 TRUE，
是否枚举到数据由 `State` 表达，CLI 打印 `callback table not initialized`。
