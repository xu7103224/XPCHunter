# 真原版 A/B 首次有效采集与双 MD5 族纠错（2026-10-26）

本文记录两件互相独立、但都把此前的对照结论推翻重做的事实。结论全部来自本次实机
kd 读内存 + IDA 静态反汇编，不是推断。

---

## 一、双 MD5 族：许可包被拒的真正原因

### 1.1 现象

真原版驱动（`View++_Driver64.sys`，MD5 `f778e54132fe131481d59c0d1075f37d`）加载
成功后，设备能打开（`ioctl=0x05E00158 key=0xCF` 均正确），但 **126 条命令全部
REJ，`result=0`**；连 `--license` 单独发 0x22 也被拒。

### 1.2 分发器的完整关卡链（`DispatchDeviceControl` @ `0x1400823EC`）

逐条反汇编得到，顺序不可跳：

| 位置 | 检查 | 说明 |
|---|---|---|
| `0x140082439` | `[rax+0x10] == 0x30` | `InputBufferLength` 必须 0x30 |
| `0x140082443` | `[rdx+0x18] != 0` | SystemBuffer 非空 |
| `0x14008244C` | `IoControlCode == GT[0x1E0]` | 实测 `0x5E00158` |
| `0x140082469` | `[buf] == 0x20240810` | Magic |
| `0x1400824BE` | `MD5(buf[0..0x28]) == buf[0x28]` | 校验和 |
| `0x1400824E7..4FD` | 三个用户指针 `< MmUserProbeAddress` | |
| `0x140082527` | `opcode-0x20 <= 0x11A` | 命令号范围 |
| `0x14008253C` | **`GT[0x304] != 0` 或 `opcode==0x22`** | **就绪位总闸** |
| `0x140082570` | `CheckProcessAccess() == 1` | |
| `0x14008258A` | `GT[0x921 + opcode-0x20] != 0` | 处理器指针 |
| `0x140082599` | `GT[0x355] == 0` | 忙标志 |

`GT[0x304]` 是总闸：它为 0 时除 0x22 一律拒绝。**而全驱动只有
`CheckSsdtHookIntegrity`（`0x1400050DC`）的最后一行会写 `GT[0x304]=1`。**

### 1.3 0x22 的三条路径（`CmdQueryProcessInfo` @ `0x14003105C`）

```
if (InSize > 0xA)  → QuerySsdHookByProcessInfo          (0x1400310B4)
else               → AllocProcessInfoBuffer + CheckSsdtHookIntegrity
```

`QuerySsdHookByProcessInfo` 要求 `InSize <= 0x12C`，把输入 `memmove` 到栈上
`Dst[304]`，然后调 `DecryptAesHexString(Dst, InSize, pSyscallCount)`；
**返回非 0（失败）就直接 return，不调 CheckSsdtHookIntegrity。**

所以路径 C（合法 AES 许可包）必须让 `DecryptAesHexString` 返回 0。

### 1.4 根因：原版有两族 MD5，笔误位置相反

`DecryptAesHexString`（`0x140002F4C`）内部：
1. 把 0x100 字节十六进制字符串解码成 0x80 字节；
2. `AesInitKeySchedule` + `AesKeyExpansion` + `AesDecryptBlocks`，密钥
   `"ShouJiErShiSiShi"`；
3. `Md5Init` / `Md5Update2(…, 0x64)` / `Md5Final2`，与明文 `[0x64..0x74)` 比对；
4. 比 `SharedUserData+0x14` 的时间窗。

注意第 3 步用的是 **`Md5Update2`/`Md5Final2`，即族 1**，而分发器校验和用的是
`InitMd5Context`/`Md5Update`/`Md5Final` → **`Md5Transform2`，即族 2**。

两族是两份独立展开的代码，长度完全相同（`0x81D` 字节），**只差 2 个字节**：

```
函数内偏移 0x470:  族1(Md5Transform)=0x81   族2(Md5Transform2)=0x83
函数内偏移 0x4DE:  族1=0xB5                 族2=0xBE
```

对应常量：

| 步 | 标准值 | 族 1 `Md5Transform`（许可包） | 族 2 `Md5Transform2`（请求校验） |
|---|---|---|---|
| K[33] | `0x8771F681` | `0x8771F681` ✅标准 | `0x8771F683` ❌笔误 +2 |
| K[39] | `0xBEBFBC70` | `0xB5BFBC70` ❌笔误 | `0xBEBFBC70` ✅标准 |

**两族各有一处笔误，位置不同。** 我方此前驱动与用户态都只有一张 K 表
（族 2 的值），因此许可包的 MD5 必然算错 → `DecryptAesHexString` 非 0 →
`CheckSsdtHookIntegrity` 不被调用 → `GT[0x304]` 恒为 0 → 除 0x22 外全部 REJ。

### 1.5 修复

- `XPCHunterDrv/src/framework/Crypto.c`：拆成 `Md5_K_FAMILY1` / `Md5_K_FAMILY2`
  两张表，`Md5Transform` 用族 1、`Md5Transform2` 用族 2（不再共用一个实现体）。
- `XPCHunterUM/src/Protocol.c`：新增 `XpchMd5Transform1` / `XpchMd5Init1` /
  `XpchMd5Update1` / `XpchMd5Final1`（族 1，K[33]=0x8771f681、K[39]=0xb5bfbc70），
  `XpchBuildLicensePacket` 的摘要改用族 1；`XpchInvoke` 的请求校验仍用族 2。

### 1.6 实机验证

```
license 0x22 -> OK, result=1, ssdt=0      （修复前：REJECTED, result=0）
handshake 0x22 (inSize=256) -> OK, result=1
handshake 0x24 -> OK, result=1, build=18362 (0x47BA)
```

#### 3.4.1 根因：`ScanWfpNblInfoSections` 描述符字段偏移写错（已修）

用 kd 在我方驱动的调用链上逐层下断（`CmdCopyKernelArrayToUserBuffer` @+0x27500 →
`InitKernelMemoryContext` @+0x11510 → `FindWfpNblInfoDispatchTableClear` @+0x369E0 →
`ScanWfpNblInfoSections` @+0x37860），得到：

- `GT[0x7B2] = 0x0005CE00`（`WfpNblInfoDispatchTableClear` 的 RVA）✅

即 `FindWfpNblInfoDispatchTableClear` 成功，失败在 `ScanWfpNblInfoSections`。
在循环内的"写 GT"分支（+0x37A0D）下断**从不命中**，确认 0x1E 次循环无一匹配。

原因是我方该函数读的描述符字段偏移与原件不符。原版
`0x14006A8A8..0x14006A8E8` 的实参映射（描述符基址 = `rsp+0x90`）：

|---|---|---|---|
| `var_108` | `rsp+0xE0` | **+0x50** | `0x20` / `0x40` |
| `var_100` | `rsp+0xE8` | **+0x58** | `8` / `1` |
| `var_D0` | `rsp+0x118` | `+0x88` | `0x40000` |
| （条目大小） | — | `+0x78` | `> 0` |

我方原先写成 `+0x70` / `+0x74`（早期自拟布局），而 `ReadPESectionEntry`
实际写的是 `+0x50` / `+0x58`，故读出恒为 0、判据永不成立。

**注意不能一刀切**：`ScanKernelMemoryDataSection`（`0x140068ABC`）
在原版里确实读 `+0x70`（`var_F0` = `rsp+0x100`，描述符基址 `rsp+0x90`），
那个是对的，不能一起改。


### 3.7 `0x119`（`CmdGetHookEntryInfo`）的诊断进展

`GetHookEntryInfoOperation` 读两个槽：
`GtFltPeSectionOfs8|GtEprocessField22` = **GT[0x8B6]**（表计数）、
`GtFltPeSectionAddr7|GtEprocessField22` = **GT[0x8B5]**（表地址）。
实机两者均为 **0**，因此函数走不到填表分支，返回 0。

这两个槽由 `ParseSyscallTableExportDir()`（`SsdtHook.c:1463`）填充。
读该函数的诊断变量（RVA 来自 map）：

| 变量 | 值 | 含义 |
|---|---|---|
| `g_DiagChainStage` | **6** | 走到最后一步（`ParseSyscallTableSections` 之后） |
| `g_DiagChainWdfRet` | 1 | `ReadWdfLibraryModule` 成功 |
| `g_DiagChainFindRet` | **0** | `FindSyscallTableDescriptor` 返回 0（失败） |

## 七、剩余 4 条的真正根因：解码层差异（2026-10-26 04:20）

### 7.1 决定性对照实验

同一时刻、同一 netio.sys、完全相同的输入：

| 项 | 真原版 | 我方 |
|---|---|---|
| `GT[0x1A1]`（netio 基址） | `fffff805 0fef0000` | `fffff805 0fef0000` |
| `GT[0x1A2]`（netio 大小） | `0x94000` | `0x94000` |
| `GT[0x7BE]`（KfdDeregisterLayerCallback 偏移） | `0x4F710` | `0x4F710` |

在 `ScanKfdDriverSections` 的 **1296 分支判定点**（原版 `0x140068908`）
下断，读到的寄存器：

| | 真原版 | 我方 |
|---|---|---|
| 首个命中节区类型 | **1296 (`0x510`)** | **1294 (`0x50E`)** |
| `+0x50`（比较 64） | `0x40` ✅ | 未到该分支 |
| `+0x78`（RVA 字段） | `0x27E18` ✅ | `0` |

**同样的 `PeBase + 0x4F710`，原版解出 1296 且字段齐全，我方解出 1294 且字段为 0。**

### 7.2 结论

问题不在业务逻辑、不在导出解析、不在 GT 映射，而在
**`ReadPESectionEntry` / 解码表（`g_PeLegacyDescrambleTable`、
`g_PeDataDescrambleTable`、`g_PeDecodeFunctionTable`）**这一层。
这是我方所有节区扫描函数（`FindNdisExports*`、`ScanKfd*`、`ScanWfp*`
等约 20 个）共同的底座，因此一次性影响 0x0E5 / 0x0F0 / 0x0F4 / 0x0F6 四条命令。

已排除的下层因素：
- `LookupExportByName` 正确（kd 单步实测 `al=1`，算出 `0x4D180`、`0x4F710`
  与真原版一致）；
- 解码上下文 `InitPESectionReadContext` 的入参正确（`Base = PeBase+Offset`、
  `Size = PeSize-Offset`、`Mode = 2`）；
- 读指针推进逻辑正确（两边都用 `Len + ReadPtr`）。

**下一步方向**：逐字节比对三张解码表。`g_PeDecodeFunctionTable` 是编译期常量
（RVA `0x988A0`，256 项 × 20 字节），可直接与原件对比；
另两张在运行期由 `InitPESectionDecodeTables` 生成，需在两边同时 dump 后比对。

### 7.3 【自我纠正】解码表本身是正确的

上节曾怀疑解码表内容不同。该怀疑**不成立**，原因是读错了 RVA。

- 原版 `g_PeLegacyDescrambleTable` 在**原版驱动**的 RVA `0x96A50`。
- 我方同名表是 `&g_PeDecodeTableRegion[0x20]`，而
  `g_PeDecodeTableRegion` 在**我方驱动**里实际位于 RVA `0x8B9D0`
  （map 实测），所以 `[0x20]` 落在 RVA `0x8B9F0`。
- 按各自正确的 RVA 读取，两边内容**逐字节相同**：
  ```
  原版 0x96A50 : 00 01 FF 00 2E 00 00 00 63 02 83 02 00 00 00 00 04 00 00 00
  我方 0x8B9F0 : 00 01 FF 00 2E 00 00 00 63 02 83 02 00 00 00 00 04 00 00 00
  ```
  表头注释里的 RVA 是**原始驱动的地址**，不是我方的，不能用它去我方模块里取数。

因此解码表这一层**不是**根因，`ReadPESectionEntry` 的解码表选择也正确。
剩余 4 条的失败点仍待定位（`ScanKfdDriverSections` 首个节点解出 1294 而非 1296
这一现象，需在两边同时 dump 完整描述符逐字段比对，而不是只比类型）。

### 7.4 真正差异：解码起点不同（0x4F715 vs 0x4F748）

在两边 `ScanKfdDriverSections` 的 1296 判定点读取寄存器，把解码位置减掉各自的
`PeBase`（`ReadNetioDriverFile` 分配的文件缓冲，每次加载地址不同，与 RVA 无关）：

| | 真原版 | 我方 |
|---|---|---|
| `PeBase` | `ffff8c88 852a0000` | `ffff8c88 85290000` |
| 解码位置（`ecx`/`r10`） | `...852ef748` | `...852df715` |
| **相对偏移** | **`0x4F748`** | **`0x4F715`** |
| `GT[0x7BE]`（起点） | `0x4F710` | `0x4F710` |
| 首个命中类型 | **1296** | 1294 |

两边起点都是 `0x4F710`，但走到"第一个满足条件的节点"时，原版已前进
`0x38` 字节、我方只前进 `0x5` 字节 —— 说明**首个条目解码出的
`+0xF0`（消耗字节数）不同**，导致后续读取的字节流错位。

配合 7.3 的结论（解码表逐字节相同），差异只能来自
**`ReadPESectionEntry` 的解码循环本身**（它按 `g_PeDecodeFunctionTable`
分发到各指令解码器，累计 `+0xF0`）。这是 662 字节的函数，
需要与原件逐条比对指令分发表内容与分发逻辑。

### 7.5 排除了"起点/输入不同"，锁定 `ReadPESectionEntry` 本身的解码结果

补做了三项验证，把范围压到唯一一处：

1. **`ScanKfdDriverSections` 确实被调用**（设对断点后命中，地址是我方
   `RVA 0x37360`；先前误用 `0x36360` 导致误判"未调用"）。
2. **入口参数与真原版完全一致**：`PeBase=ffff8c88 85290000`、
   `PeSize=0x94000`、`GT[0x7BE]=0x4F710`。
3. **输入字节流相同**：`PeBase+0x4F710` 处读出的是 x64 机器码
   （`48 89 5C 24 08 48 89 74 24 10 57 48 83 EC 20 ...`），
   两边同一文件、同一偏移，内容自然一致。该私有格式正是从**函数代码字节流**
   里解码出"节区描述符"。

第一个条目的解码结果对比：

| | 真原版 | 我方 |
|---|---|---|
| 类型（`*(WORD*)(desc+0x118 +6)`） | **1296 (`0x510`)** | **1294 (`0x50E`)** |
| `+0x78` | `0x27E18` | `0x40` |
| `+0x50` | `0x40` | （走 1294 分支） |

即：同一段机器码、同一张解码表、同一个起点，`ReadPESectionEntry`
解出的**首个条目类型就已经不同**。这就是 0x0E5 / 0x0F0 / 0x0F4 / 0x0F6
四条命令的共同根因，也是唯一的剩余缺口。

**下一步（唯一方向）**：在两边同一下断 `ReadPESectionEntry` 的入口，
逐指令对照它如何消费 `48 89 5C 24 08 ...` 这段并累计 `+0xF0`，
定位分歧出现在第几条指令、哪个解码器分派上。

### 7.6 最后一个决定性的量化差异：首条目消耗 0x38 vs 0x5

把两边"首个满足条件的节点"时的读指针位置减掉起点 `0x4F710`：

| | 起点 | 首节点时位置 | 前进量 |
|---|---|---|---|
| 真原版 | `0x4F710` | `0x4F748` | **`0x38`（56 字节）** |
| 我方 | `0x4F710` | `0x4F715` | **`0x5`（5 字节）** |

起点处的机器码是：
```
48 89 5C 24 08    mov [rsp+8], rbx      ← 正好 5 字节
48 89 74 24 10    mov [rsp+10h], rsi
57                push rdi
48 83 EC 20       sub rsp, 20h
33 C0             xor eax, eax
...
```

我方把第一条 `mov [rsp+8],rbx`（5 字节）作为一条描述符消费，
**这个长度本身是正确的**；原版却一次走完 0x38 字节才产出第一个 1296 节点。

说明原版的 `ReadPESectionEntry` 在 `DispatchInstructionDecode` 返回后，
消费量的累加方式与我方不同（原版很可能在**单次调用内**持续消费多条指令，
直到某种终止条件成立才返回一个描述符）。这是 662 字节函数内部的核心差异。

**唯一待办**：对照原版 `0x14008A54C`（`ReadPESectionEntry`）的 662 字节，
以及 `DispatchInstructionDecode` 的返回值语义，修正消费量累加逻辑。
