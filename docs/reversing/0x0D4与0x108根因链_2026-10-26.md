# 0x0D4 / 0x108 根因链（2026-10-26 实机定位）

本文记录两条命令共同阻塞点的定位过程、已用反汇编/实机核对的事实、以及剩余待完成的一处重写。
所有 GT 槽号、函数名、地址均在 **Win10 1903 build 18362** 的 guest 上实测或从原版 `View++_Driver64.sys.i64` 反汇编取得。

---

## 1. 结论速览

| 命令 | 现象 | 直接原因 |
|---|---|---|
| `0x0D4` CmdEnumObjectTypes | REJ（计数 0） | `ScanProcessVadMemory` 内 `ValidateKernelObject` 对 **全部 92 个进程返回 0** |
| `0x108` CmdEnumProcessorInfo | OK 但 0 字节 | `EnumerateProcessList` 返回 0（其内部 `EnumerateProcessInformation` 同样卡在 `ValidateKernelObject` / 条目填充） |

两者共用同一个阻塞点：`ValidateKernelObject`（原版 `0x14004F600`）。

## 2. 已排除的误判

### 2.1 `GT[0x41DB]` / `GT[0x4265]` 曾经是 0 —— 是假象
- 原因：早期部署的是 2026-10-25 04:23 的旧驱动，它早于 `BuildHookTable` 的修复。
- 换成当次构建后实测：
  - `GT[0x41DB] = 0xfffff800288c22f0 = nt!MmIsAddressValid`
  - `GT[0x4265] = 0xfffff80028b6f3a0 = nt+0x56f3a0`（`PsProcessType` 附近）
  - `GT[0x4159] = 0x66EDC0`（与原版文档记载一致）
- `BuildHookTable` 诊断：`ExportCount=0xB64`、`Iter=0x10C`、`Hits=Writes=0xFE`。
- **结论：`BuildHookTable` 工作正常；`GT[0x4158+3k]` 三元组（hash/RVA/VA）由它在 DriverEntry 写入，与命令 0x6B 无关。**

### 2.2 一次读数笔误
早期曾把 `GT[0x4265]` 的地址算成 `base+0xa84f0+0x21328 = 0x2709_8818`，正确应为 `0x2709_9818`（差 0x1000），由此错判「原版该槽为 0」。

### 2.3 命令表映射没有错
原版 `InitCommandHandlerTable` 以 `mov [rbx+0x740], CmdEnumProcessorInfo` 形式赋值，slot 232 ↔ 命令 `0x20+232 = 0x108`。
我方运行期 `GT[0x921+232] = GT[0xA09]` 实测等于 `base+0x27F10`，正是 `CmdEnumProcessorInfo` 的 RVA。

## 5. 本轮调试工具经验（避免重复踩坑）

- `g_DiagPc*` / `g_DiagVad*` 诊断变量定义在 `DriverEntry.c`，地址以 `build/bin/Release/x64/XPCHunterDrv.map` 为准（每次重编译会整体平移，例如 `0xd7598`）。
- **不要**依赖 0x13A 的 env 块偏移导出：`0x1C0..0x1DF` 被 16 个对象类型候选槽占用、`0x200..0x23F` 亦在其内；实测写入后读回仍为 0。直接用 kd 读全局变量最可靠：
  `dq XPCHunterDrv+<RVA> L1`（`XPCHunterDrv` 为模块名，kd 会解析基址）。
- kd 每次 `kd_exec` 会断住 guest，**之后所有 vmrun 命令都会失败**（表现为无输出）。必须 `kd_go` 再继续。
- 本机 `g_GlobalTable` RVA 当前为 `0xAB060`（会随代码量变化，务必每次从 map 重取）。

## 6. 后续进展（2026-10-26 晚）

### 6.1 `ValidateKernelObject` 已按原版整体重写
旧实现中段读 `0x42C/0x4186`，与原版（`0x1CF/0x1D0/0x1D1` 与 `0x37/0x3D/0x38/0x3F/0x3A/0x39`）完全不同。
已按 `0x14004F600..0x14004F9DC` 逐条重写，过程中发现并修正两处**新**缺陷：

1. `Range = *(ULONG64*)MmSystemRangeStart` —— `MmSystemRangeStart` 是**导入变量**，
   原版 `mov rax,cs:MmSystemRangeStart; mov rcx,[rax]` 取的是变量的**值**。
   多写一层解引用会去读 `0xffff800000000000` → **BSOD 0x50（写）**。正解：`(ULONG64)MmSystemRangeStart`。
2. `0x14004F763` 是 `jnb`（**大于等于即失败**），不是 `jbe`。该槽值必须**低于**
   `MmSystemRangeStart`（用户态地址）。写反方向会让全部进程校验失败。

修复后实测 `g_DiagVkStage = 10`（走到函数末尾），即全部校验通过。

### 6.2 `ScanProcessVadMemory` 条目字段顺序修正
原版 `0x14008A1FA` 是 `*((_QWORD*)&ResultStruct + 1) = FoundAddress`，
即写入**第一个 16 字节结构的高位**。旧实现写到 `OutS2Hi`（条目 +0x18），
导致条目变成 `[obj, 0, size, FoundAddress]`；原版是 `[obj, FoundAddress, size, 0]`。

### 6.3 `0x0D4` 对齐结论（已验收）
同状态、同一条命令、同一台 guest 的对照：

| 项 | 原版 | 复刻 |
|---|---|---|
| 结果 | OK | OK |
| 条目数 | 52 | 52 |
| 输出长度 | 1658 B | 1658 B |
| 条目步长/布局 | 0x20，`[obj, FoundAddress, size, 0]` | 相同 |

逐字段比较（按对象地址配对）：
- 原版 vs 原版（连跑两次）：51 条中 **49 条完全相同**，2 条仅 `FoundAddress` 不同；
- 原版 vs 复刻：50 条中 **43 条完全相同**，7 条仅 `FoundAddress` 不同，另有 1 个进程只在一侧出现（运行期间进程创建/退出）。

`FoundAddress` 是 VAD 扫描得到的地址，**原版自身两次运行就不一致**，因此这一差异属运行时波动，
与实现无关。**结论：`0x0D4` 已与原版对齐。**

### 6.4 `0x108` 剩余阻塞点（新定位）
`EnumerateProcessList` 仍返回 0。其内部第一步 `DispatchProcessHandleTableEnum`
读 `GT[0x25]`（非 0）走 `TraverseProcessHandleTableWin10`，但没有产出条目；
第二步 `EnumerateProcessInformation` 依赖：

- `NtQuerySystemInformation`（GT[0x41DE]）——**参数顺序原版是 `(0, &Dst, 0x40, 0)`**，
  旧实现写成 `(&Dst, 0, 0x40, 0)`（Class 传成栈地址）→ 恒返回 `0xC0000003`，已修正；
- `pStepCount = PageSize * min(Dst[+0x0C], Dst[+0x14])`（build<0x4F7C）
  或 `PageSize * Dst[+0x14]`（build>=0x4F7C）——旧实现取 max、偏移错、乘数用 NTSTATUS，已修正；
- 扫描区间来自 `GetKernelVirtualAddressRange` → `GT[0x8CE]/GT[0x8CF]`。
  **这两个槽由 Syscall Hook 回调在运行期写入**（`HookSyscallNtCreateThread` 写 0x8CE、
  `HookSyscallNtCreateProcess` 写 0x8CF）。未装/未触发 Hook 时恒为 0 → 扫描区间为空。

因此 `0x108` 的下一步是让 `TraverseProcessHandleTableWin10` 正常产出条目（首选，
与 Hook 状态无关），而不是依赖 0x8CE/0x8CF。

### 6.5 诊断变量一览（本次新增，均在 `DriverEntry.c`，地址查 map）
`g_DiagVkStage`（ValidateKernelObject 最后通过的第几关）、
`g_DiagEpiA..E`（进程扫描各条件命中计数）。

## 7. 第二批修复（2026-10-26 深夜）

### 7.1 `0x108` 三个连锁缺陷（已验收）

1. **`ValidateAndEnumerateObject` 类型标志槽**：原版 `0x14005011D mov ecx,81Ch`，
   旧实现读 `16960`(0x4240) → 每个句柄表对象都被判为非进程。
2. **`DecodeObjectPointerFromHandleEntry` 必须用算术右移**：
   句柄表条目只保存 48 位指针，靠 bit63 符号位恢复 `0xffff` 前缀。
   原版是 `sar rcx,10h`；旧实现用无符号 `>>`，解出 `0x0000bc077f67e380`
   这种低于 `MmSystemRangeStart` 的地址，回调全部拒绝。
3. **`EnumerateProcessList` 的上下文长度**：`ValidateAndEnumerateObject` 读 `Context+16`，
   原版的 8 字节栈缓冲靠布局恰好为 0；旧实现读到栈垃圾 → 所有条目被过滤。
   现改为显式 24 字节全零上下文。

修复后实测（同状态对照）：

| 项 | 原版 | 复刻 |
|---|---|---|
| 输出长度 | 34 B | 34 B |
| 内容 | `0000000000000000000000000000000080501e8607bcffff40304b8407bcffff5808` | **完全相同** |

`0x108 CmdEnumProcessorInfo` 逐字节一致（含 `+0x10`/`+0x18` 两个内核指针、`+0x20` 的值）。

### 7.2 `0x047` 参数映射错误（结构已通，数据源仍空）

原版 `0x1400410AE/0x1400410B1`：
```
mov r14d, r9d    ; 长度 = 第 4 参数 OutSize
mov rbx,  r8     ; 缓冲 = 第 3 参数 OutPtr
```
旧实现把 `(InputBuffer, InputSize)` 当缓冲/长度传入，而 0x047 的调用方是
`InPtr=NULL / InSize=0` → `OutSize >= 0x50` 门限失败 → 0 字节。
改为 `KernelMemoryOperationDispatch(pOutputBuffer, OutputSize)` 后**块结构已正确输出**
（每块 0x18 字节头：`+0x00 类型`、`+0x10 条目数`），但各块条目数仍为 0：

- 实测 `GT[0x5A]=0`、`GT[0x5B]=0` → **SSDT1 表未解析**（`FindSsdtServiceTableV1` 未产出），
  这是块 1 为空的原因；其余块同理依赖各自的懒加载子系统。

下一步：让 `FindSsdtServiceTableV1` 正常写入 `GT[0x5A]/[0x5B]`，再逐块核对条目。

### 7.3 `0x047` 的 SSDT1 链路定位（输入全部有效，卡在节区扫描）

实机读到的输入槽（我方，均非 0）：

| 槽 | 值 | 含义 |
|---|---|---|
| `GT[0x61]` | 目标进程 | `KeStackAttachProcess` 用 |
| `GT[0x41A7]` | `0x74A400` | 导出目录 RVA（原版 `0x140040986 mov ecx,41A7h`） |
| `GT[0x20]` | `0xffff80038e200000` | 展开后的 nt 镜像 |
| `GT[0x21]` | `0xAB2000` | 镜像大小 |

原版 `0x140040A18` 在 build >= 0x1771 时调用
`FindSsdtTableAddresses(scanPos, imageEnd, &Value, &Offset)`，其中
`scanPos = GT[0x20] + GT[0x41A7]`、`imageEnd = GT[0x20] + GT[0x21]`。
我方这三个输入与原版一致，但该函数内部的 PE 节区扫描没有产出
`Value`/`Offset`，因此 `FindSsdtServiceTableV1` 返回 0，`GT[0x5A]/[0x5B]` 仍为 0。

**下一步**：对照原版 `0x1400409xx..0x140040A56` 逐条核对
`FindSsdtTableAddresses`（我方 `SyscallTable.c:1681`）的节区筛选条件
（1368/1370 类型判断与 `SubSectionAddress`/`OffsetFieldValue` 等字段偏移）。

### 7.4 `FindSsdtTableAddresses` 的确切缺陷（已定位到变量级）

`SyscallTable.c:1681..1809`（对应原版 `0x140040A18` 调用的那个函数）里，
下列 9 个局部变量**只被读、从未被赋值**：

```
SubSectionAddress, AddressFieldValue, SizeFieldValue, AlignmentValue,
TypeFieldValue, OffsetFieldValue, DecodedFlags, EntryCumulativeSize,
EntryDataPointer
```

它们本应在 `ReadPESectionEntry(ReadContext, SectionInfo)` 成功之后
从解码出的结构体里加载（原版在 `InitHookSyscall` 一类的函数里是同一套
字段偏移：`SectionInfo+0xF0` 是条目长度、`SectionInfo+0x118` 指向子类型、
子字段按 `+0x30/+0x38/+0x50/+0x58/+0x78/+0x80/+0x88` 等偏移读取）。
由于这些值恒为 0/栈垃圾，函数里所有节区筛选条件
（`1368/1369/1370` 类型、`SubSectionAddress != 0`、
`AlignmentValue == 0x40000`、`TypeFieldValue == -1` 等）永远不成立，
所以 `Value`/`Offset` 恒为 0 → `FindSsdtServiceTableV1` 返回 0 →
`GT[0x5A]/[0x5B]` 为 0 → `0x047` 块 1 空。

**修复方式**：按原版把 `ReadPESectionEntry` 之后那段字段加载补全
（可直接参照同文件内 `InitHookSyscall`/`ScanKfdDriverSections` 的字段读取写法），
再逐条比对 1368/1370 条件。

### 7.5 已补全 9 个字段加载，但 `GT[0x5A]/[0x5B]` 仍为 0

按原版 `0x14003FDC0`（`FindSsdtTableAddresses`）内层循环的寄存器取值，
给 `SyscallTable.c` 里那 9 个变量补上了加载，偏移如下（均已核对指令）：

| 变量 | 偏移 | 原版依据 |
|---|---|---|
| `EntryCumulativeSize` | `+0xF0` | `mov eax,[var_80]`，用于推进读指针 |
| `SubSectionAddress` | `+0x38` | `0x14003FED5 mov eax,[var_138]` |
| `DecodedFlags` | `+0x20` | `0x14003FFB3 mov eax,[var_150]; test al,4` |
| `SizeFieldValue` | `+0x50` | `cmp r8,40h` / `cmp r8,40000h` |
| `AlignmentValue` | `+0x88` | `cmp r9,40000h` / `cmp r9,400000000h` |
| `AddressFieldValue` | `+0x78` | `0x14003FF79 mov eax,[var_F8]; test eax,eax` |
| `TypeFieldValue` | `+0x70` | 与 `-1` / `2` 比较 |
| `OffsetFieldValue` | `+0x40` | 偏移 RVA 计算 |
| `EntryDataPointer` | `+0x118` | `0x14003FF54 mov rax,[var_58]` → `word[+6]` 为节区类型 |

编译部署后实测：`0x047` 仍为 265 B，**`GT[0x5A]`、`GT[0x58]` 依旧为 0**。
说明还有其它上游条件不成立（例如 `InitPESectionReadContext` 的入参、
或外层 1368..1370 节区在该扫描区间内确实没出现）。
下一步应在这两处循环里加计数（外层解码条目数、命中 1368 的次数、
内层命中 1298/1065/1324 的次数），再按计数定位。

### 7.6 计数定位结果（2026-10-27）

| `g_DiagFilB` | **0x1E = 30** | 外层循环解码满 30 条后按 `SectionIndex >= 0x1E` 退出 |
| `g_DiagEpiA` | **0** | 30 条里**命中 1368–1370 的次数为 0** |
| `g_DiagFilC` | 0 | （因上一行为 0）子节区 RVA 有效次数为 0 |
| `g_DiagFilD` / `EpiB` / `EpiC` / `EpiE` | 0 | 内层根本没进入 |

**结论**：不是字段读取的问题（9 个字段已按原版偏移补全），而是**外层这 30 条描述符
里根本没有 1368–1370 类型**。可能的两个方向：

1. **扫描起点不对**：`pScanPos = GT[0x20] + GT[0x41A7]`，实测 `GT[0x41A7] = 0x74A400`。
   需要在原版驱动下读同一个槽做比对——若原版不是 `0x74A400`，说明
   `GT[GtNtDuplicateObjectPeSectionOffset | GtEprocessField26]` 这个枚举表达式
   算出的槽号（0x41A7）与真正的槽不一致。
2. **`EntryDataPointer` 偏移不对**：+0x118 只是从 `InitHookSyscall` 等同族函数
   推断而来；若原版此处用的是另一个偏移（IDv 显示为 `var_58`），
   则 `word[+6]` 读到的不是节区类型。

**下一步（最省事）**：加载原版驱动，读 `GT[0x41A7]` 与 `GT[0x20]`，与复刻值逐字节比较。
若 `0x41A7` 一致，再在复刻里把 `EntryDataPointer` 改为 `var_58` 对应的
真实偏移（用一次 dump 打印 `SectionInfo[0..0x1C0]` 看哪个 qword 指向含
`word[+6] == 1368` 的结构即可确定）。

### 7.7 原版/复刻输入逐字节比对：完全一致（2026-10-27）

加载原版驱动 `OGT` 后读同一批槽：

| 槽 | 原版 | 复刻 | 判定 |
|---|---|---|---|
| `GT[0x41A7]`（导出目录 RVA） | `0x74A400` | `0x74A400` | 相同 |
| `GT[0x20]`（展开后的 nt 镜像） | `0xffff80038e200000` | `0xffff80038e200000` | 相同 |
| `GT[0x21]`（镜像大小） | `0xAB2000` | `0xAB2000` | 相同 |

因此 **7.6 的假设 1（扫描起点不对）被推翻**。既然起点、长度、镜像内容都一致，
而两个驱动用的是同一套 `ReadPESectionEntry` 解码器，那么差异只能出在
**解码上下文的参数**或**条目结构里类型指针的偏移**上：

- `InitPESectionReadContext(pSectionData, SectionEnd-(int)pSectionData, 2, 0, -1, 0, 0, &ctx)`
  的 3/5/6/7 号参数需再核对（原版 `lea r8d,[rbx+2]`，`var_1E0/var_1E8 = rbx`，
  若 `rbx` 在进入这段时不是 0，则 3/6/7 号参数都不是我写的值）；
- 或 `EntryDataPointer` 的真实偏移不是 `+0x118`（该值目前是从
  `InitHookSyscall` 推断的）。

**下一步最省事且能一次定性**：在复刻里加一段一次性诊断——把第一条解码出的
`SectionInfo` 原始字节 dump 到 GT 的空闲槽（或直接 `DbgPrint` 不现实，
改用 `g_Diag*` 逐个存 qword），再用 kd 读回，肉眼找 `word[+6] == 1368`
的那个 qword 位于哪个偏移。这比继续猜参数更快。

### 7.8 描述符探针结果（2026-10-27，决定性）

在 `FindSsdtTableAddresses` 外层循环第一条描述符上做探针：

| 探针 | 值 | 含义 |
|---|---|---|
| `EntryDataPointer+6` 的 word | **1070 (0x42E)** | 第一条的 `+0x118` 类型是 1070，不是 1368 |
| 在 `SectionInfo[0..0x1C0)` 逐 8 字节找 `word[+6]==1368` | **0xFFFF（未找到）** | 第一条里没有任何指针指向类型 1368 |
| 类型命中计数 `g_DiagEpiA` | **1** | **30 条里有 1 条命中 1368–1370** |

**关键结论**：

1. `EntryDataPointer = *(ULONG64*)(SectionInfo + 0x118)` **偏移是正确的**——它能解出合法类型（1070、以及某条的 1368），不是错位。
2. 既然有 1 条命中 1368–1370，失败点就**只在紧随其后的两个判断**：
   ```c
   if (SubSectionAddress) {                                   // *(int*)(SectionInfo + 0x38)
       SubSectionRva = ComputedOffset + SubSectionAddress - (int)NtImageBase;
       if (SubSectionRva && SubSectionRva < NtImageSize) { 内层... }
   }
   ```
   即 `SubSectionAddress == 0`，或 `SubSectionRva` 落在 `[1, 0xAB2000)` 之外。

**下一步（只需一次计数）**：在那条命中 1368 的分支里把
`SubSectionAddress` 与 `SubSectionRva` 分别存进两个空闲 `g_Diag*` 槽读回，
即可判定是 `+0x38` 偏移不对、还是 RVA 计算式不对（原版 `0x14003FED5`
是 `mov eax,[var_138]; test eax,eax; sub eax,r12d; add eax,edx`，
其中 `r12` 是 `NtImageBase`、`edx` 是 `ComputedOffset`——与本式一致）。
