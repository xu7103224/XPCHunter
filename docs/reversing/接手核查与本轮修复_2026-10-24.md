## 二、本轮修掉的七处真缺陷

### 2.1 `pValidateFunc()` 无参调用（BSOD 0x3B，`EnumerateDriverList`）

**症状**：`--network-cli` 触发 BSOD 0x3B，栈：
```
nt!KiPageFault
ViewPlusPlusByLinxer+0x40aa0   → EnumerateDriverList+0x190
ViewPlusPlusByLinxer+0x690c0   → CmdEnumDriverObjects+0x60
ViewPlusPlusByLinxer+0x23387   → CmdQuerySsdtInfo+0x97
```

**根因**：原版 `0x14003C184` 是 `mov rcx,[rbx+50h]` 紧接 `0x14003C19A call rbp`
—— 首次调用传的是**名字指针本身**；`0x14003C1A0..A7` 再算
`指针 + 长度 - 1` 传第二次。旧代码两处都写成 `pValidateFunc()`（无参），
rcx 是上一条指令的残留垃圾值。与上一轮 `AllocateNtHandleEntry` 的
`CloseHandleFunc()` 完全同类。

**修复**：函数指针签名改为 `__fastcall (*)(__int64)`，三处调用点
（`EnumerateDriverList` 两处、`BuildDriverImagePath` 一处）都显式传地址。

### 2.2 `LookupDriverObjectEntry` 读错 GT 槽（BSOD 0x3B 的根因）

**症状**：修完 2.1 后仍崩，崩溃点前移到 `EnumerateDriverList+0x186`
（`0x140040A96 cmp qword ptr [rax], rbx`），说明判空已生效但 rax 是个**非零的坏指针**。

**根因**：原版 `0x14003B000` 是 `mov ecx, 4172h` —— 读 **GT[0x4172]**。
我方写成 `GtTotalSize | GtEprocessField104 | 0x100`：
- `GtTotalSize = 0x4000`
- `GtEprocessField104` → `GtEprocessField94` → **104**
- 再 `| 0x100`

实算 `0x4000 | 104 | 0x100 = 0x4168`，而 0x4172 的低字节是 `0x72 = 114`。
**索引差了 0xA**，读到的是别的槽（那里恰好存着本驱动自己的代码地址），
于是 `cmp [rax], rbx` 去解引用代码段 → 页错误。

同时发现旧代码把同一个槽**读了两次**（第一次判空、第二次解引用），
两次之间值可变，也一并改为只读一次。

**修复**：改用显式常量 `GtRead((GLOBAL_TABLE_INDEX)0x4172)`。

**这是本项目第三次踩「GT 槽号靠宏拼接、拼接结果与原版立即数不符」的坑**
（前两次：`GtFwpsDispatchTableBase` 被 `#define` 覆盖成 0x910、
`GtEprocessField132` 宏链把 142 压成 112）。

### 2.3 `--hotkeys-cli` 永远静默（前端）

**症状**：`xpch_frontend.exe --hotkeys-cli <pid>` 无任何输出。

**根因**：该分支直接调 `FePrintProcessHotkeys(&g_Client, pid)`，
但执行到这里时 `DoConnect()` 还没跑过，`g_Client.Opened == FALSE`，
函数第一句 `!Client->Opened` 就返回 FALSE。

**修复**：分支内先 `XpchOpen(&g_Client)`，失败时打印错误；
成功后 `XpchClose`。修复后能输出
`enum hotkeys failed, GetLastError=31`（说明链路已通，卡在驱动侧 0x33，见 §3.2）。

### 2.4 `CmdReadExportDirectory` 32 位下标被当 64 位用（BSOD 0x3B，命令 0xEC）

**症状**：`--network-cli` 跑到 NdisOidTable 节时 BSOD 0x3B，故障地址
`ViewPlusPlusByLinxer+0x6e9d3` = `CmdReadExportDirectory+0x123`。
（注：单条 `--cmd 0xEC --out 0x4000` 不崩，因为没满足输出缓冲区阈值。）

**根因**：我方编译产物是

```
14006E9B4  lea  eax, [rbp-0x18]     ; eax = ExportDirSize - 24（32 位！）
14006E9B7  mov  ecx, eax
14006E9B9  add  rax, rbx            ; 64 位相加，但 rax 高 32 位是垃圾
14006E9BC  cmp  rbx, rax
14006E9BF  ja   退出
14006E9C1  mov  rax, [rbx+8]
14006E9C8  je   0x14006E9D3
14006E9D3  mov  rax, [rbx+0x10]     ; <== 页错误
```

旧源码 `while ((ULONG64)pEntry <= (ULONG64)&pEntry[ExportDirSize - 24])`
里，下标表达式被算成 **32 位** `lea eax`，再被 `add rax, rbx` 当 64 位用，
上界被放大成巨值，循环越过用户缓冲区边界。

原版 `0x1400609FB` 是 `lea rcx,[rbx-0x18]; add rcx,r12` —— 全程 64 位。

**修复**：显式构造 64 位上界

```c
const unsigned __int64 EndLimit =
    (unsigned __int64)pEntry + (unsigned __int64)ExportDirSize - 24u;
while ((unsigned __int64)pEntry <= EndLimit) { ... }
```

**效果**：0xEC 不再崩溃，Network 页的 NdisOidTable 节点立刻拿到
**209 行真实数据（209 条全部检出 hook）**。

### 2.5 `FindObjectOperationDataSection` 指针宽度错误（命令 0x33 崩溃）

**症状**：`--cmd 0x33` 必崩 BSOD 0x3B，故障点
`ReadPESectionEntry+0x79`（`movzx eax, byte ptr [r9]`，r9 = 读指针）。

**定位**：加分级诊断后确认链条是
`CmdEnumObjectsEx → InitObjectOperationEntry → FindObjectOperationDataSection`，
且传入的 `ImageBase`/`ImageEnd`/`Size32` 都正确
（实测 `ffff8285_0d67ed60` / `ffff8285_0d947000` / `0x2C82A0`），
崩溃来自函数内部算出的读指针。

**三处指针宽度错误**：

1. **签名把 64 位指针压成 int**
   原版 `0x140036C8F/92` 是 `add rbx, r8` / `add rcx, r8`（64 位加法），
   实参是 `pFileBuffer + FileSize` 与 `pFileBuffer`。
   旧签名 `int ImageSize, int SectionBase` 把内核池地址截断成 32 位。
2. **读指针推进用 32 位加法**
   原版 `0x1400369EF add rcx, rax` 是 64 位。
   旧代码 `NewReadPtr = (ULONG)Ctx.ReadPtr + Len` 丢掉高 32 位，
   内核池地址变成低位小整数 → 越界读。
3. 循环顺序确认为「先解码、再推进」（`0x1400369DA` 先 call，
   `0x1400369EF` 后 add），与同族 `FindObjectOperationBaseOffset`
   的「先推进再解码」不同，已按本函数原始顺序保留。

**修复后**：0x33 由「必崩」变为稳定返回。诊断显示解码器本身工作正常
（连续 55 轮读到 `0x510/0x50E/0x4E6/0x42E/0x53E/0x4D7` 等合法 PE 描述符类型），
只是这段数据里没有原版要找的 **0x558 / 0x545**，
说明 `GT[0x2E3]`（`SyscallOffset=0x0DED60`）指向的节区内容与预期不同 ——
剩下的就是这个语义问题，不再是崩溃问题。

### 2.6 `FindObjectOperationSection` / `FindObjectOperationBaseOffset` 条件用未初始化变量

**背景**：命令 0x33 的处理链是

```
CmdEnumObjectsEx
  → InitObjectOperationEntry
      → FindObjectOperationDataSection   （第一环，§2.5 已修）
      → QueryObjectOperationByVersion
          → FindObjectOperationSection    （第二环）
          → FindObjectOperationBaseOffset （第三环）
```

**缺陷**：两个函数都用了**从未赋值的局部变量**做条件判断，
使分支恒不成立、函数恒返回 0。

- `FindObjectOperationSection`：`FlagsField` / `Flags2` / `TypeField` /
  `EntryOffset` 全未赋值；`EntrySize2` / `ContextOffset` 也未初始化就
  参与 `CurrentRva` 计算。
- `FindObjectOperationBaseOffset`：`EntrySize` / `RvaField` / `Flags2` /
  `EntrySize2` 同上；且字段偏移写成了 `desc+0x40/0x78/0x8C`，
  与原版不符。

**修复**：按反汇编逐条重写，描述符基址 `rsp+0x90` 换算：

`FindObjectOperationSection`（原版 `0x1400366E0`）
```
1340..1347 且 desc+0x88==0x800000 且 desc+0x70==0x200  → FoundFlag=1
0x558 且 desc+0x50&0x4000000 且 desc+0x38!=0 且 FoundFlag==1
    → rva = desc+0x38 - SectionBase + 读指针
```

`FindObjectOperationBaseOffset`（原版 `0x140036A78`）
```
模块基址 = build>=0x2800 ? GT[0x8F6] : GT[0x50]
模块大小 = build>=0x2800 ? GT[0x8F7] : GT[0x51]
0x512 且 desc+0x88==0x40000 且 desc+0x78!=0 且 desc+0x50==0x40
    → 返回 模块基址 + (desc+0x78 - SectionBase + 读指针)
```
同时把两个函数的指针参数改为 64 位、读指针推进改为 64 位加法。

**验证（kd 读 GT）**：三环全部产出真实值

```
DataSectionOffset = 0x0DEE6C      （与原版离线复现值完全一致）
VersionOffset     = 0x0DF184
BaseOffset        = 0xFFFF9D5925731B70
GT[0x2E4]         = 0xFFFF9D5925731B70   ← 已被填入
```

命令 0x33 由「必崩 BSOD 0x3B」变为**稳定返回**。

**剩余边界（能力边界，非实现缺陷）**：`GT[0x2E4]` 指向
`0xFFFF9D59_xxxxxxxx` —— **win32k 会话空间**。在 session 0 的
probe 上下文里 `kd dq` 全为 `?`（不可读）。原版前端运行在用户会话中，
天然具备该上下文。热键表按会话隔离，跨会话读不到属预期。

## 四、当前阻塞点（已定位，未修）

### 4.1 前端 `--network-cli` 握手失败 —— 已随 0xEC 修复消失

此前 `XpchHandshake` 返回 FALSE，同一台机器上 `xpch_probe.exe` 握手却成功。
在 0xEC 的 BSOD 修掉之后，前端握手恢复正常
（`device opened, ioctl=0x05E00158 key=0xCF`）。
事后判断：前一次「握手失败」发生在快照回滚后的状态上，
驱动的 `GT` 尚未完成初始化，与握手代码本身无关。

### 4.2 0x33 `CmdEnumObjects` —— 已修至稳定，剩会话隔离边界

处理链的四段已全部按原版重写（见 §2.5 / §2.6）：
`FindObjectOperationDataSection` → `QueryObjectOperationByVersion` →
`FindObjectOperationSection` → `FindObjectOperationBaseOffset`。

kd 实测三段中间值全部非 0，`GT[0x2E4]` 已填入
`0xFFFF9D5925731B70`（win32k 会话空间）。命令不再崩溃。

**剩下的不是代码缺陷**：该指针对应的热键表位于 win32k **会话空间**，
session 0 的 probe 上下文读不到（`kd dq` 全 `?`）。原版前端运行在
用户会话里，天然具备该上下文。要在此环境验证，需在同一会话内调用。

### 4.3 快照基线下的状态差异

回滚到 `pre_0x132_write_test` 后，`0x26/0xC4/0xF8/0xFB/0x10B` 全部返回 REJ。
已确认**不是代码回归**（本轮只改了 `ModuleMgmt.c`，与这些命令无关）：
- `GT[0x304] = 1`（许可已置位）
- 分派器拒绝码 = 0（命令确实执行了）
- `GT[0x421D]` / `GT[0x4160]` 等 0xC4 依赖的槽都有正常值

结论：该快照拍摄于上一轮修复验证**之前**，其中的 GT 状态与验证时不同。
要复现上一轮的 OK 结果，需要用同一份驱动重新走一遍初始化序列，
而不是直接在该快照上调用。

## 五、可复用的教训

1. **`build.bat clean` 会删掉整个 `build/bin`**，把用户态产物一起清掉。
   正确顺序永远是「先 `build.bat`（驱动）→ 再 `build_um.bat`（用户态）」。
2. **`SUBSYSTEM:WINDOWS` 的程序 stdout 不接控制台**，
   `g.sh "... | more"` 会得到空输出。CLI 输出必须重定向到文件再 `type`。
3. **kd 表达式里的数字一律按十六进制**：`+0x921*8+235*8` 的 `235` 是 0x235。
4. **快照回滚会同时回滚磁盘**，之前推送的驱动与工具全部失效，必须重推。
5. **`0x80` bugcheck（参数 `0x4F4454` = `'TDO\0'`）是 VMware Tools 的 NMI**，
   不是驱动崩溃，不要误判。
