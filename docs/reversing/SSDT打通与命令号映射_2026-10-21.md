## 二、根因：命令号映射算错了（本轮最关键的一条）

驱动命令表是 `Table[i]`，而 **`Table[i]` 对应命令号 `0x20 + i`**。
我之前一直按"命令号 = i"去查，导致整整一批命令全指错位置：

| 我之前的写法 | 实际命令号 | 实际落到的槽 |
| --- | --- | --- |
| 0x8C "枚举 SSDT" | Table[108] | `RtlZeroMemory(&Table[105], 0x30)` 的**空槽区间** |
| 0x8E "枚举 Shadow" | Table[110] | 同上，空槽 |
| 0x111 "枚举回调上下文" | Table[257] | 无关处理器 |
| 0x112 "设置回调上下文" | Table[258] | 无关处理器 |

**正确映射**（`Table[i] → 0x20+i`）：

| 功能 | Table 索引 | 正确命令号 |
| --- | --- | --- |
| `CmdEnumSyscallEntries`（tcpip 服务表） | 140 | **0xAC** |
| `CmdEnumShadowSyscallEntries`（kbdclass 服务表） | 142 | **0xAE** |
| `CmdReadSsdtEntryTable`（KiServiceTable） | 225 | **0x101** |
| `CmdReadSsdtEntryTableEx` | 226 | **0x102** |
| `CmdEnumHookInfo` | 247 | 0x117 |
| `CmdGetHookEntryInfo` | 249 | 0x119 |
| `CmdQueryHookStatus` | 250 | 0x11A |
| `CmdEnumHookDetail` | 251 | 0x11B |
| `CmdEnumCallbackContext` | 273 | **0x131** |
| `CmdSetCallbackContext` | 274 | **0x132** |
| `CmdGetSsdtTableInfo` | 198 | 0xE6 |
| `CmdQuerySsdtDetails` | 202 | 0xEA |
| `CmdEnumSsdtEntryTable` | 229 | 0x105 |

这个错误解释了此前所有"命令返回 0"的困惑 —— 那些槽本来就是空的。

## 三、三条候选数据源的甄别

本轮把三条都实机跑了一遍，结论：

### 3.1 `0xAC` / `0xAE` —— 真实数据，但不是内核 SSDT

实测 `result=1`，返回 28 项、每条 48 字节（`+0x00` 索引、`+0x10` 地址）。
但它们的数据源是：

```c
EnumSyscallTable7       → OpenTcpIpDriverSection()   → tcpip.sys 的 .data 节区
EnumShadowSyscallTable  → OpenKbdClassDriverSection() → kbdclass.sys 的 .data 节区
```

即 **TCP/IP 与键盘类驱动的服务表**（原版用来做这两个驱动的 Syscall Hook 检测），
不是内核 SSDT。放进"SSDT 子页"是语义错误。

### 3.2 `0x101` / `0x102` —— 这才是内核 SSDT

```c
SsdtBase  = GtRead(0x...|GtEprocessField187|GtEprocessField06|0x100);
SsdtCount = GtRead(GtEprocessField94|0x800);
memmove(pOutputBuffer + 2, (const void *)(SsdtBase + 8), 8 * SsdtCount);
```

直接读 `KiServiceTable` 的表项。输出布局：

```
+0x00 DWORD WindowsBuildNumber
+0x04 DWORD 条目数 N
+0x08 起     N 个 QWORD 函数地址
```

缓冲要求 `>= 8*(N-1)+16`；本机 N=23（0x101）/ 139（0x102），给 0x1000 足够。
实测地址全部落在 ntoskrnl 区间（本次开机 `fffff80604c00000-fffff806056b2000`）。

### 3.3 `0x42` / `0xE6` / `0xEA` / `0x105` —— 不可用或名不副实

- `0x42 CmdQuerySsdtInfo`：名字叫 SSDT，原始实现（0x14003B0A0）只是校验入参后
  转调 `CmdEnumDriverObjects` 枚举驱动对象。**与 SSDT 无关。**
- `0xE6` / `0xEA` / `0x105`：本机均返回 0（导出表/钩子表链条未初始化）。

## 四、本轮修掉的一个蓝屏（过程记录）

我在 0x13A（CmdDumpCallStats）的环境块里为了看 tcpip/kbdclass 节区，
直接调了 `OpenTcpIpDriverSection()` / `OpenKbdClassDriverSection()`。
这两个函数内部会 `call` GT 里的三个函数指针：

```
GT[0x421D] RtlInitUnicodeString
GT[0x421A] IoCreateFile
GT[0x4223] CloseHandle
```

诊断函数调用它们 = 在任意时刻执行三条间接调用，触发 **0x3B (SYSTEM_SERVICE_EXCEPTION,
0xC0000005)**。WinDbg 抓到 `faulting_instruction` 在 `VPChainB` 模块内。

**教训：诊断代码不能有副作用。** 现在环境块只导出 GT 槽的原值，
要判断链条通不通，看 4 个槽是否全非零即可。

顺带确认这 4 个槽在本机都是真实函数地址：

```
RtlInitUnicodeString(0x421D)=FFFFF80637833C30
IoCreateFile(0x421A)        =FFFFF80637DD4A30
CloseHandle(0x4223)         =FFFFF8063782E930
DriverObjectListHead(0x4160)=FFFFF80637D6F500
```
`OpenFileSection` 内部 trace 显示 `openStage=4`（成功拿到句柄），
说明 0xAC/0xAE 那条链本身是通的。
