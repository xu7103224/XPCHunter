# HAL 三个分发表：可行性核查（2026-10-29）

## 0. 结论

原版界面的 Hal 页有 3 个节点：

```
HalDispatchTable
HalPrivateDispatchTable
HalAcpiDispatchTable
```

**在本机 Win10 18362 上实测：前两个真实存在，第三个不存在。**

| 表 | 符号 | 地址 | 状态 |
|---|---|---|---|
| `HalDispatchTable` | `nt!HalDispatchTable` | `0xfffff8006fe23250` | ✅ 存在，可读 |
| `HalPrivateDispatchTable` | `nt!HalPrivateDispatchTable` | `0xfffff8006fe23ce0` | ✅ 存在，可读 |
| `HalAcpiDispatchTable` | — | — | ❌ **符号不存在** |

```
kd> x nt!HalPrivate*
fffff800`6fe23ce0 nt!HalPrivateDispatchTable

kd> x nt!HalAcpi*
(无输出)
```

## 1. 一个关键事实：Win10 上 HAL 已并入内核

```
kd> lm m hal
start             end                 module name
                       ← 空

kd> lm m nt
fffff800`6fa00000 fffff800`704b2000   nt
```

**没有独立的 `hal.dll` 模块。** 从 Windows 10 起 HAL 被静态链接进
`ntoskrnl.exe`，所以：

1. 三个表都在 `nt!` 命名空间下，不在 `hal!`
2. `HalAcpiDispatchTable` 在 HAL 合并过程中被移除（ACPI 分发表由
   其他机制替代）
3. 原版驱动里**搜不到** `HalPrivate` / `HalAcpi` 任何字符串
   （ascii 和 utf16 都是 0）—— 说明原版客户端并不通过驱动取这两个表

## 2. 原版是怎么做的（推断 + 证据）

证据链：

- 原版驱动 `View++_Driver64.sys` 里 `HalPrivate`/`HalAcpi`/`HalDispatch`
  的 ascii 和 utf16 出现次数**全部为 0**
- 原版驱动只有 8 个 HAL 基础函数（`FindHalDataSectionOffset` /
  `BuildHalExportTable` / `FindHalExportTableLegacy` /
  `FindHalInitSystemExport` / `FindHalInitializeProcessorExport` /
  `FindHalDllInDriverList` / `ClassifyModuleTypeHalOrNt` /
  `FindHalInitPatternOffsets`），这些是**定位 HAL 数据段**的基础设施
- `g_HalDispatchTable` / `g_HalDispatchTableEnd` 两个全局在驱动里
  只作为**特征值**用于匹配（`*pCurrentEntry == g_HalDispatchTable`），
  不是检测目标

推断：原版客户端拿到 HAL 数据段基址后，**按已知偏移自己算三个表的地址**，
再逐项读函数指针比对。`HalAcpiDispatchTable` 在 Win10 上取不到，
界面上那一项就是空的。

## 3. 我方现状

| 能力 | 状态 |
|---|---|
| HAL 数据段定位的 8 个基础函数 | ✅ 全部实现（`SsdtHook.c` 等） |
| HAL 基址 / 大小的 GT 槽 | ✅ `GtEprocessField22`(32) / `GtEprocessField23`(33) |
| **读任意内核地址的原语** | ❌ **没有** |
| `HalDispatchTable` 检测 | ❌ 未实现 |
| `HalPrivateDispatchTable` 检测 | ❌ 未实现 |
| `HalAcpiDispatchTable` 检测 | ❌ 未实现（且目标系统上不存在） |

### 3.1 为什么不能直接复用现有命令

`0xF7`（`ReadKernelMemoryToUserBuffer`）和 `0xF9`（`ReadKernelMemoryRange`）
看着像"读内核内存"，实际**只读一个固定 GT 槽**：

```c
pKernelMemCtx = GtRead(GtEprocessExtField58 | GtEprocessField54 | 0x400);
...
*pOutputBuffer = *pKernelMemCtx;      // 只解引用这一个固定位置
```

入参被完全忽略，不能指定地址。所以**无法用它读 HAL 表**。

`0xF3`（`CopyKernelArrayToUserBuffer`）同样需要先由 `0xF8`
（`InitKernelMemoryContext`）把目标地址填进 GT 槽。

## 4. 要补齐需要做什么

### 方案 A：驱动侧新增一个「读 HAL 分发表」专用命令

1. 用现有 `FindHalDataSectionOffset` 拿到 HAL 数据段基址
2. 在其中按特征扫描 `HalDispatchTable`（8~64 个 qword，全是内核代码指针）
3. 同样找 `HalPrivateDispatchTable`
4. 输出 `{表名, 基址, 项数, 前 N 项}` 给客户端
5. 客户端按 `Fun Name / Fun Entry` 显示，并用 `FeResolveSymbol`
   把地址解析成 `模块!函数名`

**风险**：驱动侧扫描逻辑是新增代码（原版没有），不是复刻。
需要在目标系统上验证扫描不会误把其他结构当成表。

### 方案 B：客户端走已有的 `0x117`（Wdf01000 Hook 表）

`0x117` 已经能给出 908 条 wdf01000 的 Hook 表条目。
但那是 wdf01000.sys 的，不是 HAL 的，语义不同。

### 方案 C：接受 `HalAcpiDispatchTable` 不可用，只做前两个

最贴近现实：先做 `HalDispatchTable` 和 `HalPrivateDispatchTable`
（本机验证存在），`HalAcpi` 那一项按「目标系统不支持」显示为空 ——
这正是原版在该系统上的表现。

## 5. 建议

**按方案 A + C 组合：**

1. 驱动新增 HAL 分发表枚举命令（扫描 + 输出）
2. 客户端 Hal 页展示三个节点，`HalAcpi` 取不到时显示
   `(not present on this build)`
3. 用 KD 交叉验证：与 `dq nt!HalDispatchTable` 的结果逐项比对

这样既补齐了能力，又与目标系统的实际情况一致 —— 而不是为了"三个节点
都有数据"去伪造 `HalAcpi`。

## 7. 本轮实际做了什么、没做成什么

### 7.1 已实现但**未启用**

驱动里新增了 `LocateHalDispatchTables()`（`IoctlDispatch.c`），思路上：
从 ntoskrnl 的 60%~95% 区间扫「表头小整数 + 后续连续内核代码指针」的
结构，命中两个即为 HAL 两个表。

**扫描判据未经校准，因此当前不调用它。** 实测证据：

- KD 给出的真值：`nt!HalDispatchTable = 0xfffff8006fe23250`
- 我的扫描找到：`0xFFFFF80070164590` —— **不一致**

说明 ntoskrnl 的 `.data` 里存在同样形态的其他结构（表头小整数 + 一串
内核指针），仅凭这两个特征无法唯一定位 HAL 表。

把未经校准的地址喂给客户端比不显示更糟，所以**保持不启用**，
客户端读到 0 时按「未解析」显示。

### 7.2 诊断块已埋好接口

`0x13A` 的 env 段 `0x200..0x23F` 已预留 8 个字段：

```
0x200 HalDataSectionOffset   GT[0x831]
0x208 NtoskrnlBase           （实测 GT[2] 才是基址）
0x210 NtoskrnlImageSize      （实测 GT[3]）
0x218 HalImageBase           GT[32]
0x220 HalImageSize           GT[33]
0x228 HalDispatchTable       扫描结果（当前 0）
0x230 HalPrivateDispatchTable
0x238 HalTableCount
```

**踩到的坑（值得记下）**：

1. `Table[282]`（`0x13A`）在当前构建里是 **NULL**，不是文档所说
   「已挂自研诊断处理器」。所以 `0x13A` 一开始无论传多大 OutSize 都
   返回 0。临时挂上 `CmdDumpCallStats` 后才通。
2. **`GT[2]` / `GT[3]` 的实际语义与枚举名相反**：
   实测 `GT[3]`（`GtNtoskrnlModuleBase`）= `0x56F3B8`（像大小），
   `GT[2]`（`GtNtoskrnlImageSize`）= `0xFFFFF8006FF6F3B8`（像内核地址）。
   代码已改为「按哪个更像内核地址」判定，不盲信槽位名。

### 7.3 结论

**HAL 三表检测未完成。** 原因是三件事叠加：

1. `HalAcpiDispatchTable` 在本机 Win10 18362 上**不存在**（1/3 目标缺失）
2. 原版驱动**没有**任何 HAL 检测代码，客户端也拿不到现成接口 ——
   这是新增能力，不是复刻
3. 我自己写的扫描判据**被实测证伪**（找到的地址与 KD 真值不符），
   在没校准前不能交付

要真正做完，需要：用 KD 在多个 build 上取真值 → 反推可靠的识别特征
（例如表头精确值 + 表项数量 + 首尾表项的函数名特征）→ 再接线。

## 8. 本轮真正交付的东西

HAL 没做成，但**排查过程中修掉了一个此前遗留的检测正确性缺陷**：

**inline hook 比对没有处理 PE 重定位。** 已加 `FeBuildRelocMask`，
并按用户提问做了量化验证（见 `重定位与动态内存影响_2026-10-29.md`）。

这是本轮实质性的产出。
