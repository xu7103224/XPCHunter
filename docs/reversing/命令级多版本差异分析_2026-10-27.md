# 命令级多版本差异分析：哪些命令真的分系统实现

日期：2026-10-27
数据来源：原版二进制本地分析（无需 IDA）——
`build/audit/_orig_funcs_ida.json`、`_orig_callgraph.json`、`_orig_cmdtable.json`
复现：`python build/audit/cmd_version_analysis.py`

## 一、总体结论

命令表 248 个槽位中：

| 分类 | 条数 | 含义 |
|---|---|---|
| 代码路径会读到构建号 `GT[0x914]` | **202** | 行为随系统变化（多数只是取结构体偏移） |
| 有**显式分版本命名**的实现 | **66** | 原版为不同系统写了不同函数 |
| 完全没有版本判断 | 46 | 纯算法/固定逻辑 |

所以答案是：**不是"每条命令都分系统实现"，但 202 条会随系统改变行为，其中 66 条有独立的分版本代码路径。**

## 二、三种分版本形态（按耦合程度由强到弱）

### 形态 A：一条逻辑拆成多条命令，由前端按系统选

这是最强的分版本——驱动里是**完全独立的命令**，调用方根据系统版本决定发哪一条：

| 功能 | Win7 | Win8 | Win10 |
|---|---|---|---|
| 进程列表 | `0x0E2 CmdEnumProcessListWin7` | `0x0E3 CmdEnumProcessListWin8` | `0x0E4 CmdEnumProcessListWin10` |
| 进程上下文 枚举/设置 | `0x11D` / `0x11E` | `0x11F` / `0x120` | `0x125` / `0x126` |
| 线程上下文 | — | — | `0x133` / `0x134` |

**对标含义**：这几组必须逐条各自对齐，不能只实现 Win10 那条。我们三条进程列表命令都实现了，
且 `0x0E4` 已在 Win10 上实测逐字节一致；`0x0E2`/`0x0E3` 只能在对应系统上验证。

### 形态 B：一条命令内部按构建号分派到不同实现函数

66 条里的主体。典型的"同一功能、不同系统不同算法"：

| 命令 | 分版本实现 | 差异本质 |
|---|---|---|
| `0x031 CmdEnumServices` | `EnumServiceTableWin7` / `Win8` / `Win10` / `Win1020H1` | 服务表结构在不同大版本里变了，遍历方式不同 |
| `0x02D CmdModuleOperation`<br>`0x035 CmdEnumKernelInfo`<br>`0x044 CmdDriverLoadUnload` | `ParseServiceTableWin7` / `Win8` | 同上 |
| `0x043 CmdEnumKernelDriver`<br>`0x053 InitRegCallback` | `ScanWin32kPatternLegacy` / `ScanWin32kPatternWin10Plus` | win32k 特征码扫描方式换了 |
| `0x048 CmdProcessMemoryOperation` | `FindKernelDataSectionOffsetWin7` / `Win8` / `Win10` | 内核数据节定位方式不同 |
| `0x058`–`0x060`（DeviceIoControl 系列） | `SwapKernelObjectPointerPreWin10` / `Win10`；`ScanKernelModuleSectionForWin10` / `Win10RS3` | 对象指针交换技巧在 Win10 前后不同；RS3 又变一次 |
| `0x07C CmdReadCpuBaseAddr` | `FindCpuMsrBaseLegacy` / `FindCpuMsrBaseWin10` | MSR 基址定位方式不同 |
| `0x103`–`0x105`（SSDT 系列） | `BuildSsdtHookTableLegacy` / `BuildSsdtHookTableWin10`、`FindHalExportTableLegacy` | SSDT/HAL 表解析方式不同 |
| `0x025`–`0x030`、`0x03C`、`0x061`、`0x0C2`、`0x0D4`、`0x0D7`、`0x108`、`0x11C` | `TraverseProcessHandleTableWin7` / `Win10` | 进程句柄表遍历结构不同 |
| `0x026`、`0x02A`、`0x02C`、`0x09F`、`0x0C2`、`0x0D7` | `QueryObjectNameLegacy` | 取对象名的方式在新系统变了 |
| `0x0A1 CmdEnumObjectHandles` | `EnumObjectHandlesWin8Plus` | Win8 起结构变化 |
| `0x033`、`0x034` | `EnumObjectLinkedListWin7` / `Win8`、`FindObjectOperationExportWin10`、`InitObjectOperationLegacy`、`RemoveObjectFromLinkedListLegacy` | 对象链表与对象操作导出位置随版本变化 |
| `0x0F3`–`0x100`（内核内存/对象类型系列） | `FindNsiDeregisterLegacyHandler` | NSI 注销处理函数定位方式不同 |

### 形态 C：共享代码 + 内联构建号判断

其余约 136 条。命令算法不变，只是**结构体偏移、条目上限、是否启用某功能**随系统变：

- 结构体偏移：全部来自 11 张 `InitEprocessOffsetsWin*` 表（已逐值对齐，见
  `多版本兼容层分析_2026-10-27.md` 第九节）；
- 功能开关：如 `HookSyscallNtLoadDriver` 在 `< 0x3FAB`(16363) 才做节区扫描；
- 条目上限：如 `MemoryCleanup` 的 `BuildNumber < 0x3FAB ? 8 : 32`。

## 四、和"仍未对齐的 3 条命令"的关系（重要）

把上一轮 A/B 的 3 条真差异放进这张矩阵，可以判断它们的性质：

| 命令 | 是否分版本实现 | 差异性质推断 |
|---|---|---|
| `0x031 CmdEnumServices` | **是**，4 个变体 | 同 6 条记录、值全同，仅**遍历起点**旋转一位 → 差异在 Win10 变体的链表起始节点，属形态 B 的实现细节 |
| `0x0D4 CmdEnumObjectTypes` | 可达 `TraverseProcessHandleTableWin7/Win10` | 条目数恰为原版 2 倍 → **可能是走错了版本路径**（用了另一套句柄表遍历），不一定是纯计数 bug |
| `0x11B CmdEnumHookDetail` | 否（无分版本家族） | 某条目指针只写 4 字节 → 纯字段宽度 bug，与版本无关 |

这改变了两条命令的排查方向：`0x031` 应直接比对 `EnumServiceTableWin10` 的遍历起点；
`0x0D4` 应先确认它选的是 Win10 那套遍历而不是 Win7 的。

## 五、验证边界

- **动态验证只覆盖 18362**。形态 A 中 `0x0E2`/`0x0E3`、形态 B 中所有非 Win10 分支，
  都只做了静态比对（函数存在 + 偏移表逐值一致 + 命令级 A/B 在 Win10 上一致）。
- **分支选择逻辑**目前只对 18362 是正确的（实测）。其它系统的"选哪个变体"没被实跑验证过。
  建议的补法见 `多版本兼容层分析_2026-10-27.md` 第七节（静态逐值 / 各系统动态 GT dump /
  临时改 `GT[0x914]` 的分支回归）。

## 七、三条剩余差异的最终对齐（2026-10-28 收尾）

### 0x11B CmdEnumHookDetail —— 已修复（diffbytes=0）

根因：**子项名字的目的偏移写错**。原版 0x140087AEB 是 `lea rdx,[r15+8]`——
名字写在子项 **+8**（紧随 +0 处的 8 字节 ChildObj 指针）；我方写成 `(_WORD*)pChild+2`
即 **+4**，名字的前 4 字节把指针的高 32 位覆盖掉。实测症状正是
`KslD.sys` 条目的 `0xFFFFBD04E9067B40` 只剩低 32 位 `E9067B40`。
两个分支（≥0x1DB0 / 旧版）都有此错，均已改为 `(_WORD *)pChild + 4`。

### 0x0D4 CmdEnumObjectTypes —— 已修复（条目数恢复正常，剩余为时变字段）

根因：**去重游标的单位错**。原版 0x14008A38F 是 `lea rax,[r15-20h]`、循环体
`sub rax,20h`——起点回退 0x20、步长 0x20（恰为一条 0x20 字节条目），逐条比较
条目首 QWORD 是否等于当前进程。我方用 `(ULONG64*)-2 / -4` 写成 -16/-32，起点落在
上一条目的**第二个 QWORD** 上，首项比较必不中等 → 去重完全失效 →
条目数恒为原版约 2 倍（44 vs 21/22）。

修复后条目数、EPROCESS 列、大小字段与原版一致。剩余 5-6 字节差异位于
条目 +8 的 `FoundAddress`（VAD 中查得的运行时对象指针），**该字段在原版自身上
同样时变**：23:04 sweep 原版条目13+8 = `53BDF960`，00:00 复测 = `536E8FD0`。
且复跑中两侧同步跟踪了活进程数变化（计数同轮从 22 → 20）。

### 0x031 CmdEnumServices —— 已修复（随偏移表槽号修复消失）

单独比对 `EnumServiceTableWin1020H1` 未发现差异（1:1 转写正确）；旧构建输出
"旋转一位"的根因是**偏移表槽号损坏的连带损伤**：旧代码把 216/152 写进
`0x183`/`0x170` 这两个无关槽位（正确应为 `0x18D`/`0x18E`），破坏了其它命令
依赖的 GT 内容。槽号修复后，新构建三次连跑自稳定且与原版同序；
复跑中两侧还同步跟随了活链表的旋转（两轮之间首条目从 `B06E6D` 变为 `70686D`，
原版与我方**同轮一致地**变化）。

### 全命令 A/B 复跑验收（最终构建，两轮）

| 分类 | 条目 | 说明 |
|---|---|---|
| 逐字节一致 | **122** | 含 0x031、0x11B、0x047、0x0D5、0x0E4、0x0FF、0x108 |
| 运行时波动 | `0x04D`、`0x0D4` | 原版自身跨时间同样变化（0x04D 见 2026-10-26 实测；0x0D4 见上） |
| 设计差异 | `0x020`、`0x13A` | 原版返回未初始化残留码 / 我方自有诊断命令 |

两轮结果完全一致；第二轮中 0x0D4 的计数与 0x031 的首条目在两侧**同步**变化，
进一步确认剩余差异是系统状态而非实现。

复现脚本：`build/g_goal_ab.bat`（双方各跑全量扫描）+ `build/g_goal_cmp.ps1`（guest 内比对）。

### 结果

| 检查项 | 结果 |
|---|---|
| bugcheck | **无**（三轮开机均带 Verifier，含两次全命令 sweep） |
| 特殊池分配 | 尝试 761,980 次，成功 761,980 次，失败 0 |
| IRQL / 死锁 / DMA 检查 | 全过 |
| 池增长实验 | 同一驱动实例连跑两轮全量 sweep：当前字节数两轮**精确相同**（22,441,722），当前分配数相同 (0/4) → 常驻池为设计内缓存（GT[0x20] 展开镜像 11.16MB + ntoskrnl 原始文件缓冲），**非泄漏**；数百 MB 瞬时分配全部正确释放 |
| 自稳定性（我方） | 0x031 连续两次逐字节相同；0x0D4 相邻两次 +8 字段漂移 22 字节（与原版同类，见第七节） |

### 对 0x031/0x0D4 的附加证据

Verifier 会话内同 boot A/B 曾出现 0x031 DIFF（328/328）与 0x0D4 DIFF——
随后实测确认这是**开机后服务/进程表收敛期**的活状态漂移：0x031 的服务数
在几分钟内 17 → 7，我方连续两次运行完全一致（diff=0）；0x0D4 计数同步从
20 → 35 跟随进程表。结合第七节"两侧同步跟踪活状态"的证据，
这两条的剩余差异定性不变：**活系统状态，非实现差异**。

### 收尾

`verifier /reset`（RESET_EXIT=0）、驱动已停删。如需复验，
重新执行 `verifier /standard /driver XPCHunterDrv_new.sys` + 重启即可。

## 九、剩余 3 条命令的最终定性（2026-10-28，指令级核实）

对 0x0D4 / 0x04D / 0x020 逐条做了指令级/语义级对拍，结论：
**实现与原版一致，剩余输出差异全部为运行时状态，原版自身同样不可复现。**

### 0x0D4 —— 扫描逻辑指令级一致；+8 字段为活表邻居槽

18362 分支（`ScanProcessVadMemory` 的 else 路径）与原版 0x14008A07C..0x14008A0B3
逐条件核对，9 项判据完全一致：

```
p[0]==Obj && p[1]>base && p[2]>base && p[-1]>base && p[-2]>base
&& p[-3]>base && p[-5]==0 && p[3]>base   →   FoundAddress = p[-1]
```

`FoundAddress = p[-1]` 读的是**动态表里匹配项的前一个槽**——表插入/删除时
邻居内容自然变化。4 连跑对照实验（同一窗口、同一系统）：

| 驱动 | 漂移条目 | 模式 |
|---|---|---|
| 我方 | 2 / 35 | 条目6：0 → 稳定值（对象注册）；条目30：r2==r3 稳定、r1/r4 各异 |
| 原版 | 1 / 36 | 条目15：三个不同值 `23646420`→`22B55D00`→`2258FFD0`×2 |

两个驱动表现出**同类阶跃漂移**，且我方条目6 的稳定值 `22B55D00` 同时出现在
原版输出中（同一内核对象）。原版跨 30 分钟同样变化（`53BDF960`→`536E8FD0`）。
定性：活内核状态，非实现差异。

### 0x04D —— 字段来自活 NtQuerySystemInformation，原版自比即不稳定

输出 = Part1(0x38) + Part2 + BuildDevicePath 拼接。差异集中在每条
0x34 步长记录的 +11/+12 DWORD（`OutputBuffer[13n+11/12]`），这两个字段
我方**有写**（`*(CurrentEntry-16d)` / `*(CurrentEntry-9d)`），数据源是
GT 解析的真实 `NtQuerySystemInformation` 调用（魔法参数 0x100000018）——
活系统数据天然时变。实测：原版自比差 45 字节，我方自比差 83 字节。

### 0x020 —— GT 写槽字面量核实一致；返回码为原版未初始化 RAX

原版 0x14007F384 反汇编核实两处 GT 写的字面槽号：

```
mov ecx, 0x185 ; call GtWrite    ← 我方 0x185 一致
mov ecx, 0x82e ; call GtWrite    ← 我方 0x82E 一致
```

（注意：IDA 反编译显示的符号名 `GtEprocessField123|0x100` 按我们头文件
求值是 0x17B，与原版字面量 0x185 不同——再次证明 IDB 符号名不可信，
必须以二进制字面量为准。）

处理器流程一致（GT 写入、ProbeForRead、attach、ReadProcessMemoryWithAttach）。
**原版处理器是 void 函数**：探针看到的 RES=104/88/112 是 RAX 未初始化残留，
逐次变化，不可复现也不应复现。输出两侧恒为空。

### 结论

三条命令的实现均已与原版对齐到**指令级/字面量级**；输出中剩余的差异
字节全部落在原版自身同样时变/未初始化的字段上——这些命令在原版两次
运行之间也不逐字节相同。至此不存在已知的实现差异：
**除运行时状态外，126 条命令与原版逐字节一致。**

复现脚本：`build/g_4d22.bat`（0x04D 2×2）、`build/g_d4x4.bat` +
`build/g_d4swap.bat`（0x0D4 双驱动 4 连跑）、`build/g_4d22sum.ps1`、
`build/g_x4sum.ps1`、`build/g_y4sum.ps1`（guest 内分析）。

## 十、最终全量 A/B 与 0x031 背靠背铁证（2026-10-28）

### 最终全量 tally（当前提交构建，同 boot）

SAME=121。非一致 5 条，逐条归因：

| 条目 | 现象 | 归因 |
|---|---|---|
| `0x020` | STATUS：resO=224/OK vs resM=0/REJ；**输出双方均为空** | 原版 void 处理器的 RAX 未初始化残留（跨运行 224/104/88/112 随机）；GT 写槽字面量 0x185/0x82e 已核实一致 |
| `0x031` | 同长（341/341）逐记录指针不同 | 活链表状态，见下——背靠背采集已证伪 |
| `0x04D` | 同长（1718/1718），每条 0x34 记录 +11/+12 共 8 字节 | 活 NtQuerySystemInformation 数据；原版自比即差 45 字节 |
| `0x0D4` | 同长（794/794），2 条的 +8 FoundAddress | 动态表邻居槽；双驱动 4 连跑同类漂移 |
| `0x13A` | 我方独有诊断命令 | 设计差异 |

### 0x031 背靠背铁证

交换驱动作 m→o→m 三次采集（间隔 ~90 秒）：

```
m1: count=7 首节点 D0826D00  len=351
o1: count=7 首节点 D0826D00  len=351   ← o1 vs m1 diff=0
m2: count=7 首节点 D0826D00  len=351   ← m1 vs m2 diff=0
```

**原版与我方背靠背采集逐字节一致**；同驱动 3 分钟后重采也一致。
此前 sweep 中的 0x031 差异（每条记录 +0/+0x18/+0x20 的指针字节）是
采集窗口之间活链表的状态变化——该窗口内 gtmr 链表有插入/删除
（计数在 6/7/17 间波动即为佐证）。

### 结论（最终）

126 条命令中，与原版逐字节一致 **121 条**；其余 5 条全部为
**运行时状态（4 条，原版自身同样不可复现）或设计差异（1 条）**。
不存在已知的实现差异。
