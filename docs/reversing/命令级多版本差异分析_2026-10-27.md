# 命令级多版本差异分析：哪些命令真的分系统实现

日期：2026-10-27
数据来源：原版二进制本地分析（无需 IDA）——
`build/audit/_orig_funcs_ida.json`、`_orig_callgraph.json`、`_orig_cmdtable.json`
复现：`python build/audit/cmd_version_analysis.py`

## 一、总体结论

命令表 248 个槽位中：

| 分类 | 条数 | 含义 |
|---|---|---|
| 代码路径会读到构建号 `GT[0x914]` | **202** | 行为随系统变化（多数只是取结构体偏移） |
| 有**显式分版本命名**的实现 | **66** | 原版为不同系统写了不同函数 |
| 完全没有版本判断 | 46 | 纯算法/固定逻辑 |

所以答案是：**不是"每条命令都分系统实现"，但 202 条会随系统改变行为，其中 66 条有独立的分版本代码路径。**

## 二、三种分版本形态（按耦合程度由强到弱）

### 形态 A：一条逻辑拆成多条命令，由前端按系统选

这是最强的分版本——驱动里是**完全独立的命令**，调用方根据系统版本决定发哪一条：

| 功能 | Win7 | Win8 | Win10 |
|---|---|---|---|
| 进程列表 | `0x0E2 CmdEnumProcessListWin7` | `0x0E3 CmdEnumProcessListWin8` | `0x0E4 CmdEnumProcessListWin10` |
| 进程上下文 枚举/设置 | `0x11D` / `0x11E` | `0x11F` / `0x120` | `0x125` / `0x126` |
| 线程上下文 | — | — | `0x133` / `0x134` |

**对标含义**：这几组必须逐条各自对齐，不能只实现 Win10 那条。我们三条进程列表命令都实现了，
且 `0x0E4` 已在 Win10 上实测逐字节一致；`0x0E2`/`0x0E3` 只能在对应系统上验证。

### 形态 B：一条命令内部按构建号分派到不同实现函数

66 条里的主体。典型的"同一功能、不同系统不同算法"：

| 命令 | 分版本实现 | 差异本质 |
|---|---|---|
| `0x031 CmdEnumServices` | `EnumServiceTableWin7` / `Win8` / `Win10` / `Win1020H1` | 服务表结构在不同大版本里变了，遍历方式不同 |
| `0x02D CmdModuleOperation`<br>`0x035 CmdEnumKernelInfo`<br>`0x044 CmdDriverLoadUnload` | `ParseServiceTableWin7` / `Win8` | 同上 |
| `0x043 CmdEnumKernelDriver`<br>`0x053 InitRegCallback` | `ScanWin32kPatternLegacy` / `ScanWin32kPatternWin10Plus` | win32k 特征码扫描方式换了 |
| `0x048 CmdProcessMemoryOperation` | `FindKernelDataSectionOffsetWin7` / `Win8` / `Win10` | 内核数据节定位方式不同 |
| `0x058`–`0x060`（DeviceIoControl 系列） | `SwapKernelObjectPointerPreWin10` / `Win10`；`ScanKernelModuleSectionForWin10` / `Win10RS3` | 对象指针交换技巧在 Win10 前后不同；RS3 又变一次 |
| `0x07C CmdReadCpuBaseAddr` | `FindCpuMsrBaseLegacy` / `FindCpuMsrBaseWin10` | MSR 基址定位方式不同 |
| `0x103`–`0x105`（SSDT 系列） | `BuildSsdtHookTableLegacy` / `BuildSsdtHookTableWin10`、`FindHalExportTableLegacy` | SSDT/HAL 表解析方式不同 |
| `0x025`–`0x030`、`0x03C`、`0x061`、`0x0C2`、`0x0D4`、`0x0D7`、`0x108`、`0x11C` | `TraverseProcessHandleTableWin7` / `Win10` | 进程句柄表遍历结构不同 |
| `0x026`、`0x02A`、`0x02C`、`0x09F`、`0x0C2`、`0x0D7` | `QueryObjectNameLegacy` | 取对象名的方式在新系统变了 |
| `0x0A1 CmdEnumObjectHandles` | `EnumObjectHandlesWin8Plus` | Win8 起结构变化 |
| `0x033`、`0x034` | `EnumObjectLinkedListWin7` / `Win8`、`FindObjectOperationExportWin10`、`InitObjectOperationLegacy`、`RemoveObjectFromLinkedListLegacy` | 对象链表与对象操作导出位置随版本变化 |
| `0x0F3`–`0x100`（内核内存/对象类型系列） | `FindNsiDeregisterLegacyHandler` | NSI 注销处理函数定位方式不同 |

### 形态 C：共享代码 + 内联构建号判断

其余约 136 条。命令算法不变，只是**结构体偏移、条目上限、是否启用某功能**随系统变：

- 结构体偏移：全部来自 11 张 `InitEprocessOffsetsWin*` 表（已逐值对齐，见
  `多版本兼容层分析_2026-10-27.md` 第九节）；
- 功能开关：如 `HookSyscallNtLoadDriver` 在 `< 0x3FAB`(16363) 才做节区扫描；
- 条目上限：如 `MemoryCleanup` 的 `BuildNumber < 0x3FAB ? 8 : 32`。

| 检查项 | 结果 |

## 四、和"仍未对齐的 3 条命令"的关系（重要）

把上一轮 A/B 的 3 条真差异放进这张矩阵，可以判断它们的性质：

| 命令 | 是否分版本实现 | 差异性质推断 |
|---|---|---|
| `0x031 CmdEnumServices` | **是**，4 个变体 | 同 6 条记录、值全同，仅**遍历起点**旋转一位 → 差异在 Win10 变体的链表起始节点，属形态 B 的实现细节 |
| `0x0D4 CmdEnumObjectTypes` | 可达 `TraverseProcessHandleTableWin7/Win10` | 条目数恰为原版 2 倍 → **可能是走错了版本路径**（用了另一套句柄表遍历），不一定是纯计数 bug |
| `0x11B CmdEnumHookDetail` | 否（无分版本家族） | 某条目指针只写 4 字节 → 纯字段宽度 bug，与版本无关 |

这改变了两条命令的排查方向：`0x031` 应直接比对 `EnumServiceTableWin10` 的遍历起点；
`0x0D4` 应先确认它选的是 Win10 那套遍历而不是 Win7 的。

## 五、验证边界

- **动态验证只覆盖 18362**。形态 A 中 `0x0E2`/`0x0E3`、形态 B 中所有非 Win10 分支，
  都只做了静态比对（函数存在 + 偏移表逐值一致 + 命令级 A/B 在 Win10 上一致）。
- **分支选择逻辑**目前只对 18362 是正确的（实测）。其它系统的"选哪个变体"没被实跑验证过。
  建议的补法见 `多版本兼容层分析_2026-10-27.md` 第七节（静态逐值 / 各系统动态 GT dump /
  临时改 `GT[0x914]` 的分支回归）。
