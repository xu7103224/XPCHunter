# G1 剩余 29 项的定性依据（2026-10-22）

清单 154 项中剩 29 项未勾选。本文逐条给出**为什么不能勾**的实测/静态证据，
区分三类：

- **A 原版即如此**：原驱动在 Win10 上同样取不到数据，不是移植缺陷
- **B 需要内核任意地址读**：原版通过其完整 GT 描述表拿到了地址，本复刻没有
- **C 无数据源**：原版驱动里根本没有对应命令

---

## A 类：原版在 Win10 上同样不工作（1 项）

### 1. `Restore / Restore All`（SSDT 恢复）

0xE7 `CmdRestoreSsdtTable` 需要 `GT[0x80A]` + `GT[0x80B]` 非零。
两者由 `ParseKernelDataSectionRelocs` 产出，而它的第一道门是 `GT[0x802]`：

    v6 = GtRead(GtFwpsDispatchTableBase | GtNtoskrnlImageSize)   // = GT[0x802]
    if (v6 && v4 && v4 < a2) { ... }

`GT[0x802]` 的唯一写入者是 `InitProcessNotify` 里的模块名匹配：

    0x0E L"tdx.sys"  -> 0x322 / 0x323
    0x0E L"td.sys"   -> 0x802 / 0x803    <-- 就是这里

**`td.sys` 是 Windows XP/2003 的 TDI 驱动，Win10 不存在。**
实测同一枚举里 `tdx.sys` 正常命中：

    GT[0x322] = FFFFF80539BB0000
    GT[0x323] = 0x26000
    GT[0x802] = 0                         <-- td.sys 不命中

证明遍历与字符串比较都对，断点只在"Win10 没这个驱动"。
→ 原版在 Win10 上走同一条路径，同样返回 0。

不把 0x802 改指 tdx.sys：两组槽用途不同，tdx.sys 的导出布局 ≠ td.sys，
改指属于猜实现。

## B 类：需要内核任意地址读（4 项）

这 4 项的共同前置是"按任意内核虚拟地址读内容"。逐条核实过现有命令：

| 命令 | 实际能力 | 能否读任意内核地址 |
| --- | --- | --- |
| 0x215 ReadKernelMemoryToUserBuffer | 读**一个固定 GT 槽**（IDA 核对原版语义相同） | ✗ |
| 0x217 CmdReadKernelMemoryRange | 读**一个固定 GT 槽** | ✗ |
| 0x20 / 0x25 / 0x37 | 进程内存（0x25 实为读命令行） | ✗ |
| 0x40 ReadPhysicalMemory | 输出 7928 字节的物理内存**上下文表**，不是任意读 | ✗ |

原版是通过其完整的 GT 描述表在初始化时把目标地址解析好存进槽里；
本复刻没有那张表，因此拿不到。

### 2. `KiDebugRoutine Hooked`
`KiDebugRoutine` 是 ntoskrnl 未导出全局。用 WinDbg 核对过它**不在**
KUSER_SHARED_DATA 里：

    0: kd> dt nt!_KUSER_SHARED_DATA 0xFFFFF78000000000 KiDebugRoutine
    Cannot find specified field members.
    0: kd> dt nt!_KUSER_SHARED_DATA 0xFFFFF78000000000 KdDebuggerEnabled
    +0x2d4 KdDebuggerEnabled : 0x3 ''

（此前按 +0x2D0 读过，得到 `00B60A0300000310`，明显不是指针。）

### 3. `Find PTE Hook in 0x%p`
判定需要读目标 VA 的自映射 PTE 项并比对 PFN。

### 4. `Find Next ClassInitData`
需要读 ntoskrnl 数据段扫描 win32k 类初始化结构。

### 5. `Dump Kernel Memory`
即"按任意内核地址转储"。

**这四项在 Driver 页状态栏都始终显示**（KiDebugRoutine / Find PTE Hook /
Find Next ClassInitData 三段），并写明不可用原因 —— 拿不到结论本身
就是要展示的信息，不做假阴性。

## C 类：无数据源（24 项）

### 6. `Restore KernelCallbackTable Replaced`（0x131）

已确认不是环境问题：
- 命令号正确（`Table[273]` → 0x131）
- 包装函数、`OutputSize==1352` 校验、`GT[0x902]` 实测非零
  `FFFFF80538150000`（volmgr 导出目录）都正常
- 但在处理器入口加的**无条件标记**（导出到 env+0x348）实测**始终为 0**
- 且 0x131 既不在 0x13A 的 HANDLED 也不在 REJECTED 表里

→ 请求在**协议层**就被丢弃，没进命令表查找。已记录下一步方向
（在 probe 侧打印 InSize/OutPtr 实际值，或对 DispatchDeviceControl 下断点）。

### 7. `View CmpNotifyChange`
0x127 `CmdEnumRegistryContext` 实测返回真实数据（输出必须恰好 1800 字节，
48 字节/条，共 37 条，形如 `index + QWORD 回调地址`）。
但用 WinDbg 反查前几条：

    0: kd> u fffff8024520b670 L4
    Npfs+0xb670  push rbp ...

全部落在 **Npfs**（命名管道文件系统）—— 这是**文件系统上下文表**，
不是 `CmRegisterCallback` 的注册表回调链。拿它冒充就是伪造数据。

### 8. `View HotKey`
热键表在 win32k 内部，用户态接口不暴露逐进程热键列表，
命令表里也没有对应命令。视图已就位并显示
`no data source (...)`。

> **2026-10-24 更正**：本条定性错误。原版对话框通过**命令 0x33
> CmdEnumObjects** 读取 win32k 热键链表（详见
> `剩余9项能力边界实测_2026-10-23.md` 的同日更正与
> `100%完成度定义与验收清单.md` 的 View HotKey 条目）；
> 前端已按原版 7 列与 EPROCESS 过滤实现。

### 9–10. `Forbid Injecting Module` / `Forbid Locking Work Station`

0x79 `CmdCallbackControl` 的 `TargetObject` 必须**精确等于**驱动解析出的
16 个候选对象类型槽之一，不匹配直接返回 0。

实测已通过 `ln` 确认的槽：

    IoFileObjectType     FFFFF8024156F3C8   GT[0x422F]
    IoDriverObjectType   FFFFF8024156F500   GT[0x4160]
    IoDeviceObjectType   FFFFF8024156F890   GT[0x4163]
    PsProcessType        FFFFF8024156F390   extra[4]
    PsThreadType         FFFFF8024156F3B8   extra[7]

缺的两项：

- `MmSectionObjectType` = `FFFFF8024156F478`（WinDbg `x` 确认），
  **不在**驱动导出的 16 个候选槽里
- `IoDesktopObjectType` 属 win32k，同样不在候选槽里

原驱动里有 `"MmSectionObjectType"` 字符串（`0x1400D3894`），
但**零交叉引用** —— 说明原版也没把它接到 0x79 的校验路径上。

### 11–32. Network 页 22 项

命令表 282 槽逐槽审计（`命令表1比1对齐审计_2026-10-22.md`）确认：
原驱动**没有任何网络相关命令**。

曾怀疑 0x112 `CmdEnumAleEndpointLayers` 是数据源，但查其实现
`EnumerateAleEndpointLayers`：8 个层标识 DWORD 解码后是 `\FileSystem\RAW`，
属于文件系统过滤层，与 NDIS/WFP 的 ALE 无关。

Network 页提示已从 `not implemented yet` 改为
`no data source in this driver` 并指向审计文档 —— 这一页的性质是
"原版也没有"，不是"还没做"。

## 2026-10-28 复验：B 类 4 项理由修正 + 0x131 定性收尾

### B 类：阻塞理由从「我方缺表」修正为「协议本身不提供任意内核读」

10-22 的措辞是「原版通过其完整的 GT 描述表把目标地址解析好存进槽里；
本复刻没有那张表」。**该前提已过时**：2026-10-27 起 11 张 EPROCESS 偏移表
1438 条 `GtWrite` 与原版逐值一致（见 `多版本兼容层分析_2026-10-27.md` 第九节），
「那张表」我方已具备且与原版相同。

对原版 `CmdReadKernelMemoryRange`（0x14006BBB8）的反编译复核确认：
**原版读命令同样不接收用户地址**——`a1/a2`（输入缓冲）在函数体内完全未使用，
地址只能来自 GT 预解析槽（`GtEprocessField205|GtObjectTypeField02|0x400`），
固定复制 8 字节。0xF7 同族。

因此 B 类 4 项的正确定性是 **A 类（原版能力边界）**：
不是「我们还没做到」，而是「这份驱动协议里不存在任意内核 VA 读通道」。
四项的前端展示维持现状（写明不可用原因，不做假阴性）。

### B-2（KiDebugRoutine）应归入 A 类

`KernelViews.c` 2026-10-23 已用 kd 实测订正：`x nt!KiDebugRoutine` 在
Win10 18362 上无此符号（Win8 起该全局被删除，调试挂钩改为 PTE/中断路径）。
目标在 Win10 上不存在，检查对象本身为零。前端已按
"not present on this Windows version" 输出。

### C-6（0x131 协议层丢弃）—— 已有对等结论

2026-10-28 全命令 A/B 复跑中，0x131 在原版与我方返回**逐字节相同**
（在 122 条一致集合内）。无论原版在协议层如何处置该命令，我方行为
已与原版一致；该条目对前端不可用是**原版行为**，应归 A 类。
10-22 记录的"下一步 probe 侧打印"方向不再需要。
