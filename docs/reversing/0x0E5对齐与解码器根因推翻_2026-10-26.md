## 二、被推翻的旧结论（重要）

### 2.1 "ReadPESectionEntry 解码器是 4 条命令的共同根因" —— ❌ 错误

此前怀疑解码循环存在 `TypeField > 6` 分派错误，导致首个条目解出类型 1294 而非 1296，
消耗量 5 字节 vs 原版 56 字节。

**推翻依据（静态逐条核对，全部一致）**：

1. **原版 `ReadPESectionEntry`（`0x14008a54c`）与我方实现逐行等价**
   - 反汇编 186 条指令逐条比对：`cmp ax,6 / ja`、`mov ecx,[rbx+20h] / inc esi /
     test cl,40h`、`cmp cx,5`、`and ecx,0FFFFFFBFh` 等全部对应
   - 原版 `r12d = 1`（`++ByteIndex`/`++BufferPos`）、`r13d = 4`（到界）、
     `r14d = 2`（错误）也都一致

2. **原先的表格误读已纠正**
   - 表项 `00ffffff ffff0005 0000003a` 中，我按 `00ffffff` 后紧接的值误判
     TypeField = 0xFFFF；实际 `DWORD[1] = 0xffff0005`，
     `*(USHORT*)(entry+4) = 0x0005 = 5`
   - kd 实测 `cx = 5` 完全证实：首字节 `0x48` 是 **REX 前缀（Type 5）**，
     走 Type 5 分支，**根本不是 `TypeField > 6` 分支**

3. **解码表数据逐字节相同**
   - 原版 Mode==2 用 `unk_140097E50`（RVA `0x97E50`）
   - 我方 `g_PeDecodeTableRegion`（RVA `0x8B9D0`）+0x1420 = Data 表
   - 逐 20 字节比对 opcode `0x48`/`0x89`/`0xE5` 等表项，**内容完全相同**

4. **函数指针表 38 项一一对应**
   - 原版 `off_1400A3DD0` 与我方 `g_PeDecodeFunctionTable[38]` 逐项核对一致

5. **`ScanKfdDriverSections` 字段偏移已确认正确**
   - 原版 `0x1400687D0`：`+0x50(v20) / +0x58(v21) / +0x70(Value) / +0x78(v23) /
     +0x88(v24) / +0x90(v25)`，与我方实现完全对应

**结论**：解码底座是正确的，4 条命令各有独立的业务层缺陷。

### 2.2 "探针参数 `--out` 无效" —— 实际是参数名错误

`xpch_probe.exe` **没有 `--out` 参数**，正确的是 `--dump <n>`。
此前用 `--out 200` 时参数被忽略，输出缓冲只有 1 字节，
`CmdEnumKernelHandleTable` 因 `OutputSize < 0x28` 直接 REJ —— 这不是驱动缺陷。

修正参数后 `0xE5` 立即 OK。**A/B 采集脚本本身用的是 `g_Shapes` 表，不受影响。**

## 三、`0x0E5` 的真实根因与修复

### 3.1 根因：`FindNdisExportsBySectionScanV2` 的 1298 分支被误写成 `else-if` 独占分支

原版 `0x140061554` 第二段（`0x1400616E9`–`0x14006180F`）是**单一 while 循环、
各类型判断是顺序独立 if**：

```
LABEL_loop:
  ReadPESectionEntry(); if (ret) return ret;
  v14 = +0xF0 + ReadPtr;  ReadPtr += +0xF0;
  v15 = *(WORD*)(+0x118 + 6);
  if (v15 == 1349) return ret;
  if (v15 == 1298 && +0x88==0x40000 && +0x50==64 && +0x58==1) {
      rva = v14 + (+0x78) - a1;
      if (rva && rva < a2) v11 = rva;      // cmovb，然后【继续往下判】
  }
  if (v15 == 1368) goto LABEL_801;          // 只 v11 = 0
  if ((WORD)(v15 - 1139) <= 1) goto LABEL_7E0;
  if (v12 == 1 && +0x88==0x40000 && +0x50==64) {
      rva = v14 + (+0x78) - a1;
      if (rva && rva < a2) { GtWrite(0x379, v6+rva); return; }
  }
LABEL_803: ++v13; if (v13 >= 0xC8) return ret; goto LABEL_loop;
LABEL_7E0:
  if (v11 && !v12) { GtWrite(0x378, v6+v11); v12 = 1; }
LABEL_801: v11 = 0; goto LABEL_803;
```

**关键**：1298 分支在设完候选 `v11` 之后，仍要继续判 1368 / 1139-1140 /
`v12 == 1` 写 `0x379`。我方把它写成 `else if` 链，导致：

- 1298 条目永远跳过 `0x379` 写入
- `0x378` 的落地也被吞掉
- `v12` 恒为 0 → `GT[0x379]` 恒 0 → `0x0E5`（`CmdEnumKernelHandleTable`
  读 `GtEprocessExtField35` = `0x379`）返回 0

### 3.2 修复

`XPCHunterDrv/src/services/SsdtHook.c` 的 `FindNdisExportsBySectionScanV2`：

- 1298 判断改为**独立的 `if`**（不再是 `else if` 链的一环）
- `1368` 分支只做 `InnerFound = 0`（原版不写 `0x378`、不置 `v12`）
- `1139/1140` 分支写 `0x378` 并置 `InnerLoop = 1`，然后**继续循环**
  （原版无 `break`）

### 3.3 验证

```
dump 0xE5 outSize=0xC8 -> OK, result=1
```

A/B 比对：`0x0E5` 归入"结构等价（差异仅为内核地址）"，**长度 168B 完全一致**。

## 四、失败的尝试（已回滚，务必记下）

### 4.1 加 `continue` 的写法导致 12 条连带退化

第一次修正时我加了 `continue` 显式跳回循环头，结果：

```
0x0F3 / 0x0E8 / 0x0FC / 0x0FE / 0x0FF / 0x100 / 0x119 / 0x11B 等 12 条
从「已对齐」退化为 REJ
```

**原因**：`continue` 让 `++InnerEnd` 的递增时机与原版 `v13` 错位，
且 `InitKernelDataSectionTable` 的后续调用链（`FindNdisMGetOffloadHandlersExport` 等）
被提前 `return` 打断，宝塔式崩塌。

**正确做法**：不加 `continue`，靠 `else if` 自然落到循环尾部。

### 4.2 `FindNdisExportsBySectionScan` 的 `+0x38` / `+0x78` 字段改动同样触发 12 条退化

单独把第一段 `+0x40` 改成原版的 `+0x38`、1298 分支 `+0x40` 改成 `+0x78`，
A/B 立刻从 25 OK 掉到 17 OK，退化集合与 4.1 完全相同。

**结论**：这两处字段偏移的原版值虽已从反汇编确认（`v21 = rbp-0x38 → +0x38`、
`v24 = rbp+0x08 → +0x78`），但**当前 `+0x40` 的写法在本机上恰好让第一段命中**，
贸然改动会破坏既有链路。**必须与其余 3 条一起整体验证，不能孤立修改。**

### 4.3 kd 断点残留会污染 A/B 采集

多次出现"编译部署后 A/B 突然掉到 17 OK"，实际是 guest 里还挂着上一轮的
`bu` 断点，采集过程中被命中导致命令超时/失败。

**规则**：跑 A/B 前必须
1. `kd break` → `bc *` → `bl`（确认输出为空）→ `kd go`
2. 再重启驱动
3. 最后跑采集

## 五、剩余 3 条的实际阻塞点

### `0x0F0`（`EnumKernelModules`，输出 8120B 模块列表）

- 读 `GT[0x37F]`（`GtEprocessExtField41`）
- 由 `FindNdisExportsBySectionScan` 的 1296 分支写入
- 当前 `GT[0x37C] = 0x665d0`、`GT[0x37D] = ndis+0x665d0` 均正确
- 但第二段循环**未命中 1296 类型**，`Found` 恒 0
- 阻塞点：第一段 `1368` 命中后 `NdisOffset` 更新，第二段从新偏移扫描；
  需确认第二段实际解码出的类型序列是否包含 1139/1140（`Found=1` 的前置条件）

### `0x0F4`（`CmdEnumKernelMemoryContext`，输出 40B）

- 读 `GT[0x7C0]`，由 `ScanKfdDriverSections` 写
- 该函数字段映射已确认与原版一致（`+0x50/+0x58/+0x70/+0x78/+0x88/+0x90`）
- 阻塞点：`GT[0x7BA]` 的对比基准。当前 `GT[0x7BA] = fffff80153e37560`（落在 ndis），
  需匹配 `ModuleBase + SavedRva`

### `0x0F6`（`CmdCopyKernelDualArrayToUserBuffer`，输出 96B）

- 读 `GT[0x7C5]/[0x7C6]/[0x7C7]`，由 `ScanWfpStreamShimSections` 写
- 字段映射已按原版修正为 `+0x70(RVA) / +0x88(0x40000) / +0x80(比较1) / +0xF0(64)`
- 但该修正**尚未单独验证**（与 `0x0F0` 改动一起被打包测试，无法区分归因）

## 六、方法论记录

1. **kd 表达式数字一律按十六进制解析** —— `dd addr+8*0x376` 中 `0x376` 是十六进制
2. **map 文件的偏移列与 RVA 列差 0x1000** —— `0001:00036360` → RVA `0x37360`
3. **`g_GlobalTable` RVA 随构建变化** —— 必须每次从 map 重新取
   （历史值：`0xA84F0` 原版、`0xA8060`、`0xA9060`、`0xAE060`）
4. **kd 断点必须成对清理** —— `bc *` 后 `bl` 确认空，再 `kd go`
5. **单条命令验证与 A/B 全量扫描的结论可能不同** —— `0xE5` 单测 OK 但 A/B REJ，
   根因是 A/B 顺序执行时前置状态不同；反之 A/B 里 OK 单测 REJ 也存在
