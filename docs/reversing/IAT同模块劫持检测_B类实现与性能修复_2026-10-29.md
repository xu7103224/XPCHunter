# IAT 同模块劫持检测（B 类）：从漏检到亚秒级检出

日期：2026-10-29
代码：`XPCHunterUM/src/HookViews.c`（`FeScanModuleIat` / `FeExpMapBuild`）
验证：win10dev（Win10 18362.30），私有测试 DLL `iatdll.dll` + `iathost.exe`

---

## 1. 问题：B 类此前完全漏检

IAT（导入地址表）篡改有两类：

| 类型 | 表现 | 旧判据 | 结论 |
|------|------|--------|------|
| A 类 | 槽值指向**所有已加载模块之外**（野代码/跳板） | 地址归属扫描 | 一直能检出 |
| B 类 | 槽值指向**同模块内的另一个函数**（如 `A.dll!Foo` → `A.dll!Bar`） | 仅看地址是否在模块内 | **完全漏检** |

B 类的危害是真实的：地址看起来合法，`EnumProcessModules` + 范围判断永远通过，但程序行为已被改变。

### 实测复现

```
iatdll.dll 导出 RealTargetAdd（返回 a+b）和 FakeTargetAdd（返回 a+b+1000）
iathost.exe 的 IAT[RealTargetAdd] 被改写为 FakeTargetAdd 的地址

改前：call RealTargetAdd(1,2) = 3
改后：call RealTargetAdd(1,2) = 1003     ← 劫持真实生效
旧扫描输出：0 entries                     ← 漏检
```

## 2. 应然地址怎么求

B 类的判据是「槽里的地址 != 这个导入名**应该**解析到的地址」。应然地址的求法：

1. 从 `IMAGE_IMPORT_DESCRIPTOR.OriginalFirstThunk`（INT）取第 k 项，得到
   `IMAGE_IMPORT_BY_NAME` 的 RVA（`WORD Hint; CHAR Name[]`）。
2. 在 `descriptor.Name` 指向的那个 DLL 的**导出表**里按名字查到函数 RVA。
3. `应然地址 = dllBase + 函数RVA`；与 IAT 槽的实际值比较。

## 3. 第一版实现与它的性能灾难

第一版直接照上面三步逐槽做，用的是 `ReadProcessMemory`：

```
每个 IAT 槽 1 次跨进程读（读导入名）
+ 每个被导入的 DLL 1 次建表，表内每个导出名各 1 次跨进程读
```

量级：ntdll 一个 DLL 就有 2490 个导出名。在 Services 会话（Session 0）下，
单次跨进程读实测可达数十毫秒。

**结果：单个进程 60~90 秒跑不完。只能默认关闭，用 `XPCH_IAT_DEEP=1` 手动开。**

这不是可交付的状态。

## 4. 性能修复：把逐项读改成整块读

三处改造，全部是「先算范围，再一次整块读，之后纯内存指针运算」：

| 位置 | 改前 | 改后 |
|------|------|------|
| 导入描述符数组 | 64 次 `ReadProcessMemory`（每次 20 字节） | **1 次** 读 64×20 字节 |
| 描述符的 DLL 名字 | 每描述符 1 次 | **1 次** 读 [minRva, maxRva) 整块 |
| 导入名字符串 | 每 IAT 槽 1 次 | **1 次** 读本描述符 [minRva, maxRva) 整块 |
| 导出表三张表 | 每表 1 次（本来就是整块） | 不变 |
| 导出名字符串 | 每名 1 次 | **1 次** 读 [minRva, maxRva) 整块 |

跨进程调用数从「每模块上千次」降到「每模块十余次」。

### 实测效果

```
explorer.exe（239 个已加载模块），B 类开启：
  改前：60~90 秒，且经常跑不完
  改后：0.65 秒
```

因为性能已可接受，**B 类改为默认开启**；保留 `XPCH_IAT_NO_DEEP=1` 作为排查逃生口。

## 5. 修复过程中踩的两个坑（都是真 bug，不是调参）

### 坑 1：INT 数组不是定长，必须遇 0 终止

`OriginalFirstThunk` 是以 NULL 结尾的数组。第一版读了固定 4KB，把后面的
`.rdata` 无关数据也当成 RVA 扫进 `minRva`/`maxRva` 计算，`maxRva` 被撑到
几十 MB，触发跨度上限检查（`< 0x100000`）后整块读被放弃 → B 类静默判 0。

诊断输出暴露了这一点：

```
[bdiag] i=0 haveInt=1 intGot=4096 blob=0000000000000000 got=0
        firstOft=000000000213B0     ← INT[0] 正常
```

`blob=NULL, got=0` 说明整块读根本没建立。修正后：

```
[bdiag] i=0 haveInt=1 intGot=4096 blob=000002D9D3094660 got=272 min=213A0
```

### 坑 2：`sprintf_s` 溢出会直接杀进程

B 类命中时的输出用了：

```c
sprintf_s(e->TargetModule, sizeof(e->TargetModule),
          "!%s (expected %016I64X, got %016I64X)", impName, expected, target);
```

`TargetModule` 只有 64 字节，而 `!函数名 (expected 16 个十六进制) ` 很容易超。
MSVC 的 `sprintf_s` 在溢出时**不是截断**，而是调用 invalid parameter handler
终止进程——扫描进程在打印第一条结果时就死了。

改为 `_snprintf_s(..., _TRUNCATE, ...)`，并把格式缩短为只显示 expected
（实际值在 `IatAddress`/`Target` 字段里已有）。


## 7. 与误报的关系

B 类判据要求「能确定应然地址」才报：

- 转发导出（forwarder）查不到 → 跳过
- 序数导入（`IMAGE_ORDINAL_FLAG` 置位，无名字）→ 跳过
- 模块不在已加载列表中 → 跳过
- 导出表读失败 / 名字块不完整 → 跳过

因此 B 类的取向是**宁漏不误报**：只有拿到确定答案且确实不同才输出。
代价是某些经过复杂转发或延迟绑定的导入不会被判 B 类，但这部分本来
也无法从静态导出表推出应然地址。
