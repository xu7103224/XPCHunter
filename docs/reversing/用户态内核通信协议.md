# 用户态 ↔ 内核通信协议（完整还原）

来源：原始驱动 `DispatchDeviceControl`（0x1400823EC，0x26C 字节）、
`DecryptInputBuffer`（0x1400813C0）、`GenerateEncryptionKey`（0x140081314）；
用户态设备名来自 `PCHunter64.exe` 的 UTF-16 字符串 `0x457008`。

## 1. 设备名

```
\\.\View++ByLinxer
```

- 用户态用 `CreateFileW(L"\\\\.\\View++ByLinxer", ...)` 打开
- 内核侧 `IoCreateDevice` / 符号链接 `\DosDevices\View++ByLinxer`
- **同一字符串**也是 `GenerateEncryptionKey(L"View++ByLinxer")` 的入参
  （驱动 DriverEntry 第 123 行），用于派生 GT[0x1E0]（密钥）与 GT[0x1E1]（密钥字节）

实测该密钥值：`GT[0x1E0] = 0x05E00158`，`GT[0x1E1] = 0xCF`
（`s = "View++ByLinxer"` 时，算法见 `oracle_genkey.py`）

## 2. 请求缓冲区布局（0x30 = 48 字节）

`DispatchDeviceControl` 要求 `Parameters.DeviceIoControl.InputBufferLength == 0x30`，
且 `Irp->AssociatedIrp.SystemBuffer != 0`（0x140082439 / 0x140082443）。

```
偏移  大小  字段                     说明
0x00  4     Magic                    必须 == 0x20240810（解密之后）  0x140082469
0x04  4     Command                  命令号，范围 [0x20, 0x13A]     0x140082521..52C
0x08  8     OutputBuffer             用户态输出缓冲区（< MmUserProbeAddress）
0x10  8     ContextPointer           上下文指针（< MmUserProbeAddress）
0x18  8     ExtraPointer             附加指针（< MmUserProbeAddress）
0x20  4     OutputSize               输出缓冲区大小
0x24  4     ContextSize              上下文大小
0x28  16    Checksum                 MD5 前 4 字节（解密后再算）    0x1400824BE
0x38  --                                 (0x30 字节到此为止)
```

注意：`0x28` 处虽然字段注释写成 16 字节，但驱动只比较 **DWORD**
（`mov rax,[...]; cmp eax,[rdi+28h]`），所以只需前 4 字节正确。

## 3. 加密（解密）

`DecryptInputBuffer`（0x1400813C0）对**前 0x30 字节**逐字节变换：

```c
Key = (UCHAR)GtRead(0x1E1);          // 0xCF
for (i = 0; i < 0x30; i++)
    buf[i] = ~(buf[i] ^ Key);
```

它是自反的（`~~x == x`），所以**加密与解密是同一个函数**：
用户态发送前调用一次，内核收到后再调用一次，得到明文。

## 4. 校验和

`0x140082491..4C1`：

```c
MD5_Init(&ctx);
MD5_Update(&ctx, buf, 0x28);          // 只对前 0x28 字节
MD5_Final(digest, &ctx);
if (*(DWORD *)digest != *(DWORD *)(buf + 0x28))
    return FALSE;                     // 0x1400824BE jnz
```

即：**对加密后的前 0x28 字节做 MD5，取前 4 字节放进 0x28**。
注意顺序——先加密，再对密文算 MD5（因为 `DecryptInputBuffer` 在
`cmp [rdi], 20240810h` 之前就被调用了，而 MD5 是在之后算的，此时 buf
已经解密；但 `MD5_Update` 用的是同一个 rdi，即**已解密的内容**）。

精确顺序（按地址）：
1. `0x140082464 call DecryptInputBuffer` —— 原地解密 0x30 字节
2. `0x140082469 cmp dword [rdi], 0x20240810` —— 校验 Magic（明文）
3. `0x140082491 MD5_Update(ctx, rdi, 0x28)` —— 对**明文前 0x28 字节**求 MD5
4. `0x1400824BE cmp eax, [rdi+0x28]` —— 比较明文里的 Checksum 字段

所以用户态侧构造顺序是：
```
填 Magic/Command/三个指针/两个size
计算 MD5(前 0x28 字节) → 写前 4 字节到 +0x28
整体做一次 ~(x ^ Key) 加密
DeviceIoControl
```

## 5. 命令分派

`0x140082521..5BA`：

```c
Command = *(DWORD *)(buf + 4);
if ((ULONG)(Command - 0x20) > 0x11A)  goto Unlock;      // 合法范围 [0x20, 0x13A]
if (!GtRead(0x304) && Command != 0x22) goto Unlock;     // 未初始化则只放行 0x22
if (Command != 0x22) {                                  // 非 0x22 需要先初始化回调
    InitCallbackFunctions();
    if (!GtRead(0x353)) GtWrite(0x353, 1);
}
if (!CheckProcessAccess()) goto Unlock;                 // 进程访问校验
Handler = GtRead(0x921 + (Command - 0x20));             // 命令表
if (!Handler) goto Unlock;
if (GtRead(0x355)) goto Unlock;                         // 重入锁
GtWrite(0x355, 1);
Result = Handler(OutputBuffer, OutputSize, ContextPointer, ContextSize);
GtWrite(0x355, 0);
```

**关键点**：命令号 `0x20 + i` 直接映射到 `GT[0x921 + i]`，这就是上一轮发现的
命令处理函数表（281 项，`Table[i]` 对应 `Command = 0x20 + i`）。

因此：

| 命令号 | 索引 | 函数 |
| --- | --- | --- |
| 0x20 | 0 | CmdReadProcessMemory |
| 0x21 | 1 | CmdResetProcessContext |
| … | … | … |
| 0x22 | 2 | CmdQueryProcessInfo（唯一不需要初始化的命令） |
| 0x3E | 30 | CmdThreadMonitor |
| 0x13A | 282 | 表尾 |

实测上限：`Command - 0x20 <= 0x11A`，即 `Command ∈ [0x20, 0x13A]`，
共 **283** 个命令位；表实际填写 281 项（部分为空）。

## 6. 并发控制

- `GT[0x355]`：重入标志。非 0 则拒绝（返回 FALSE），处理完清零。这是**全局串行锁**。
- `GT[0x353]`：回调已初始化标志。
- `GT[0x304]`：驱动整体就绪标志。
- `g_Event`（0x1400CCFC0）：`KeWaitForSingleObject` … 处理 … `KeSetEvent`，构成临界区。

## 7. 返回值

`Handler` 返回 `bool`（`al`），写入 `IRP->IoStatus.Status` 的对应值。
Handler 自身把真正的输出写进 `OutputBuffer`。

## 8. 用户态侧实现要点

```c
HANDLE h = CreateFileW(L"\\\\.\\View++ByLinxer", GENERIC_READ|GENERIC_WRITE,
                       FILE_SHARE_READ|FILE_SHARE_WRITE, NULL, OPEN_EXISTING, 0, NULL);

UCHAR req[0x30] = {0};
*(DWORD*)(req+0x00) = 0x20240810;
*(DWORD*)(req+0x04) = Command;
*(PVOID*)(req+0x08) = OutputBuffer;
*(PVOID*)(req+0x10) = ContextPointer;
*(PVOID*)(req+0x18) = ExtraPointer;
*(DWORD*)(req+0x20) = OutputSize;
*(DWORD*)(req+0x24) = ContextSize;

MD5(req, 0x28) → *(DWORD*)(req+0x28) = digest[0];

for (i = 0; i < 0x30; i++) req[i] = ~(req[i] ^ KeyByte);   // KeyByte = 0xCF

DWORD ret = 0;
DeviceIoControl(h, <any IOCTL code>, req, 0x30, NULL, 0, &ret, NULL);
```

**IOCTL 码本身不需要特定值** —— 驱动只检查 `InputBufferLength == 0x30` 和
`SystemBuffer != NULL`，不比对 `IoControlCode`。用户态随便传一个
`METHOD_BUFFERED` 的码即可（原始 PCHunter64 用的具体码还需从它的
`DeviceIoControl` 调用点确认）。
