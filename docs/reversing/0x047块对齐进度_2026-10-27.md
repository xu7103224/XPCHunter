## 四、本轮修复的三处实现缺陷

三处都是"顺序"问题：**公式里该用推进后的读指针，却用了推进前的或另一个变量**。

### 1. `ScanKernelPeExportSection` → 块 9 第二份（0 → 2 条）

```
原版 0x14003F3BA:  sub eax, ebp / add eax, ecx
                   ebp = GT[0x20], ecx = ctx 读指针（含基址）
旧实现用:          RvaBase - NtImageBase + AccumulatedOffset
                   AccumulatedOffset 从 0 起、不含基址
```
丢了基址后算出巨大负数，`Rva < NtImageSize` 恒失败。改用
`SectionContext.ReadPtr` 后立刻写出 `GT[0x2CF]`。

### 2. `EnumProcessPeExportDataByIndex` → 块 5（0 → 3 条）

原版 `0x14003F8E2..F925` 的顺序是：
1. `ctx+0x08 += [desc+0xF0]`（先推进并把新值存回）
2. `eax = (+0x40) - GT[0x20] + (DWORD)推进后的读指针`

旧实现先算 RVA 再推进，**差一条**，算出 `0x44aa69`（原版 `0x44aa70`，
末位不对齐），dispatch 把它当 LIST_ENTRY 遍历时立即失败。
修正后 `GT[0x2BB]` 与原版逐位相同。

### 3. 早前已修的（本轮沿用）

- `ReadWriteKernelMemory` → 块 6（0 → 215）：被减数应为 `GT[0x20]` 而非
  `GT[0x42E2]`；描述符基址 `rbp-0xa8`，故 `var_110(0x118)→+0x70`、
  `var_130(0xf8)→+0x50`、`var_108(0x120)→+0x78`。
- `EnumProcessPeExportDataEx` → 块 10（0 → 30）。
- `EnumProcessPeExportData` → 块 9 第一份（0 → 12）。

## 五、块 11 的定位结果（唯一剩余）

### 本轮新增的否定性结论（两个实验）

实验 1：把第一轮上限从 5 放宽到 0xC8，并额外接受 `0x50E`
→ 块 11 **仍为 0**，说明第一轮的类型判据不是唯一卡点。

实验 2：在实验 1 基础上同时修正第二轮的字段判据（见下）
→ 块 11 **仍为 0**，说明第二轮命中的 `0x4DB` 条目字段也不满足。

### 第二轮字段判据曾写反（已修正）

原版两个判据的行号与字段：

```
0x14003F208  cmp [rbp+0D0h+var_F0], 40000h   ; var_F0(0xe8) → +0x50
0x14003F212  cmp [rbp+0D0h+var_B8], 40h      ; var_B8(0x120) → +0x88
```

（描述符基址 `var_140` = `rsp+0x98`，故偏移 = 栈帧 offset − 0x98）

旧实现写成了 `+0x88==0x40000 && +0x50==0x40`，两个字段互换。
已修正为 `+0x50==0x40000 && +0x88==0x40`。
修正后实测 `0x4DB` 条目的 `+0x88` 恰为 `0x40`，与判据吻合。

### 第一轮的实际解码序列（诊断实测）

```
轮次  type    len     读指针低32
[0]  0x050E  0x0005   0xd7975265     ← opcode 0x65（GS 前缀）
[1]  0x050E  0x0005   0xd797526a
[2]  0x04E6  0x0001   0xd797526b
[3]  0x04E7  0x0001   0xd797526c
[4]  0x04E4  0x0002   0xd797526e
```

推进链自洽（每轮 += 上级 len），起点 `GT[0x20]+0x775260` 与 opcode `0x65`
均与原版一致，因此第 0 条的类型不可能与原版不同——
这意味着**原版前 5 条里同样不含 `0x559`**，原版 `GT[0x33D]` 的来源仍需另找。

### 本轮又排除的一条路径（会导致驱动加载失败）

尝试在 `ReadPESectionEntry` 的**正常解码成功路径**上补写
`+0x118 = 解码表 + 20*opcode + 0xB40`（原版 0x14008A7B2/7B9 在
`loc_14008A790` 分支写），结果 **`sc start` 报错误 31**，
驱动初始化失败（`InitAllHookSubsystems` 置 Success=0）。

这说明当前「只在 `STATUS_ACC==2` 路径写 `+0x118`」的选择
是维持其它 Hook 子系统可用的前提，不能简单照搬原版那一处赋值。
该改动已回滚。

### 由解码表反推的独立验证

按 `g_PeDecodeTableRegion` 逐字节数据计算 `opcode 0x65`：

```
base=region0      off=0x1324  type=0x0000
base=legacy(0x20) off=0x1344  type=0x00D6
base=data(0x1420) off=0x2744  type=0x0561
base=legacy2(2820)off=0x3B44  type=0x01A4
```

即用 `g_PeDataDescrambleTable` 推算 opcode `0x65` 的类型应为 **`0x561`**，
而实机采样得到 `0x50E`；且整个 52448 字节表区里**不存在** `0x50E`
这个类型值（扫描所有 20 字节条目的 `+6` 字段，命中数 0）。

这印证了 `+0x118` 在正常路径确实未被指向本次解码的表项。

### kd 实测：两边的解码序列逐字节相同

在原版 `ReadPESectionEntry`（RVA `0x8a54c`）入口下断点、打印 `[rcx+8]`
（读指针），拿到第一轮的实际推进序列：

```
0x775260 → +5 → 0x775265 → +5 → 0x77526a → +1 → 0x77526b → +1 → 0x77526c
```

本方实测的推进序列（`GT[0x20]+0x775260` 起）

```
buf+0 → buf+5 → buf+10 → buf+11 → buf+12
```

**完全一致**。这意味着两边解码出的条目长度相同，因此
`*(WORD*)(Entry[0x118]+6)` 得到的类型序列也必然相同
（本方为 `0x50E, 0x50E, 0x4E6, 0x4E7, 0x4E4`）。

而 `0x559` 对应的 opcode 是 `0xE9`（jmp rel32），这 5 条里没有。
即原版第一轮在 5 次 `ReadPESectionEntry` 调用内**同样不可能**命中 `0x559`。

这与「原版 `GT[0x33D]` 由 `ScanKernelPeExportData` 写出」的断点证据并存，
说明还缺一个环节未解开——最可能是 `ScanKernelPeExportData` 的
`SectionIndex` 计数语义与原版不同（例如原版把一次调用内部的多条
指令也计入，或上限并非 5）。

### 硬件写断点确证了 GT[0x33D] 的写入者

用 `ba w8 <GT[0x33D]地址> "kb 5; g"` 捕获到：

```
ViewPlusPlusByLinxer+0x2a001   ← GtWrite 内部
ViewPlusPlusByLinxer+0x3f23f   ← ScanKernelPeExportData（0x14003F232 之后）
ViewPlusPlusByLinxer+0x41308   ← dispatch（0x140041308）
```

即原版 `GT[0x33D]` **确实由 `ScanKernelPeExportData` 的正常路径写出**。
配合「驱动刚加载时 `GT[0x33D]/[0x2CF]/[0x5F]` 全为 0」的测量，
可断定原版第一轮在 5 条内确实命中了 Type `0x559`。

### 解码表的真实类型映射（按正确对齐重算）

之前扫描时按 20 字节对齐遍历，但表项在 `0x1420 + 20k`（余 12），
导致「表里没有 0x50E」的错误结论。按正确对齐重算：

| type | opcode |
|---|---|
| `0x50E` | `0x89` |
| `0x4E6` | `0x56` |
| `0x4E7` | `0x57` |
| `0x4E4` | `0x54` |
| `0x559` | `0xE9`（无 `+0xB40`）／`0x59`（加 `+0xB40`） |

本方第一轮类型序列 `0x50E, 0x50E, 0x4E6, 0x4E7, 0x4E4`
即 opcode `0x89, 0x89, 0x56, 0x57, 0x54`。

### `+0x48` 是前缀、被消费掉

起点 `0x775260` 的字节是 `48 89 5c 24 08 57 ...`。`0x48` 的表项
`+4`（TypeField）= `5`（≤6，前缀），走前缀分支后被 `++BufferPos` 消费；
下一条 `0x89` 的 TypeField = `0x31`（>6），触发 `break`。

**关键差异**：原版在 TypeField>6 从主循环 `break` 后，仍会经
`0x14008A727 → loc_14008A790 → 0x14008A7B2` 设置 `+0x118 = 表基址 + 20*op + 0xB40`；
本方这条路径上完全不写 `+0x118`，于是调用方读到的是上一轮遗留指针。

### 本轮尝试但仍未打通的两处

**尝试 1**：在 break 后补写 `+0x118 = DecodeTablePtr + 20*OpcodeByte + 2880`
（把 `OpcodeByte` 提升到函数级）。实测 `Entry[0x118]` 变成
`0xfffff80436cff8a4`，减模块基址得 `0x61f8a4`，远超模块大小 `0xd6000`，
是野指针；`TypeField` 虽读得 `0x31`，但类型序列与 `GT[0x33D]` 均未变化。
说明 `DecodeTablePtr` 在本路径上取到的并非 `g_PeDataDescrambleTable`。

**尝试 2**：无条件写入同一表达式，结果与尝试 1 相同。

两处均已回滚（会改变 `InitAllHookSubsystems` 依赖的行为，风险高于收益）。

### 本轮的关键测量：三个槽只剩一个缺口

kd/诊断实测（本方运行时）：

| 槽 | 本方 | 原版 | 状态 |
|---|---|---|---|
| `GT[0x5F]` | RVA `0x45e530` | RVA `0x45e530` | 逐位相同 |
| `GT[0x2CF]` | RVA `0x45e560` | RVA `0x45e560` | 逐位相同 |
| `GT[0x33D]` | **0** | RVA `0x45e550` | 唯一缺口 |

三者都指向 nt `.data` 段相邻的全局链表头（kd 读 `0x45e550` 处为
`ffffc104cd767f90 ffffc104cd767f90`，自环空链表）。

这极大地缩小了问题：三个扫描器的**公式与判据结构都已正确**，
只是 `ScanKernelPeExportData` 的第一轮（Type `0x559`）在本方解码序列里
一次都没出现。

### 本轮两项新的否定性实验

**实验 A：消费者侧补 `+0xB40`**

由解码表反推，`+0x118` 指向的若是「操作码表项」其 `+6` 为 `0xFFFF`
（无效），而「表项 + 0xB40」才是类型表，opcode `0x65` 在那里是 `0x561`：

```
opcode  entry_off(entry+6)  entry+0xB40(类型)
0x65    0x001c04 -> 0xFFFF   0x002744 -> 0x0561
0x48    0x0019c0 -> 0xFFFF   0x002500 -> 0xFFFF
0x8B    0x001efc -> 0x0510   0x002a3c -> 0xFFFF
```

在 `ScanKernelPeExportData` 里读类型时加 `+0xB40`，实测 5 条类型变为
`0xFFFF, 0xFFFF, 0x556, 0x557, 0x554`——仍无 `0x559`，且块 6/9/10
不受影响（它们读的是自己的扫描器）。该实验无收益，已回滚。

**实验 B：修正 `CalcOpcodeSize` 的地址模式映射**

原版 `0x14008C26B..C287`：
```
v7 = *(DWORD*)(ctx+8); v8 = v7-1
if (v8 == 0) RegIndex = 4     即 v7 == 1
else if (v8 == 1) RegIndex = 11  即 v7 == 2
if (v7 == 0) RegIndex = 16
```
本方旧实现写成 `1→11、2→4`，两个分支互换。修正后实测
第 3 条起长度变成 **0**（读指针不再推进，5 条都读同一位置），
比修正前更糟。已回滚。

这说明 `CalcOpcodeSize` 当前版本虽与反汇编不符，却是让整个
解码链前两轮能走通的前提——改动会连带破坏 `DispatchInstructionDecode`
的返回值语义。

### 原版 `GT[0x33D]` 的性质

原版值 `0xfffff8046445e550`（RVA `0x45e550`）。kd 读该处：

## 六、贯穿全过程的规律（四条）

**规律 1：累加器就是 `ctx+0x08`（读指针）**
`ReadPESectionEntry`（0x14008A54C..A7E4）全段无 `mov [rdi+8],..`，
推进责任在调用方；原版各扫描器的 `add [var_1C8], rax` 累加的正是它。

**规律 2：被减数是 `GT[0x20]`（PeFileBase）**
原版各分支都是 `sub eax, r12d`，`r12 = GtRead(0x20)`。

**规律 3：描述符偏移 = 栈帧 offset − 该函数描述符基址的 offset**
各函数基址不同（`rbp-0x60` / `rbp-0xa8` / `rsp+0x90` / `rsp+0x98` /
`rbp-0x70`），不能套用同一组偏移。

**规律 4：推进与取值的先后因函数而异**
- 先推进后取值：`ScanKernelPeExportSection`、`ScanKernelPeExportData`、
  `EnumProcessPeExportDataByIndex`
- 先取值后推进：`ReadWriteKernelMemory`

必须逐个核对，不能统一。

## 七、反查 GT 哈希槽的方法

驱动内部的 SHA1 是**非标准变体**（消息字按小端直读、不做 bswap，
输出再做字节交换）。用标准 SHA1 反查导出名会全部失败，曾因此误判
"哈希表无效"。正确实现：

```python
import struct
def sha1_variant(data: bytes) -> int:
    h=[0x67452301,0xEFCDAB89,0x98BADCFE,0x10325476,0xC3D2E1F0]
    msg=bytearray(data); msg.append(0x80)
    while len(msg)%64!=56: msg.append(0)
    msg+=(len(data)*8).to_bytes(8,'big')
    for off in range(0,len(msg),64):
        w=list(struct.unpack('<16I',msg[off:off+64]))   # 不做 bswap
        for i in range(16,80):
            x=w[i-3]^w[i-8]^w[i-14]^w[i-16]
            w.append(((x<<1)|(x>>31))&0xFFFFFFFF)
        a,b,c,d,e=h
        for i in range(80):
            if i<20: f=(b&c)|((~b)&d); k=0x5A827999
            elif i<40: f=b^c^d; k=0x6ED9EBA1
            elif i<60: f=(b&c)|(b&d)|(c&d); k=0x8F1BBCDC
            else: f=b^c^d; k=0xCA62C1D6
            t=((((a<<5)|(a>>27))&0xFFFFFFFF)+f+e+k+w[i])&0xFFFFFFFF
            e,d,c,b,a=d,c,((b<<30)|(b>>2))&0xFFFFFFFF,a,t
        h=[(x+y)&0xFFFFFFFF for x,y in zip(h,[a,b,c,d,e])]
    return struct.unpack('>I',struct.pack('<I',h[0]))[0]
```

已验证的映射：
- `0xF3C88A38` → `CmUnRegisterCallback`（RVA 0x823260）

## 八、踩过的坑

1. **kd 的 IPv4 socket 失败 = 端口被残留 kd.exe 占用**。`tasklist` 找到后
   `taskkill /F /PID` 清掉，即可恢复。
2. **`vm_start` 会终止 kd**。正确顺序：`kd_attach`(wait=false) → vmrun start。
3. **`g_GlobalTable` RVA 每次重编都可能变**，必须从 map 重取
   （本轮是 `0xab060`，曾误用 `0xac060` 导致读到全 0）。
4. **kd 断点会让 Guest 冻结**，此时所有 vmrun 调用失败。部署前务必
   `bc *` + `kd_go`，或直接 `kd_detach`。
5. **在 `GtWrite` 这类热路径上设自恢复断点会淹没 KDNET**，改用 `kd_sample`。
6. **诊断写入 0x047 输出尾部**必须放在 0x1400 之后（原版全通时用到 0x12D0），
   并在验证后删除。
7. **map 第三列是完整 VA**，RVA 要减 `0x140000000`；LTCG 会重排函数顺序。
8. **C1001 内部编译器错误**：`taskkill /F /IM mspdbsrv.exe` + `rm -rf build/obj` 后重试。
9. **probing 前先确认 Guest 未被 kd 冻结**，否则 vmrun 报
   "VMware Tools 未在客户机中运行"。
