## 二、kd 恢复与环境修正

本轮最大的环境突破：**kd 双机调试恢复可用**。

此前 `kd_attach` 一直报
`Failed to initialize IPv4 socket / HRESULT 0x80004005`，排查发现是
**残留的 kd.exe（PID 31092）仍占用宿主的 UDP 192.168.75.1:50000**，
新 kd 无法绑定端口。`taskkill` 掉后立即恢复。

另需注意：`ntdrive` 的 `vm_start` 会终止 kd 进程；正确顺序是
**先 `kd_attach`（wait_for_target=false，进入 waiting），再用 vmrun 启动 VM**。

## 三、kd 实测的关键结论

在同一会话内先后加载原版与本方驱动，逐槽对比（全部一致）：

| 槽 | 原版 | 本方 |
|---|---|---|
| `GT[0x20]` | `0xffffc104d7000000` | `0xffffc104d7000000` |
| `GT[0x21]` | `0x00ab2000` | `0x00ab2000` |
| `GT[0x41B0]` | `0x007692a0` | `0x007692a0` |
| `GT[0x42FA]` | `0x00769220` | `0x00769220` |
| `GT[0x435D]` | `0x00775260` | `0x00775260` |
| `GT[0x43AB]` | `0x00713c20` | `0x00713c20` |

**这推翻了上一轮"根因是 GT[0x20] 影像缓冲区差异"的判断**——缓冲区完全相同。
所有差异都出在实现本身，已逐一定位修复。

`GT[0x20]` 处确认是 PE 文件影像（`MZ` 开头），`GT[0x20]+RVA` 是映射后的函数体。

## 四、本轮修复的三处实现缺陷

三处都是"顺序"问题：**公式里该用推进后的读指针，却用了推进前的或另一个变量**。

### 1. `ScanKernelPeExportSection` → 块 9 第二份（0 → 2 条）

```
原版 0x14003F3BA:  sub eax, ebp / add eax, ecx
                   ebp = GT[0x20], ecx = ctx 读指针（含基址）
旧实现用:          RvaBase - NtImageBase + AccumulatedOffset
                   AccumulatedOffset 从 0 起、不含基址
```
丢了基址后算出巨大负数，`Rva < NtImageSize` 恒失败。改用
`SectionContext.ReadPtr` 后立刻写出 `GT[0x2CF]`。

### 2. `EnumProcessPeExportDataByIndex` → 块 5（0 → 3 条）

原版 `0x14003F8E2..F925` 的顺序是：
1. `ctx+0x08 += [desc+0xF0]`（先推进并把新值存回）
2. `eax = (+0x40) - GT[0x20] + (DWORD)推进后的读指针`

旧实现先算 RVA 再推进，**差一条**，算出 `0x44aa69`（原版 `0x44aa70`，
末位不对齐），dispatch 把它当 LIST_ENTRY 遍历时立即失败。
修正后 `GT[0x2BB]` 与原版逐位相同。

### 3. 早前已修的（本轮沿用）

- `ReadWriteKernelMemory` → 块 6（0 → 215）：被减数应为 `GT[0x20]` 而非
  `GT[0x42E2]`；描述符基址 `rbp-0xa8`，故 `var_110(0x118)→+0x70`、
  `var_130(0xf8)→+0x50`、`var_108(0x120)→+0x78`。
- `EnumProcessPeExportDataEx` → 块 10（0 → 30）。
- `EnumProcessPeExportData` → 块 9 第一份（0 → 12）。

## 五、块 11 的定位结果（唯一剩余）

诊断输出（已清理）显示 `ScanKernelPeExportData` 第一轮实际行为：

```
marker        = 0xAAAA0001  （函数已进入）
type0..type4  = 0x50E, 0x50E, 0x4E6, 0x4E7, 0x4E4   （5 条，无 0x559）
hit559        = 未置位
```

把上限从 5 放宽到 0xC8 后：
```
hit559        = 置位（第 6 条之后才出现）
secondPass    = 0x77531a
hit4DB        = 置位
该 0x4DB 条目 +0x88 = 0x40（判据要求 0x40000）
```

即：我方从 `GT[0x20]+0x775260` 解码的前 5 条里没有 `0x559`，
而原版在同样的 5 条上限内能命中。**输入完全相同、窗口参数完全相同、
`ReadPESectionEntry` 参数完全相同**，因此差异只能出在解码器对
同一段**代码字节**的输出序列上。

`GT[0x33D]` 在原版的值为 `0xfffff8046445e550`（RVA `0x45e550`），
kd 读该处内容为 `ffffc104cd767f90 ffffc104cd767f90`——**自环的双向链表头**
（空链表），与 `GT[0x5F]`(RVA 0x45e530)、`GT[0x2CF]`(RVA 0x45e560)
相邻，三者都是 nt `.data` 段的全局链表头。

已恢复原版 5 条上限（不放宽），保留原版语义。

## 六、贯穿全过程的规律（四条）

**规律 1：累加器就是 `ctx+0x08`（读指针）**
`ReadPESectionEntry`（0x14008A54C..A7E4）全段无 `mov [rdi+8],..`，
推进责任在调用方；原版各扫描器的 `add [var_1C8], rax` 累加的正是它。

**规律 2：被减数是 `GT[0x20]`（PeFileBase）**
原版各分支都是 `sub eax, r12d`，`r12 = GtRead(0x20)`。

**规律 3：描述符偏移 = 栈帧 offset − 该函数描述符基址的 offset**
各函数基址不同（`rbp-0x60` / `rbp-0xa8` / `rsp+0x90` / `rsp+0x98` /
`rbp-0x70`），不能套用同一组偏移。

**规律 4：推进与取值的先后因函数而异**
- 先推进后取值：`ScanKernelPeExportSection`、`ScanKernelPeExportData`、
  `EnumProcessPeExportDataByIndex`
- 先取值后推进：`ReadWriteKernelMemory`

必须逐个核对，不能统一。

## 七、反查 GT 哈希槽的方法

驱动内部的 SHA1 是**非标准变体**（消息字按小端直读、不做 bswap，
输出再做字节交换）。用标准 SHA1 反查导出名会全部失败，曾因此误判
"哈希表无效"。正确实现：

```python
import struct
def sha1_variant(data: bytes) -> int:
    h=[0x67452301,0xEFCDAB89,0x98BADCFE,0x10325476,0xC3D2E1F0]
    msg=bytearray(data); msg.append(0x80)
    while len(msg)%64!=56: msg.append(0)
    msg+=(len(data)*8).to_bytes(8,'big')
    for off in range(0,len(msg),64):
        w=list(struct.unpack('<16I',msg[off:off+64]))   # 不做 bswap
        for i in range(16,80):
            x=w[i-3]^w[i-8]^w[i-14]^w[i-16]
            w.append(((x<<1)|(x>>31))&0xFFFFFFFF)
        a,b,c,d,e=h
        for i in range(80):
            if i<20: f=(b&c)|((~b)&d); k=0x5A827999
            elif i<40: f=b^c^d; k=0x6ED9EBA1
            elif i<60: f=(b&c)|(b&d)|(c&d); k=0x8F1BBCDC
            else: f=b^c^d; k=0xCA62C1D6
            t=((((a<<5)|(a>>27))&0xFFFFFFFF)+f+e+k+w[i])&0xFFFFFFFF
            e,d,c,b,a=d,c,((b<<30)|(b>>2))&0xFFFFFFFF,a,t
        h=[(x+y)&0xFFFFFFFF for x,y in zip(h,[a,b,c,d,e])]
    return struct.unpack('>I',struct.pack('<I',h[0]))[0]
```

已验证的映射：
- `0xF3C88A38` → `CmUnRegisterCallback`（RVA 0x823260）
- `0x992020AA` → `KeRegisterBugCheckCallback`（RVA 0x195E50）
- `0x33CFA96A` → `IoRegisterFsRegistrationChangeMountAware`（RVA 0x775260）
- `0x496CD1FE` → `PsLookupProcessByProcessId`（RVA 0x66EDC0）

## 八、踩过的坑

1. **kd 的 IPv4 socket 失败 = 端口被残留 kd.exe 占用**。`tasklist` 找到后
   `taskkill /F /PID` 清掉，即可恢复。
2. **`vm_start` 会终止 kd**。正确顺序：`kd_attach`(wait=false) → vmrun start。
3. **`g_GlobalTable` RVA 每次重编都可能变**，必须从 map 重取
   （本轮是 `0xab060`，曾误用 `0xac060` 导致读到全 0）。
4. **kd 断点会让 Guest 冻结**，此时所有 vmrun 调用失败。部署前务必
   `bc *` + `kd_go`，或直接 `kd_detach`。
5. **在 `GtWrite` 这类热路径上设自恢复断点会淹没 KDNET**，改用 `kd_sample`。
6. **诊断写入 0x047 输出尾部**必须放在 0x1400 之后（原版全通时用到 0x12D0），
   并在验证后删除。
7. **map 第三列是完整 VA**，RVA 要减 `0x140000000`；LTCG 会重排函数顺序。
8. **C1001 内部编译器错误**：`taskkill /F /IM mspdbsrv.exe` + `rm -rf build/obj` 后重试。
9. **probing 前先确认 Guest 未被 kd 冻结**，否则 vmrun 报
   "VMware Tools 未在客户机中运行"。
