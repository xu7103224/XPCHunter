## 二、本轮修掉的根因（全部按反汇编逐条核对）

贯穿整轮的一个系统性缺陷是：**反编译产物里的判据字段被写成"声明后从不赋值"
的独立局部变量**，导致每条判据恒假、函数永不产出。共修掉 6 个函数：

| 函数 | 原版地址 | 空壳变量数 |
|---|---|---|
| `EnumerateProcessCallbackContext` | 0x14003EAA8 | 6 处结构性错误 |
| `ResolveSsdtTablePointer` | 0x1400401DC | 8 |
| `ResolveSsdtTablePointerEx` | 0x1400403B4 | 8 |
| `ParseNtSectionsForShadowSsdt` | 0x140040C14 | 偏移错位 |
| `ReadWriteKernelMemory` | 0x14003F998 | 6 |
| `ScanKernelPeExportSection` | 0x14003F274 | 7 |
| `EnumProcessPeExportDataByIndex` | 0x14003F7D0 | 5 |
| `EnumProcessPeExportDataEx` | 0x14003F5E0 | 7 |
| `ScanKernelPeExportData` | 0x14003F060 | 6 |
| `EnumProcessPeExportData` | 0x14003F414 | 6 |

### 三条贯穿性规律

**规律 1：累加器就是 `ctx+0x08`（读指针）**

`ReadPESectionEntry`（0x14008A54C..A7E4）内部**不写** `[ctx+8]`（全段无
`mov [rdi+8],..`），推进责任在调用方。原版各扫描器里的
`add [rsp+..var_1C8], rax` 累加的正是 ctx+0x08，因此公式
`字段 - 基址 + 累积量` 必须用 ctx 读指针，不能另设从 0 起的累加器。

**规律 2：被减数是 `GT[0x20]`（PeFileBase），不是导目录偏移**

原版各分支都是 `sub eax, r12d`，而 `r12 = GtRead(0x20)`。旧实现减的是
`PeFileOffset`（`GT[0x42E2]` 等），两者相差一个导出目录偏移，使算出的 RVA
整体偏大、`RVA < ImageSize` 判据失败。这一处修正直接让块 6 从 0 条变为
**215 条**（与版完全一致）。

**规律 3：描述符偏移 = 栈帧 offset − 描述符基址的 offset**

各函数的描述符基址不同（`rbp-0x60` / `rbp-0xa8` / `rsp+0x90` / `rsp+0x98` /
`rbp-0x70`），必须按各自栈帧换算，不能套用同一组偏移。例如
`ReadWriteKernelMemory` 的描述符基址是 `rbp-0xa8`，故：
`var_F8(0x130)→+0x88`、`var_110(0x118)→+0x70`、`var_130(0xf8)→+0x50`、
`var_108(0x120)→+0x78`。

### 块 2/3/6/9/10 的数值一致性证明

不同 VM 会话下 ntoskrnl 重定位基址不同。把每个条目的内核指针减去各自
nt 基址后，块 2 的 5 条 RVA 完全对应，差值恒为 `0x49E0000`；
块 6 的 215 条同为同一批对象。

## 三、剩余三个卡点（均已定位到具体槽）

### 块 5（类型 5，原版 3 条）

- 源：`GT[0x2BB]` = `0xfffff80674e4aa69`（已由 `EnumProcessPeExportDataByIndex`
  写入，值为 `NtoskrnlModuleBase + RVA`，末位奇数）
- dispatch 把它当 `LIST_ENTRY` 头遍历（`pEnumList = *pEnumList`），
  而实际指向的是代码地址，`MmIsAddressValid` 之后的循环条件立即失败
- 原版 `GT[0x2BB]` 是堆地址（`0xffffc28a...`），说明原版该槽在 dispatch
  之前被另一条构建链表的路径覆盖过；IDB 里 `0x2BB` 只有
  `0x14003F941` 一个写点，未见其他显式写入

### 第二份块 9（类型 9，原版 2 条）

- 源：`GT[0x2CF]` = 0（`ScanKernelPeExportSection` 未写出）
- 该函数读 `GT[0x42FA] = 0x769220`（有效），但窗口内未命中
  `Type 0x512 + (+0x88==0x40000) + (+0x78 非零) + (+0x50==0x40) + (+0x58==1)`

### 块 11（类型 11，原版 1 条）

- 源：`GT[0x33D]` = 0（`ScanKernelPeExportData` 未写出）
- 实测第一轮解码 5 条、`Type 0x559` 命中 **0 次**
- `GT[0x435D] = 0x775260` 已确认为
  `nt!IoRegisterFsRegistrationChangeMountAware` 的 RVA
  （哈希 `0x33CFA96A` → 该导出，非标准 SHA1 变体复算验证通过）

## 四、验证方法（可复现）

反查 `GT[0x4158+3k+1]` 槽对应的导出名需要复刻驱动内部的**非标准 SHA1 变体**
（消息字按小端直读、不做 bswap，输出再做字节交换）：

```python
import struct
def sha1_variant(data: bytes) -> int:
    h=[0x67452301,0xEFCDAB89,0x98BADCFE,0x10325476,0xC3D2E1F0]
    msg=bytearray(data); msg.append(0x80)
    while len(msg)%64!=56: msg.append(0)
    msg+=(len(data)*8).to_bytes(8,'big')
    for off in range(0,len(msg),64):
        w=list(struct.unpack('<16I',msg[off:off+64]))   # 不做 bswap
        for i in range(16,80):
            x=w[i-3]^w[i-8]^w[i-14]^w[i-16]
            w.append(((x<<1)|(x>>31))&0xFFFFFFFF)
        a,b,c,d,e=h
        for i in range(80):
            if i<20: f=(b&c)|((~b)&d); k=0x5A827999
            elif i<40: f=b^c^d; k=0x6ED9EBA1
            elif i<60: f=(b&c)|(b&d)|(c&d); k=0x8F1BBCDC
            else: f=b^c^d; k=0xCA62C1D6
            t=((((a<<5)|(a>>27))&0xFFFFFFFF)+f+e+k+w[i])&0xFFFFFFFF
            e,d,c,b,a=d,c,((b<<30)|(b>>2))&0xFFFFFFFF,a,t
        h=[(x+y)&0xFFFFFFFF for x,y in zip(h,[a,b,c,d,e])]
    return struct.unpack('>I',struct.pack('<I',h[0]))[0]
```

用标准 SHA1 会全部匹配失败——这一点曾导致误判"哈希表无效"。

## 五、踩过的坑

1. **过期 `g_GlobalTable` RVA 会伪造"槽为 0"的结论**。必须每次从
   `build/bin/Release/x64/XPCHunterDrv.map` 重取 `g_GlobalTable` 地址。
2. **VMware Tools 在 kd 停在 `kd>` 时失去响应**，`vmrun` 全部失败；
   需 `kd_go` 或 `vm_reboot mode=hard`。
3. **宿主 kd 的 IPv4 socket 初始化失败**（`HRESULT 0x80004005`）时
   `kd_attach` 永远失败，与 VM 无关；此时只能靠代码级诊断。
4. **诊断写入 0x047 输出尾部会污染正常输出**：12 块全通时原版用到
   0x12D0，因此诊断必须放在 0x1400 之后，并在验证后删除。
5. **`taskkill` ntdrived 会让 MCP 工具层与 daemon 失联**且断掉 kd 会话。
6. **map 第三列是完整 VA**（`0x14007DCF0`），RVA 要减 `0x140000000`；
   LTCG 会重排函数顺序，不能靠 map 相邻关系推断代码位置。
