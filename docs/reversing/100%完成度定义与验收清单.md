      此前这一条判为「原版在 Win10 上同样不工作」，两个理由都**已被推翻**：

      ① 「td.sys 是 XP/2003 驱动，Win10 不存在」→ 错。实测

      2. **读指针推进位置**（`FindFwps*` 两处，另一提交）。
      3. **TargetRva 用错量**：原版是

### Tab 5 · Network（30 项）

**整页状态：链路已复刻，本虚拟机环境下无数据。**

【2026-10-23 重大更正】此前这里写「驱动命令表里没有 Network 命令」、
「本复刻没有通用内核读通道」，**两条都是错的**。用原版前端 IDB 反查到了
完整链路（详见 `Network页数据链路与能力边界_2026-10-23.md`）：

| 命令 | 驱动处理器 | 前端封装 | 语义 |
|---|---|---|---|
| 0xF1 | `Table[209] MiniFilterAcquireForModWrite` | `sub_1400262E0` | Fwps 修改写分发表 |
| 0xF2 | `Table[210] CmdInitFwpsDispatchTables` | `sub_140026340` | Fwps 分发表（Win8） |
| 0xF3 | `Table[211] CmdCopyKernelArrayToUserBuffer` | `sub_1400263A0` | 内核数组 → 用户 |
| 0xF6 | `Table[214] CmdCopyKernelDualArrayToUserBuffer` | `sub_140026400` | 双数组变体 |
| 0xF7 | `Table[215] CmdReadKernelMemoryToUserBuffer` | `sub_140026590` | 单个内核指针 |
| 0xF9 | `Table[217] CmdReadKernelMemoryRange` | `sub_140026650` | 另一内核指针 |

入口是 `CNetworkOtherDialog` 的刷新函数 `sub_1400A01E0`，
用一个 `switch (a6)` 按 6 个子视图分发到上面六个封装。
注意 `0xF7`/`0xF9` 的准确语义是「读 GT 里存的**那个**内核指针所指向的
8 字节」，**不接收用户指定地址** —— 是按子系统的定点读，不是任意 VA 读。
（因此 Dump Kernel Memory 那条「无法实现」的判定依然成立，理由改为
「只有定点读、没有任意地址读」。）

**但这台虚拟机上原版自己也拿不到数据**：把原版驱动装进同一台
Win10_Dev（build 18362）逐条实测，0xF1/0xF2/0xF3/0xF6/0xF7/0xF9
**全部返回 result=0**；kd 读原版 GT 可见 `GT[0x7FA..0x800]` 全为 0
（`fwpkclnt.sys` 本身加载了，基址 0xFFFFF80586670000 / 0x7A000 字节，
但四个 `FindFwps*` 一个都没命中）。原因是本虚拟机没有安装/激活
WFP 过滤驱动，fwpkclnt.sys 里没有可解析的分发表实例。

因此下面 21 项的正确状态是「**链路已复刻，本环境无数据**」，
需在装有 WFP/NDIS 过滤组件的机器上才能取到值 ——
既不是「未实现」，也不是「无能力」。

本轮同时修掉一个实质缺陷：`FindFwpsTcpIpDispatchTable` 与
`FindFwpsDispatchTableWin8` 的 Win10 分支里，读指针推进写在了
`ReadPESectionEntry` **之前**（与 0x131 同类缺陷），现已改为先解码再推进。
这个错位在有 WFP 的机器上必然导致解析失败，属于必修项。

已在真实数据上跑通的对照项：Network 页 `netio.sys` 解析

## 六、每个条目的"完成"标准（避免自欺）

一条只能在以下三种证据都具备时打勾：

1. **有对应驱动命令或明确的用户态数据源**，且该命令在实机 `HANDLED`；
2. **有实机证据**：GUI 截图（含该条目的可见效果）或 CLI 原始输出；
3. **行为与原版一致**：文案、列名、右键菜单项与原版功能地图对得上。

仅"界面上有个按钮"不算完成；仅"驱动命令返回 1"也不算完成。
