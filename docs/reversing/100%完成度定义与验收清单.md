      ① `ReadGdtr` 原为假实现（limit 写死 0xFFFF、base 取 KPCR+0x28），
         已改为 base=KPCR+0x00（实测 == `r gdtr` 基址），并用显式结构体

- [x] Hook 表枚举 — 0x117 返回两张表共 908 条（454 + 454），已接入页面并解出
      索引 / 当前地址 / 磁盘原始地址 / 原始 16 字节 / 两个改写标志。

- [x] `Restore Over. Hooks/Patches` 恢复 — 0x118 `CmdCheckBytePattern`（入 8 字节：
      `byte0==1` 走全索引 0..0x1FF，否则 `SBYTE1`=TableType、`HIDWORD`=索引）。
      Ring0 Hooks 页已加按钮，实测状态栏显示
      `nothing to restore - all 908 hook entries match their on-disk originals
      (0 modified, driver result=0)`。**这是正确结果**：驱动只在
      「表项当前值 ≠ 磁盘原始值」时才写回，本机 908 条两个改写标志全为 0，
      没有任何待恢复项。截图 `ring0_restore_buttons_2026-10-21.png`，
      CLI 原文 `ring0_restore_cli_2026-10-21.txt`
      **证据强度的诚实说明**：因本机无待恢复项，`WritePhysicalMemoryQword` /
      `WritePhysicalMemoryBuffer` 的写回分支**从未被实际执行**。本项勾选依据是
      「命令通道、入参封装、状态判读、界面呈现」四项均实机验证通过，
      而"写回后系统状态改变"这一点无法在本机证明（需要一台真被 hook 的机器）。
- [ ] `Restore KernelCallbackTable Replaced` — **0x131** `CmdEnumCallbackContext`
      （出 1352 字节）+ **0x132** `CmdSetCallbackContext`（入 48 字节：
      `[24]==1` 装 Hook、`[25]==1` 写 16 字节补丁）。Ring0 Hooks 页已加按钮，
      实测状态栏显示 `callback table not initialized (cmd 0x131 result=0)`。
      驱动取 `GT[2308]`（GtHookTableCount）为 0 后调
      `BuildCallbackContextHookTargets()` 仍未建立表，故
      `EnumCallbackContextTable` 返回 0 —— **环境状态，如实呈现，未伪装成功**。
      CLI 原文 `ring0_restore_cli_2026-10-21.txt`
      （此前把命令号误记为 0x111/0x112；`Table[i]` 对应命令 `0x20+i`）

      **不勾选的理由**：枚举本身就没成功（`ready=0`、`slots=0`），拿不到任何
      回调槽，因此无法证明"恢复"这个动作可行。这与当初 SSDT 子页
      "UI 就位但数据源返回 0"按同一标准处理 —— 入口接好不等于功能完成。

## 六、每个条目的"完成"标准（避免自欺）

一条只能在以下三种证据都具备时打勾：

1. **有对应驱动命令或明确的用户态数据源**，且该命令在实机 `HANDLED`；
2. **有实机证据**：GUI 截图（含该条目的可见效果）或 CLI 原始输出；
3. **行为与原版一致**：文案、列名、右键菜单项与原版功能地图对得上。

仅"界面上有个按钮"不算完成；仅"驱动命令返回 1"也不算完成。
