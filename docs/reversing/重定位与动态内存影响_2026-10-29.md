# 重定位与动态内存对 inline hook 检测的影响（2026-10-29）

## 0. 问题

用户提问：「你有没有检查重定向偏移？或者类似这种的动态加载过程会改变的内存？」

**答：之前的实现没有。这是一个真实缺陷，已修复。**

修改前，比对是裸 `memcmp(mem16, diskBytes, 16)`，完全没有考虑
PE 重定位、ASLR 搬移、CFG、hotpatch 等动态变化。虽然实测在系统 DLL 上
没有出现过误报，但那是**运气**，不是设计正确。

## 1. 哪些内存会「动态加载过程中改变」

把 inline hook 检测的潜在误报源逐项列出，并给出当前处理状态：

| 变化源 | 为什么会变 | 是否影响 `.text`（代码段） | 当前处理 |
|---|---|---|---|
| **PE 重定位（ASLR）** | 模块实际基址 != 首选基址，加载器搬移所有重定位目标 | **x64 系统 DLL：不影响**（重定位全在 `.rdata`/`.data`） | ✅ **本轮新增掩码跳过** |
| CFG 的 `.00cfg` | 控制流保护表在加载时填充 | 否（独立节） | ✅ 不涉及（非可执行节） |
| hotpatch padding | 编译器在函数前留 `CC CC CC CC` + `mov edi,edi` | 是（首字节） | ✅ 跳过首字节 `0xCC`/`0x90` |
| IAT 填充（延迟加载） | 首次调用时写入真实地址 | 否（IAT 在 `.idata`） | ✅ 不涉及（走 IAT 检测路径） |
| 只读数据被运行时改写（如 `NlsAnsiCodePage`） | 系统初始化时填充 | 否（在 `.data`） | ✅ 用「可执行节」过滤 |
| `fothk` 段 | Windows 的 hotpatch 支持段 | 是（但通常为空） | ✅ 首字节过滤 |
| 页交换 / COW | 写入时复制 | 不影响内容 | ✅ `ReadProcessMemory` 已处理 |
| 函数指针表初始化 | 驱动/模块注册回调 | 否 | ✅ 不涉及 |

## 2. 量化：ASLR 重定位对代码段的实际影响

写了个工具统计「导出函数前 16 字节里含几个重定位项」：

```
ntdll.dll      exports=2490  with-reloc-in-first-16=0 (0.0%)
kernel32.dll   exports=1465  with-reloc-in-first-16=0 (0.0%)
kernelbase.dll exports=1889  with-reloc-in-first-16=0 (0.0%)
user32.dll     exports=1014  with-reloc-in-first-16=0 (0.0%)
gdi32.dll      exports=698   with-reloc-in-first-16=0 (0.0%)
advapi32.dll   exports=755   with-reloc-in-first-16=0 (0.0%)
shell32.dll    exports=476   with-reloc-in-first-16=0 (0.0%)
comctl32.dll   exports=119   with-reloc-in-first-16=0 (0.0%)
ole32.dll      exports=252   with-reloc-in-first-16=0 (0.0%)
ucrtbase.dll   exports=2484  with-reloc-in-first-16=0 (0.0%)
```

**全部为 0。** 原因不是没有重定位表，而是**重定位项根本不在代码段**：

```
ntdll.dll 重定位项：655 个，最小 RVA = 0x133008
ntdll .text 范围  ：0x1000 .. 0x12F1EE
                    ↑ 重定位从这里开始（.rdata），.text 内一个都没有
```

x64 用 RIP 相对寻址，代码里几乎不出现绝对地址，所以重定位全落在
`.rdata`/`.data` 的数据指针上。

**结论：对本机 Win10 18362 的系统 DLL，ASLR 不会造成代码段误报。**

## 3. 但仍然必须实现这条防护

理由：

1. **第三方 DLL 可能不同**。手写汇编、特定编译器、32 位混合模块
   （虽然当前只扫 64 位）都可能生成 `mov rax, [abs]` 这类绝对寻址。
2. **Windows 版本会变**。未来版本可能改变编译器选项。
3. **正确性不能靠运气**。当前 0 命中是**数据特性**，不是**设计保证**。
   一旦某个模块在代码段有重定位，naive memcmp 会立刻误报。

## 4. 实现

`FeBuildRelocMask()`（`HookViews.c`）：

```c
static void FeBuildRelocMask(const BYTE *pView, const IMAGE_NT_HEADERS64 *dNt,
                             const IMAGE_SECTION_HEADER *pSec, DWORD secCount,
                             DWORD rva, int len, BYTE *Mask)
{
    /* 遍历 .reloc 段，把落在 [rva, rva+len) 的重定位目标位置在 Mask 里标 1 */
}
```

比对处改为掩码感知：

```c
BYTE relocMask[16];
BOOL differ = FALSE;
FeBuildRelocMask(pView, dNt, pSec, secCount, funcRva, 16, relocMask);
for (m = 0; m < 16; m++) {
    if (relocMask[m])          /* 重定位目标：跳过，磁盘值与内存值必然不同 */
        continue;
    if (mem16[m] != diskBytes[m]) {
        differ = TRUE;
        break;
    }
}
if (!differ)
    continue;
```

实现细节：

- 重定位表本身是 RVA，先换算到文件偏移
- 块边界严格校验（`SizeOfBlock >= 8` 且不越出表范围）—— 早期版本没校验，
  遍历时越界导致段错误
- `IMAGE_REL_BASED_ABSOLUTE`（type 0）是填充项，跳过
- 每项按 8 字节标记（DIR64）；HIGHLOW 是 4 字节，多标 8 字节只是宁可
  少判一点，不会漏判

## 5. 验证

### 5.1 重定位防护不能挡掉真实 hook

加掩码后重跑私有 DLL 正向验证：

```
HOOKED: 8D -> 8C
hooktest.dll-->Ring3 Inline Hook  fn=hooktest.dll!HookTargetAdd
```

**仍然检出。** 保护是精准的，没有过度过滤。

### 5.2 不引入新的误报

扫 explorer 前 8 个模块（含 ntdll / KERNEL32 / KERNELBASE，
都是 ASLR 搬移过的系统 DLL）：

```
=== Ring3 Hooks (pid 4516): 0 entries (IAT + inline) ===
(no IAT entries outside all modules, no inline-patched exports)
```

**0 条。** 加防护前后行为一致。

## 6. 排查过程中发现的两个 bug

### 6.1 重定位表遍历越界（工具里的）

第一版 `CountRelocHits` 直接在 `while (off < d.Size)` 里读 `blk->SizeOfBlock`，
没有校验块本身是否越界。`SizeOfBlock` 为 0 或超范围时死循环/段错误。
修正为 `while (off + sizeof(IMAGE_BASE_RELOCATION) <= d.Size)` 且
每块都检查 `bs >= 8 && off + bs <= d.Size`。

### 6.2 「0% 命中」差点被当成「不需要防护」

统计出全 0 后的第一反应是「那就不用做了」。但查了 `.text` 范围和
最小重定位 RVA 才明白：**0 是这段代码的特性，不是普遍规律**。
如果只看那个 0 就跳过实现，遇到第一个代码段有重定位的模块就会立刻误报。
