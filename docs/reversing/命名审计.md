# 命名审计（复刻代码 + 原始 IDB 函数名）

> 起因：多轮分析反复撞上"名字在骗人"——同一个 `ReadContext` 被用在**三种不同的东西**上，
> `CumulativeSize` 其实是上下文的读指针，`FieldValue` 是数组游标，
> `v18b`/`v47` 这类是反编译残留占位名。命名混乱已成为**误判的直接来源**
> （本 session 我就因为照着名字推断，连续错了三次）。
> 故先做命名，再动其它修正。

---

## 一、判据：什么才算"名字有问题"

只有能拿出证据的才列入，避免"看着不顺眼就改"：

| 判据 | 说明 | 是否算问题 |
|---|---|---|
| **P1 反编译残留** | `v\d+` / `v\d+[a-z]` 形式（`v18b`、`v47`） | ❌ **CLAUDE.md 2.2 明令禁止** |
| **P2 角色不符（有证据）** | 该变量的**地址被传给某 API** 或**被赋值来源**证明了它的真实角色与名字矛盾 | ❌ 必须改 |
| **P3 一名多用** | 同一名字在不同位置指不同角色（`ReadContext` 三用） | ❌ 必须改（否则后续无人能靠名字判断） |
| **P4 语义不足** | `Result` / `Index` / `Buffer` / `Count` / `Flag` | ✅ **CLAUDE.md 2.2 明确列为可接受**，**不算问题** |
| **P5 函数名与实物不符** | 函数体做的事与名字无关（`MiniFilterPreCreate` 实为节区扫描器） | ❌ 必须改 |

> **不列为问题**：`Result`(数百处)、`Index`、`Buffer`、`Size`、`Count`、`Flag` 等。
> 上一版扫描把它们统计成"819 处语义不足"是**误报**，按判据 P4 撤回该统计。

## 三、问题清单二：一名三用 —— `ReadContext`（P3，约 120 处）

**同一个名字被用在三种完全不同的东西上**，这是最危险的一类：

| 角色 | 判据（硬证据） | 处数 | 建议名 |
|---|---|---|---|
| **(a) 真·解码上下文** | 其**地址**被传给 `InitPESectionReadContext` 的第 8 实参，且自身不被从内存赋值 | 39（仅 `SsdtHook.c`） | `DecodeContext` |
| **(b) 描述符 SectionInfo** | 它是 `ReadPESectionEntry` 的**第 2 实参**（该函数会 `memset(第2实参, 0x120)`，原始反汇编实证 `mov r8d,120h` + `call memset`） | ~80 | `SectionEntry` / `SectionInfo` |
| **(c) 表元素** | 被从内存赋值（`ReadContext = FieldValue[1]`） | 1 | `RangeStart` |

典型现场（`SsdtHook.c:1694` 起）—— 同函数内 (b)(c) 两错并存：

```c
_DWORD ReadContext[20];                                     // (b) 描述符，却只有 80 字节
InitPESectionReadContext(..., (__int64)&SectionType3);       // 上下文是另一个 8 字节标量
ReadPESectionEntry((PUCHAR)&SectionType3, ReadContext)       // 第 2 实参(描述符)才是它
```

## 四、问题清单三：`CumulativeSize` / `FieldValue` 家族（P2，176 处）

这两个名字在 PE 扫描器家族里被大量自动生成，**实测角色与名字矛盾**：

| 现名 | 实际角色 | 证据 | 建议名 |
|---|---|---|---|
| `CumulativeSize`（当上下文用时） | 实为**解码上下文**，其中 `+0x08` 是**读指针**（每轮按指令长度推进） | ① 6 个扫描函数帧布局一致（该变量地址 == 上下文+8）；② `SSDT.c:703/742`、`SsdtHook.c:2367` 把 `CumulativeSize` **当第 8 实参**传给 `InitPESectionReadContext`；③ `ReadPESectionEntry` 对上下文**只读**、自身不推进，故推进责任必在调用方 | `DecodeContext`（若同函数还需一个计数器，另起 `ConsumedBytes`） |
| `FieldValue` / `FieldValue2`（当表游标） | 实为**24 字节区间表的游标** | `FindNdisRegisterTdiCallBackExport` 内 `FieldValue += 3`（步长 3 qword = 0x18）+ 哨兵比较 `*FieldValue > 0xFD010111` + 循环边界是地址 + 下游 `AdjustRelocationOffsets(SectionType3, …, …)` | `RangeEntry`（游标）/ `RangeTable`（基址） |
| `FieldValue[1]`（当区间端点） | 实为**区间起点** | 同一 `do/while` 内参与 `<= LoopIndex \|\| >= FieldValue2` 区间判断 | `RangeStart` |
| `FieldValue[2]`（当区间端点） | 实为**区间终点** | 同上 | `RangeEnd` |
| `SectionType3`（当上下文） | 被复用为上下文缓冲区 | `InitPESectionReadContext(..., &SectionType3)` | `DecodeContext` |

| 方案 | 示例（0x1400142A8） | 优点 / 缺点 |
|---|---|---|

疑为**同一目标的多个版本/构建号变体**——这也正是需要方案 A 的"再加区分"的原因。

**待办**：定下命名约定（建议 A，并在同槽多生产者处用匹配类型序列做后缀区分），

## 七·原、剩余 22 处栈越界的处理配方（别名类，不能批量改）

**状态**：栈越界批量修已完成 161 → 22 处（86%）。**剩余 22 处全部是"别名变量"**
——同一个变量既被当整数（`X = <int>` / `X += <n>`）、又被取址当解码上下文传参。

**为什么不能批量改**：改类型必然编译失败。本 session 已被编译器拦下 5 次：
`PeContext`（`PeParse.c` 4 处 + `ContextMgmt.c` 6 处）、
`SectionContext`（`SyscallTable.c` 1 处 + `PeSectionParse.c` 4 处）。
C 语言里也**不存在**"既是可赋值整数、又能容纳 0x48 字节"的声明写法
（结构体不可赋值、数组不可赋值），故无批量解。

**逐处配方（按两种情况）**：

**情况 A：该函数另有已正确声明为 0x48 的上下文变量**
→ 说明只是**传错了变量**，改传正确的那个即可（1 行改动）。
验证方式：改后构建应仍干净，且 `_scan_oob.py` 的上下文计数减 1。
注意：这类改动编译器不会报错（类型都对），**必须读函数确认**再改。

**情况 B：该函数确实只有一个变量承担两个角色（真别名）**
→ 按角色拆成两个变量：
```c
PE_DECODE_CONTEXT X;        // 作上下文用（0x48 字节）
__int64          XValue;    // 作整数用（原 X = <int> / X += <n> 全部改到它）
```
其中 `X += <每轮长度>` 这一族的语义已确证是**上下文的读指针推进**
（证据三条：① 6 个扫描函数帧布局显示该槽位 == 上下文+8；
② `SSDT.c:703/742`、`SsdtHook.c:2367` 直接把它当第 8 实参传入；
③ `ReadPESectionEntry` 对上下文只读、自身不推进，故推进责任必在调用方）
→ 应写成 `X.ReadPtr += <每轮长度>`（`PE_DECODE_CONTEXT` 的 `ReadPtr` 字段，+0x08）。

### 十·第三次更正：路径只有**两条**（此前记录的"三条"有误）

重新精读反汇编（0x140072EC8）后发现此前规格的两处错误：

1. **搬运调用只有两个，不是三个**：
   - `Handle88 == 0` → 调 `SendIoControlWithQuotaBufferEx`（0x1400730F8）
   - `Handle88 != 0 && var_48(GT0x198) != 0` → 调 `AllocBufferAndSendIoControl`（0x1400730CE）
   - `Handle88 != 0 && var_48 == 0` → **不调用**，`edi` 保持 `0xC0000001`（失败）
     直接跳到后处理（0x1400730A2 `jz loc_140073105`，而 0x140073105 是**汇合点**
     不是路径入口 —— 这处误读是此前规格出错的原因）
   （此前记录的"路径 B/C"实际是同一个 `SendIoControlWithQuotaBufferEx` 调用）

2. **`r12` / `var_8C` 是计数器**，非函数指针：
   - `r12d` 初值 0（0x140072FE8 `mov r12d, ebx`），循环中 `++`（0x14007314E）
   - `var_8C` 初值 0（0x140072FE5），错误分支里判断它决定是否清零（0x140073157）
   - 而 `GT 0x17B`(var_70) 与 `GT 0x179`(var_60) 是**函数指针**：
     前者在收尾处被 `call r13`（0x1400731B8，释放句柄）、后者作为子调用第 1 实参
   → 即 GT 0x17A/0x17B/0x179 这些槽**存的是函数指针**（由节区扫描器定位后解析而来），
     与"GT 描述表"章节的"写入方=扫描器 / 读取方=Send*IoControl"配对**一致**；
     消费者把它们**当函数指针调用**。

3. **栈参数映射已用 IDA 精确测定**（`op.addr` 真实位移，rbp = entry_rsp - 0x3F）：
   | IDA 名 | 位移 | 形参 |
   |---|---|---|
   | `arg_10` | 0x57 → entry_rsp+0x18 | 3 PageIndex |
   | `arg_18` | 0x5F → entry_rsp+0x20 | 4 AddressField |
   | `arg_20` | 0x67 → entry_rsp+0x28 | 5 pOutputBuffer |
   | `arg_28` | 0x6F → entry_rsp+0x30 | 6 OutputSize |
   | `arg_30` | 0x77 → entry_rsp+0x38 | 7 ResultBuffer |
   | `arg_38` | 0x7F → entry_rsp+0x40 | 8 Flag |
   与调用点实参（`&flag, Addr[2], ebx, r15d, rsi, r14d, [r13+0x20], r12b`）逐位吻合 ✓
