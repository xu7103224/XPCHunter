**过程中发现并修复的真实缺陷**：`RegisterMiniFilterRegistry` 中三处
`memset(&ObjectAttributes.SecurityDescriptor, 0, sizeof(ObjectAttributes) - 24)` 存在 **8 字节栈越界**
（偏移 32 处写 24 字节，结构仅 48 字节），触发 C4789 警告。原始驱动的写法是
`*(_OWORD *)&ObjectAttributes.SecurityDescriptor = 0`（**恰好 16 字节**：SecurityDescriptor +
SecurityQualityOfService 两个指针），复刻把 16 误写成 `sizeof-24`。已改为逐字段赋值，与原始语义等价。

**SDK 差异处理**：本机 WDK 的 `FLT_REGISTRATION` 比原驱动编译时多一个
`SectionNotificationCallback` 字段（`sizeof` 为 112 而非 104）。FltMgr 按 `Version` 校验 `Size`，
故 `Size` 固定为 104（0x68），与原始一致。

**逆向要点（一个易错的细节）**：原始指令为 `mov sil, byte ptr [rax+23h]`，即读取
`Iopb + 0x23` 处的字节。经核对 WDK 头文件布局：`FLT_IO_PARAMETER_BLOCK.Parameters` 位于 0x18，
其中 `SetVolumeInformation.FsInformationClass`（`FS_INFORMATION_CLASS` 枚举，经 `POINTER_ALIGNMENT`
对齐）位于 Parameters+0x08 = **Iopb+0x20**，故所读字节是该 32 位字段的**最高字节**（bits 24-31），
C 表达式必须写 `FsInformationClass >> 24`。

> 注意：项目宏 `HIBYTE(x)` 定义为 `(x >> 8) & 0xFF`，若照 IDA 显示的 `HIBYTE(...)` 直接套用，
> 会读到 Iopb+0x21，行为与原驱动不一致。此处已按实际字节偏移实现并在编译后反汇编复核。

### 2026-09-17：P1 起步 —— DisableObjectProtectEx（已完成并验证）

| 项目 | 原状态 | 现状 |
|---|---|---|
| `DisableObjectProtectEx` (0x140007D54, 495B) | `return 0;` 占位（B 类），被 ObjectMgmt/Operation 两处调用 | 已 1:1 实现 |

**逆向要点（栈槽复用）**：IDA 的反编译把栈上相邻槽位合并成了 `IO_STATUS_BLOCK[4]` 数组，产生
`IoStatusBlock[2] = CloseHandleFunc` 这类失真语句。对照反汇编后确认真实布局是：
函数指针 spill 槽 + **栈传参**（`[rsp+0x20]`/`[rsp+0x28]` 是第 5、6 个参数），
并非 IO_STATUS_BLOCK。逻辑为：

```
读 5 个已解析例程指针（RtlInitUnicodeString / 打开对象 / FsControl / 关闭句柄 / 释放池）
→ 全部非空才继续
→ 构造 L"\Callback"（5 个 dword 编码串）并 RtlInitUnicodeString
→ OBJECT_ATTRIBUTES{Length=0x30, RootDirectory=0, ObjectName=路径, Attributes=0x240, 两个指针字段清零}
→ Open(&Handle, 1, &OA)               // 访问掩码 1
→ FsControl(Handle, 0xF000F, 0, 0, &FileHandle, 0)
→ ExAlloc(PagedPool, 0x100000)，写入 FileHandle，WalkObjectTypeList(buf, 0x20000, OutputBuffer, BufferSize)
→ ExFree(buf) → Close(FileHandle) → FreePool(Handle)
```

**验证结果**：

| 验证项 | 结果 |
|---|---|
| 编译 | 0 错误 0 警告 |
| 产物大小 | 487,424 → **488,960**（+1,536，确认进二进制） |
| 5 个全局表索引 | 按内联后的 RIP 相对寻址逐条还原，`g_GlobalTable[0x421D/0x4238/0x41C6/0x4223/0x4334]` **全部匹配** ✓ |
| 调用序列与参数 | Open(&h,1,&oa) / FsControl(h,0xF000F,0,0,&fh,0) / ExAlloc(1,0x100000) / 遍历深度 0x20000 / 清理顺序 均一致 ✓ |
| 函数大小 | 复刻 1344B vs 原始 495B —— 差异来自 LTCG 将 `WalkObjectTypeList` 内联，非逻辑缺失 |

> **审计提示**：此后做函数大小比对时，对"复刻明显大于原始"的情形要先排查内联（本例 2.7 倍），
> 不要误判为缺陷；反过来"复刻明显小于原始"才是可疑信号。

### 2026-09-17：节区条目缓冲越界（已定论，修复待办）

**结论：这是复刻引入的缺陷，原始驱动没有此问题。**

证据链（三步，均为直接证据）：

1. **结构体大小确为 0x120 字节**：原始 `ReadPESectionEntry`(0x14008A54C) 与复刻实现
   (PEDecoder.c:133) 都是 `memset(..., 0, 0x120)` —— 两者一致。
2. **原始函数的缓冲更大**：原始 `ParseNtSectionsForModuleList1`(0x1400455E4) 栈帧 `sub rsp, 1C0h`，
   局部变量延伸到偏移 0x1c8；若缓冲仅有 0x120，栈帧不会有这么大 → 原始声明的缓冲约 0x1A8 字节。
   故原始在 `+0x1A0` 读取的是**自身缓冲未填充的尾部**（垃圾值，但不越界）。
3. **复刻声明过小**：复刻声明 `_DWORD SectionEntry[72]`（正好 0x120），同样在 `+0x1A0` 读取
   → **越过缓冲边界，读到相邻栈变量**。虽然两者拿到的都是无意义值，但复刻是真实越界读取。

**受影响位置（7 处，偏移 >= 0x120 即越界）**：

| 文件:行 | 访问偏移 | 代码 |
|---|---|---|
| PeSectionParse.c:73 | +0x1A0+6 | `WORD SectionType = *(WORD *)((char *)SectionEntry + 0x1A0 + 6);` |
| PeSectionParse.c:87 | +0x120 | `if (*(ULONG64 *)((char *)SectionEntry + 0x120) == 0x40000 &&` |
| PeSectionParse.c:138 | +0x1A0+6 | 同上（第二个函数） |
| PeSectionParse.c:152 | +0x120 | 同上（第二个函数） |
| ModuleMgmt.c:1471 | +0x1A0+6 | `WORD SectionFlags = *(WORD *)((char *)SectionEntry + 0x1A0 + 6);` |
| ModuleMgmt.c:1475 | +0x120 | `*(ULONG64 *)((char *)SectionEntry + 0x120) == 0x20 &&` |
| ModuleMgmt.c:1476 | +0x128 | `*(_DWORD *)((char *)SectionEntry + 0x128) == 2)` |

**修复方案**：把这三个函数里的节区条目缓冲声明从 `[72]`（0x120）扩大到至少 0x1A8 字节
（如 `_DWORD SectionEntry[106]`），以覆盖实际访问到的最大偏移 0x1A6+2。
扩大局部数组不影响其它行为，且更贴近原始函数的真实栈布局。

**✅ 已修复（2026-09-17）**：三处缓冲声明由 `[72]`（0x120）扩大为 `[112]`（0x1C0），
覆盖最大访问偏移 0x1A8：

| 文件:行 | 函数 | 改动 |
|---|---|---|
| PeSectionParse.c:59 | `ParseNtSectionsForModuleList1` | `[72]` → `[112]` |
| PeSectionParse.c:125 | `ParseNtSectionsForModuleList2` | `[72]` → `[112]` |
| ModuleMgmt.c:1455 | `ScanFileForPeSectionInfo` | `[72]` → `[112]` |

验证：编译 0 错误 0 警告；产物 494,592 字节；`grep -c "_DWORD SectionEntry\[112\]"` = 3，
其余 39 处 `[72]` 声明**未改动**（那些函数无越界访问）。

**关于保真度的说明**：原始驱动的缓冲究竟多大（0x1A8 还是同样 0x120）尚无定论。
若原始也是 0x120，则原始本身存在越界读，本次扩大属**有意偏离**——但两种情况下
`+0x1A0` 处读到的都是无意义值（未初始化内存），故行为性质不变，而本次改动**消除了真实的栈越界**。
此处优先内存安全。

**复现方法**：扫描规则为「`(char *)SectionEntry + 偏移` 形式，且 偏移 >= 0x120」。

> **⚠ 扫描方法的一个陷阱（务必注意）**：初次用「任意 `SectionEntry + 常量` 且按 ×4 换算」的宽模式扫描，
> 报出 107 处，**绝大多数是假阳性**——因为 `SectionEntry` 在多数上下文里是按字节寻址的指针
> （如 `*(ULONG64 *)(SectionEntry + 0x58)` 表示偏移 0x58，而非 0x58×4 = 0x160）。
> 判据是：`MemoryOps.c` 被误报的 `+0xF0` 恰是已验证的 `SizeOfRawData` 字段偏移，本就在 0x120 内。
> **只有施加在 `(char *)` 显式转换之后的偏移才按字节计**，据此复核后真实越界为 7 处（上表）。
> 另：`_DWORD SectionEntry[72]` 声明在全项目共出现 **43 处**（PeSectionParse/ModuleMgmt/SsdtHook/
> Minifilter），但仅上表 3 个函数存在越界访问——**不要为其它 40 处做无谓改动**。

### 2026-09-21（续二）：SendIoControlWithBufferSwap 实现完成（但尚无调用者）

实现要旨（与上一节的分析一致，补充实测细节）：

| 项目 | 结论 |
|---|---|
| 前半段语义 | 用反斜杠拼宽字符路径：搬入前缀 → 强制末宽字符 = 0x005C → 追加名字 → 补 0 宽字符 |

### 2026-09-21（续）：SendIoControlWithBufferSwap 分析结论（未实现，留给下一轮）

`SendIoControlWithBufferSwap`(0x1400731F4, 760 字节) 尚无任何声明与实现，
本轮已完成反汇编通读与结构还原，但因涉及 7 个子调用 + 2 个间接调用，
且需要换取内存/IOCTL 两层协作，留待单独一轮实现。已确定的结论：

**签名**（由寄存器用途与栈 home 槽位推出）：

```c
char SendIoControlWithBufferSwap(
    PVOID BufferDesc1,   // rcx：+0x04 = 长度(字节)，+0x08 = 源指针
    PVOID BufferDesc2,   // rdx：+0x0C = 长度(字节)，+0x10 = 源指针
    PVOID OutputBuffer,  // r8 ：输出缓冲区
    ULONG OutputSize);   // r9d：输出缓冲区大小（32 位，见 `mov [rax+20h], r9d`）
```

**功能（路径拼接，非"发送 IOCTL"字面含义）**：
把 `BufferDesc1` 的源数据 memmove 到输出缓冲区，**把其最后一个宽字符强制改写为
`0x005C`（反斜杠）**（`mov [rax+r12-2], cx`，cx = 0x5C），再追加 `BufferDesc2`
的源数据，并以一个 0 宽字符（`mov [rdx+rcx], bx`，bx = 0）结尾 ——
即"用反斜杠拼出完整宽字符路径"。容量校验为
`len2 + len1 + 2 < r9d`（不满足则直接返回 0）。

**关键局部结构**（基址 var_60 = rbp-0x09，相对偏移已换算）：

| 相对偏移 | 内容 | 证据 |
|---|---|---|
| -0x28 | UNICODE_STRING（Length/MaximumLength/Buffer） | `[var_88+2]=dx`、`[var_88]=dx`、`[var_80]=r12` |
| +0x00 | 交换内存句柄（传 &此 给 `SwapKernelMemoryPointer`） | `lea rcx,[var_60]`；事后 `*rdi = [var_60]` 写回 |
| +0x08 | OBJECT_ATTRIBUTES.Length = 0x30 | `mov [var_58], 30h` |
| +0x10 | OBJECT_ATTRIBUTES.ObjectName/Attributes = 0 | `mov [var_50], rbx` |
| +0x18 | OBJECT_ATTRIBUTES.SecurityDescriptor = &UNICODE_STRING | `mov [var_48], rax`（rax = &var_88） |
| +0x20 | SecurityQualityOfService = 0x240 | `mov [var_40], 240h` |
| +0x28 | 16 字节清零（SecurityQualityOfService+…） | `movdqu [var_38], xmm0`（xmm0 已 xorps 清零） |

**GT 索引**：0x184、0x41C6、0x4223、0x17C、0x4334、0x179、0x197（全部要求非 0，
否则直接返回）；结果经 `GtRead(0x914)` 按构建号 0x1DB0 分岔：
低于则 `call r14`（间接调用，来自 GT 0x41C6），否则 `SendDeviceIoControlWithRetry`。

**子调用顺序**：`SwapKernelMemoryPointer` → `DispatchIoControlForServer2022`(0x20019)
→ [构建号分岔] `SendDeviceIoControlWithRetry` 或间接调用 →
`DispatchIoControlByBuildNumber` → `DispatchHookSwapByVersion`(×2，用于取/还回调)
→ `AllocBufferAndQuerySystemInfo` → 结果判定
（`[r12+0x14] != 0` 时置返回 1）。

**下一步落点**：`inc/XPCHunterDrv.h` 中 `DispatchIoControlForServer2022` 与
`AllocBufferAndQuerySystemInfo` 的签名是多行形式，需先逐一核对调用约定
（参数个数、`__fastcall`、结构体指针类型），再落笔实现。

且低 32 位截断往返一致），随后 `InitPESectionReadContext` + 循环解码节区描述符；
差别只在「基准值取哪个 GT 索引」「识别哪些类型码」「结果写哪个 GT 索引」「循环上限」。

验证：编译 0 错误 0 警告；产物 495,104 字节（未变，该支路待 `InitImageNotify` 枢纽激活）。

### 2026-09-21：PE 解码上下文越界 + 读指针语义错误（根因已修，调用点尺寸待批量修）

**背景**：为还原 `ParseNtKernelDataSectionsV2`(0x1400137BC) 而逐条阅读其反汇编时，
发现其"累计大小"变量与 PE 解码上下文重叠，顺藤摸瓜查出复刻的 PE 解码器
（`framework/PEDecoder.c`）存在两个相互纠缠的缺陷。

#### 缺陷 1：`DEC_CTX_*` 宏集被同时用于两个不同结构

`InitPESectionReadContext`(0x14008A7E4, 95 字节) 的**全部 10 处写入偏移**
（反汇编直接读出，逐条对应，无推断成分）：

| 原始指令 | 偏移 | 含义 |
|---|---|---|
| `mov [r10+8], rcx` | +0x08 | Base（**读指针初值**） |
| `mov [r10+18h], r8d` | +0x18 | Mode |
| `mov [r10+10h], rax` | +0x10 | Base + (int)Size（结束边界；rax = `movsxd edx` + rcx） |
| `mov [r10+1Ch], r8d` | +0x1C | Mode 副本 |
| `mov [r10+40h], eax` | +0x40 | 第 5 参数 ExtraField |
| `mov [r10+28h], r9` | +0x28 | 第 4 参数 |
| `mov [r10+30h], rax` | +0x30 | 第 6 参数 |
| `mov [r10+38h], rax` | +0x38 | 第 7 参数 |
| `Mode==2 ? [r10+20h]=1 : [r10+20h]=r8d` | +0x20 | 地址大小 |
| `mov [r10], rax` | +0x00 | 解码表指针（Mode==2 → 0x140097E50，否则 0x140096A50） |

`ReadPESectionEntry`(0x14008A54C) 对**上下文**的访问并集为
`0x00/0x08/0x10/0x18/0x1C/0x20/0x28/0x30/0x38/0x40` —— **与上表完全一致**，
故上下文共 **0x48 字节**。

而复刻把这套 `DEC_CTX_*` 宏**同时**当作 0x120 字节指令描述符的偏移用，
于是 `InitPESectionReadContext` 把后 4 个参数写到了
`0xDC/0xF0/0xF8/0x100`（描述符的布局），`ReadPESectionEntry` 又从这些偏移读回来。

**后果**：上下文在调用点只声明为 `__int64`（8 字节），
每次 `InitPESectionReadContext` 都写坏调用者栈上约 0x100 字节；
`ReadPESectionEntry` 则从上下文 0xF0 之外越界读。

#### 缺陷 2（更隐蔽）："+0x08 是读指针"，不是累计大小

四步直接证据：

1. `InitPESectionReadContext` 把第 1 个参数（Base）写入 `+0x08`，把 Base+Size 写入 `+0x10`。
2. `ReadPESectionEntry` 对上下文**只读** —— 反汇编中 14 处 `[rdi+..]` 访问全部是读，
   无一处写入；它以 `[rdi+8]` 为操作码指针、以 `[rdi+10h]` 为结束边界。
3. 因此**推进读指针的责任在调用方**：三个扫描函数（V1/V2/V3）里那句
   `累计变量 += *(DWORD*)(条目+0xF0)` 改写的正是 `+0x08`。
   帧布局可证：上下文起始于 `rsp+0x50`，该变量位于 `rsp+0x58`（= 上下文+8），
   条目缓冲区起点为 `rsp+0xA0`（= 上下文 0x48 字节之后按 16 字节对齐），
   两者之间没有第三个变量可容纳它；V1(0x140062884)/V2(0x1400130C4)/V3(0x1400132EC)
   三个函数的帧布局完全一致（分别用 var_1A8、var_198 表示该槽位）。
4. 独立佐证：复刻自身的 `ReadPESectionEntry((PUCHAR)&CumulativeSize, ...)`
   共出现 5 处（SsdtHook/PeParse）—— 复刻代码已把 `CumulativeSize` 当上下文传入。

**结论**：该变量是上下文的读指针（初值 = Base），不是从 0 开始的累计长度。
复刻把它初始化为 0 是错的，会改变命中时计算出的候选值
（`候选值 = 条目[0x38] - 文件缓冲基址 + 读指针`）。

#### 本次已修（可完全验证部分）

| 位置 | 改动 | 验证依据 |
|---|---|---|
| `InitPESectionReadContext` | 10 处写入偏移全部按上表改正（原 4 处错位） | 反汇编逐条对应 |
| `ReadPESectionEntry` 描述符初始拷贝 | 越界的 3 处**读取源**由 `+0xDC/+0xF0/+0xF8` 改为 `+0x40/+0x28/+0x30` | 上下文只有 0x48 字节 |
| `ReadPESectionEntry` 的 `ResultBase` | 2 处 `CTX_Q(Context, DEC_CTX_PARAM5)`(读 +0xF0) 改为 `CTX_OFF_PARAM4`(+0x28) | 原始为 `[rdi+28h] + [rdi+8]` |
| 头文件 | 新增 `PE_DECODE_CONTEXT` 类型（0x48 字节）与 `CTX_OFF_*` 偏移宏 | 上表 |
| 新增常量 | `CTX_OFF_*` 一组（上下文专用），与描述符用的 `DEC_CTX_*` 分开 | —— |
| 4 个扫描函数的累计变量 | `FindKernelDataSectionV2` / `ParseMiniFilterDataSection` / `FindKernelDataSectionByDebug` / `ParseNtKernelDataSectionsV2`：删除独立的 `CumulativeSize`，改为 `ReadContext.ReadPtr += 描述符[0xF0]`，候选值公式改用 `(unsigned int)ReadContext.ReadPtr` | 上下文改为 `PE_DECODE_CONTEXT`（0x48 字节），不再越界 |

**6 个函数的一致验证**：对 V1(0x140062884)、V2(0x1400130C4)、V3(0x1400132EC)、
`ParseNtKernelDataSectionsV2`(0x1400137BC)、`ParseMiniFilterDataSection`(0x140014ACC)、
`FindKernelDataSectionByDebug`(0x140013E6C) 逐个核对帧布局，累计变量的地址一律等于
「上下文起始 + 8」（分别表现为 `var_1A8`=ctx+8、`var_198`=ctx+8、`var_188`=ctx+8），
**六个函数无一例外**。

> **为什么两种解释都得到同一结论**：`InitPESectionReadContext` 把 Base 写入 +0x08，
> 若调用方源码里那个"独立变量"恰好也分配在 +0x08（原始帧布局确实如此），
> 则调用方先执行的 `= 0` 会被随后的初始化函数覆盖 —— 无论源码意图是
> 「上下文的读指针」还是「独立的累计长度」，**该槽位在循环首次使用时的有效初值都是 Base**。
> 故本修正对两种解释都成立。

验证：编译 0 错误 0 警告；产物仍为 495,104 字节（该支路尚未被枢纽激活）。

## 4. 已确认的功能性缺陷（由上述缺口导致）

### 4.1 驱动卸载路径被优化成死循环

`DriverUnload` 对 5 个 minifilter 函数返回值做 AND 判断；原始驱动中成功返回非零则继续清理。
复刻中 `MiniFilterFormatFileNameWithPath()` 返回 0、`MiniFilterActiveRoutine()` 返回 `STATUS_SUCCESS`(0)，
MSVC/LTCG 常量折叠后**整段清理代码被判为不可达并删除**。产物反汇编（0x14000c780）显示无条件
`jmp` 回到 `KeDelayExecutionThread`，无出口。

可验证证据：产物二进制中**不含** `IoDeleteSymbolicLink`、`ZwSetValueKey` 字符串。
后果：驱动加载后无法卸载，且永不删除设备对象/符号链接、不释放缓冲区。

### 4.2 Minifilter 从未注册

复刻产物的导入表中**没有任何 FltMgr 函数**（原始导入 8 个：`FltRegisterFilter`、`FltStartFiltering`、
`FltCreateFile`、`FltGetFileNameInformation` 等）。源码中名为 `InitMiniFilterDriver` 的函数
实际是 minifilter **枚举例程**，不调用 `FltRegisterFilter`。
后果：文件系统监控功能整体不可用。

### 4.3 `InitKernelMemoryContext` 函数名与地址错配（新发现）

- IDA：`InitKernelMemoryContext` = **0x14006BF2C**（768 字节，调用 29 个子函数）
- IDA：`ReadObjectTypeOffset` = **0x14006EAF0**（48 字节）
- 复刻源码 `DriverEntry.c:733` 的 `InitKernelMemoryContext` 注释写「对应原始驱动 sub_14006EAF0」
  且自述「实际为 ReadObjectTypeOffset 的别名」——**即复刻实现了 48 字节的 `ReadObjectTypeOffset`，
  却挂上了 `InitKernelMemoryContext` 的名字**。

后果：真正的 768 字节编排函数未实现，其下 26 个 WFP/KFD/NSI（网络过滤驱动）扫描与导出查找函数
（`ScanKfdDriverSectionV2/V3`、`ScanWfp*Sections`、`ScanNsi*Section`、`FindKfd*/FindWfp*/FindNsi*` 等，
合计 9,958 字节）全部无法到达。

> 这类「名字对、地址错」的缺陷无法被按名审计发现，本报告通过 §1-⑦ 的映射校验定位。

### 4.4 缺失的原始导入（13 个）

| 缺失导入 | 影响 |
|---|---|
| `FltRegisterFilter` 等 8 个 FltMgr 函数 | minifilter 未注册（见 4.2） |
| `IoDeleteSymbolicLink` | 卸载不清理（见 4.1） |
| `ZwSetValueKey` | minifilter 实例注册表项未写入 |
| `ExGetPreviousMode` | IRP 分发的请求者模式校验缺失（安全相关） |
| `__C_specific_handler` | 原始用 SEH 做安全探测，复刻无 |
| `NtBuildNumber` | 复刻改用 `RtlGetVersion`（功能可接受，属实现偏离） |

复刻新增导入 7 个：`PsSetLoadImageNotifyRoutine`、`RtlGetVersion`、`ZwCreateFile`、`__chkstk`、`_vsnwprintf`、`strncmp`、`strstr`。

### 4.5 分析文档 §4 的导入表描述与实物不符

`docs/reversing/View++_Driver64_逆向分析报告.md` §4 声称原始驱动导入
`CmRegisterCallback`、`CmRegisterCallbackEx`、`CmUnRegisterCallback`、`ObRegisterCallbacks`、
`ObUnRegisterCallbacks`、`PsSetCreateProcessNotifyRoutine(Ex)`、`PsSetCreateThreadNotifyRoutine`、
`PsSetLoadImageNotifyRoutine`——**经核对原始导入表，这些 API 一个都不存在**
（PCHunter 是直接操作通知数组，不调用注册 API）。该节内容需要修正。

## 5. 不确定性与局限

1. **D2 类 25 个函数（11,507 字节）尚未定性**，最坏情况下确定缺口会扩大到 11.0%。需逐个反编译核对。
2. 指纹匹配对「同族 PE 扫描器」区分度有限（它们共享 `InitPESectionReadContext` + `ReadPESectionEntry` 调用形态），
   C 类判定采用保守阈值，可能存在少量漏判为 D2。
3. 本审计只比对**函数级**的对应关系与调用图，不校验逐行算法等价性。即使函数存在且规模相当，
   内部逻辑仍可能有差异（已知 4 处签名缺陷是在此前编译警告清零时通过 IDA 复核发现的）。
4. 未做运行时验证（内存中加载、IOCTL 行为、卸载流程），仓库内亦无此类测试记录。

## 6. 建议修复优先级

**P0 — 恢复运行时正确性**
1. 补 `MiniFilterFormatFileNameWithPath` 等卸载链上的函数 + `MiniFilterActiveRoutine`，消除卸载死循环，
   恢复 `IoDeleteSymbolicLink`/`ZwSetValueKey` 导入
2. 补 minifilter 注册链（`FltRegisterFilter`/`FltStartFiltering`）+ 5 个 Pre 回调（557/1908/1257/1231/509 字节）
3. 修正 `InitKernelMemoryContext` 错配，补齐其 26 个子函数（WFP/KFD/NSI 子系统）

**P1 — 大函数占位**
`SendIrpToDiskDevice`(1519B)、`ParseNtRelocSection`(1190B)、`EnumProcessHandleInfo`(1021B)、

**P2 — 小函数与安全项**
`CheckProcessAccess`、`InitCallbackFunctions`、`InitThreadCallback`、`MiniFilterQueryIdleRoutine`；
补 `ExGetPreviousMode` 请求者模式校验与 SEH 保护

**P3 — 收尾**
D2 类 25 个函数逐个定性；修正分析报告 §4；完成 IDA 侧参数/局部变量重命名；
