### 2026-10-08：Crypto 模块整批缺陷修正（已完成并验证）

**触发**：审计 `Sha1Transform`（L5-0 首个待验证项）时发现原始 SHA1 与复刻不一致，
顺藤摸瓜查出整个 Crypto.c 存在 7 处结构性缺陷。

**缺陷清单与证据**

| # | 位置 | 缺陷 | 证据 |
|---|------|------|------|
| 1 | `Md5_S[64]` | 构造为 `[S11..S14,S21..S24,S31..S34,S41..S44]×4`，**48 处与标准 MD5 不符** | 原始 `Md5Transform`(0x140003168)/`Md5Transform2`(0x140059CEC) 均为完全展开的 64 步（各 2077B，无位移表）。用 IDA 指令查询提取 64 条循环移位立即数：44 处 `rol` + 20 处 `ror`（ror 15→17, 10→22, 12→20, 11→21, 9→23），还原后为 7,12,17,22 / 5,9,14,20 / 4,11,16,23 / 6,10,15,21 —— 即标准 MD5 |
| 2 | `MD5_CONTEXT` | 误写为 `State@0x00/Count[2]@0x10/Buffer@0x18`，**与实物完全不符** | `InitMd5Context`(0x140059CB4) memset 0x58 且 State 写 +0x00；`Md5Update`(0x14005A50C) 计数在 +0x50、缓冲从 +0x10 起、`Md5Transform2(State=+0x00, Block=+0x10)`；`Md5Final`(0x140059C14) 长度尾写 +0x48/+0x4C。**真布局：State@0x00, Buffer@0x10, Count(字节)@0x50** |
| 3 | 族 1 MD5 被别名 | `Md5Init/Md5Update2/Md5Final2` 被实现为族 2 的别名，但两族布局不同 | `Md5Init`(0x140003A28) State 写 +0x48；`Md5Update2`(0x140003A60) 计数在 +0x00、缓冲从 +0x08 起、`Md5Transform(State=+0x48)`；`Md5Final2`(0x140003988) 长度尾写 +0x40/+0x44。**族 1 布局：Count@0x00, Buffer@0x08, State@0x48**，与族 2 恰好错位 |
| 4 | MD5 计数语义 | 套用 RFC1321 的 `Count[0] += Length<<3` 位计数 + 双字进位 | 原始 `Md5Update` 只有一条 `add [rcx+50h], edx`（按**字节**直接累加单个 64 位量），无 <<3、无拆分 |
| 5 | `SHA1_CONTEXT` | 误写为 `State[5]@0x00/Count[2]@0x14/Buffer@0x1C`，**State 与计数整体错位 8 字节** | `Sha1InitContext`(0x140076500) memset 0x60 且 State 写 +0x08..+0x18；`Sha1Update`(0x14007761C) 计数为**单个 64 位位计数**在 +0x00（`mov r11,[rcx]`/`add [rcx],Length<<3`）、缓冲从 +0x1C 起。**真布局：Count(64 位)@0x00, State@0x08, Buffer@0x1C，共 0x60** |
| 6 | `Sha1Transform` | 引入了原始驱动**不存在**的输入字节交换 `RtlUlongByteSwap(((PULONG)Buffer)[i])` | 对整个 `.text` 扫描 `bswap`（0F C8..CF）仅 4 处，全部在其他函数（`ByteSwap64`/`InitSyscallNumberTable`×2/`HookSyscallNtOpenKey`）；`Sha1Transform` 4314 字节内 bswap=0、movbe=0、xchg=0。入口仅把 0x40 字节 memmove 到栈槽（0x140076578）后按小端原样参与运算 |
| 7 | `InitGtKey`(DriverEntry.c) | `ULONG ShaContext[12]` 仅 0x30 字节，**不足原始 0x60**，上下文溢出覆盖相邻缓冲 | 原始 `sub_140029F0C` 序言 `sub rsp,184h`，SHA1 上下文槽 var_88 为 `_QWORD[12]`=0x60，摘要槽 var_28 为 0x18 |

**SHA1 字节序定案（重要）**

原始驱动的 SHA1 是**非标准变体**：输入不交换、输出交换
（出口 0x1400764AC 起对每个 State 做 `shr edx,8` 逐字节大端展开）。
这一结论经过三重独立证据：
1. 全镜像 `bswap` 扫描 —— 哈希函数内为 0；
2. `Sha1Transform` 入口 memmove + 原样 `mov r14d,[rbp+57h+var_68]` 参与首轮运算；
3. 离线 harness 对照 4 组 RFC1321 标准向量 —— 无论输入是否交换，
   该结构都**不等于**标准 SHA1 值（输入交换变体亦 ≠ 标准，因输出端另有交换）。

驱动内部（建表/查表 `Sha1HashToDword`、密钥派生 `InitGtKey`）自洽，故保留
"不交换输入"才是对实物的 1:1 复刻；先前"能算出标准 SHA1 值"的写法反而是失真。

**修正内容**

- `XPCHunterDrv/inc/xpc_structs.h`：重写 `MD5_CONTEXT`（族 2）、新增
  `MD5_CONTEXT_LEGACY`（族 1）、重写 `SHA1_CONTEXT`，均附逐条反汇编依据。
- `XPCHunterDrv/src/framework/Crypto.c`：重写 `Md5_S`、`Md5Transform`（改用 `Md5_Id` 索引）、
  两族共 6 个包装函数（`InitMd5Context/Md5Update/Md5Final` 与 `Md5Init/Md5Update2/Md5Final2`
  各自独立实现，不再互相别名）、`Sha1InitContext`、`Sha1Transform`（去掉输入交换）、
  `Sha1Update`（单 64 位位计数）、`Sha1FinalTransform`（按 64 位位计数取字节）、
  `Sha1HashToDword`、`DecryptAesHexString`（改用族 1 三件套，与原始调用目标一致）；
  删除失效的 `ByteReverse` 与重复的 `Md5Init`。
- `XPCHunterDrv/inc/XPCHunterDrv.h`：`Md5Final2/Md5Update2/Md5Init` 签名改用
  `PMD5_CONTEXT_LEGACY`。
- `XPCHunterDrv/src/DriverEntry.c`：`InitGtKey` 改用 `SHA1_CONTEXT ShaContext;`（0x60）。

**验证**

### 2026-10-08（续二）：InitProcessNotify 重写（L5-0 第 2 项，已完成并验证）

**触发**：L5-0 第 2 项，复核 `InitProcessNotify`（2369 字节 / 501 条指令）。

**发现的实质缺陷**：原实现只是一个"遍历驱动链表比对单个类型码 0x14"的空架子，
与实物差距极大 —— 实物是**按 6 种类型码分派、共 23 条驱动名比对**的模块识别器。

**实物算法（逐条转写自 0x14001EFA0~0x14001F8E0）**

- 取 GT 条目 1 → `+0x28` 为环形链表头 → `+0x00` 取首节点，遍历至回到表头；
- 每节点：名字指针 `+0x60`、基址字段 `+0x50`（任一为 0 则跳过）、类型码 `+0x58`；
- 比较函数 `StringCompare3Way @0x14007DA0C`（**大小写不敏感**：
  把 a-z 减 0x20 后比较，返回 0 即相等）；
- **比较长度恰为 `Type >> 1`**：首分支用即时数（等价 Type>>1），
  其余分支用 `movzx r8d,[rbx+58h]; shr r8d,1` 动态取；
- 命中写 (基址 = `node+0x30`, 大小 = `*(ULONG*)(node+0x40)`) 到一对 GT。

### 2026-09-17：节区条目缓冲越界（已定论，修复待办）

**结论：这是复刻引入的缺陷，原始驱动没有此问题。**

证据链（三步，均为直接证据）：

1. **结构体大小确为 0x120 字节**：原始 `ReadPESectionEntry`(0x14008A54C) 与复刻实现
   (PEDecoder.c:133) 都是 `memset(..., 0, 0x120)` —— 两者一致。
2. **原始函数的缓冲更大**：原始 `ParseNtSectionsForModuleList1`(0x1400455E4) 栈帧 `sub rsp, 1C0h`，
   局部变量延伸到偏移 0x1c8；若缓冲仅有 0x120，栈帧不会有这么大 → 原始声明的缓冲约 0x1A8 字节。
   故原始在 `+0x1A0` 读取的是**自身缓冲未填充的尾部**（垃圾值，但不越界）。
3. **复刻声明过小**：复刻声明 `_DWORD SectionEntry[72]`（正好 0x120），同样在 `+0x1A0` 读取
   → **越过缓冲边界，读到相邻栈变量**。虽然两者拿到的都是无意义值，但复刻是真实越界读取。

**受影响位置（7 处，偏移 >= 0x120 即越界）**：

| PeSectionParse.c:73 | +0x1A0+6 | `WORD SectionType = *(WORD *)((char *)SectionEntry + 0x1A0 + 6);` |
| PeSectionParse.c:87 | +0x120 | `if (*(ULONG64 *)((char *)SectionEntry + 0x120) == 0x40000 &&` |
| PeSectionParse.c:138 | +0x1A0+6 | 同上（第二个函数） |
| PeSectionParse.c:152 | +0x120 | 同上（第二个函数） |

### 2026-09-21（续九）：SendIoControlWithQuotaBuffer 原型冲突定案（错位一格，无活缺陷）

对续八登记的"原型冲突"做了核对，结论比原先判断更明确，**同时修正我上一轮的一处过度担心**：

**证据二：IDA 的栈槽名称揭示了被调用方的真实形参顺序。**

```
(HandlerFunc, Arg2, Arg3, Arg4, Dst, NumberOfBytes, …)
```

所以该函数**作为独立单元能正常工作**，但与原始真实签名不一致 —— 属**保真度缺陷**，

然后同时修正头文件声明、函数体与调用点（本轮新增的那处调用已按实测 ABI 布局，
修正后可去掉强制转换）。

**结论修正**：判据 A 只能证明"**名称归属错误**"，**不能**证明"逻辑缺失"。
复刻中一个函数可以承载另一个原始函数的函数体 —— 这正是本类 13 项的成因。

| 判定 | 依据强度 | 明细 |
|---|---|---|
| **确认为缺口** | 函数体级证据 | `SendReadMemoryIoControl`(866B)：原始函数体两次调用 `SendIoControlWithBufferSwap`，而复刻中该函数**无任何调用者**（未进 map） |

4. 若调用方体内已有等价逻辑（可能内联、可能改名）→ 非缺口，只需修正名称归属。

### 2026-09-21（续二）：SendIoControlWithBufferSwap 实现完成（但尚无调用者）

实现要旨（与上一节的分析一致，补充实测细节）：

| 项目 | 结论 |
|---|---|
| 前半段语义 | 用反斜杠拼宽字符路径：搬入前缀 → 强制末宽字符 = 0x005C → 追加名字 → 补 0 宽字符 |

| 返回值 | `char`，结果 = (输出缓冲 +0x14 处的 DWORD > 0) |

### 2026-09-21（续）：SendIoControlWithBufferSwap 分析结论（未实现，留给下一轮）

`SendIoControlWithBufferSwap`(0x1400731F4, 760 字节) 尚无任何声明与实现，
本轮已完成反汇编通读与结构还原，但因涉及 7 个子调用 + 2 个间接调用，
且需要换取内存/IOCTL 两层协作，留待单独一轮实现。已确定的结论：

**签名**（由寄存器用途与栈 home 槽位推出）：

```c
char SendIoControlWithBufferSwap(
    PVOID BufferDesc1,   // rcx：+0x04 = 长度(字节)，+0x08 = 源指针
    PVOID BufferDesc2,   // rdx：+0x0C = 长度(字节)，+0x10 = 源指针
    PVOID OutputBuffer,  // r8 ：输出缓冲区
    ULONG OutputSize);   // r9d：输出缓冲区大小（32 位，见 `mov [rax+20h], r9d`）
```

**功能（路径拼接，非"发送 IOCTL"字面含义）**：
把 `BufferDesc1` 的源数据 memmove 到输出缓冲区，**把其最后一个宽字符强制改写为
`0x005C`（反斜杠）**（`mov [rax+r12-2], cx`，cx = 0x5C），再追加 `BufferDesc2`
的源数据，并以一个 0 宽字符（`mov [rdx+rcx], bx`，bx = 0）结尾 ——
即"用反斜杠拼出完整宽字符路径"。容量校验为
`len2 + len1 + 2 < r9d`（不满足则直接返回 0）。

**关键局部结构**（基址 var_60 = rbp-0x09，相对偏移已换算）：

| 相对偏移 | 内容 | 证据 |
|---|---|---|
| -0x28 | UNICODE_STRING（Length/MaximumLength/Buffer） | `[var_88+2]=dx`、`[var_88]=dx`、`[var_80]=r12` |
| +0x00 | 交换内存句柄（传 &此 给 `SwapKernelMemoryPointer`） | `lea rcx,[var_60]`；事后 `*rdi = [var_60]` 写回 |
| +0x08 | OBJECT_ATTRIBUTES.Length = 0x30 | `mov [var_58], 30h` |
| +0x10 | OBJECT_ATTRIBUTES.ObjectName/Attributes = 0 | `mov [var_50], rbx` |
| +0x18 | OBJECT_ATTRIBUTES.SecurityDescriptor = &UNICODE_STRING | `mov [var_48], rax`（rax = &var_88） |
| +0x20 | SecurityQualityOfService = 0x240 | `mov [var_40], 240h` |
| +0x28 | 16 字节清零（SecurityQualityOfService+…） | `movdqu [var_38], xmm0`（xmm0 已 xorps 清零） |

**GT 索引**：0x184、0x41C6、0x4223、0x17C、0x4334、0x179、0x197（全部要求非 0，
否则直接返回）；结果经 `GtRead(0x914)` 按构建号 0x1DB0 分岔：
低于则 `call r14`（间接调用，来自 GT 0x41C6），否则 `SendDeviceIoControlWithRetry`。

**子调用顺序**：`SwapKernelMemoryPointer` → `DispatchIoControlForServer2022`(0x20019)
→ [构建号分岔] `SendDeviceIoControlWithRetry` 或间接调用 →
`DispatchIoControlByBuildNumber` → `DispatchHookSwapByVersion`(×2，用于取/还回调)
→ `AllocBufferAndQuerySystemInfo` → 结果判定
（`[r12+0x14] != 0` 时置返回 1）。

**下一步落点**：`inc/XPCHunterDrv.h` 中 `DispatchIoControlForServer2022` 与
`AllocBufferAndQuerySystemInfo` 的签名是多行形式，需先逐一核对调用约定
（参数个数、`__fastcall`、结构体指针类型），再落笔实现。

（Minifilter.c:297，签名 `NTSTATUS(PFLT_CALLBACK_DATA, PCFLT_RELATED_OBJECTS, PVOID*)`）
冲突 —— 0x140014078 无参数（不从 rcx/rdx/r8/r9 读值），而 FLT PreCreate 回调必须有 3 个参数。
其真实功能与本家族其它成员相同（PE 节区扫描）。故复刻中改名为 `FindKernelDataSectionV4`。
**审计清单里的「MiniFilterPreCreate(557B)」= `FindKernelDataSectionV4`。**

家族共性（7 个函数一致，已交叉验证）：都取 GT 0x20(文件缓冲基址) / 0x21(文件大小) /
0x3(镜像基址) 并做同一种自洽校验（基准值须落在 (镜像基址, 镜像基址+文件大小) 内，
且低 32 位截断往返一致），随后 `InitPESectionReadContext` + 循环解码节区描述符；
差别只在「基准值取哪个 GT 索引」「识别哪些类型码」「结果写哪个 GT 索引」「循环上限」。

验证：编译 0 错误 0 警告；产物 495,104 字节（未变，该支路待 `InitImageNotify` 枢纽激活）。

### 2026-09-21：PE 解码上下文越界 + 读指针语义错误（根因已修，调用点尺寸待批量修）

**背景**：为还原 `ParseNtKernelDataSectionsV2`(0x1400137BC) 而逐条阅读其反汇编时，
发现其"累计大小"变量与 PE 解码上下文重叠，顺藤摸瓜查出复刻的 PE 解码器
（`framework/PEDecoder.c`）存在两个相互纠缠的缺陷。

#### 缺陷 1：`DEC_CTX_*` 宏集被同时用于两个不同结构

`InitPESectionReadContext`(0x14008A7E4, 95 字节) 的**全部 10 处写入偏移**
（反汇编直接读出，逐条对应，无推断成分）：

| 原始指令 | 偏移 | 含义 |
|---|---|---|
| `mov [r10+8], rcx` | +0x08 | Base（**读指针初值**） |
| `mov [r10+18h], r8d` | +0x18 | Mode |
| `mov [r10+10h], rax` | +0x10 | Base + (int)Size（结束边界；rax = `movsxd edx` + rcx） |
| `mov [r10+1Ch], r8d` | +0x1C | Mode 副本 |
| `mov [r10+40h], eax` | +0x40 | 第 5 参数 ExtraField |
| `mov [r10+28h], r9` | +0x28 | 第 4 参数 |
| `mov [r10+30h], rax` | +0x30 | 第 6 参数 |
| `mov [r10+38h], rax` | +0x38 | 第 7 参数 |
| `Mode==2 ? [r10+20h]=1 : [r10+20h]=r8d` | +0x20 | 地址大小 |
| `mov [r10], rax` | +0x00 | 解码表指针（Mode==2 → 0x140097E50，否则 0x140096A50） |

`ReadPESectionEntry`(0x14008A54C) 对**上下文**的访问并集为
`0x00/0x08/0x10/0x18/0x1C/0x20/0x28/0x30/0x38/0x40` —— **与上表完全一致**，
故上下文共 **0x48 字节**。

而复刻把这套 `DEC_CTX_*` 宏**同时**当作 0x120 字节指令描述符的偏移用，
于是 `InitPESectionReadContext` 把后 4 个参数写到了
`0xDC/0xF0/0xF8/0x100`（描述符的布局），`ReadPESectionEntry` 又从这些偏移读回来。

**后果**：上下文在调用点只声明为 `__int64`（8 字节），
每次 `InitPESectionReadContext` 都写坏调用者栈上约 0x100 字节；
`ReadPESectionEntry` 则从上下文 0xF0 之外越界读。

#### 缺陷 2（更隐蔽）："+0x08 是读指针"，不是累计大小

四步直接证据：

1. `InitPESectionReadContext` 把第 1 个参数（Base）写入 `+0x08`，把 Base+Size 写入 `+0x10`。
2. `ReadPESectionEntry` 对上下文**只读** —— 反汇编中 14 处 `[rdi+..]` 访问全部是读，
   无一处写入；它以 `[rdi+8]` 为操作码指针、以 `[rdi+10h]` 为结束边界。
3. 因此**推进读指针的责任在调用方**：三个扫描函数（V1/V2/V3）里那句
   `累计变量 += *(DWORD*)(条目+0xF0)` 改写的正是 `+0x08`。
   帧布局可证：上下文起始于 `rsp+0x50`，该变量位于 `rsp+0x58`（= 上下文+8），
   条目缓冲区起点为 `rsp+0xA0`（= 上下文 0x48 字节之后按 16 字节对齐），
   两者之间没有第三个变量可容纳它；V1(0x140062884)/V2(0x1400130C4)/V3(0x1400132EC)
   三个函数的帧布局完全一致（分别用 var_1A8、var_198 表示该槽位）。
4. 独立佐证：复刻自身的 `ReadPESectionEntry((PUCHAR)&CumulativeSize, ...)`
   共出现 5 处（SsdtHook/PeParse）—— 复刻代码已把 `CumulativeSize` 当上下文传入。

**结论**：该变量是上下文的读指针（初值 = Base），不是从 0 开始的累计长度。
复刻把它初始化为 0 是错的，会改变命中时计算出的候选值
（`候选值 = 条目[0x38] - 文件缓冲基址 + 读指针`）。

#### 本次已修（可完全验证部分）

| 位置 | 改动 | 验证依据 |
|---|---|---|
| `InitPESectionReadContext` | 10 处写入偏移全部按上表改正（原 4 处错位） | 反汇编逐条对应 |
| `ReadPESectionEntry` 描述符初始拷贝 | 越界的 3 处**读取源**由 `+0xDC/+0xF0/+0xF8` 改为 `+0x40/+0x28/+0x30` | 上下文只有 0x48 字节 |
| `ReadPESectionEntry` 的 `ResultBase` | 2 处 `CTX_Q(Context, DEC_CTX_PARAM5)`(读 +0xF0) 改为 `CTX_OFF_PARAM4`(+0x28) | 原始为 `[rdi+28h] + [rdi+8]` |
| 头文件 | 新增 `PE_DECODE_CONTEXT` 类型（0x48 字节）与 `CTX_OFF_*` 偏移宏 | 上表 |
| 新增常量 | `CTX_OFF_*` 一组（上下文专用），与描述符用的 `DEC_CTX_*` 分开 | —— |
| 4 个扫描函数的累计变量 | `FindKernelDataSectionV2` / `ParseMiniFilterDataSection` / `FindKernelDataSectionByDebug` / `ParseNtKernelDataSectionsV2`：删除独立的 `CumulativeSize`，改为 `ReadContext.ReadPtr += 描述符[0xF0]`，候选值公式改用 `(unsigned int)ReadContext.ReadPtr` | 上下文改为 `PE_DECODE_CONTEXT`（0x48 字节），不再越界 |

**6 个函数的一致验证**：对 V1(0x140062884)、V2(0x1400130C4)、V3(0x1400132EC)、
`ParseNtKernelDataSectionsV2`(0x1400137BC)、`ParseMiniFilterDataSection`(0x140014ACC)、
`FindKernelDataSectionByDebug`(0x140013E6C) 逐个核对帧布局，累计变量的地址一律等于
「上下文起始 + 8」（分别表现为 `var_1A8`=ctx+8、`var_198`=ctx+8、`var_188`=ctx+8），
**六个函数无一例外**。

> **为什么两种解释都得到同一结论**：`InitPESectionReadContext` 把 Base 写入 +0x08，
> 若调用方源码里那个"独立变量"恰好也分配在 +0x08（原始帧布局确实如此），
> 则调用方先执行的 `= 0` 会被随后的初始化函数覆盖 —— 无论源码意图是
> 「上下文的读指针」还是「独立的累计长度」，**该槽位在循环首次使用时的有效初值都是 Base**。
> 故本修正对两种解释都成立。

验证：编译 0 错误 0 警告；产物仍为 495,104 字节（该支路尚未被枢纽激活）。

## 4. 已确认的功能性缺陷（由上述缺口导致）

### 4.1 驱动卸载路径被优化成死循环

`DriverUnload` 对 5 个 minifilter 函数返回值做 AND 判断；原始驱动中成功返回非零则继续清理。
复刻中 `MiniFilterFormatFileNameWithPath()` 返回 0、`MiniFilterActiveRoutine()` 返回 `STATUS_SUCCESS`(0)，
MSVC/LTCG 常量折叠后**整段清理代码被判为不可达并删除**。产物反汇编（0x14000c780）显示无条件
`jmp` 回到 `KeDelayExecutionThread`，无出口。

可验证证据：产物二进制中**不含** `IoDeleteSymbolicLink`、`ZwSetValueKey` 字符串。
后果：驱动加载后无法卸载，且永不删除设备对象/符号链接、不释放缓冲区。

### 4.2 Minifilter 从未注册

复刻产物的导入表中**没有任何 FltMgr 函数**（原始导入 8 个：`FltRegisterFilter`、`FltStartFiltering`、
`FltCreateFile`、`FltGetFileNameInformation` 等）。源码中名为 `InitMiniFilterDriver` 的函数
实际是 minifilter **枚举例程**，不调用 `FltRegisterFilter`。
后果：文件系统监控功能整体不可用。

### 4.3 `InitKernelMemoryContext` 函数名与地址错配（新发现）

- IDA：`InitKernelMemoryContext` = **0x14006BF2C**（768 字节，调用 29 个子函数）
- IDA：`ReadObjectTypeOffset` = **0x14006EAF0**（48 字节）
- 复刻源码 `DriverEntry.c:733` 的 `InitKernelMemoryContext` 注释写「对应原始驱动 sub_14006EAF0」
  且自述「实际为 ReadObjectTypeOffset 的别名」——**即复刻实现了 48 字节的 `ReadObjectTypeOffset`，
  却挂上了 `InitKernelMemoryContext` 的名字**。

后果：真正的 768 字节编排函数未实现，其下 26 个 WFP/KFD/NSI（网络过滤驱动）扫描与导出查找函数
（`ScanKfdDriverSectionV2/V3`、`ScanWfp*Sections`、`ScanNsi*Section`、`FindKfd*/FindWfp*/FindNsi*` 等，
合计 9,958 字节）全部无法到达。

> 这类「名字对、地址错」的缺陷无法被按名审计发现，本报告通过 §1-⑦ 的映射校验定位。

## 2026-09-30（六）：解析器族描述符字段偏移的系统性缺陷（已修复）

### 发现与根因

对 4 个"流程确立前"的转写实现做交叉验证时，用 **capstone 字节级解码**
（新增工具 `build/audit/_authfields.py`）核对 `0x120` 字节 PE 指令描述符的
字段访问，发现该族解析器的字段偏移存在**系统性错误**。

**根因**：早期转写时把 IDA 栈帧显示的数值（`var_38`、`var_70` 等）直接当成了
描述符偏移，而 IDA 的 `SectionEntry = [rsp+A0h]`，故正确映射为
`描述符偏移 = IDA 的 rsp 偏移 − 0xA0`。这一换算在早期被遗漏。

**同时暴露出一个更严重的问题**：IDA 在这批函数上的**栈帧分析本身已损坏**
（`var_B8` 声明在 `[rsp+190h]`，与 `var_19x` 系列自相矛盾），
这正是 Hex-Rays 无法反编译它们的根因。因此**不能信任这些函数的 IDA 栈帧名**。

### 权威字段映射（capstone 原始字节 + IDA 伪代码变量声明，两法一致）

| 偏移 | 语义 | 使用处 |
|---|---|---|
| +0x20 | SectionFlags（**BYTE**） | PNSC 的 1327 确认判据 |
| +0x38 | 段1 的 1369/1368 RVA | 全部 |
| +0x40 | 1294 槽偏移 / PCCS 1351 判据 | V3/PNFC/PCFS/PCCS |
| +0x50 | EntrySize（==64 判据） | 全部 |
| +0x58 | Dst 写索引 | 全部 |
| +0x70 | TypeField（仅 PCCS 1351 用） | PCCS |
| +0x78 | 1298 分支的 RVA | V3/PNFC/PNSC/PCFS/PCCS |
| +0x88 | Flags2 | 全部 |
| +0x90 | Dst 读索引 | 全部 |
| +0xD8 | PNEPC 路径 a 第一判据 | PNEPC |
| +0xDC | ExtraFlags | 全部 |
| +0xF0 | 指令长度 | 全部 |
| +0x118 | 类型指针 | 全部 |

### 已修正 21 处（commit `4821ceb`）

| 错误 | 修正 | 处数 |
|---|---|---|
| 1298 分支 RVA | 0x38 → 0x78 | 4 |
| ==64 判据 | 0x70 → 0x50 | 14 |
| 1294 槽偏移 | 0x38 → 0x40 | 3 |
| Dst 读索引 | 0x100 → 0x90 | 3 |
| PCCS 1351 判据 | 0x110 → 0x70 | 1 |
| PNEPC 路径 a | 0xB8→0xD8、0x38→0x40 | 2 |
| PNSC 1327 判据 | ULONG64@0x50 → UCHAR@0x20 | 1 |

**影响**：这些偏移决定从描述符哪一字段取 RVA/序号/标志。错误偏移读到的是
相邻字段，编译期无法发现，运行时会静默产生完全错误的回调地址。

### 全仓复查结论

对全部 `ReadPESectionEntry` 消费者做了字段集合扫描（脚本 `build/audit/_authfields.py`）。
其余"可疑偏移"（`0x28/0x3C/0x60/0xD0/0xE8/0x80/0xA` 等）**逐个人工核查均为误报**：

- `0x28/0x3C` = PE 头字段（节表 RVA / `e_lfanew`），非描述符字段；
- `0x60/0xD0/0xE8/0x120` = **另一套越界读取布局**（如 `ParseNtSectionsForModuleList1`、
  `ScanFileForPeSectionInfo`），代码注释已单独说明其来源；
- `0xA/0xD/0xE` = `FindKernelObjectFieldOffsetsWin8` 的**指令流扫描**（非描述符）。

### 方法论沉淀（新增）

**判据 F**：凡消费者读取"描述符/结构体"字段处，若其偏移集合中出现
"大面积与同族不一致"的值，必须用 **capstone 对原始字节解码**独立验证，
不得依赖 IDA 栈帧名（IDA 在结构体识别失败时会给出自相矛盾的声明）。

**推论**：本仓所有"无法反编译"的函数，其 IDA 栈帧分析很可能都不可靠。
凡曾依赖这些 `var_N` 名转写的地方，都应以 capstone 原始字节重新核对。

2. **地址命中**：其原始地址（或 `sub_XXXXXXXXXXXXXXXX` 形式）在源码注释中出现过

## 2026-10-08：构建环境不稳定性的定位（C1001 / D8040 的真实成因）

### 现象

对**同一份源码**连续多次执行 `build.bat Clean` + `build.bat`，产物在
**548,864 字节（正确）**与 **2,097,152 字节（残缺）**之间随机跳变，
并伴随 `fatal error C1001`（内部编译器错误）。

### 定位过程与证据

| 观察 | 数据 |
|---|---|
| 连续 3 次构建的图像大小 | 548,864 / 2,097,152 / 548,864（随机） |
| C1001 报出位置 | `MemoryOps.c(352)` → `ThreadMgmt.c(623)` → `SsdtHook.c(4907)` → `MemoryOps.c(384)`（**每次不同文件**） |
| 单线程编译（`CLToolMultiProcessor=false`） | **连续 2 次均为 0 个 C1001、0 error / 0 warning** |
| 单线程完整构建 | **exit=0、0 C1001、产物 548,864 字节（正确）** |
| 并发 cl.exe 数量 | 与构建损坏同时出现 |

一次更早的构建还报出：
- `fatal error D8040: 创建子进程或与子进程通讯时出错`
- 24 个 `fatal error C1083: 无法打开 ... .obj: Permission denied`

### 两个叠加的环境原因

1. **僵尸 `link.exe` 进程持有 `.obj`/`.sys` 句柄** —— 一次被中断的构建留下
   PID 33168 与 99484 两个 `link.exe`，导致 `Clean` 删不掉 obj、
   重编报 `C1083 Permission denied`。`taskkill` 后该类错误消失。

2. **并行编译在资源紧张时崩溃** —— 临时目录一度累积 **81,792 个文件**；
   即使清理到 15,796 个之后，多线程构建仍会间歇性报 C1001，
   而同一份代码单线程编译**稳定通过**。

### 结论（重要）

- **代码库本身是健全的**：单线程编译 0 error / 0 warning，产物大小正确。
- **C1001 不是代码缺陷**，位置随并行调度漂移，是编译环境问题。
- 因此，**判定"C1001 是否为真实缺陷"必须以单线程构建为准**；
  多线程构建失败时**不可**据此修改源码（否则会把环境问题误诊为代码问题）。
- 这也解释了此前另一次记录过的"C1001 会在文件间漂移"的现象 —— 同一根因。

### 建议的构建规程（新增）

1. 构建前检查并清理僵尸进程：`taskkill /F /IM link.exe`；
2. 若出现 C1001/D8040/C1083，先按单线程复验：
   `msbuild ... /p:CLToolMultiProcessor=false`；
3. 单线程通过即视为代码无误；多线程失败不修改源码；
4. 定期清理 `%TEMP%`（累积速度很快，本次达 8 万文件量级）。

### 产物验证

单线程完整构建后：产物 **548,864 字节**；
`SendDeviceIoControl`(528B) 与 `AllocDualBufferAndSendIoControl`(528B)
均以预期大小进入 `.text`，与上一轮提交时的状态一致。

### ⚠ 一次真实事故与自我更正（重要）

我在实现本族时把 `ReadNtoskrnlNlsFile` 判为"缺失"并**重复实现了一遍**，

对这种写法匹配失败。

**教训（已回写方法论）**：
- 判定"缺失函数"**不能只信扫描脚本**；
- 必须**交叉验证**：扫描结果 + 全文 grep（`grep -rn "\bNAME\s*("`）双重确认；
- 最可靠的最终判据是**链接器**：`/OPT:REF` 下若真缺定义会报 LNK2019，
  而重复定义报 LNK2005 —— 两者都是当场可见的硬信号，应尽早触发构建。

**本轮的实际代价**：一次重复实现（约 25 行）+ 一次 LNK2005 构建失败，
