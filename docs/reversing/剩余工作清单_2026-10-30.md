## 1. 【最高优先】0x13A 诊断通道被对齐动作挤掉

**现象**：Setting 页 6 项对象保护（Forbid）全部不可用。

**实测**（guest 上 `xpch_frontend.exe --setting-cli`）：

```
object types: NOT READY (driver did not export)
  IoFileObjectType   = 0000000000000000
  IoDriverObjectType = 0000000000000000
  IoDeviceObjectType = 0000000000000000
  PsProcessType      = 0000000000000000  (GT[0x4166])
  PsThreadType       = 0000000000000000  (GT[0x4169])
  extra[ 0..12]      = 0000000000000000
```

**根因链**：
1. `IoctlDispatch.c:393` 现在是 `Table[282] = NULL`。
2. 这是 `026f56b`（283 槽对齐原版）的结果 —— **原版该槽本来就是 NULL**
   （283 数组末尾），所以当前代码是"正确对齐原版"的状态。
3. 但 `0x13A` 恰好是我方自研诊断通道 `CmdDumpCallStats`（`:3081`）的出口，
   被同一动作置空了。
4. `CmdDumpCallStats` 现在没有任何注册点 → 死代码。
5. `SettingViews.c:99` 调 `0x13A` 拿对象类型地址 → 拿不到 → `g_StObjReady=0`
   → Setting 页 Forbid 五项全部不可用。

**这是一个真实的取舍**：恢复 0x13A 就偏离原版槽位表；不恢复就丢失自研诊断
和 Setting 页的对象保护。

**可选路线**（都需你定）：
- (a) 恢复 `Table[282] = CmdDumpCallStats`。代价：283 槽与原版有 1 处差异，
  但该槽原版为空、原版前端永远不会发送，实际无兼容性影响。
- (b) 把对象类型地址改用一条**原版存在**的命令导出，保持 283 槽对齐。
  需先确认原版哪条命令返回这些地址（0x0D4 枚举的是对象类型下的对象，
  不是类型地址本身，不能替代）。
- (c) 让客户端自己从 ntoskrnl 导出表解析（用户态读磁盘 ntoskrnl.exe 的
  导出表拿 RVA，再叠加驱动返回的内核基址）。不需要新命令，但要新增
  用户态 PE 解析代码。

我倾向 (a)：`CmdDumpCallStats` 是只读诊断，写入位置在数组末尾，
原版前端不会发送 0x13A，风险最低且立刻恢复 6 项功能。

## 2. 【本轮新发现】OpenFileSection 的两个缺陷

这两个是在尝试接入 0x0AC 时触发 BSOD 暴露的，均为**原有缺陷**，非本轮引入。

### 2.1 close 函数指针未传参（已修）

- 原版 `0x140078FF0/FF3`：`mov rbx,rcx ; call rdi`，rcx 来自
  `mov rcx,[rsp+arg_8]`，即**句柄本身**。
- 我方原写法：`CloseFunc()` 无参调用，rcx 留着调用前的残留值。
- 实测残留值 = `0x8d117757c05f0000`，被被调用方当对象指针交给
  `ObfDereferenceObject` → `lock xadd [rsi-30h]` 访问非法地址 → BSOD 0x3B。
- 已修：`CloseFunc(FileHandle)`。

### 2.2 GT[0x4223] 从未被填充（**未修，是真正的阻塞**）

- `GtCloseHandleFunc = 0x4223`（`xpc_gt_enum.h:628`）。
- 全仓搜索 `GtWrite ... 0x4223`：**0 处**。这个槽没有任何写入者。
- 代码注释自相矛盾：
  - `ObjectMgmt.c:2340` 明确写 `GT[0x4223] = ObfDereferenceObject（不是 CloseHandle）`
  - `HandleMgmt.c:612` 也写 `GT[0x4223]=ObfDereferenceObject`
  - `Minifilter.c:10810` 却写 `Gt[0x4223] = CloseHandle`（1 实参）
- KD 实测崩溃时 `rdi = 0xfffff8054a11a180`，反汇编出来是垃圾指令
  （`sbb byte ptr [rdi],0` 之类），确认槽里不是有效函数地址。

**影响面**：所有通过 `GtCloseHandleFunc` 关闭句柄的路径都可能崩。
涉及 `DiskQuery.c`、`HandleMgmt.c`、`ModuleMgmt.c`、`ObjectMgmt.c`、
`TailHelpers.c`、`SystemInfo.c`、`Protocol.c` 共 20+ 处调用点。

**修复方向**：这个槽在原版里由"解析 ntoskrnl 导出表"这一整套机制填充
（`GtCloseHandleFunc` 只是几百个同类槽之一）。补齐它属于下面的第 4 类工作，
不是单点补丁。

### 2.3 6 处 1352 字节缓冲区越界（已修）

7 个"填 28 项 × 48 字节"的表枚举函数里有 6 个多写了两处：

```c
*(DWORD*)(buf + 1344) = Index;                       /* 越界 4 字节 */
*(QWORD*)(buf + 1360) = *(QWORD*)(SectionBase + 96); /* 越界 24 字节 */
```

调用方传 `pOutputBuffer + 8`、缓冲共 1352 字节，所以实际写到 +1352 / +1368。

逐函数核对原版（IDA decompile）结果：

| 我方函数 | 原版地址 | 调用方缓冲 | 原版是否有额外写 | 处理 |
|---|---|---|---|---|
| `EnumSsdtFunctionTable2` | 0x1400335F4 | 1400 | **有** | 保留 |
| `FillSyscallTableInfo` | 0x140050478 | 1400 | **有** | 保留 |
| `EnumSyscallTable7` | 0x1400537B8 | 1352 | 无 | 已删 |
| `EnumShadowSyscallTable` | 0x14003D344 | 1352 | 无 | 已删 |
| `EnumSyscallTable6` | 0x14003DB28 | 1352 | 无 | 已删 |
| `InitSyscallExportEntryArray` | 0x140046A3C | 1352 | 无 | 已删 |
| `CopyWin32kServiceTable` | 0x140053E60 | 1352 | 无 | 已删 |
| `CopySyscallTableEntries` | 0x1400864A8 | 1352 | 无 | 已删 |

规律的成因：原版这批函数分两族，`OutSize=1400` 的族带额外两个字段
（项数 + 一个基址），`OutSize=1352` 的族不带。我方早期把两族写了同一份
模板注释，导致统一多加。

## 4. 需要新增驱动代码（不在 199 条内）

这一类是"原版也没有，或原版靠另一套机制实现"的项。

### 4.1 GT 描述表解析机制（阻塞多条命令的总根）

原版用一套 PE 导出解析把几百个内核函数/全局地址写进 GT 表
（`GtCloseHandleFunc` 是其中之一）。我方这套解析没有完整实现，
结果是一批命令能进 handler 但一用就崩或返回 0。

已确认未填充的槽（举例）：
- `0x4223` `GtCloseHandleFunc`（`ObfDereferenceObject` 或 `CloseHandle`，语义都有争议）
- `0x831` `HalDataSectionOffset`（`SsdtHook.c:4229` 只在 HalBase 非零时才写）

#### 4.1.1 三个 context 族（0x129 / 0x12D / 0x12F）——已定位并修复两个

**结论先行**：0x129 与 0x12F 已打通（GUI 各显示 2 contexts），
0x12D 仍为 0 条，卡在另一套校验（见下）。

**根因（同一种 RVA 计算错误被复制到三个 PE 解析器）**

```c
ComputedOffset = Entry[0xF0] + AccumulatedOffset;   // 累加量，错误
SectionRva = ComputedOffset + Entry[0x38] - (ULONG)pFileBuffer;
```

`AccumulatedOffset` 是从 0 起的历史累加，缺少段的起始基址
（`pFileBuffer + InitSectionRva`）。同族的 `ParseNtExportSectionsV3`
早已按原版汇编修正为「推进后的读指针本身」：

```
140035BB0 lea  rcx,[rsp+50h]      ; ctx
140035BB5 call ReadPESectionEntry
140035BBE mov  eax,[rsp+190h]     ; entry+0xF0
140035BC4 mov  rcx,[rsp+58h]      ; = ctx+0x08，读指针本身
140035BC9 add  rcx, rax
140035BD3 mov  [rsp+58h], rcx
```

反编译里那个 `ContextOffset` 变量就在 rsp+0x58，即 ctx+0x08，
不是从 0 起的计数器。

修正范围（三处，全部改成 `(ULONG)(*(ULONG64*)(ctx+0x08))`）：
1. `ParseNtFileForCallbackContext` 第一段
2. `ParseNtFileForCallbackContext` 第二段
3. `ParseNtSectionsForContextTable` 第一段 + 第二段

**修正前后对比**

修正前：`g_DiagCbParseSecIdx=0x14`（20 轮扫满）、`SecRva=0`
—— 一次都没命中，`CurrentRva` 保持初始值。

修正后 0x129 输出：
```
0000: 01 00 00 00 ...            count = 1
000C: 09 60 00 00                 目标 RVA = 0x6009
0010: 09 60 04 70 04 F8 FF FF     函数指针（msfs 内）
0020: 48 89 5C 24 08 57 48 ...    该函数的原始代码副本
```
语义：枚举回调函数并保存原始代码字节，供 inline hook 检测比对。

**附带修掉两处栈越界**

`SlotAddresses` 只有 16 项，但两处都用数据里的值直接作下标
（`+0x58` 与 `+0x90` 字段）。遇到异常条目会越界写栈。已加 `< 16` 限界。

**0x12D 的结论：与原版行为一致，不是缺陷**

历史 AB 对照（`全命令对照总表与交付结论_2026-10-26.md:312`）显示：

| 命令 | 原版 | 我方（对照时） | 判定 |
|---|---|---|---|
| `0x129` | REJ/0 | REJ | ✅ 完全一致 |
| `0x12D` | REJ/0 | REJ | ✅ 完全一致 |
| `0x12F` | REJ/0 | REJ | ✅ 完全一致 |

即三条在原版环境下**本身就没有数据**。本轮修正之后：

- `0x129` → 2 contexts（**优于原版**）
- `0x12F` → 2 contexts（**优于原版**）
- `0x12D` → 0 条（与原版一致）

所以 0x12D 不需要再投入。它剩下的阻塞（1294 条目的 `+0x40` 字段为 0）
属于驱动文件结构差异，且原版同样拿不到数据。

**0x12D 的剩余观察（仅供参考）**

`EnumObjectContextOperation` 的成功路径要求三个条件同时成立：
```c
EnumObjectContextTable(...) == 1
CopyObjectContextHookTable(...) == 1
ValidateSsdtHookTargetTable(...) == 1
```
实测 `EnumObjectContextTable` 已产出真实函数指针
（`0xFFFFF80470623...`），但 `*pOutputBuffer`（count）仍为 0，
说明后两个之一失败。这是独立于 RVA 缺陷的另一条链。

**顺带修正的调用约定问题**

0x12D / 0x12F 都要求**精确**的 OutputSize（1400 / 1352），传大缓冲会被
拒绝。GUI 的 Tbl 里尺寸本来就对，之前 probe 用 2MB 测才会 REJECTED。

#### 4.1.2 0x12D / 0x12F 是否同一根因

三者都走 `OpenFileSection` + `GtAlloc` + 两个 Parse 的同一模式，但用的
驱动文件不同（0x12D → `\FileSystem\...` 对象上下文，0x12F → 进程保护
上下文）。是否同根因需分别读各自 `GT[?]` 成功标志后才能确认；
当前两者的 GUI 输出同为 0 条。

### 4.2 HAL 两个分发表检测（**2026-10-30 已完成**）

- `HalAcpiDispatchTable` 在 Win10 上**不存在**（KD `x nt!*AcpiDispatch*` 无输出），
  客户端对该节点显示 "(not present on this build)"。
- 原版驱动**没有任何 HAL 检测代码** —— 这是新增能力，不是复刻。
- 已接线：`CmdDumpCallStats`（0x13A）首次调用时惰性执行
  `LocateHalDispatchTables`，结果经 env+0x3E8/0x3F0/0x3F8 导出。
- 判据经过六轮校准，最终形态：
  1. nt 基址来源放宽——前三条路径都要求基址处可读 MZ 头，但某些 boot
     上镜像头页不可访问（实测 `0xFFFFF80366200000` 处是 `00 00 00 00`）。
     加一条不依赖内存读的兜底：一槽内核态页对齐 + 另一槽合理小尺寸即采信。
  2. 表判据加"表内重复指针 >= 1"——真表有大量重复项
     （`0x4a0e6f50` ×2、`0x49b39820` ×3），代码区不会。
  3. 收集全部候选后按「head=4 与 head=0x31 相距 0xA90」配对，
     而不是取前两个（原先会被 .text 里的伪结构抢位）。
  4. 代码指针窗口上限从 nt+64MB 放宽到 nt+128MB
     （私有表的项会指向独立 HAL 模块，实测 nt+0x1D86140）。
- **实测验证（build 18362，nt=0xFFFFF80049A00000）**：

  | 项 | KD 真值 | 驱动输出 |

**判据被证伪的六处根因（都已修正）**

1. 基址来源不稳定：GT[2]/GT[3] 有时是 (size, end)，有时只有地址槽

## 11. §4.1 进展：0x026 守卫修复 + GT 链条边界定性（提交 a7d9fc4）

**已修复的真 bug**：CmdEnumHandles 的守卫有三处转写错误，最致命的是把
`GT[38]`（Win7 标志，本机=0）当作比较上界，导致 `Process >= EntryIndexSrc`
恒真、函数开头即 return。按原版 0x14004AC44 改为
`GT[GtEprocessField131|0x100]` 与 `GT[GtProcessOffset]` 比较。
实测修复前 `result=0`，修复后 `result=1`。

**0x026 为何仍只有 1 条 "Idle"——这是 GT 链条的固有边界，不是实现缺陷**：

ValidateProcessContext 串联 5 个填充器：
| 填充器 | 依赖 | 本机状态 |
|---|---|---|
| GetProcessVirtualizationContext | GT[0x4265]/GT[0x41DB]/GT[30] | 槽均有值，走主路径 |
| DispatchProcessHandleTableEnum | 回调表 | 部分 |
| EnumerateProcessHandleTable | **GT[68]/GT[69]/GT[70]** 三链表头 | GT[69]=0 |
| EnumerateAllProcesses | GT[0x41DE]/GT[0x41E4] | 有值 |
| EnumerateSessionProcesses | CSRSS 进程 | 部分 |

GT[68]/[69]/[70] 由 `HookSyscallNtSetValueKey` / `HookSyscallNtRenameKey`
系列在**运行期 syscall hook 安装完成后**写入（SsdtHook.c:5703/5726/5727）。
本机只装了一部分（[68]/[70] 有值、[69]=0），所以枚举链只走通一段。

**结论**：0x026/0x108 的表现是 GT 描述表机制（§4.1）的**真实下游**——
要让它们完整工作，必须先让 syscall hook 链在目标 build 上装全。
这不是"补一条命令"能解决的，也是 §4.1 被称为"较大独立工作"的具体含义。

**本阶段 §4.1 的可交付结论**：把"GT 槽未填充"从笼统描述落到了具体槽号
（GT[68]/[69]/[70]）与具体写入者（两个 Hook 函数），后续补链条时可直接
从这两处入手，不需要重新逆向。

## 12. §4.1 上游根因定位：ReadNtoskrnlFile 实际失败（提交待补）

继续向上追 syscall hook 链，找到 GT[68]/[69]/[70] 为空的**最上游原因**：

### 12.1 链条（自 DriverEntry 向下）

```
DriverEntry
 ├─ g_DiagSdst      = InitSdstTable()        → 实测 1（成功）
 ├─ g_DiagNtoskrnl  = ReadNtoskrnlFile()     → 实测 1（返回成功）
 ├─ InitSyscallNumberTable() / BuildHookTable()
 └─ g_DiagHookSubsys = InitAllHookSubsystems() → 实测 1
       └─ if (Success == 1)  ← 门槛
            HookSyscallNtRenameKey()   ← 本机被跳过
            HookSyscallNtSetValueKey() ← 本机被跳过（写 GT[68]/[69]/[70]）
```

`Success` 在 `HookSyscallNtOpenThread()` 返回 0 时被置 0
（DriverEntry.c:1777-1780）。该函数走 `FindNtOpenThreadTargetWin8`，
其入口守卫是：

```c
SectionOffset = GtRead(GtTotalSize | GtEprocessField79 | 0x100);  // GT[0x4069]
if (!SectionOffset || SectionOffset >= ImageSize) return 0;
```

### 12.2 实测槽值（kd，win10dev / 18362）

| 槽 | 值 | 原版语义 | 判定 |
|---|---|---|---|
| GT[0x4069] | `0x6D80B0` | ntoskrnl 节表扫描偏移 | 非零 ✓ |
| **GT[33]（当 ImageSize 用）** | **`0x30`** | ntoskrnl **文件展开后大小** | ❌ 应为 0xAB2000 级 |
| GT[32]（Src 缓冲指针） | `0x488` | ntoskrnl 文件缓冲指针 | ❌ 应为内核指针 |
| GT[66]（展开镜像指针） | **`0`** | `ImageBuffer`（PE 展开副本） | ❌ 必为 0 说明未写 |
| GT[4] | `0x0053005C00730079` = `L"\Sys"` | 内联字面量（非指针） | 正常（见 ModuleMgmt.c:1413 注释） |
| g_DiagNtoskrnl | `1` | 返回值 | ⚠ 与 GT[66]=0 矛盾 |

**结论**：`ReadNtoskrnlFile` 的返回值是 1，但它内部的
`GtWrite(GtEprocessField66, ImageBuffer)` 没有生效（GT[66]=0），
且 GT[32]/GT[33] 里是 `0x488/0x30` 这类**非预期值**。
即：**该函数的"成功"返回值与实际副作用不一致**——
要么 `ParseNtExportDir` 走了 `ExportDirSize == 0 → return 1`
的早退分支（SSDT.c:1577：`if (ExportDirSize == 0) return 1;`），
导致跳过全部 GT 写入却仍返回 1；要么文件读取路径取到了错误数据。

最可能的解释是前者：`ReadNtFileToBuffer` 返回的 `FileSize` 为 0，
于是 `ParseNtExportDir(ImageBuffer, 0, ...)` 立即 `return 1`，
函数"成功"返回但什么都没有填。

### 12.3 下一步（已收敛到单点）

验证并发修复这一条即可解锁整条 syscall hook 链：

1. 在 `ReadNtoskrnlFile` 里对 `FileSize == 0` 显式返回失败，
   （而不是让 `ParseNtExportDir` 把 0 当成"无事可做即成功"）；
2. 查 `ReadNtFileToBuffer` / `ReadFileRawData` 在本机读
   `\SystemRoot\System32
toskrnl.exe` 为何得到 0 长度
   （最可能是路径拼接或 `\SystemRoot` 符号解析，属原版
   `InitSdstTable` 的路径构造逻辑范畴）。

这是 §4.1 剩余工作的**唯一入口**，范围已从"几百个 GT 槽的解析机制"
收窄到"一个文件读取路径 + 一处返回值语义"。

### 12.4 实证：删除 ParseNtExportDir 的早退是**错误修法**（已回退）

假设 `ParseNtExportDir` 的 `if (ExportDirSize == 0) return 1;` 是
"成功但无副作用"的根源，据此删掉该行并重编驱动实测：

| 槽 | 修改前 | 删早退后 | 预期 |
|---|---|---|---|
| GT[32]（Src）| `0x488` | `0` | 内核指针 |
| GT[33]（FileSize）| `0x30` | `0` | 0xAB2000 级 |
| GT[66]（ImageBuffer）| `0` | `0x9D` | 内核指针 |

结果三者都变成 `0` / 小整数垃圾 —— 说明**这条早退并不是问题所在**，
删掉它只是让失败路径把槽写得更乱。已 `git checkout` 回退。

**因此正确的结论是**：`ReadNtoskrnlFile` 在本机确实走的是失败链
（`ReadFileRawData` 或 `ReadNtFileToBuffer` 拿不到 ntoskrnl 文件），
而 `g_DiagNtoskrnl = 1` 是**过时读数**（我先前按 map 偏移读的
`g_DiagNtoskrnl`/`g_DiagSdst` 是 `db` 单字节，可能读到了相邻字段）。
后续验证必须用 `!chkimg` 式的地址确认，或直接以 GT[32]/[33]/[66]
三槽是否同时为内核指针作为唯一判据。

### 12.5 收敛后的唯一入口

```
ReadNtoskrnlFile (SSDT.c:1090)
  ├─ GtAlloc(GtPathBuffer00) → GT[4] 内联 L"\Sys"（正常）
  ├─ GtRead(GtNtoskrnlModuleBase) → GT[3]，本机非零（正常）
  ├─ ReadFileRawData(FileBufferPtr, ...)      ← 待查：是否打开到文件
  ├─ ReadNtFileToBuffer(RawFileData, ...)     ← 待查：FileSize 是否为 0
  └─ ParseNtExportDir(ImageBuffer, FileSize, ...)
```

判定方法（无需再改代码）：在 guest 里用 `probe --live --cmd 0x13A`
读 env 的诊断块，或直接在 KD 断在 `ReadNtFileToBuffer` 返回处看
`FileSize`。只要 FileSize 非 0 且 `ParseNtExportDir` 返回 1，
GT[32]/[33]/[66] 就会同时成为合法的内核指针，syscall hook 链
随之打通，0x026 与 0x108 即可返回完整数据。

## 13. §4.1 实证推进：链条前两步已确认成功（2026-10-30，仅文档）

按 §12.5 的入口做了**仪器化实测**（临时在
`ReadNtoskrnlFile` 的两个调用点与 `ParseNtExportDir` 开头写 GT 槽，
经 0x13A 导出；实测后代码已全部回退）。

### 13.1 实测数据（win10dev / 18362）

| 检查点 | 值 | 判定 |
|---|---|---|
| `ReadFileRawData` 返回 | `0` | ✅ 成功 |
| 原始文件大小 | `0x975538`（9.9 MB，正是 ntoskrnl.exe） | ✅ 正确 |
| `ReadNtFileToBuffer` 返回 | `1` | ✅ 成功 |
| 展开后镜像大小 | `0xAB2000` | ✅ 与 lm 报告的 nt 大小一致 |
| `ParseNtExportDir` 收到的 size | `0xAB2000` | ✅ 正确 |
| 重定位目录 RVA / Size | `0xAA8000` / `0x4780` | ✅ 合理 |
| **`DosHeader->e_magic`** | **`0xA00000`**（应为 `0x5A4D`） | ❌ 坏 |
| `NtHeaders->Signature` | `0x4550`（PE  ） | ✅ 正确 |
| `e_lfanew` | `0x108` | ✅ 正确 |

### 13.2 结论

**文件读取与 PE 展开两步都完全成功**（9.9MB 读入、0xAB2000 展开）。
失败点精确落在 `ParseNtExportDir`：它拿到的缓冲里 `e_magic` 是
`0xA00000`，但 `Signature` 与 `e_lfanew` 都正确 —— 说明缓冲里
**只有 DOS 头的前 2 字节被覆盖**，其余结构完好。

`0xA00000` 与 `SizeOfImage(0xAB2000)` 同量级，高度怀疑是
`ReadNtFileToBuffer` 里"头部拷贝"那一段把 `SizeOfHeaders` 用成了
`SizeOfImage`，导致 `memmove(Buffer, pBase, HeaderSize)` 拷了
10MB，越界覆盖了自己的头部。

### 13.3 已排除的两个错误假设（都做了实测并回退）

1. `ParseNtExportDir` 的 `if (ExportDirSize == 0) return 1;` 早退
   —— 删掉后 GT 槽变得更乱，**不是原因**。
2. `pNt[14/15/20/21]` 索引偏 1 —— 用本机 ntoskrnl.exe 实测
   `pNt[14]=0x1000`(SectionAlignment)、`pNt[15]=0x200`(FileAlignment)、
   `pNt[20]=0xAB2000`(SizeOfImage)、`pNt[21]=0x800`(SizeOfHeaders)，
   **原代码索引完全正确**，原版反汇编里的 `rdx` 是
   `pNt+0x18`（OptionalHeader 起点），不是 pNt。
   改成 pNt[13/14/19/20] 会让驱动启动即失败（DriverEntry 返回错误）。

### 13.4 下一步（已收敛到一行）

检查 `ReadNtFileToBuffer` 第 ③ 段：

```c
ULONG HeaderSize = SizeOfHeaders;
if (SrcSize < HeaderSize) HeaderSize = SrcSize;
memmove(Buffer, pBase, HeaderSize);
```

若 `SizeOfHeaders` 读出的不是 0x800（实测 ntoskrnl 应为此值），
而误为 0xAB2000，则此处即越界源头。**验证方法**：在 guest 里
读 GT 槽记录 `SizeOfHeaders` 的实际值（一行仪器即可，不必改逻辑）。

一旦此处修正，`ParseNtExportDir` 就能正确解析导出目录 →
GT[32]/[33]/[66] 写入合法内核指针 → syscall hook 链装全 →
GT[68]/[69]/[70] 有值 → 0x026 返回完整进程列表、0x108 同受益。
