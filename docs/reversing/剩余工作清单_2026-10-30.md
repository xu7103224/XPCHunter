## 1. 【最高优先】0x13A 诊断通道被对齐动作挤掉

**现象**：Setting 页 6 项对象保护（Forbid）全部不可用。

**实测**（guest 上 `xpch_frontend.exe --setting-cli`）：

```
object types: NOT READY (driver did not export)
  IoFileObjectType   = 0000000000000000
  IoDriverObjectType = 0000000000000000
  IoDeviceObjectType = 0000000000000000
  PsProcessType      = 0000000000000000  (GT[0x4166])
  PsThreadType       = 0000000000000000  (GT[0x4169])
  extra[ 0..12]      = 0000000000000000
```

**根因链**：
1. `IoctlDispatch.c:393` 现在是 `Table[282] = NULL`。
2. 这是 `026f56b`（283 槽对齐原版）的结果 —— **原版该槽本来就是 NULL**
   （283 数组末尾），所以当前代码是"正确对齐原版"的状态。
3. 但 `0x13A` 恰好是我方自研诊断通道 `CmdDumpCallStats`（`:3081`）的出口，
   被同一动作置空了。
4. `CmdDumpCallStats` 现在没有任何注册点 → 死代码。
5. `SettingViews.c:99` 调 `0x13A` 拿对象类型地址 → 拿不到 → `g_StObjReady=0`
   → Setting 页 Forbid 五项全部不可用。

**这是一个真实的取舍**：恢复 0x13A 就偏离原版槽位表；不恢复就丢失自研诊断
和 Setting 页的对象保护。

**可选路线**（都需你定）：
- (a) 恢复 `Table[282] = CmdDumpCallStats`。代价：283 槽与原版有 1 处差异，
  但该槽原版为空、原版前端永远不会发送，实际无兼容性影响。
- (b) 把对象类型地址改用一条**原版存在**的命令导出，保持 283 槽对齐。
  需先确认原版哪条命令返回这些地址（0x0D4 枚举的是对象类型下的对象，
  不是类型地址本身，不能替代）。
- (c) 让客户端自己从 ntoskrnl 导出表解析（用户态读磁盘 ntoskrnl.exe 的
  导出表拿 RVA，再叠加驱动返回的内核基址）。不需要新命令，但要新增
  用户态 PE 解析代码。

我倾向 (a)：`CmdDumpCallStats` 是只读诊断，写入位置在数组末尾，
原版前端不会发送 0x13A，风险最低且立刻恢复 6 项功能。

## 2. 【本轮新发现】OpenFileSection 的两个缺陷

这两个是在尝试接入 0x0AC 时触发 BSOD 暴露的，均为**原有缺陷**，非本轮引入。

### 2.1 close 函数指针未传参（已修）

- 原版 `0x140078FF0/FF3`：`mov rbx,rcx ; call rdi`，rcx 来自
  `mov rcx,[rsp+arg_8]`，即**句柄本身**。
- 我方原写法：`CloseFunc()` 无参调用，rcx 留着调用前的残留值。
- 实测残留值 = `0x8d117757c05f0000`，被被调用方当对象指针交给
  `ObfDereferenceObject` → `lock xadd [rsi-30h]` 访问非法地址 → BSOD 0x3B。
- 已修：`CloseFunc(FileHandle)`。

### 2.2 GT[0x4223] 从未被填充（**未修，是真正的阻塞**）

- `GtCloseHandleFunc = 0x4223`（`xpc_gt_enum.h:628`）。
- 全仓搜索 `GtWrite ... 0x4223`：**0 处**。这个槽没有任何写入者。
- 代码注释自相矛盾：
  - `ObjectMgmt.c:2340` 明确写 `GT[0x4223] = ObfDereferenceObject（不是 CloseHandle）`
  - `HandleMgmt.c:612` 也写 `GT[0x4223]=ObfDereferenceObject`
  - `Minifilter.c:10810` 却写 `Gt[0x4223] = CloseHandle`（1 实参）
- KD 实测崩溃时 `rdi = 0xfffff8054a11a180`，反汇编出来是垃圾指令
  （`sbb byte ptr [rdi],0` 之类），确认槽里不是有效函数地址。

**影响面**：所有通过 `GtCloseHandleFunc` 关闭句柄的路径都可能崩。
涉及 `DiskQuery.c`、`HandleMgmt.c`、`ModuleMgmt.c`、`ObjectMgmt.c`、
`TailHelpers.c`、`SystemInfo.c`、`Protocol.c` 共 20+ 处调用点。

**修复方向**：这个槽在原版里由"解析 ntoskrnl 导出表"这一整套机制填充
（`GtCloseHandleFunc` 只是几百个同类槽之一）。补齐它属于下面的第 4 类工作，
不是单点补丁。

### 2.3 6 处 1352 字节缓冲区越界（已修）

7 个"填 28 项 × 48 字节"的表枚举函数里有 6 个多写了两处：

```c
*(DWORD*)(buf + 1344) = Index;                       /* 越界 4 字节 */
*(QWORD*)(buf + 1360) = *(QWORD*)(SectionBase + 96); /* 越界 24 字节 */
```

调用方传 `pOutputBuffer + 8`、缓冲共 1352 字节，所以实际写到 +1352 / +1368。

逐函数核对原版（IDA decompile）结果：

| 我方函数 | 原版地址 | 调用方缓冲 | 原版是否有额外写 | 处理 |
|---|---|---|---|---|
| `EnumSsdtFunctionTable2` | 0x1400335F4 | 1400 | **有** | 保留 |
| `FillSyscallTableInfo` | 0x140050478 | 1400 | **有** | 保留 |
| `EnumSyscallTable7` | 0x1400537B8 | 1352 | 无 | 已删 |
| `EnumShadowSyscallTable` | 0x14003D344 | 1352 | 无 | 已删 |
| `EnumSyscallTable6` | 0x14003DB28 | 1352 | 无 | 已删 |
| `InitSyscallExportEntryArray` | 0x140046A3C | 1352 | 无 | 已删 |
| `CopyWin32kServiceTable` | 0x140053E60 | 1352 | 无 | 已删 |
| `CopySyscallTableEntries` | 0x1400864A8 | 1352 | 无 | 已删 |

规律的成因：原版这批函数分两族，`OutSize=1400` 的族带额外两个字段
（项数 + 一个基址），`OutSize=1352` 的族不带。我方早期把两族写了同一份
模板注释，导致统一多加。

## 4. 需要新增驱动代码（不在 199 条内）

这一类是"原版也没有，或原版靠另一套机制实现"的项。

### 4.1 GT 描述表解析机制（阻塞多条命令的总根）

原版用一套 PE 导出解析把几百个内核函数/全局地址写进 GT 表
（`GtCloseHandleFunc` 是其中之一）。我方这套解析没有完整实现，
结果是一批命令能进 handler 但一用就崩或返回 0。

已确认未填充的槽（举例）：
- `0x4223` `GtCloseHandleFunc`（`ObfDereferenceObject` 或 `CloseHandle`，语义都有争议）
- `0x831` `HalDataSectionOffset`（`SsdtHook.c:4229` 只在 HalBase 非零时才写）

### 4.2 HAL 两个分发表检测

- `HalAcpiDispatchTable` 在 Win10 上**不存在**（KD `x nt!*AcpiDispatch*` 无输出）。
- 原版驱动**没有任何 HAL 检测代码** —— 这是新增能力，不是复刻。
- 现有 `LocateHalDispatchTables`（`IoctlDispatch.c:2975`）判据被 KD 真值证伪：
  扫描结果 `0xFFFFF80070164590` vs 真值 `0xfffff8006fe23250`。
- 函数当前**未被调用**，`g_HalScanCount` 恒为 0。
- 要做需：KD 在多个 build 上取真值 → 反推可靠特征 → 再接线。

### 4.3 其它原版没有的能力

- 任意内核 VA 读取原语
- 内核定时器 / 工作项 / 通知例程枚举
- 注册表回调链（`CtlpCallbackListHead` 等）
- 内核 Dump / 内核编辑器
