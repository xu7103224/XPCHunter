## 已修复的两个缺陷

### 1. `GetCallbackContextBase` 的驱动名被截断

原版把名字拆成 `_DWORD EncodedName[4]` + 3 个独立后缀变量 + 终止符，
靠**栈上连续布局**拼成一整条宽字符串：

```
EncodedName[0..3] @ rbp-0x30，Suffix1 @ -0x20，Suffix2 @ -0x1C，
Suffix3 @ -0x18，Terminator @ -0x14
```

解码后是 `\Driver\Volmgr`（build ≥ 0x1770）或 `\Driver\Ftdisk`。

我方照抄成独立局部变量时，编译器不保证它们紧跟数组 —— 与
`DriverSection.c` 里 netio/usbport 等路径被截断属同一类缺陷。
名字截断后 `OpenFileSection` 必然失败 → `EnumCallbackContextTable` 返回 0
→ 0x131 恒为 `result=0`。

修法：改成单个显式 `_DWORD EncodedName[8]`，布局由语言保证。

### 2. `ParseNtExportSectionsV3` 的 `ContextOffset` 语义错

原版反编译里 `ContextOffset` 声明在 `[rsp+58h]`，而 `PE_DECODE_CONTEXT`
起点在 `[rsp+50h]` —— **`ContextOffset` 就是上下文 +0x08（读指针本身）**，
不是从 0 起的累计计数器。汇编可证：

```
140035BB0 lea  rcx,[rsp+50h]      ; ctx
140035BB5 call ReadPESectionEntry
140035BBE mov  eax,[rsp+190h]     ; entry+0xF0  消耗字节数
140035BC4 mov  rcx,[rsp+58h]      ; ← ctx+0x08 读指针
140035BC9 add  rcx, rax           ; 读指针 += 消耗量
140035BD3 mov  [rsp+58h], rcx     ; 写回
140035BEA mov  eax,[rsp+0D8h]     ; entry+0x38（RIP 相对位移）
140035BED sub  eax, r15d          ; - ImageBase
140035BF0 add  eax, ecx           ; + 读指针
```

即 `TargetRva = 读指针(推进后) - ImageBase + entry[0x38]`，
`entry[0x38]` 是 RIP 相对位移。

我方实现成从 0 累加的独立变量，漏掉了基址 `ImageBase + InitSectionRva`，
所有 TargetRva 全错。修法：直接用 `((PE_DECODE_CONTEXT*)&ctx)->+0x08`，
两段循环都是「读完 → 先推进 → 再用推进后的值」。

## 剩余差距（已定位到具体位置）

诊断计数（`g_DiagPe*`，随 `0x13A` 的 env 块 0x3B8 起导出）：

```
第一段解码条目数      g_DiagPeL1        = 8
第一段选定的 RVA      g_DiagPeLoop1Exit = 0x16078
第二段解码条目数      g_DiagPeL2        = 108
类型 1294 出现次数    g_DiagPe1294      = 17
通过全部条件的次数    g_DiagPeCond      = 11
实际填写条目数        g_DiagPeDst       = 11
最后一条的类型码      g_DiagPeType1294  = 0x545 = 1349  ← 终止标记
```

**第二段循环在第 108 条取出类型码 `1349`（解码序列的终止标记）而提前 break。**
原版能填满 28 条，说明它不会在这里遇到 1349 —— 即我方
`ReadPESectionEntry` 对某类指令**消耗的字节数与原版不同**，累积偏移漂移后
把普通字节误读成终止标记。

前 11 条能逐字节吻合，说明基址、位移计算、条件判断都已正确；
问题只在解码器推进量的保真度。

## 附带记录

- `ParseNtExportDir` 名字有误导：它实际是**基址重定位应用器**（遍历
  IMAGE_BASE_RELOCATION 块，按 HIGHLOW/DIR64 加上 Delta），
  不是导出目录解析器。28 条的 RVA 全部来自 `ParseNtExportSectionsV3`。
- 原版 `OpenFileSection` 的调用族里，只有 `GetCallbackContextBase`
  用了「数组 + 独立后缀变量」的拆分写法；其余
  （`GetCallbackContextBase2` / `BuildRegistryDriverPath` /
  `EnumerateSyscallContextVector` 等）都已经是单数组，无同类问题。
