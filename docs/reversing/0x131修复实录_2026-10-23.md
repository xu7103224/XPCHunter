## 已修复的两个缺陷

### 1. `GetCallbackContextBase` 的驱动名被截断

原版把名字拆成 `_DWORD EncodedName[4]` + 3 个独立后缀变量 + 终止符，
靠**栈上连续布局**拼成一整条宽字符串：

```
EncodedName[0..3] @ rbp-0x30，Suffix1 @ -0x20，Suffix2 @ -0x1C，
Suffix3 @ -0x18，Terminator @ -0x14
```

解码后是 `\Driver\Volmgr`（build ≥ 0x1770）或 `\Driver\Ftdisk`。

我方照抄成独立局部变量时，编译器不保证它们紧跟数组 —— 与
`DriverSection.c` 里 netio/usbport 等路径被截断属同一类缺陷。
名字截断后 `OpenFileSection` 必然失败 → `EnumCallbackContextTable` 返回 0
→ 0x131 恒为 `result=0`。

修法：改成单个显式 `_DWORD EncodedName[8]`，布局由语言保证。

### 2. `ParseNtExportSectionsV3` 的 `ContextOffset` 语义错

原版反编译里 `ContextOffset` 声明在 `[rsp+58h]`，而 `PE_DECODE_CONTEXT`
起点在 `[rsp+50h]` —— **`ContextOffset` 就是上下文 +0x08（读指针本身）**，
不是从 0 起的累计计数器。汇编可证：

```
140035BB0 lea  rcx,[rsp+50h]      ; ctx
140035BB5 call ReadPESectionEntry
140035BBE mov  eax,[rsp+190h]     ; entry+0xF0  消耗字节数
140035BC4 mov  rcx,[rsp+58h]      ; ← ctx+0x08 读指针
140035BC9 add  rcx, rax           ; 读指针 += 消耗量
140035BD3 mov  [rsp+58h], rcx     ; 写回
140035BEA mov  eax,[rsp+0D8h]     ; entry+0x38（RIP 相对位移）
140035BED sub  eax, r15d          ; - ImageBase
140035BF0 add  eax, ecx           ; + 读指针
```

即 `TargetRva = 读指针(推进后) - ImageBase + entry[0x38]`，
`entry[0x38]` 是 RIP 相对位移。

我方实现成从 0 累加的独立变量，漏掉了基址 `ImageBase + InitSectionRva`，
所有 TargetRva 全错。修法：直接用 `((PE_DECODE_CONTEXT*)&ctx)->+0x08`，
两段循环都是「读完 → 先推进 → 再用推进后的值」。

## 剩余差距（已定位到具体位置）

诊断计数（`g_DiagPe*`，随 `0x13A` 的 env 块 0x3B8 起导出）：

```
第一段解码条目数      g_DiagPeL1        = 8
第一段选定的 RVA      g_DiagPeLoop1Exit = 0x16078
第二段解码条目数      g_DiagPeL2        = 108
类型 1294 出现次数    g_DiagPe1294      = 17
通过全部条件的次数    g_DiagPeCond      = 11
实际填写条目数        g_DiagPeDst       = 11
最后一条的类型码      g_DiagPeType1294  = 0x545 = 1349  ← 终止标记
```

**第二段循环在第 108 条取出类型码 `1349`（解码序列的终止标记）而提前 break。**
原版能填满 28 条，说明它不会在这里遇到 1349 —— 即我方
`ReadPESectionEntry` 对某类指令**消耗的字节数与原版不同**，累积偏移漂移后
把普通字节误读成终止标记。

前 11 条能逐字节吻合，说明基址、位移计算、条件判断都已正确；
问题只在解码器推进量的保真度。

### 下一步

1. 在 `ReadPESectionEntry` 里按指令类型逐类比对消耗量（原版 0x14008A54C，
   662 字节；重点是各 `SET_D(SectionInfo, DEC_CTX_CONSUMED, n)` 分支的 n）。
2. 对同一个文件（volmgr.sys，0x1A000 字节）在第 N 条处比对原版与本方的

3. 修好后重跑逐字节比对，目标 28/28。

## 附带记录

- `ParseNtExportDir` 名字有误导：它实际是**基址重定位应用器**（遍历
  IMAGE_BASE_RELOCATION 块，按 HIGHLOW/DIR64 加上 Delta），
  不是导出目录解析器。28 条的 RVA 全部来自 `ParseNtExportSectionsV3`。
- 原版 `OpenFileSection` 的调用族里，只有 `GetCallbackContextBase`
  用了「数组 + 独立后缀变量」的拆分写法；其余
  （`GetCallbackContextBase2` / `BuildRegistryDriverPath` /
  `EnumerateSyscallContextVector` 等）都已经是单数组，无同类问题。

# 【2026-10-23 后续：根因更正 —— 不是解码漂移，而是 FillExportEntrySlot 的兜底从未生效】

上文「第二段：为什么只有 11 条」的结论是**错的**。双机差分证明解码器完全正确，
真正缺失的是 28 项表里 17 个「默认槽」的来源。以下为实测过程与最终修复。

## 1. 用双机差分否证「消耗量漂移」

在原版 `ParseNtExportSectionsV3` 第二段循环的类型读取点（`0x140035C96`，
即 `movzx ebx,[rax+6]`）挂硬件执行断点，命令列表 `dw @rax+6 L1; dq @rdx L1; g`
逐次打印「类型码 + 推进后的读指针」。取到原版完整 108 条序列，与我方
GT[0x4F00] 追踪的 64 条逐条比对：

| 序号 | 读指针 | 类型码 | 长度 | 与我方 |
|---|---|---|---|---|
| 0 | 0x15C107D | 0x50E | 5 | 同 |
| 1 | 0x15C1082 | 0x50E | 5 | 同 |
| 2 | 0x15C1083 | 0x4E7 | 1 | 同 |
| … | … | … | … | 全同 |
| 63 | 0x15C11C2 | 0x50A | 2 | 同 |

**64 条读指针与类型码完全一致**，且两边都在第 108 条（读指针 0x15C1282）
遇到类型 0x545（1349）而退出。解码器、消耗量、循环边界、终止判断全部一致。
「漂移」假设不成立，此前对该路径的一切怀疑都不成立。

## 2. 11 vs 28 的真实解释

在原版 `0x140035D08`（只有类型 == 0x50E 才会到达）再挂一个打印断点，
取到 17 条 0x50E 条目的字段：

| 读指针 | +0x50 标志 | +0x88 | +0x40 位移 | +0x90 | +0xDC | 判定 |

| 0x15C1082 | 0x4041 | 0x40 | 0x18 | 0x06 | 0x44 | 同上 |
| 0x15C10AC | 0x4041 | 0x40 | 0x70 | 0 | 0 | **命中 slot 0** |
| 0x15C10C0 | 0x10041 | 0x40 | 0x88 | 0 | 0 | **命中 slot 3** |
| 0x15C10CA | 0x10041 | 0x40 | 0x90 | 0 | 0 | **命中 slot 4** |
| 0x15C10D8 | 0x10041 | 0x40 | 0xB8 | 0 | 0 | **命中 slot 9** |
| 0x15C10E6 | 0x10041 | 0x40 | 0xE0 | 0 | 0 | **命中 slot 14** |
| 0x15C10F4 | 0x10041 | 0x40 | 0xE8 | 0 | 0 | **命中 slot 15** |
| 0x15C1102 | 0x10041 | 0x40 | 0xF0 | 0 | 0 | **命中 slot 16** |

原版输出里其余 17 个槽的 RVA 全是同一个值 **0x125D40**，它们来自另一趟。

## 3. 17 个默认槽的真实来源：FillExportEntrySlot

`BuildCallbackContextHookTargets`（0x140035EE0）在
`ParseNtExportSectionsV3 + ParseNtExportDir` 都返回 1 之后，
遍历 28 项做「命中则拷 16 字节」，最后调用 `FillExportEntrySlot(pTargetTable)`。

`FillExportEntrySlot`（0x14007A9EC）：

```
v3 = GT[0x2A7]                 ; 若为 0 → ScanKernelModulePESections() 后重读
v4 = GT[76]   (GtEprocessField66)     ; 节区缓冲基址
v5 = GT[33]   (GtEprocessField23)     ; ntoskrnl ImageSize
v6 = GT[3]    (GtNtoskrnlModuleBase)
若 (v3 && v4 && v5 && v6 && v3+32 <= v5)：
    对 28 项中 +4(RVA) == 0 的槽：
        +0 = 1; +4 = v3; +8 = v3 + v6;
        +0x10 = 16 字节 @ (v3+v4); +0x20 = 16 字节 @ (v3+v4+16)
```

实测原版 `GT[0x2A7] = 0x125D40`、`GT[0x2A8] = ntoskrnl + 0x125D40`，
正是那 17 个槽的值。我方该槽为 **0**，于是 17 个槽保持 0。

## 4. 根因：ScanKernelModulePESections 有 5 处错位转写

原版 `0x14007870C` 的反汇编（0x14007873F..0x1400788DC）读出后发现，
我方这版（`SsdtHook.c`）与原文有实质差异：

| # | 我方旧实现 | 原版 | 后果 |
|---|---|---|---|
| 1 | `(unsigned int)ImageBase + TargetOffset1` | `mov ecx,ebx; add rcx,r14`（64 位加法） | 基址被截成 32 位，起点非法 |
| 2 | 解码**之前**推进读指针（用上一轮消耗量） | 解码后 `add rcx,[entry+0xF0]` 再写回 | 偏移错位一条 |
| 3 | 用 `entry+0x00`/`+0x28`/`+0x24` 当字段 | 消耗量 `+0xF0`、段1 目标 `+0x38`、段2 目标 `+0x78` | 字段全错 |
| 4 | 标志位读 `entry+0x80` | `test qword [entry+0x50], 0x4000000` | 条件全错 |
| 5 | 段 1 未命中仍继续段 2 | `cmp ebx,100h; jnb exit` 直接返回 | 控制流不符 |

其中 #1 是致命项：起点变成 0x00CDD750（非法地址），
`ReadPESectionEntry` 首轮即报错，两段循环都没跑起来，`GT[0x2A7]` 永远为 0。

## 5. 修复与验证

按原版汇编逐句重写 `ScanKernelModulePESections`（见
`XPCHunterDrv/src/services/SsdtHook.c`）。修复后：

- `GT[0x2A7] = 0x0000000000125D40`
- `GT[0x2A8] = 0xFFFFF80534525D40`
- **命令 0x131 输出与原版逐字节 100% 一致：1352/1352 字节，28/28 条目全同**
  （对比文件 `build/audit/orig_131.txt` 与 `build/audit/mine_131_new.txt`）
- 回归检查：全量扫描后 `HANDLED=244` 与修复前一致；34 条拒绝仍是
  与原版设计空槽一一对应（另 1 条 0x115 为盲扫请求形状不合导致的 reason 7）

## 6. 方法论记录（本次最有效的一条）

> 不要靠读源码猜「哪一步错了」。把原版驱动当参照系，在**同一条代码路径上
> 打硬件执行断点**，逐次打印关键寄存器/内存，把两边的时序数据摆在一起比对。

本次两个断点各自解决了一个悬案：

1. `0x140035C96`（类型读取点）→ 直接否证「解码漂移」，省掉对整个
   `ReadPESectionEntry`（662 字节）的逐分支审计。
2. `0x140035D08`（0x50E 专属分支）→ 直接算出原版只有 11 条能通过条件，
   把注意力从解析器转移到后续的补槽函数。

另外两条操作要点：
- 原版 `GT[0x304]`（驱动就绪旗）由 `CheckSsdtHookIntegrity` 尾部置 1；
  当握手包暂时不被原版接受时，可用 kd `eq` 直接置位来解锁整条命令通路。
- 原版的 28 项表在 `GT[0x904]` 置 1 后**不会重建**；连续两次 0x131 只有
  第一次会走解析路径，关注断点时必须先重启驱动。
