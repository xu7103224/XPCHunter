# 进程枚举打通与「解码上下文读指针」缺陷类型（2026-10-21）

## 一、结论

命令 **0xE4（CmdEnumProcessListWin10）已打通**：实机返回 `result=1` 与真实的 EPROCESS 链表，
条目 0x298(664) 字节，末项「有后继」标记写在 `+0x290`。

打通它需要连修四处同源缺陷，它们属于同一个类型：

| 位置 | 症状 | 根因 |
| --- | --- | --- |
| `ParseNdisGetVersionSection` | `ndisVer` 恒 0 | 描述符字段位错 + 读指针未推进 |
| `ScanTextSectionPattern` | **BSOD 0x3B**（r9=3，`movzx eax,[r9]`） | 读指针被写成整数 3 |
| `ScanDataSectionPattern` | 恒不匹配（静默错值） | 用局部整数累加，从不写回读指针 |
| `ParseNtKernelDataSections` | `GT[0x36C]` 恒 0 | 同上；另 `InnerFound` 初值写错 |
| `EnumProcessListWin10Operation` | **用户态堆损坏 c0000374** | 把「逐字段拷贝」误移植成越界循环 |

## 二、缺陷类型：`ctx+0x08` 是**读指针**，必须按指针加法推进

PE 解码上下文 `PE_DECODE_CONTEXT` 的真实布局（`XPCHunterDrv.h`）：

```
+0x00 DecodeTablePtr  解码表
+0x08 ReadPtr         当前读指针（初值 = Base，由调用方按解码长度推进）  ← 关键
+0x10 EndPtr          缓冲区结束（Base + Size）
```

`ReadPESectionEntry`（原始 0x14008A54C）**不**回写 `ctx+0x08`：它从 `[ctx+8]` 取游标，
把本次消费字节数写在**描述符**的 `+0xF0`（`PE_DESC_SECTION_SIZE`）。推进责任在调用方。

原始调用方的形态（以 `ScanTextSectionPattern` 0x140062c97..0x140062cb4 为例）：

```
mov eax, [rsp+var_68]    ; desc+0xF0 = 本条目消费字节数
mov rcx, [rsp+var_1A0]   ; ctx+0x08  = 读指针
add rcx, rax             ; 读指针 += 消费字节数
mov [rsp+var_1A0], rcx   ; 写回
```

`ScanDataSectionPattern`(0x140062e16..e2d)、`ParseNtKernelDataSections`(0x140062a28..a3d)
是同一形态，逐条核对过。

**坑**：Hex-Rays 把 `ctx+0x08` 显示成一个整数局部量 `CumulativeSize`（因为调用方既把它
当指针累加、又拿它的低 32 位参与 RVA 计算），照抄伪代码就会写成整数累加器，或写成
`ctx+0x08 = 累加值` 的整数赋值 —— 两种都会把指针弄坏。正确写法只有一种：

```c
ReadContext.ReadPtr += PE_DESC_SECTION_SIZE(&SectionEntry);   /* 指针加法，紧跟 ReadPESectionEntry 之后 */
```

两种错误形态的实机表现不同，且都出现过：

* `ctx+0x08 = (ULONG64)SectionSize;`（整数赋值）→ 第二轮 `ReadPESectionEntry` 从地址 3
  取操作码 → **BSOD 0x3B**。栈：`ExceptionCode c0000005, Rip View___Driver64+0x554e9`，
  上下文 `r9=3`、`ds:0000000000000003=??`。
* 用局部 `CumulativeSize` 累加、从不写回 → 每轮解析**同一个**描述符 →
  条件恒不成立（`GT[0x366]`/`GT[0x36C]` 恒 0），命令静默返回 REJECTED。

另外注意：有若干调用点把推进写在 `ReadPESectionEntry` **之前**（用上一轮的长度），
首次迭代会拿未初始化描述符的 `+0xF0` 去加，同样危险 —— 推进必须紧跟取描述符之后。

## 三、已修的四处（含反汇编依据）

1. **`ParseNdisGetVersionSection`**（原 0x140062170）
   - 判据字段修正为 `desc+0x70`（版本值）、`desc+0x74`（标志）。
   - 实机确认 `GT[0x363] = 0x00060053`。
2. **`ScanTextSectionPattern`**（原 0x140062BD0，写 `GT[0x366]`）
   - 读指针改为 `ReadContext.ReadPtr += PE_DESC_SECTION_SIZE(&SectionEntry)`。
   - 判据 = `type==1296 && desc+0x88==0x40000 && desc+0x78!=0 && desc+0x50==64`，
     RVA = `读指针 + desc+0x78 - ImageBase`（0x140062cd9/ce7/cf2/cfd 逐条核对）。
   - 实机确认 `GT[0x366]` 从 0 → `FFFFF80027EE6788`。
3. **`ScanDataSectionPattern`**（原 0x140062D50，写 `GT[0x374]/GT[0x375]`）
   - 读指针改为指针加法；字段判据修正为 `type==1294 && desc+0x50==0x40000 && desc+0x88==0x40`，
     RVA 取 `desc+0x40`（旧代码把三个字段全写错了位置）。
4. **`ParseNtKernelDataSections`**（原 0x140062884，写 `GT[0x36C]`）
   - 外层/内层两处读指针都改为指针加法（内层嵌套读也只在类型命中时推进，
     与原始 0x140062a96..aab 一致）。
   - 内层 `InnerFound` 初值 = `IsWin10`（原始 0x140062a0a `mov sil,[rsp+var_1C0]`），旧代码恒 0。
   - 实机确认 `GT[0x36C]` 从 0 → `FFFFF80027EE6648`。

## 四、命令 0xE4 的重写（`EnumProcessListWin10Operation`）

旧实现把每个版本的字段映射写成：

```c
for (i = 0; i < FieldCount; i++)            /* FieldCount = 456/459/460/463/467/472 */
    *(_QWORD *)(OutputPtr + 80 + i * 8) = Eprocess[StartField + i];
```

`FieldCount` 实际是 **EPROCESS 字段索引**（与 `LinkField=481/484/485/488/497` 同一套），
不是字段个数。于是单个 664 字节条目被写到 `80 + 456*8 = 3728` 字节，越界 3064 字节。
实机表现：`Critical error detected c0000374` → `ntdll!RtlReportCriticalFailure+0x56`
（用户态 fail-fast，不是内核 bugcheck；`kd` 侧 `.bugcheck` 显示 code 0）。

原始实现是**逐字段显式拷贝**，按 NDIS 版本分 12 个分支：

| 版本 | 字段数 | 链表偏移 | 分派链位置 |
| --- | --- | --- | --- |
| 0x50001 | 29 | 0x2F0 | 0x14005e44c |
| 0x50002..0x5FFFF | 29 | 0x2F8 | 0x14005e661 |
| 0x60000 | 52 | 0xFE8 | 0x14005e869 |
| 0x60001 | 52 | 0x1000 | 0x14005ebcd |
| 0x60014 | 53 | 0x1478 | 0x14005ef2c |
| 0x60015..0x60027 | 48 | 0xF88 | 0x14005f29c |
| 0x60028..0x60031 | 48 | 0xF20 | 0x14005f5c6 |
| 0x60032..0x60045 | 48 | 0xF40 | 0x14005f8f0 |
| 0x60046..0x6004F | 48 | 0xF20 | 0x14005fc1a |
| 0x60050..0x60051 | 48 | 0xF20 | 0x14005ff44 |
| 0x60052 | 48 | 0xF28 | 0x14006026e |
| 0x60053+ | 48 | 0xF08 | 0x140060598 |

这些表由 `tools/ida_extract_proc_tables.py` 从反汇编直接生成（不手抄），已合入
`XPCHunterDrv/src/services/Operation.c`。单位是 `PROC_FIELD_MAP{Src,Dst}` 表 + 循环，
落地字节与原版逐字段拷贝完全一致。

其余与原始对齐的细节：

* 前置校验顺序：链表头非空/高于 `MmSystemRangeStart`/版本非 0 → 输出指针非空 →
  `OutSize >= 0x298` → 两个 `MmUserProbeAddress` 边界 → `ProbeForWrite` → 清零。
* 循环头条件：`index < 0x1000 && Eprocess > MmSystemRangeStart && CheckMemoryValid(Eprocess)==1
  && RemainingSize >= 0x298`。
* 尾项标记：`if (PrevEntry) *(UCHAR*)(PrevEntry + 0x290) = 1;`
* 下一个条目地址 = `Out + (OutSize - RemainingSize)`（原始尾部的等价写法）。

## 六、待核查：32 个「疑似未推进读指针」的调用点

用下面的判据扫过全仓（`ReadPESectionEntry` 调用点落在循环内、且窗口内没有对该上下文的
`ReadPtr +=` 推进）：仍有 **32 处**需要逐个对照原始函数。已确认的头部：

```
features/PeParse.c:261/296/331/356/1417/2480      kernel/Minifilter.c:3484/3672/5012/7826/7886/8178/8227/8392
kernel/ContextMgmt.c:3429                          kernel/ModuleMgmt.c:4339
kernel/PeSectionParse.c:934/990                    kernel/Registry.c:716
services/SsdtHook.c:2049/2093/2184/2227/2764/2801/2881/3013/3329/3375
services/SyscallTable.c:1380
```

（另有若干调用点把推进写在了 `ReadPESectionEntry` 之前，首轮会用到未初始化描述符，
同样需要改到取描述符之后。）

处理顺序建议：先 `SsdtHook.c` 的（SSDT/ShadowSSDT 与 Hook 检测是前端主功能的数据源），
再 `Minifilter.c` / `PeParse.c`。每处都必须先看原始反汇编确认推进点与推进量，禁止批量套用。

## 八、部署提醒（本次踩到两次）

* 驱动已加载时 `.sys` 文件被映射，`copyFileFromHostToGuest` 会**静默失败**
  （返回码 127），`sc start` 随后返回 1056（已在运行）—— 于是测试跑在旧镜像上。
  可靠流程：`vmrun reset` → 等 IP → 推送 → `sc create`/`sc start` → `sc query` 看
  `STATE : 4 RUNNING`。仅 `sc stop` 有时不生效，此时只能 reset。
* guest 若停在 kd 的 `kd>` 提示符（用户态 fail-fast 也会让内核调试器断下），
  所有 `runProgramInGuest` 都会超时（rc=124），而界面看起来像「命令挂了」。
  先 `kd_go`（或看 `vm_state probe=true` 的 `guest_frozen`）再判断。
