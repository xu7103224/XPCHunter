# 原版 UI + 自研驱动联调：0x25 槽位缺陷与蓝屏根因

日期：2026-10-29
环境：Win10_x64_Main（Windows 10 LTSC 17763.8027，8 核 4 GB，NAT）
目的：用原版 PCHunter64.exe 作为"参照客户端"驱动我方 `XPCHunterDrv.sys`，
      以验证驱动实现是否与原版逐字节等价。

## 一、结论（先看这里）

1. **发现并修复了一个真实的内核缺陷**：`CmdEnumKernelDrivers`（命令 0x25）
   把第三个函数指针槽算成了 `0x4278`，实际应为 `0x42AA`。
   0x4278 是 SSDT 哈希常量槽，`InitSyscallNumberTable` 往里写
   `0x59FA3B98`；驱动拿到这个值直接 `call rbp` → 内核页错误 → 蓝屏。

2. **修复后原版 UI 能加载我方驱动且不蓝屏**，`sc query View++` 显示 RUNNING。
   手动 `sc create` + `sc start` 后，探针握手完全正常：
   - `open device ok`（`\\.\View++ByLinxer`）
   - `0x22` → `result=1`
   - `0x24` → `result=1, build=17763 (0x4563)`

3. **仍未打通**：原版 UI 自身不建主窗口。它启动后卡在"创建服务 → 加载驱动"
   之后，进程存活但 `MainWindowHandle=0`。同时它反复弹 `License过期！`——
   因为本 VM 的时间被 VMware 周期性拉回宿主时间（2026-10-28），
   而 pchunter.ek 授权截止 2024 年。这两件事都**不是驱动缺陷**。

## 二、缺陷详情

### 2.1 现象

原版 UI 加载我方驱动后，第一次启动触发 bugcheck：

```
SYSTEM_SERVICE_EXCEPTION (3b)
Arg1: 0000000080000003   (STATUS_BREAKPOINT / 异常码)
Arg2: fffff80704d342c5   (nt!KeCheckStackAndTargetAddress+0x45, int 3)
PROCESS_NAME: PCHunter64.exe
STACK_TEXT:
  ...
  nt!KiPageFault+0x43d
  0x59fa3b98                     <-- 跳到了这个地址
  View___Driver64+0x22e39       <-- 我方驱动
SYMBOL_NAME: View___Driver64+22e39
```

`0x59fa3b98` 是个 32 位值，落在用户态地址空间。内核 `call` 到那里必然页错误；
随后异常分发又撞到非法 handler，最终 0x3B。

### 2.2 定位

`View___Driver64+0x22e39` 用 map 文件回查：

```
0x140022D70  CmdEnumKernelDrivers   (+0xC9 = 0x22E39)
```

反汇编（dumpbin `/range:0x140022D70,0x140022EE0`）：

```
140022DD4  call qword ptr [14008D2E0h]   ; ProbeForWrite
140022DDA  mov  ecx,4226h                ; GtObjectTypeRefFunc
140022DDF  call 14001EA90                ; GtRead
140022DE4  mov  ecx,4271h                ; GtTotalSize|GtObjectTypeField42|GtDriverObject
140022DE9  call 14001EA90                ; GtRead
140022DF1  mov  ecx,42AAh                ; ← 修复后：第三个槽
140022DF9  call 14001EA90                ; GtRead
...
140022E37  call rbp                      ; ← 崩溃点（rbp = 第三个槽的值）
```

修复前后对比（我方构建）：

| | 槽 1 | 槽 2 | 槽 3 |
|---|---|---|---|
| 原版 `0x14004F3xx` | `0x4226` | `0x4271` | **`0x42AA`** |
| 修复前我方 | `0x4226` | `0x4271` | **`0x4278`** ← 错 |
| 修复后我方 | `0x4226` | `0x4271` | **`0x42AA`** ✓ |

原版汇编（`0x14004F3C5  mov ecx,42AAh; call GtRead`）是唯一权威依据。

### 2.3 根因

`XPCHunterDrv/inc/xpc_gt_enum.h` 里的别名链把 `GtEprocessField120` 塌缩了：

```c
enum { GtEprocessField110 = 120, GtEprocessField120 = 130, ... };
#define GtEprocessField120  GtEprocessField110   // index 120   ← 宏覆盖了枚举
```

于是 `GtUninstallHookSyscallPeOffset | GtEprocessField120`
= `0x4228 | 120` = **`0x4278`**，而不是原版要的 `0x42AA`。

`0x4278` 恰好是 `GtSyscallHashInit94`（SSDT 哈希表初值），
`InitSyscallNumberTable()` 在 `SSDT.c` 里显式写入：

```c
GtWrite(17016, 0x59FA3B98LL);   /* 17016 = 0x4278 */
```

崩溃时 `rbp` 正好等于 `0x59FA3B98` —— 与 dump 完全吻合。

### 2.4 为什么一直没发现

`XPCHunterUM/src/frontend.c` 的 `g_FeSkip` 把 0x25 列在跳过列表：

```c
static const ULONG g_FeSkip[] = { 0x25, 0x28, 0x30, 0x56, 0x115 };
```

我方客户端**从不发送 0x25**，所以 126 条命令的 A/B 比对里这条一直是"跳过"。
原版 UI 一启动就发 0x25，直接踩中。

### 2.5 修复

`XPCHunterDrv/src/services/IoctlDispatch.c`：

```c
/* 修复前 */
__int64 ServiceTable = GtRead(GtUninstallHookSyscallPeOffset | GtEprocessField120);
__int64 (*pCurrentThreadFunc)(void) = (__int64 (*)(void))ServiceTable;
if (!pObjectTypeFunc || !pDriverObjectFunc || !ServiceTable) return 0;

/* 修复后 */
__int64 (*pCurrentThreadFunc)(void) =
    (__int64 (*)(void))GtRead((GLOBAL_TABLE_INDEX)0x42AA);
if (!pObjectTypeFunc || !pDriverObjectFunc || !pCurrentThreadFunc) return 0;
```

反汇编验证：新构建的槽位常量已是 `4226h / 4271h / 42AAh`，与原版逐条一致。

## 三、环境障碍（与驱动无关）

### 3.1 时间被拉回，License 判过期

`pchunter.ek` 授权截止 2024-09。本机系统时间 2026-10-28，原版 UI 弹
`License过期！`（`#32770` 对话框，Static id=65535）。已在 guest 侧做：

```
bcdedit /set testsigning on
bcdedit /set nointegritychecks on
sc config W32Time start= disabled
reg add "HKLM\SOFTWARE\VMware, Inc.\VMware Tools" /v TimeSync /d 0
vmx: tools.syncTime = "FALSE" + time.synchronize.* = "FALSE"
```

`Set-Date -Date '2024-09-01 12:00:00'` 能成功，且 45 秒内不回跳。
但**每次 VM 重启**会从宿主 RTC 重新读时间，需要重新设一次。

### 3.2 vmrun 的 guest 通道被我误停 VMTools 搞坏

为了阻止时间同步，执行了 `sc config VMTools start= disabled` + `sc stop VMTools`。
结果 vmrun 的 `runProgramInGuest` / `copyFileFromGuestToHost` 全部超时（exit 124），
因为这两个 API 依赖 vmtoolsd。

恢复办法（已用 VNC 控制台执行成功）：

```
sc config VMTools start= auto
sc start VMTools
```

### 3.3 VNC 控制台通道（不依赖 VMware Tools）

`vmx` 里开启：

```
RemoteDisplay.vnc.enabled = "TRUE"
RemoteDisplay.vnc.port = "5911"
```

> 不要设 `RemoteDisplay.vnc.password` / `.key`——VMware 对设置了密码的
> VNC 会强制走 SecurityType=2（DES 挑战），而它的挑战响应实现与标准
> RFB 客户端不兼容（实测发完响应后服务端不再回 4 字节 SecurityResult）。
> 去掉密码后 SecurityType=1（None），可直接连接。

主机侧 `C:\Users\Administrator\AppData\Local\Temp\vnc_tool.py` 是一个
最小 RFB 3.8 客户端，支持：截图（raw encoding）、鼠标点击、键盘输入
（含 Ctrl/Enter/Tab/Delete 等特殊键）。用它可以在 vmtoolsd 失效时
仍然驱动 guest 桌面。

## 四、当前状态与后续

| 项 | 状态 |
|---|---|
| 0x25 槽位缺陷 | 已修复（源码 + 反汇编双重验证） |
| 原版 UI 加载我方驱动是否蓝屏 | **不再蓝屏**，服务 RUNNING |
| 设备对象/IOCTL 通道 | 正常（手动加载后 0x22/0x24 握手通过） |
| 原版 UI 是否显示主窗口 | 未达成；进程存活但不建窗口 |
| License 校验 | 受时间问题阻塞（重启后需重设时间） |

后续要打通"原版 UI 出数据"，需要按顺序解决：

1. VM 启动后立刻设时间（或用 VNC 脚本设），确认 `pchunter.ek` 校验通过；
2. 确认原版 UI 创建 `View++` 服务后是否真的 `sc start` 成功 ——
   目前观察到服务能创建为 RUNNING，但设备对象在 UI 侧加载后一度消失，
   需要确认是否 `DriverUnload` 被提前调用；
3. 若 UI 仍不建窗口，用 Process Monitor 或 ETW 抓它的文件/注册表行为，
   定位它卡在哪一步（它做过标题混淆 `rasnnzb`/`hvhhme`，属正常反调试）。
