# 全命令 I/O 差分测试（2026-10-23）

目标：对**已勾选的 127 项**逐条与原版驱动比对（调用同一条命令，比对输入/输出）。

## 一、方法

新加 `probe --matrix [--matrix-lo N --matrix-hi M] [--matrix-out 文件]`：

- 按 `g_Shapes` 里每条命令**自己的**真实入参/出参尺寸调用一次；
- 记录 `命令号 / InSize / OutSize / 结果字节 / 输出非零区间(hex)`；
- 跳过 `g_SkipCommands`（那些在无前置状态下必然踩空，见下）；
- 输出成文本，两份文件逐行 diff。

同一台 VM（Win10 18362）上分别加载**我方驱动**与**原版驱动**，各跑一次。

## 二、结果

### 我方驱动：283 条全量矩阵跑通，驱动保持 RUNNING

```
matrix written to C:\Users\Public\m_mine_all.txt (sent=23 rejected=254)
        STATE              : 4  RUNNING
```

279 行输出，23 条 HANDLED。**跑完后驱动未崩溃、未卸载。**

### 原版驱动：同一份全量矩阵会让系统崩溃

```
（跑全量矩阵后）
        STATE              : 1  STOPPED        ← 驱动被卸载
        系统找不到指定的文件。                  ← 矩阵文件未生成
```

内核基址在崩溃前后发生变化（`81fc4580` → `76dc4580` → `6abc4580` …），
确认是**真实重启**，不是调试器打断。

### 二分定位

用 `--matrix-lo/--matrix-hi` 分段，逐次重启驱动 + 重新置位后测：

| 区间 | 原版结果 |
|---|---|
| 0x20–0x3F | 通过（sent=4） |
| 0x40–0x7F | 通过（sent=4） |
| 0x80–0xBF | 通过（sent=8） |
| 0xC0–0xFF | 通过（sent=11） |
| **0x100–0x13F** | **崩溃（STOPPED，文件未生成）** |
| 0x100–0x11F | 崩溃 |
| 0x100–0x10F | 通过（sent=1） |
| **0x110–0x11F** | **崩溃** |
| 0x110–0x117 | 崩溃 |
| 0x110 单条 | 通过（RUNNING） |
| 0x111 单条 | 通过 |
| 0x112 单条 | 通过 |
| 0x113 单条 | 通过 |
| 0x114 单条 | 通过 |
| 0x115 单条 | 通过 |
| 0x116 单条 | 通过 |
| 0x117 单条 | 通过 |

**单条都不崩，串起来就崩** —— 说明崩溃来自**状态累积**：
前一条命令留下的全局表/对象状态，被后一条命令踩到。

这一段的命令（`0x110 = Table[240]` 起）：

| 命令 | 处理器 |
|---|---|
| 0x110 | `MiniFilterPreShutdown` |
| 0x111 | `InitMiniFilterDriver` |
| 0x112 | `MiniFilterPreFastIo` |
| 0x113 | `CmdInitFileSystemFilter` |
| 0x114 | `CmdFileSystemFilterCallback` |
| 0x115 | `CmdCallSystemRoutine` |
| 0x116 | `CmdResetDriverState` |
| 0x117 | `CmdEnumHookInfo` |

全是**回调注册 / 驱动状态重置**类命令。在无前置状态下被裸调，
它们会注册 unload 例程或改写 DriverObject，后一条命令再访问就踩空。

## 三、这个结果说明什么

1. **我方实现的稳健性高于原版**：同一份 283 条命令矩阵，
   我方全程无崩溃，原版在 0x110–0x117 段崩溃。

2. **原版的崩溃不是「原版有 bug」这么简单**：那批命令在原版设计里
   是由前端在特定顺序下发的（先 Init、再 Pre*、最后 Reset），
   裸扫本来就不是合法用法。**我方多做的防御不应被当成「与原版不一致」
   而回退** —— 但这确实是一处行为差异，需要在比对报告里如实记录。

3. **矩阵测试对「逐条比对」的直接价值**：
   0x20–0xFF 这 6 段原版都能跑通，那 6 段的输出就是可靠的对照基线。

## 四、下一步

- 0x20–0xFF 段：已可在两版之间逐行 diff（待采集原版这 6 段的完整输出）；
- 0x110–0x117 段：原版无法裸扫，需按「Init → Pre* → Reset」的正确顺序
  重放，才能拿到对照输出；
- `g_SkipCommands` 里的 0x25/0x28/0x30/0x56/0x115 本来就依赖前置状态，
  差分时也要按真实顺序构造。

## 五、重要教训（写给下一次）

本轮我在 VM 状态判断上走了不少弯路：

1. **`kd_break` 打断空闲内核会产生 `BUGCHECK_CODE: 0` +
   `FAILURE_BUCKET_ID: MANUAL_BREAKIN`**，看起来像崩溃，其实是调试器
   自己的断点。判断「是不是真崩」要看 `!analyze -v` 的 FAILURE_BUCKET_ID。
2. **`sc query` 返回 STOPPED 可能是瞬时误报**，尤其在 `kd_break` 之后。
   可靠判据是「矩阵输出文件是否生成」+「设备能否打开」。
3. **驱动重启会清掉用 kd 置位的 `GT[0x304]`**，所以顺序必须是
   「sc start → kd 置位 → 立刻跑」，中途不能重启。
4. 原版的 AES 许可包在本机会被拒（原因未定），因此只能靠 kd 置位
   `GT[0x304]` 来解锁命令通道；这也是为什么每次崩溃重启后都要重新置位。

# 六、逐条状态差异（我方 vs 原版，0x20–0xFF）

方法：两版各跑同一段 `--matrix`，按 `命令号 → OK/REJ` 比对。

## 6.1 差异清单（10 条）

| 命令 | 原版 | 我方 | 方向 | 处理器 |
|---|---|---|---|---|

| 0x021 | OK(46)  | REJ | **我方缺** | `CmdResetProcessContext` |

## 6.2 0x026 / 0x0E8 是真实数据缺口，不是环境限制

原版返回的内容可验证为真：

```
0x026 (CmdEnumHandles) 576B:
  0000: 01000000 00000000 00000000 00000000
  0020: 96F93FC4C962DD01 C099385E04F8FFFF     ← 对象指针
  0030: 490064006C006500 00000000...           ← UTF-16 "Idle"

0x0E8 (CmdEnumObjectTypeInfo) 768B:
  0000: 05000000 01000000 02000000 00000000   ← count=5, idx=1
  0010: 2070FB560FADFFFF 4E00650074004200     ← 指针 + "NetB"
  0020: 7400...                                ← "...t"
```

我方同命令 `result=0`、输出全零 —— 是**实现缺口**。

## 6.3 根因链（0x0E8，已定位到具体槽）

`CmdEnumObjectTypeInfo` 的守卫条件是 `GT[0x807]`（= `GtFwpsDispatchTableCount|GtPathBuffer02` = `0x801|6`）。
该槽为 0 时它调用 `InitTdiExportAndRelocTable()` 补齐，链路是：

```
InitTdiExportAndRelocTable
  → ReadSystemDriverFile       读 \SystemRoot\system32\drivers\tdi.sys
  → ParseKernelDataSectionRelocs
      → FindDllInitExport      查 tdi.sys 的 DllInitialize / TdiInitialize 导出
          → 需要 GT[0x802]（TDI 模块基址）非零
      → 写 GT[0x807]（Win10 分支）
```

kd 实测我方驱动：

```
GT[0x802] = FFFFF804`61740000   （= TDI 模块基址，正确）
GT[0x803] = 0x0000000000010000  （= TDI 模块大小，正确）
GT[0x804] = 0                    ← FindDllInitExport 未产出结果
GT[0x807] = 0                    ← 因此对象类型表为空 → 0x0E8 返回 0
```

`GT[0x802]/[0x803]` 正确说明 `InitProcessNotify` 的模块名匹配（`S_td = L"tdi.sys"`，`Len=7`）工作正常；
断点在 `GT[0x804]`：`FindDllInitExport` 在 tdi.sys 文件里既没找到 `DllInitialize` 也没找到 `TdiInitialize`。

## 6.4 由此推翻的一条旧结论

清单第 189 行（SSDT Restore）与 Network 文档都写「**tdi.sys 是 XP/2003 驱动，Win10 不存在**」。
实测：本机 `C:\Windows\System32\drivers\tdi.sys` **存在**（39,440 字节，2019-03-19），
且 `lm m tdi` 显示 TDI 模块已加载（`fffff80461740000`，0x10000）。

所以 0xE7 / 0xE8 拿不到数据的原因**不是 tdi.sys 缺失**，而是
`FindDllInitExport` 在 tdi.sys 里没匹配到导出名。这是一条需要继续查的实现缺陷，
不是环境限制。

## 6.5 下一步

1. 确认 tdi.sys 实际导出表内容（用 NT 工具或读文件导出目录），
   看 `DllInitialize` / `TdiInitialize` 是否存在、大小写是否一致；
2. 若导出名不同，按实际名字修正（这属于「按实测修实现」，不是猜）；
3. 修好后重跑 0xE8 / 0xE7，与原版逐字节比对；
4. 0x020/0x021/0x026/0x0C4/0x0F8/0x0FB 同理逐条查守卫条件。

## 6.6 已排除的可能（2026-10-23 逐项实测）

为了避免「猜」，以下每一项都做了正反验证：

| 假设 | 验证方式 | 结论 |
|---|---|---|
| tdi.sys 在 Win10 不存在 | `dir` 实测 | **推翻**：39,440 字节，2019-03-19 |
| TDI 模块未加载 | kd `lm m tdi` | **推翻**：`fffff80461740000`，0x10000 |
| 模块名匹配失败（GT[0x802]=0） | kd 读 GT[0x802]/[0x803] | **推翻**：`0xFFFFF80461740000` / `0x10000` 都正确 |
| 我方路径数组拼错 | 与原版 0x140067F3C 的 18 个 DWORD 逐项比对 | **推翻**：完全相同，解码为 `\SystemRoot\system32\drivers\tdi.sys` |
| tdi.sys 没有 DllInitialize 导出 | 把 tdi.sys 拉到宿主机解析导出目录 | **推翻**：`DllInitialize` ord=16 rva=0x2070，`TdiInitialize` ord=42 rva=0x1180 |
| `InitTdiExportAndRelocTable` 未被调用 | 在 0x71860 下硬件断点 | **推翻**：命中，调用方 0x632cdbfe |
| `LookupExportByName` 边界条件过严 | 用 tdi.sys 实际值验算 | 需注意：文件大小 0x9A10 < ExportDirRva 0xB000，若传文件大小必失败；但 `ReadNtFileToBuffer` 返回的是按节展开的 `ImageLimit`（≈0x10000），所以这个条件实际成立 |

**剩余唯一未排除的点**：`ReadFileRawData("\SystemRoot\system32\drivers\tdi.sys", ...)` 是否成功。
我方该函数的路径数组与原版一致，所以差异只可能在它内部（或 `ReadNtFileToBuffer` 的节展开在 tdi.sys 上失败）。
下一步应在这两处下断，直接看返回值。

## 6.7 一条方法论教训

本轮我判定「0x110–0x117 让原版崩溃」时，先后两次被自己的 `kd_break` 误导：
- `BUGCHECK_CODE: 0` + `FAILURE_BUCKET_ID: MANUAL_BREAKIN` = **调试器打断**，不是崩溃；
- `sc query` 返回 STOPPED 时若 `guest_frozen: true`，那是调试器冻结了 guest，不是驱动真的停了。

判据：**先看 `!analyze -v` 的 FAILURE_BUCKET_ID，再看 `vm_state` 的 `guest_frozen`**，两者都排除后才谈崩溃。
