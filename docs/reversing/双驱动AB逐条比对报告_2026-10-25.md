# 双驱动 A/B 输入输出逐条比对（2026-10-25）

## 0. 目的与方法

按"分别用命令调用两个驱动的接口，各自保存输入输出，逐条比对，
分析功能是否对齐"执行。

### 工具

| 组件 | 说明 |
|---|---|
| `xpch_probe.exe --ab` | A/B 采集模式。每条命令记录**完整输入 + 完整输出 + 返回码 + GetLastError** |
| guard 缓冲 | 实际分配 `OutSize + 256KB`，只把 `OutSize` 传给驱动。不校验尺寸的处理器越界写只落进 guard，不破坏堆 |
| `ab_last.txt` | 每条调用前用 `CreateFile`+`FlushFileBuffers` 落盘"正在调哪条"，BSOD 后能精确定位 |
| `build/ab_diff.py` | 逐条比对：状态 / 返回码 / 输入 / 输出，并对输出差异分级 |

### 采集范围

命令号 0x20–0x13A 共 283 个。跳过 157 条（见下），实际采集 **126 条**。

**跳过的理由分两类**：

1. **缺少前置状态会崩**（与 `g_SkipCommands` 一致）：
   0x22（会清空命令表槽 198..224）、0x25、0x28、0x30、0x56、0x115。

2. **实机证实盲调必崩**（本轮新发现，三条都有原版对照）：
   - `0x78 CmdQuerySystemInfoEx` — BSOD 0x50
     `nt!ObpCaptureObjectCreateInformation+0x141`，arg1=`0xfffff80300000000`
   - `0xC2 CmdEnumGdiObjects` — 同址 BSOD 0x50
   - `0xEC CmdReadExportDirectory` — BSOD 0x3B（给足 2MB 仍崩）
   三条命令**在原版驱动上崩溃位置与参数完全一致**，不是复刻偏差，
   而是"缺前置上下文时走到对象创建路径"。

3. **操作类命令**（`g_AbDangerous`，约 150 条）：
   会创建/打开对象、装卸驱动、改内核内存、装 hook。自动化盲调会污染
   系统状态或直接把 guest 弄坏。原版前端只在用户点击并带真实句柄时发送。

## 3. 逐条分析

### 3.1 `0x021 CmdResetProcessContext`：返回值截断，非门禁差异

我方 `res=46` 来自代码：

```c
GtWrite((GLOBAL_TABLE_INDEX)0x185, 0);
return GtWrite(GtEprocessModuleEntrySize | GtEprocessField22, 0);
```

反汇编确认我方写索引 `0x82E`（`mov ecx,82Eh`），`GtWrite` 返回
`(unsigned int)Index = 2094`，而分发器只取低 8 位：`2094 & 0xFF = 46`。

**原版 `sub_14007F118` 的代码与此完全相同**（`GtWrite(GtFwpsDispatchTableBase|GtEprocessField36, 0)`
= `0x800|46` = `0x82E`，同一索引）。两边实现一致，差异只在原版该次返回 REJ——
说明原版在执行前被某道关卡拦下，与本函数无关。

### 3.2 `0x026 CmdEnumHandles`：原版状态本身不稳定

- 2026-10-23 矩阵（`m_o1.txt`，OutSize=576）：原版 **OK**，返回
  `01000000...CB36CE06 0163DD01 ...`（含 FILETIME）
- 本轮 A/B（同样 OutSize=576）：原版 **REJ**
- 本轮单独跑 0x26：原版 **仍 REJ**

同命令、同尺寸、同机器，跨会话语义不稳。可能依赖 `InitCallbackFunctions`
填的 GT 槽在 A/B 循环中被前序命令改变。**不作为实现差异认定**。

### 3.3 `0x027 CmdCheckProcessAccess`：上轮结论需订正

| 场景 | 原版 | 我方 |
|---|---|---|
| A/B（InSize=0，OutSize=8192） | **OK / res=1** | REJ |
| 上轮 `--raw 0x27`（InSize=0，OutSize=0x4000） | REJ | REJ |

原版在**给了输出缓冲**时返回 OK，无输出缓冲时返回 REJ。这说明原版
`sub_1400800C0` 里有**输出缓冲相关的分支**，而我方上次重写时只按
"InSize==16 才处理"实现，漏了这条。

⚠ 这是本轮 A/B 发现的**真实实现缺口**，需要重新对照原版反汇编修正。

### 3.4 `0x0D4 / 0x0E8`：我方返回数据，原版返回 0 条

原版 `CmdEnumObjectTypes`（`0x140088A60`）在 build 18362 走
`DispatchEnumObjectTypes`，末尾 `return *OutputBuffer != 0`。
原版返回 REJ 说明**枚举到 0 条**；我方返回 2816B 数据。

我方 `CmdEnumObjectTypes` 转调 `EnumObjectTypeInfoOperation`，
该函数按 build 分支（`Operation.c:1786` 有 `BuildNumber >= 0x23F0`）。
需核对我方在 0x47BA 时是否走了与原版相同的 `DispatchEnumObjectTypes`
等价路径，还是走了能枚举到数据的另一条。

⚠ 待进一步核对。

### 3.5 `0x0E1 CmdEnumProcessListEx`：**推翻上轮"双方都 REJ"的结论**

上轮结论是"原版与我方 0xE1 都 REJ，逐字节一致"。本轮 A/B 推翻了它：

```
原版: CMD 0x0E1 INSZ=0 OUTSZ=480 RES=1 OK
      OUT 88678E5705F8FFFF0000000000000000000000000000000000
          20A2070ED1FFFF108779070ED1FFFF801363070ED1FFFF
          F7F111A12359C0479A68D0BAFB577901 0600000001000000 ...
我方: CMD 0x0E1 INSZ=0 OUTSZ=480 RES=0 REJ
```

原版返回 181 字节，含真实内核指针 `0xFFFFF805578E6788` 与若干
`0xFFFFD10E07A22020` 这类会话空间地址；我方 REJ。

上轮之所以判"一致"，是因为当时用 OutSize=0x1E0 且未做 A/B 完整采集，
两边都 REJ 就下了结论。**这正是本轮 A/B 比对的价值所在。**

⚠ 这是**真实的实现缺口**：我方的 `CmdEnumProcessListEx` 在同样入参下
没有返回原版的数据。

**已单独复测确认稳定**（两驱动分别加载、各自单跑 0xE1）：
```
原版: CMD 0x0E1 INSZ=0 OUTSZ=480 RES=1 OK   OUT <181 字节>
我方: CMD 0x0E1 INSZ=0 OUTSZ=480 RES=0 REJ
```

**根因方向（未闭环）**：原版 `sub_140062ED8` 的入口守卫是

```
0x140062EF8  mov esi, r9d        ; r9d = 分发器第4参数
0x140062EFB  mov rbx, r8         ; r8  = 分发器第3参数
0x140062F16  test rax,rax        ; GT[0x366] 进程链表头
0x140062F38  test r14,r14
0x140062F48  cmp r14,[MmSystemRangeStart]
0x140062F51  test r15d,r15d      ; GT[0x363] 构建号
0x140062F63  cmp esi, 3Ch ... 0x3C0   ; 要求 >= 960
0x140062F69  jb  loc_14006662A   ; 否则返回 0
```

按分发器映射（`+0x20`=InSize→rdx、`+0x24`=OutSize→r9d），`esi` 应为
OutSize=480，`480 < 0x3C0` 应当走失败分支。**但原版实测返回了 181 字节
真实数据**，与这条推断矛盾。

三种可能，需后续用单步/断点确认：
1. 我方分发器把 OutSize 放在 `r9d` 之外的寄存器，与原版 ABI 不一致
   （我方 `Handler(CtxPtr, OutSize, ExtraPtr, CtxSize)`，
   即 rcx=CtxPtr, rdx=OutSize, r8=ExtraPtr, r9d=CtxSize）；
2. 原版该命令还有另一条未识别的成功路径；
3. probe 构造的请求里 `+0x24` 实际不是 480。

**已验证参数映射是一致的**（读原版 `DispatchDeviceControl`）：

```
0x1400824C7  mov eax,[rdi+20h]  → var_C4 → 0x1400825B3 mov edx, var_C4  ; 第2参数
0x1400824CE  mov eax,[rdi+24h]  → var_C8 → 0x1400825AB mov r9d, var_C8  ; 第4参数
```

我方 `DriverEntry.c` 的取值与之一致：
```c
OutSize = *(ULONG *)(Buffer + 0x20);   /* → rdx */
CtxSize = *(ULONG *)(Buffer + 0x24);   /* → r9d */
```
客户端 probe 也是 `+0x20 = InSize(0)`、`+0x24 = OutSize(480)`。

所以 **r9d = 480**，`cmp esi,3C0h; jb fail` 应当失败，
**但原版实测返回 OK + 181 字节**。这条矛盾目前无法用已读到的汇编解释。

**已确认的事实**：拿同样的 probe、同样的 OutSize，
原版出数据、我方不出。差异真实存在，不是采集噪声。
准确的根因需要下断点单步跟踪 `0x140062ED8` 的入口守卫，
看 `esi` 实际值——本轮未完成这一步。

## 4. 结论

### 已确立

1. **A/B 采集与比对基础设施已建立**，可复用：`--ab` + `ab_diff.py`，
   带 guard 缓冲、崩溃定位、确定性验证。
2. **115 / 126（91.3%）命令在状态、返回码、输入、输出上完全一致。**
3. 我方采集的**确定性已验证**（连跑两次状态差异 0 条）。
4. 发现**三条原版也会崩的命令**（0x78 / 0xC2 / 0xEC），崩溃位置与参数
   完全一致，非复刻偏差。
5. **两条上轮结论被推翻**：0x27（原版给缓冲时 OK）与 0xE1（原版有 181B
   真实数据）。这两条是本轮最有价值的发现。

### 未完成

- 8 条状态差异中，`0x027 / 0x0D4 / 0x0E8 / 0x0FC / 0x10B / 0x0E1` 的
  根因尚未逐条修到与原始反汇编一致。已定位方向，未实施修复。
- 157 条被跳过的命令未做 A/B（原因见 §0，其中 150 条为操作类，
  需要构造真实对象/上下文才能调用，不能盲扫）。

### 与"功能是否对齐"的回答

**大部分对齐，但不是全部。** 126 条可比命令里 115 条完全一致；
11 条有差异，其中 3 条是运行时数据（可排除），8 条是状态差异，
经分析至少 2 条（0x27、0xE1）是**我方真实的实现缺口**，
其余 6 条方向已定位待修。
