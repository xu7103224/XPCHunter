## L4：实机验证（当前最大盲区）

**现状：驱动从未在真实内核上装载运行过。** 所有验证都是静态的。

计划：
1. 在测试机（虚拟机快照）装载驱动，确认 `DriverEntry` 与
   `InitImageNotify` 枢纽链路不崩溃（这是本会话重点修复的路径）；
2. 按命令 58 做一次 IOCTL 端到端验证，与原版 PCHunter 行为比对；
3. 重点覆盖本会话修复/新增的路径：IOCTL 发送链、Syscall 导出族、
   Fwps 调度表族、ALE 端点族；
4. 用 `verifier`（Driver Verifier）跑一轮，捕捉内存越界与句柄泄漏。

**风险**：这些函数操作内核内存、摘链、写 CR0 等，静态正确性不等于运行安全。
**必须先在快照虚拟机内进行。**

## L5：对已覆盖函数的持续验证（贯穿性）

**证据**：本会话每轮验证都发现真实缺陷 —— 6 个解析器 21 处字段偏移、
`SendIoControlWithBufferSwap` 出口路径合并、`InitImageNotify` 哨兵判据、
11 个命名与功能完全不符的函数。

**方法**（已固化为判据 F / 三重确认）：
1. 优先验证**不可反编译**的函数（其 IDA 栈帧名不可信，
   本会话已证实在这些函数上 IDA 栈帧分析是损坏的）；
2. 用 capstone 对原始字节独立核对结构体字段偏移、形参偏移；
3. 对照**调用方契约**反推被调用方签名；
4. 可疑信号：偏移集合与同族大面积不一致、伪代码出现 `XxxCopy` 变量、
   函数体极短但原始体积大。

**候选对象**（尚未逐条核对的大函数）：
`ParseNtExportSectionsForProcessContext`(972)、`SendDeviceIoControl`(688) 的实参细节、
以及所有"不可反编译 + 体积 >300B"的函数。

## 风险与诚实声明

- **96% 覆盖率 ≠ 96% 正确性**：剩余验证工作量无法从覆盖率推算。
- **实机验证为零**：这是评估中最大的不确定性，静态一致性无法替代运行验证。
- **不可反编译的函数**（约 20 个，含本次待写的 `MiniFilterPreCreate`）：
  只能逐条转写，出错概率高于其它路径，每处都须在注释中标注来源与存疑点。
- **构建环境不稳定**（僵尸 `link.exe` + 并行编译崩溃）：已定性为环境问题，
  但会持续产生 2MB 残缺产物；每次构建都须核对产物大小。
