## 二、推翻上轮的错误结论（教训）

上一轮我写下"真原版在同样状态下也是 REJ，这三条不是实现缺陷"。
**该结论完全错误**，错误原因是**测量方法**：

我用单条 `--dump` 调用去测原版，而 `0x0F0/0x0F4/0x0F6` 的正常路径依赖
`InitKernelMemoryContext` / `InitKernelDataSectionTable` 这两条"槽空才调用"的
初始化链，链上的前置函数由**别的命令**（全量顺序扫描中先跑的那些）触发。
单条调用时前置槽为空，所以原版单测也 REJ —— 但那不代表全量扫描下也 REJ。

**正确做法**：用与基准采集完全相同的方式（`--ab` 全量顺序扫描）重测原版。
实测原版 `ok=28`（与 `AB_realorig.txt` 一致，两次采集 0 条状态差异），
证明那三条命令在原版上确实成功，我方必须对齐。

**方法论教训**：验证"某命令是否可达"时，必须复现基准采集的**调用顺序与上下文**，
不能拿单条调用否定全量扫描的结论。

## 三、根因一：0x22 握手把命令表 198..224 清零（影响面最大）

### 3.1 分发器的真实寄存器映射

`DriverEntry.c:542-545,605` 对应原版 `0x1400825AB`：

```
OutSize  = *(ULONG  *)(Buffer + 0x20);   // 请求的 InSize 字段
CtxSize  = *(ULONG  *)(Buffer + 0x24);   // 请求的 OutSize 字段
CtxPtr   = *(ULONG64*)(Buffer + 0x10);
ExtraPtr = *(ULONG64*)(Buffer + 0x18);
Result = Handler(CtxPtr, OutSize, ExtraPtr, CtxSize);
                       ↑ edx
```

所以 `CmdQueryProcessInfo(ProcessId, BufferSize, OutBuf, OutputSize)` 的
第 2 形参 `BufferSize` 拿到的是 **请求的 InSize**，与 OutSize 无关。

### 3.2 路径 A 会毁掉命令表

`CmdQueryProcessInfo` 原版 `0x14003105C`：

```c
if ((unsigned int)BufferSize > 0xA)
    return QuerySsdHookByProcessInfo(...);   // 路径 B/C
AllocProcessInfoBuffer();                     // 路径 A
return CheckSsdtHookIntegrity(...);
```

`AllocProcessInfoBuffer`（`MemoryCleanup.c:24`）里有：

```c
__int64 *Buffer = GtAlloc(GtCommandHandlerBase);   // = &g_GlobalTable[0x921]
memset(Buffer + 198, 0, 0xD8);                     // 清空 GT[0x921+198 .. 0x921+224]
```

`0xD8 = 27 * 8`，正好覆盖命令表槽 **198..224**，即命令 `0xE6..0x100`，
其中就有 `0xF0`(槽208)、`0xF4`(槽212)、`0xF6`(槽214)。

### 3.3 实测证据

用 `find immediate 1984` 定位写 `GT[0x7C0]` 的代码，再 dump 命令表区：

```
kd> dq <命令表基址>+8*0xc6 L 40
...  00000000`00000000 00000000`00000000     ← 槽 198..224 全 0
...  00000000`00000000 fffff800`2674f7d0     ← 槽 225 起恢复有效指针
```

同时 `g_DiagAllocProcBufCalls`（`GT[0x4F90]`）在每次 `0x22` 后自增，
从 0 → 1 → 2 → 3，与"每次握手都清表"完全吻合。

### 3.4 正确做法：路径 C，两个条件缺一不可

原版 `QuerySsdHookByProcessInfo`（`0x1400310B4`）在
`DecryptAesHexString` **成功**时会调 `CheckSsdtHookIntegrity`，后者无条件
`GtWrite(GtCallbackField54=0x304, 1)` —— 这才是置"驱动就绪标志"的地方。

进入该分支的条件：
- `MaxCount`（= 请求 InSize）`!= 0` 且 `< 0x1000` 且 `<= 0x12C`
- `OutputSize == 4`（严格相等）

所以客户端调用 `0x22` 必须同时满足：

```
InSize  == 0x100   （合法 AES 许可包，> 0xA 避开路径 A）
OutSize == 4       （严格相等，才进 QuerySsdHookByProcessInfo 的检查）
```

**此前只改 OutSize 不够**（会走路径 B，`GT[0x304]` 不置位，全盘 REJ）；
只改 InSize 也不够。两个条件必须同时满足。

### 3.5 修复点

`XPCHunterUM/src/Protocol.c` 的 `XpchHandshake`、
`XPCHunterUM/src/probe.c` 的 5 处 `0x22` 调用
（`--license`、`--dump` 就绪、`--stats`、`--ab` 握手）全部改为
`ULONG OutBuf; XpchInvoke(..., 许可包, 0x100, &OutBuf, 4, ...)`。

## 四、根因二：FindNdisExportsBySectionScan 字段与位置量（0x0F0）

原版 `0x140061254`，描述符基址 `rbp-0x70`：

| 变量 | 偏移 | 用途 |
|---|---|---|
| v21 | `rbp-0x38` → `+0x38` | 第一段 1368 的 RVA 字段 |
| v22 | `rbp-0x20` → `+0x50` | 比较 64 |
| v23 | `rbp-0x18` → `+0x58` | 比较 1 / 5 |
| v24 | `rbp+0x08` → `+0x78` | 1298/1296 的 RVA 字段 |
| v25 | `rbp+0x18` → `+0x88` | 比较 0x40000 |

**关键的位置量修正**：原版

```
v9 = v26 + v19;    // 先算（v19 是 ctx.ReadPtr，初值 = ImageBase+NdisOffset）
v19 += v26;        // 后推进
```

我方此前先推进再算、且 `v19` 用从 0 起的本地累积量，
算出的 `v9` 是模块内偏移而非 VA，减 `ImageBase` 后成负数，判据恒假。

修复后 `GT[0x37E]`/`GT[0x37F]` 成功写入，`0x0F0` 对齐（长度 8120 B 与原版相同）。

## 五、根因三：ScanWfpStreamShimSections 字段（0x0F6）

原版 `0x14006A508`，描述符基址 `rbp-0x50`
（`int v21[16]; // [rsp+B0h] [rbp-50h]`）：

| 变量 | 栈位置 | 偏移 | 用途 |
|---|---|---|---|
| v22 | `rbp-0x10` | `+0x40` | RVA 字段 |
| v23 | `rbp+0x00` | `+0x50` | 比较 0x40000 |
| v24 | `rbp+0x20` | `+0x70` | 1351 分支比较 1 |
| v25 | `rbp+0x38` | `+0x88` | 1294 比较 64 / 1351 比较 0x800000 |

此前代码把 `+0x70` 当 0x40000、`+0x78` 当 1、`+0x80` 当 64，三处都错
（`+0x40` 当 RVA 反而是对的）。修复后 `GT[0x7C5..0x7C7]` 写入成功，
`0x0F6` 对齐。

## 六、根因四：ScanKfdDriverSections 的 1049 分支比较字段（0x0F4）

原版 `0x1400687D0`，描述符基址 `rbp-0x60`
（`_DWORD v19[20]; // [rsp+A0h] [rbp-60h]`）。
IDA 的局部量写作 `[rbp+100h+var_XXX]`，实际地址 = `rbp+0x100-var_XXX`：

| 变量 | 实际地址 | 偏移 |
|---|---|---|
| var_110 | `rbp-0x10` | `+0x50`（`cmp r8, 40h` 比较 64） |
| var_108 | `rbp-0x08` | `+0x58`（1296 存 SavedField） |
| Value | `rbp+0x10` | `+0x70`（1049 的写出值） |
| var_E8 | `rbp+0x18` | `+0x78`（RVA / 1298 的写出值） |
| var_D8 | `rbp+0x28` | `+0x88`（比较 0x40000 / 0x10000 / 0x2000000） |
| var_D0 | `rbp+0x30` | `+0x90`（1298 的 SavedField 比对） |

### 6.1 关键突破：1049 的比较字段是 +0x80

汇编 `0x1400689A7` 是 `cmp r15d, [rbp+100h+var_108]`，按上式应读 `+0x58`。
但实测同一份 netio 数据下，两个条目的字段是**交叉匹配**的：

| 偏移 | 1296 候选 | 1049 条目 |
|---|---|---|
| `+0x50` | 64 | 64 |
| `+0x58` | **8** | 0 |
| `+0x70` | 0 | **0x578** |
| `+0x78` | 0x27E18 | 0 |
| `+0x80` | 0 | **8** |
| `+0x88` | 0x40000 | 0x2000000 |

若按 `+0x58` 比较：`SavedField(8) != 1049.F58(0)` → 不成立。
若按 `+0x80` 比较：`SavedField(8) == 1049.F80(8)` → **成立**。

而原版运行时写入 `GT[0x7C0] = 0x578`，正好等于 1049 条目的 `+0x70`，
证明原版确实走了 1049 分支。所以正确的比较字段是 **`+0x80`**。

（推测原因：这两处偏移在反汇编里被 IDA 归为同一个 `var_108`，
但描述符的字段语义随指令形状（前缀数量/操作数个数）变化，
`+0x58` 与 `+0x80` 在两条不同形状的指令下承载了同一个逻辑量。
以实测数据为准。）

修复后 `GT[0x7C0] = 0x578`，与原版完全一致，`0x0F4` 对齐（40 B 输出）。

## 七、顺带修复：名字缓冲区越界与截断

`Minifilter.c` 中 15 处 `char NameBuf[32]` 全部扩到 `char NameBuf[40]`，
其中 `FindKfdDeregisterLayerCallbackExport` 改为显式逐字节填充。

原因有两条：
1. `"KfdDeregisterLayerChangeCallback"` 长度正好 32 字符，`char[32]` 放不下
   终止符 → 栈溢出；
2. MSVC 会把短 `strcpy` 优化成立即数存储，长度容易截断
   （`"DllInitialize"` 曾因此变成 `"DllIniti"`，导致导出查找失败）。

## 八、剩余 8 条输出长度差异的共同根因：GT 槽冲突

当前 8 条"双方都 OK 但输出长度不同"：

```
0x031 (18条/6条)   0x047 (4816B/0)   0x04D (41条/23条)  0x0D4 (38条/5条)
0x0D5 (27条/26条)  0x0E4 (608B/420B) 0x0FF (136条/93条) 0x108 (33B/0)
```

以 `0x108`（`CmdEnumProcessorInfo`，原版 `0x14002FDD4`）为例，
原版反汇编读到 7 个 GT 槽，我方枚举映射与之逐项比对：

| 原版指令 | 真实槽 | 我方枚举 | 结果 |
|---|---|---|---|
| `lea ecx,[rdi+4Bh]` | `GT[75]` | `GtObjectTypeCount`=75 | ✓ |
| `mov ecx,1CFh` | `GT[0x1CF]` | `GtKiFastCallEntryAddr\|GtNtoskrnlImageSize` | ✓ |
| `mov ecx,873h` | `GT[0x873]` | `GtEprocessModuleListOffset\|GtPspTerminateThreadAddr` | ✓ |
| `lea ecx,[rdi+38h]` | `GT[56]` | `GtProcessOffset`=56 | ✓ |
| `lea ecx,[rdi+37h]` | `GT[55]` | `GtProcessEprocess`=55 | ✓ |
| `lea ecx,[rdi+35h]` | `GT[53]` | `GtEprocessField43`=53 | ✓ |
| `mov ecx,4265h` | `GT[0x4265]` | `GtObjectTypeInfoPtr`=0x4265 | ✓ |

七个槽号全部对得上。问题在运行时值。实测：

```
GT[75]     = 0                     ← 应为 2080（InitEprocessOffsetsWin10_18362 写）
GT[56]     = 0xfffff8002855d000    ← 应为偏移 544，却是内核指针
GT[55]     = 0x29e000              ← 应为偏移 1608，却是镜像大小样值
GT[53]     = 0x6b000               ← 应为 1056
GT[0x1CF]  = 0x28                  （合理）
GT[0x873]  = 0x190                 （合理）
GT[0x4265] = 0xfffff80028b6f3a0    （合理，应为指针）
```

`InitEprocessOffsetsWin10_18362` 的写法是"仅当当前值为 -1 才写入"：

```c
if ((unsigned int)GtRead(GtProcessEprocess) == -1)  GtWrite(GtProcessEprocess, 1608);
if ((unsigned int)GtRead(GtProcessOffset)  == -1)  GtWrite(GtProcessOffset,  544);
if ((unsigned int)GtRead(GtEprocessField43) == -1) GtWrite(GtEprocessField43, 1056);
...
GtWrite(GtObjectTypeCount, 2080);   // 这条是无条件的
```

`GT[75]` 是无条件写入却读到 0，`GT[55]`/`GT[56]` 是内核指针/镜像大小样值 ——
说明**这些低索引槽在我方构建里被其它模块当作别的语义写过了**（GT 槽冲突），
于是"仅当 -1 才写"的守卫失效，偏移量永远写不进去。

原版能用同一批槽号而不冲突，说明我方某些模块把指针/大小写进了本应是
EPROCESS 偏移的槽 —— 需要逐模块审计 GT 槽的写者集合。

### 待办（明确的下一步）

1. 查清 `InitEprocessFieldOffsets` 为何没能让 `GT[75]=2080` 生效：
   该函数里 `GtWrite(GtObjectTypeCount, 2080)` 是无条件写，
   但运行时读到 0 —— 说明要么该函数未执行到那一步，
   要么写完之后被别的模块清零
2. 对所有"EPROCESS 偏移类"GT 槽（53/55/56/75 等）做写者审计：
   找出把指针或镜像大小写进这些槽的模块，改为写入正确的槽
3. 上述修好后，其余 7 条长度差异很可能一并解决（它们都依赖这批偏移）

已排除：`GT[0x914]=0x47BA`（构建号）、`GT[0x304]=1`（就绪标志）、
`GT[0x353]=1`（已初始化）、`GT[0x1E0]=0x05E00158`（ioctl 码）均正常，
说明驱动整体初始化是完成的，问题只在这几个低索引槽。

## 九、方法论记录（本轮新增）

1. **验证"某命令是否可达"必须复现基准采集的调用顺序** ——
   单条 `--dump` 会因前置初始化链未跑而得到与原版不同的结论
2. **分发器 ABI 必须从汇编读**，不能按形参名猜：
   `Handler(rcx=CtxPtr, edx=[buf+0x20], r8=ExtraPtr, r9=[buf+0x24])`，
   其中 `[buf+0x20]` 是请求的 **InSize** 字段
3. **描述符字段偏移以实测数据为准** —— 当反汇编的 `var_XXX` 与实际数据
   矛盾时，用"哪个偏移能让判据成立/能让输出值对得上"来定案
4. **`GtAlloc(Index)` 返回 `&g_GlobalTable[Index]`**（不是解引用），
   所以 `memset(GtAlloc(0x921)+198, ...)` 清的就是 GT 表本身
5. **kd 的 `bu`/`bp` 在 deferred 加载的驱动上均不可靠** ——
   改用"GT 槽前后变化"判断函数副作用
6. **临时诊断槽必须先查占用** —— `0x7E2`/`0x740`/`0x800`/`0x1C00` 等都已被
   其它模块使用；本轮最终用 `0x1D00`/`0x1E00` 完成定位后已全部移除
