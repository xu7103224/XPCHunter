## 二、Ring0 受阻的根因链（已完整定位）

### 2.1 实测现象

驱动命令 `0x117 CmdEnumHookInfo`：
- `sc query` 层：**HANDLED**（处理器确实执行，`count=1`）
- 但 `lastResult=0`，输出缓冲只有 build 号后全零：

```
=== raw 0x117 outSize=0x2000 -> REJECTED result=0 ===
  0000: BA 47 00 00 00 00 00 00 00 00 00 00 00 00 00 00
  0010: 00 00 00 00 ...
```

`0x47BA` = 18362（build 号），之后两个 Count 都是 0。

### 2.2 代码追踪

`EnumHookInfoOperation`（`Operation.c:1951`）的核心前置：

```c
if (!GtRead(GtDisableHookProtectionAddr1 | GtEprocessField150))
    ParseSyscallTableExportDir();
Count1 = GtRead(GtDisableHookProtectionAddr1 | GtEprocessField150);
pTable1 = GtRead(GtDisableHookProtectionAddr2 | GtEprocessField151);
if (Count1 && pTable1 && ...) { ... }
```

槽位换算：`0x817|0xA0 = 0x8B7`。实测该槽为 0，所以 `Count1 = 0`，
两个 if 都不成立，函数返回 0。

### 2.3 为什么 `GT[0x8B7]` 是 0

由 `ParseSyscallTableExportDir` 填充。**该函数在复刻里是空壳** ——
`SyscallTable.c` 的注释自己写着：

> 本函数属"缺失函数"（复刻中原不存在），且其调用方
> ParseSyscallTableExportDir 在复刻中是空壳 —— 该链条尚有 5 个被调用方缺失

原始 `ParseSyscallTableExportDir`（0x1400865C8，0xC8 字节）的完整调用链：

```c
v0 = GtRead(GtExReleaseFastMutexUnsafe);
if (v0 && ReadWdfLibraryModule(&v2, &v1)) {
    FindSyscallTableDescriptor(v2, v1, v0);
    BuildExportSectionMapping(v2, v1);
    ParseSyscallTableDataSection(v2, v1, v0);   /* 已实现 */
    ParseSyscallTableSections(v2, v1, v0);      /* 已实现 */
    if (ParseNtExportDir(v2, v1, v0, 0) == 1) {
        CollectSyscallEntries4(v2, v1, v0);
        CollectTwoSyscallTables(v2, v1, v0);
        CollectSyscallExportEntries(v2, v1, v0);
    }
    ExFree(v2);
}
```

缺失的 6 个函数（IDA 实测大小）：

| 函数 | 地址 | 大小 |
| --- | --- | --- |
| `ReadWdfLibraryModule` | 0x140086EA4 | 0x12B |
| `FindSyscallTableDescriptor` | 0x140085E34 | 0x27F |
| `BuildExportSectionMapping` | 0x140086908 | 0xB6 |
| `CollectSyscallEntries4` | 0x140086868 | 0x9E |
| `CollectTwoSyscallTables` | 0x140086740 | 0x127 |
| `CollectSyscallExportEntries` | 0x140086690 | 0xAE |

合计 **0x7D7 ≈ 2007 字节**。

`ReadWdfLibraryModule` 已完整反编译（本次已确认其语义）：
读 `\SystemRoot\system32\drivers\wdf01000.sys`（路径为 21 个 int 打包的
UTF-16，已解码验证），经 `ReadFileRawData` → `ReadNtFileToBuffer` 展开到内存。

### 2.4 为什么没有本轮就补完

这 6 个函数还依赖一批**未初始化的 GT 槽**。例如
`CollectSyscallExportEntries`：

```c
v8 = GtAlloc(GtKeGetCurrentIrql | GtPathBuffer04 | 0x3100);
...
GtWrite(Gt821 | GtEprocessField148, 1);
```

这些复合索引（`GtKeGetCurrentIrql|GtPathBuffer04|0x3100` = ？）在补链前需要
逐个确认语义与取值，否则会写出"看起来跑了但数据是垃圾"的实现 ——
这比标 blocked 更糟。

**已确认的下一步顺序**（写进待办）：
1. 确认 `GtKeGetCurrentIrql|GtPathBuffer04|0x3100` 等 4 个复合索引的真实槽号；
2. 按上表逐个实现 6 个函数（从 `ReadWdfLibraryModule` 开始，它已反编译完成）；
3. 实机验证 `GT[0x8B7]` 非零 → 0x117 返回真实 Hook 表。

## 三、Ring3 Hooks 实现（已完成）

### 3.1 算法

用户态可做，不需要驱动：

1. `EnumProcessModulesEx(LIST_MODULES_ALL)` 取目标进程的全部模块
   → 得到 `{基址, 映像大小, 模块名}` 范围表；
2. 对每个模块读 PE 头 → `DataDirectory[IMAGE_DIRECTORY_ENTRY_IMPORT]`
   → 遍历 `IMAGE_IMPORT_DESCRIPTOR` 取每个 `FirstThunk` 指向的 IAT 块；
3. 逐个 IAT 条目（每描述符最多 512 项）判断目标地址是否落在
   **任一已加载模块**的 `[Base, Base+Size)` 内；
4. 落在范围外 → 记为可疑，输出格式沿用原版的
   `%s-->Ring3 Hook  iat=... target=...`。

全程只 `ReadProcessMemory`，不写目标进程。

### 3.2 实测

```
=== Ring3 Hooks (pid 8348): 0 suspicious IAT entries ===
(no IAT entry points outside all loaded modules)
```

扫描自身进程得 0 条 —— 正常进程的 IAT 全部指向已加载模块，结果合理。

### 3.3 正例验证未完成（如实记录）

为了证明检测器**能**报出问题，写了一个测试程序
（`build/sign/bld_hooktest.bat` 构建，源码在临时目录）：

```c
// 把本进程 IAT 的第一个可用条目改成指向 VirtualAlloc 出来的堆地址
iat[0] = (ULONG_PTR)fake;
```

该程序在 guest 里**成功执行了 patch**：

```
patched IAT at 00007FF773E96000 (was 00007FFF0FF69E40) -> 00000174C76B0000
```

但随后进程没能保持存活到扫描时（`tasklist` / `wmic` 都取不到 PID，
`Sleep(180000)` 在 vmrun 非交互会话下似乎未按预期保持）。
因此 **正例扫描未拿到**，检测器的召回率尚未被实机证明。

下一步做正例验证的可靠办法：让测试程序把 PID 写进文件后自行 `Sleep`，
由另一个 bat 读取该 PID 再扫描；或者直接在同一个进程里先 patch、再调用
`FeScanRing3Hooks(GetCurrentProcessId())`（自检模式）。
