## 第二次错在哪

**方法错误**：我用 `dumpbin /disasm` 里 `lea rax,[handler]` 的**出现顺序**
去推断槽位号，假设第 N 个 `lea` 就对应 Table[N]。

**为什么必错**：原版函数里有整段清零的写法：

```c
v0 = GtAlloc(GtCommandHandlerBase);
memset(v0, 0, 0x8D8u);
v0[3] = 0;
*v0 = CmdReadProcessMemory;          // lea #1  -> Table[0]
v0[1] = CmdResetProcessContext;      // lea #2  -> Table[1]
v0[2] = CmdQueryProcessInfo;         // lea #3  -> Table[2]
v0[4] = CmdGetModuleCount;           // lea #4  -> Table[4]，跳过了 3！
...
memset(v0 + 105, 0, 0x30u);          // 105..110 全空，lea 序列跳过 6 个
```

`memset` 覆盖的槽位不会产生 `lea`，顺序推断从这里开始就整体错位。
例如 `CmdCloseProcessHandle`：

- 误判位置：Table[110]（0x08E）
- 原版实际：Table[128]（0x0A0）

差了 18 个槽位。

## 原版真实布局（IDA decompile 确认）

`InitCommandHandlerTable` 共初始化 283 个槽位（`0x8D8 / 8 = 283`），
其中 **35 个是显式 NULL**：

```c
v0[3] = 0;                            // 1 个
v0[97] = 0;  v0[98] = 0;              // 2 个
memset(v0 + 105, 0, 0x30u);           // 105..110，6 个
memset(v0 + 114, 0, 0x30u);           // 114..119，6 个
v0[121] = 0; v0[122] = 0; v0[123] = 0; // 3 个
memset(v0 + 131, 0, 0x40u);           // 131..138，8 个
v0[165] = 0; v0[166] = 0;             // 2 个
memset(v0 + 185, 0, 0x30u);           // 185..190，6 个
                                       // 282 数组末尾，1 个
```

合计 1+2+6+6+3+8+2+6+1 = **35 个**。

我方原本的 NULL 位置与之**完全一致**，无需修改。

---

## 为什么不能填这 34 个槽位

那 34 个槽位（排除数组末尾的 282）对应的函数，在原版的**正确槽位**
已经有注册，我方也在正确位置注册过了。填到空槽位等于**重复注册**：

| 空槽位 | 命令 | 若填入的函数 | 该函数原版正确槽位 |
|---|---|---|---|
| Table[3] | 0x023 | `CmdGetModuleCount` | Table[4]（0x024） |
| Table[97] | 0x081 | `RegisterFormatNameCallback` | Table[100]（0x084） |
| Table[98] | 0x082 | `MiniFilterFormatFileNameEx` | Table[101]（0x085） |
| Table[105] | 0x089 | `CmdQueryProcessNameByPid` | Table[120]（0x098） |
| Table[110] | 0x08E | `CmdCloseProcessHandle` | Table[128]（0x0A0） |
| Table[114] | 0x092 | `CmdEnumObjectHandles` | Table[129]（0x0A1） |
| Table[121] | 0x099 | `CmdInstallShadowHook` | Table[143]（0x0AF） |
| Table[131] | 0x0A3 | `CmdInstallSyscallHook3` | Table[147]（0x0B3） |
| Table[165] | 0x0C5 | `CmdRestoreSsdtTable` | Table[199]（0x0E7） |
| Table[185] | 0x0D9 | `CmdWriteKernelMemoryRange` | Table[219]（0x0FB） |
| Table[189] | 0x0DD | `CmdEnumObjectTypeTable` | Table[223]（0x0FF） |

全部 34 个都是这种情况。填上之后，同一个处理器会响应两个命令号，
命令语义被污染，且与原版行为不一致（A/B 逐字节比对会多出差异）。

## 连带纠正的另一个错误

第二次修复时我据此声称"内核 Dump 内存已经可用了，推翻之前 §2.2 需新增命令的结论"。
**这个推翻不成立**：`0x0D9`（Table[185]）在原版就是 NULL，
`CmdWriteKernelMemoryRange` 这个函数虽然存在于代码里，但**从未被注册**。

所以 §2.2 / §2.3 的剩余项（HAL、内核定时器、工作项、过滤驱动、
FilterManager、APFN、消息钩子）确实需要新增驱动命令。

## 教训

**不要用「出现顺序」推断结构体索引**。当反汇编里有 `memset` 整段清零、
或编译器优化改变了指令顺序时，顺序推断必然错位。要么用显式偏移
（`[rbx+348h]` → 索引 105），要么直接看反编译的 C 代码
（`v0[105] = ...` 无歧义）。
