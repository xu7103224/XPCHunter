# Process 页落地 + 对「0xE4 返回真实 EPROCESS 链表」的更正（2026-10-21）

## 一、更正前一结论

`1c061e6` 里写的"0xE4 返回真实 EPROCESS 链表"**是错的**。当时的证据只是
"条目 +0x00 是内核地址、步长 0x298、+0x290 有后继标记"，这些还不足以证明是 EPROCESS。
后续用调试器直接检查才发现问题：

```
kd> dt nt!_EPROCESS FFFFD20EAE83A1A0
   +0x2e8 UniqueProcessId  : 0xfffff807`090360c0   ← 应该是个小整数 PID
   +0x2f0 ActiveProcessLinks : [ 0xfffff807`08fabb00 - 0 ]  ← 指向 ntoskrnl 数据段
   +0x450 ImageFileName    : [15] ""                ← 空
   +0x498 ActiveThreads    : 0
```

即：`GT[0x36C]` 在本移植里指向 **ndis.sys 的数据段**（实测 = ndis 基址 + 0xE6648），
沿它的 `+0xF08` 走出来的"进程"是错位内存，PID 全是同一个内核指针。

而且**原始驱动枚举的本来就不是 EPROCESS**：0x60053 分支的字段源偏移一直到 `0xFE8`、
链表偏移 `0xF08`，而 18362 的 `sizeof(_EPROCESS)` 远小于此（`ActiveProcessLinks` 在 0x2F0）。
所以原始那条链是一个 >0x1000 字节的私有结构，不是 EPROCESS。
根因在 `ParseNtKernelDataSections` 的地址计算（`GT[0x36C]` 指向哪里），仍待修。

## 二、现在的做法（0xE4 的兜底枚举）

在 `EnumProcessListWin10Operation` 里加了一条**内核自身可靠**的枚举路径，
输出格式与原始完全一致（664 字节条目、同一套字段映射、+0x290 后继标记）：

1. **定位链表头**：从 `IoGetCurrentProcess()` 的 `ActiveProcessLinks` 节点向前走，
   第一个落在 ntoskrnl 模块区间（`[GtNtoskrnlModuleBase, +GtNtoskrnlImageSize)`）内的
   节点就是 `PsActiveProcessHead`（它是 ntoskrnl 的全局变量）。
   > 这一步是必须的：新创建的进程挂在**表尾**，它的 Flink 直接就是表头，
   > 若只从当前进程往后走一圈，就只能拿到"当前进程之后"的那一个。
2. **环形遍历**：从 `head->Flink` 起步，`EPROCESS = 节点 - LinksOffset`，
   直到节点回到表头。LinksOffset 按构建号取（17763 → 0x2E8，18362..19045 → 0x2F0），
   未知版本仍走原始 `GT[0x36C]` 路径。
3. **字段拷贝**：布局表里有几个字段的 Src 到 0xFE8（属于原始那个私有结构），
   对真 EPROCESS 就是越界读 —— 实测直接 BSOD 0x3B。兜底路径里按
   `Src + 8 <= 0xA80` 过滤掉这些字段。
4. **进程名**：把 `EPROCESS.ImageFileName`（+0x450，15 字节内联）写到条目的空闲槽
   `+0x08`（布局表的 Dst 从 0x50 起，0x08..0x2F 没人用）。不 attach、不追指针链。

## 三、进程映像路径（0x2A）暂不可用

`0x2A CmdEnumThreads` 的实现其实是**进程映像路径查询**（入 8 字节 PID，出
`WCHAR[260]`，成功返回 1）。但它的 `GetProcessImagePathByAttach` 依赖
`GT[GtEprocessField33]`（EPROCESS 里镜像路径字段的偏移），本移植里该槽没有被正确
初始化，于是 `*(ImagePath + 0x18)` 读在垃圾地址上 —— **实测 BSOD 0x3B**
（`View___Driver64+0x5e079`，`mov rsi,[rsi+18h]`，即 `GetProcessImagePathByAttach+0xD9`）。

因此：
* 前端只显示 `ImageFileName`（短名，如 `svchost.exe`），不显示完整路径；
* `FeLoadProcessPath()` 保留但**不调用**；
* 待修：`GT[GtEprocessField33]`（对应原始 0x14004A3D4 的字段发现逻辑），
  修好后就能恢复完整路径列。

## 四、前端 Process 页

`XPCHunterUM/src/ProcessList.c`（数据层）+ `frontend.c`（界面）：

* `FeLoadProcessList()` — 0xE4 取列表；条目 +0x00 EPROCESS、+0x108 PID、+0x08 名字、
  +0x290 结束标记；最多 512 项（0x298×512）。
* 界面：顶部 [Connect] [Refresh Processes] [Scan All] [Send] + 命令/尺寸输入；
  中部 Process 列表（PID | Name | EPROCESS）；底部状态行与"命令测试器"列表。
  启动即自动 Connect（含握手）并刷新一次。
* 无头验证入口：`xpch_frontend.exe --proclist-cli`，打印
  `pid / eprocess / name`，用于实机回归。

**必须握手**：`GT[0x304]`（驱动就绪标志）为 0 时，除 0x22 外的命令全部被拒
（`DispatchDeviceControl` 的 `GtRead(0x304) == 0 && Command != 0x22` 守卫）。
所以 `DoConnect()` 与 `RunProcListCli()` 在打开设备后都先 `XpchHandshake()`。

## 六、构建脚本的坑

`build.bat` 的 LTCG 链接阶段偶发写出 **2MB 全零的 .sys**（PE 头都是 0）。
`build.bat` 仍打印 "Build complete"。对策：构建后校验文件头是否为 `MZ`，
不是就重试（实测重试一次即成功）。

## 九、Process 页子视图：数据源映射与已落地部分（2026-10-21）

依据「命令表 → 处理器名」+ 193 条 HANDLED 校准，7 个子视图的数据源如下：

| 子视图 | 数据源 | 状态 |
| --- | --- | --- |
| Windows | `EnumWindows` + `GetWindowThreadProcessId`（纯用户态） | **已实现并实机验证** |
| Modules | `0x49 CmdEnumProcessModules` | 待逆向输出布局 |
| Threads | `0x3B CmdEnumThreadsEx`（注意 `0x2A` 名为 EnumThreads，实为映像路径查询且会挂死） | 待逆向输出布局 |
| Handles | `0x54 CmdEnumProcessHandles` / `0x61 CmdEnumHandlesByPid` | 待逆向输出布局 |
| Memory | `0x37 CmdReadProcessMemoryEx`（内部 `QueryProcessMemoryRegions`） | 待逆向输出布局 |
| Timers | 暂无对应命令（可能要走对象枚举路径） | 待定 |
| HotKey | 暂无对应命令（窗口热键表在 win32k，需 ShadowSSDT 侧支持） | 待定 |

进程操作：`0x28 CmdProcessOperation`（结束/挂起，破坏性，扫描时主动跳过）、
`0xA2 CmdTerminateProcessByEProcess`、`0xD2/0xD3 Enable/DisableProcessProtect`。

**已落地：Windows 子视图**（`XPCHunterUM/src/ProcessViews.c`）
* `FeLoadProcessWindows(pid, max, list)`：`EnumWindows` 过滤目标 PID，取
  `HWND / 线程 ID / 窗口类名 / 窗口标题`。
* 无头入口 `xpch_frontend.exe --windows-cli <pid>`。
* 实机验证（会话 1，explorer.exe PID 5092）：

```

  hwnd=0000000000010178 tid=5892 class=ForegroundStaging   title=(?)
  hwnd=0000000000010144 tid=5564 class=ForegroundStaging   title=(?)
  hwnd=00000000000100F0 tid=5204 class=tooltips_class32    title=(?)
  ...
```

  注意：同一条命令在 **session 0**（vmrun runProgramInGuest）里返回 0 个窗口，
  因为 `EnumWindows` 只枚举当前窗口站/桌面的窗口 —— 子视图必须在交互会话里跑。
