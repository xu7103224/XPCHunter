# Process 页落地 + 对「0xE4 返回真实 EPROCESS 链表」的更正（2026-10-21）

## 一、更正前一结论

`1c061e6` 里写的"0xE4 返回真实 EPROCESS 链表"**是错的**。当时的证据只是
"条目 +0x00 是内核地址、步长 0x298、+0x290 有后继标记"，这些还不足以证明是 EPROCESS。
后续用调试器直接检查才发现问题：

```
kd> dt nt!_EPROCESS FFFFD20EAE83A1A0
   +0x2e8 UniqueProcessId  : 0xfffff807`090360c0   ← 应该是个小整数 PID
   +0x2f0 ActiveProcessLinks : [ 0xfffff807`08fabb00 - 0 ]  ← 指向 ntoskrnl 数据段
   +0x450 ImageFileName    : [15] ""                ← 空
   +0x498 ActiveThreads    : 0
```

即：`GT[0x36C]` 在本移植里指向 **ndis.sys 的数据段**（实测 = ndis 基址 + 0xE6648），
沿它的 `+0xF08` 走出来的"进程"是错位内存，PID 全是同一个内核指针。

而且**原始驱动枚举的本来就不是 EPROCESS**：0x60053 分支的字段源偏移一直到 `0xFE8`、
链表偏移 `0xF08`，而 18362 的 `sizeof(_EPROCESS)` 远小于此（`ActiveProcessLinks` 在 0x2F0）。
所以原始那条链是一个 >0x1000 字节的私有结构，不是 EPROCESS。
根因在 `ParseNtKernelDataSections` 的地址计算（`GT[0x36C]` 指向哪里），仍待修。

## 二、现在的做法（0xE4 的兜底枚举）

在 `EnumProcessListWin10Operation` 里加了一条**内核自身可靠**的枚举路径，
输出格式与原始完全一致（664 字节条目、同一套字段映射、+0x290 后继标记）：

1. **定位链表头**：从 `IoGetCurrentProcess()` 的 `ActiveProcessLinks` 节点向前走，
   第一个落在 ntoskrnl 模块区间（`[GtNtoskrnlModuleBase, +GtNtoskrnlImageSize)`）内的
   节点就是 `PsActiveProcessHead`（它是 ntoskrnl 的全局变量）。
   > 这一步是必须的：新创建的进程挂在**表尾**，它的 Flink 直接就是表头，
   > 若只从当前进程往后走一圈，就只能拿到"当前进程之后"的那一个。
2. **环形遍历**：从 `head->Flink` 起步，`EPROCESS = 节点 - LinksOffset`，
   直到节点回到表头。LinksOffset 按构建号取（17763 → 0x2E8，18362..19045 → 0x2F0），
   未知版本仍走原始 `GT[0x36C]` 路径。
3. **字段拷贝**：布局表里有几个字段的 Src 到 0xFE8（属于原始那个私有结构），
   对真 EPROCESS 就是越界读 —— 实测直接 BSOD 0x3B。兜底路径里按
   `Src + 8 <= 0xA80` 过滤掉这些字段。
4. **进程名**：把 `EPROCESS.ImageFileName`（+0x450，15 字节内联）写到条目的空闲槽
   `+0x08`（布局表的 Dst 从 0x50 起，0x08..0x2F 没人用）。不 attach、不追指针链。

## 三、进程映像路径（0x2A）暂不可用

`0x2A CmdEnumThreads` 的实现其实是**进程映像路径查询**（入 8 字节 PID，出
`WCHAR[260]`，成功返回 1）。但它的 `GetProcessImagePathByAttach` 依赖
`GT[GtEprocessField33]`（EPROCESS 里镜像路径字段的偏移），本移植里该槽没有被正确
初始化，于是 `*(ImagePath + 0x18)` 读在垃圾地址上 —— **实测 BSOD 0x3B**
（`View___Driver64+0x5e079`，`mov rsi,[rsi+18h]`，即 `GetProcessImagePathByAttach+0xD9`）。

因此：
* 前端只显示 `ImageFileName`（短名，如 `svchost.exe`），不显示完整路径；
* `FeLoadProcessPath()` 保留但**不调用**；
* 待修：`GT[GtEprocessField33]`（对应原始 0x14004A3D4 的字段发现逻辑），
  修好后就能恢复完整路径列。

## 十一、0x49 CmdEnumProcessModules 实测（2026-10-21）

* **入参**：无。处理器 `CmdEnumProcessModules(DeviceObject, Irp, Out, BufferSize)`
  完全不看前两个参数，直接读 `GT[0x89C]`/`GT[0x89D]`（两份内核模块表，
  由 `ParseNtSectionsForModuleList1/2` 从 PE 节区里解析）。
  所以它**不是"选中进程的模块"**，而是内核模块表。
* **校验**：`BufferSize % 4 == 0` 且 `BufferSize >= 0x50`，
  否则返回 0；缓冲先被清零。
* **布局（从实现读出）**：
    +0x00 DWORD  = 1（类型 1 存在）
    +0x10 DWORD  = 0
    +0x18 DWORD  = 类型 2 的条目数（实测 2）
    类型 1 条目从 +0x18 起（`pOutputBuffer + 6` 个 DWORD），
    剩余空间再放类型 2 条目；具体条目结构与 `pModuleList1/2` 的节点一致。
* **实测（outSize=0x600）**：`result=1`，但非零字节只有 0x20 个：
    `+0x00 = 1`、`+0x18 = 2`，没有任何模块条目 —— 说明 `GT[0x89C]/GT[0x89D]`
    在本移植里没被解析出内容（`ParseNtSectionsForModuleList1/2` 未产出）。
  **结论：Modules 子视图目前被这个前置问题阻塞**，不是前端的问题。

### 顺带修掉的工具缺陷

`xpch_probe --dump` 原先只在**结果字节非 0** 时打印缓冲；而一大批命令
（0x49、0x54、0x37 等）按设计返回 0 却带有完整输出 —— 这会让"逆向输出布局"
这件事根本没法做。已改为：只要给了 `--dump`，无论结果字节如何都打印。

## 十二、0x49 空表的门控定位（2026-10-21）

把 `ParseNtSectionsForModuleList1/2` 的 6 个入口输入槽导出到 env 块
（0xA0/0xB8/0xBC/0xF4/0xF8/0xFC），实机读数：

```
+0A0 KernelBase(low)  = 0xDA800000
+0B8 KernelSize       = 0xAB2000
+0BC NtImageBase(low) = 0x66000000
+0F4 SectionOffset    = 0x36A010
+0F8 MatchOffset      = 0x00000000   ← 唯一为 0 的
+0FC AltMatchOffset   = 0x770930
```

两个函数开头都是
`if (!KernelBase || !KernelSize || !NtImageBase || !SectionOffset || !MatchOffset || !AltMatchOffset) return 0;`
所以 **GT[0x4477]（MatchOffset）= 0 就是空表的唯一门控**。

进一步在原始 IDB 里搜立即数 0x4477，只有两处命中（0x14004548C、0x14004564C），
**都在两个 Parse 函数里，都是 GtRead** —— 原始驱动自己不写这个槽。
也就是说 `GT[0x4477]` 是**外部输入**（由前端或某个索引被动态计算的 GtWrite 提供）。

下一步：到原版前端 `PCHunter64.exe` 里找 0x4477（或等价的动态索引写入），
确认这个"模块链表匹配偏移"的来源后再补上。补上即可解阻 0x49 → Modules 子视图。

## 十九、进程终止路径核查（2026-10-21 07:33）

结论：**0x28 根本不是终止命令**，`0xA2` 的终止实现也不生效。

1. `0x28 CmdProcessOperation` → `ValidateProcessObject != 1 || ProcessOperationWithAttach`；
   而 `ProcessOperationWithAttach`（ProcessMgmt.c:2939，对应原始 0x140080428）的
   实际动作是：KeAttachProcess → 清 `EPROCESS+CallbackField124` 的 0x2000 位
   （进程保护/页表标志）→ `ClearProcessPageTableFlags` → 还原线程字节 → KeDetachProcess，
   返回值只是 **detach 是否成功**。它不做任何终止。
2. `0xA2 CmdTerminateProcessByEProcess` → `TerminateProcessByEProcessOperation`：
   实测返回 0，进程仍然存活。

实测（自建 timeout.exe）：

### 21.2 两个真实缺陷

**缺陷 A（客户端）：`FeKillProcess` 给 0xA2 传错了入参格式。**
0xA2 与 0x28 的入参格式不同：

| 命令 | 要求 `InputSize` | 入参 |
| --- | --- | --- |
| `0x28 CmdProcessOperation` | 16 | `{QWORD PID, QWORD EPROCESS}` |
| `0xA2 CmdTerminateProcessByEProcess` | 8 | `{QWORD EPROCESS}` |

旧代码两者共用 16 字节 `in[2] = {PID, EPROCESS}`，于是 0xA2 的
`if (InputSize == 8)` 直接不成立 → 返回 0。实机 trace `stage=6`
（入参校验失败）正是这一条。已在 `ProcessViews.c:FeKillProcess` 按命令分别组装。

**缺陷 B（驱动）：0xA2 读的槽号移植错了。**
原始 `0x140054609` 是**单一立即数** `mov ecx, 42BCh`，本移植却写成
`GtRead(GtUninstallHookSyscallPeOffset | GtEprocessField138)`
= `0x4228 | 0x8A` = **0x42AA** —— 少了 0x12，落到了 112 组。
`0x42AA` 是 `PsGetCurrentThreadId` 的 VA 槽，所以旧实现"终止"时其实是在调
`PsGetCurrentThreadId(EPROCESS)`，返回值是当前线程号（实测 `directRet=0x1308`），
进程毫发无损。已改为字面数并新增枚举名
`GtTerminateProcessByEprocess = 0x42BC`（见 `xpc_gt_enum.h`）。

**顺带修掉（1:1 保真）**：`GetExportDirSize`（`SSDT.c`）的
`IMAGE_EXPORT_DIRECTORY` 字段偏移整体错位一格（把 `+0x20` 当
AddressOfFunctions，实为 AddressOfNames），返回值变量名也不符——原始
`0x14000588E` 是 `cmovb ebx, esi`，`esi = [+0x18]`，**返回的是 NumberOfNames**。
已按原始反汇编重写（偏移/校验链/返回值全部对齐）。修后 `ExportCount` 仍为 2916、
`hits/writes` 仍为 254，无回归。

### 21.3 结论：0xA2 在 Win10 上**不是**终止命令

修正后实机 trace：

```

check1=1 check2=1 sdst=562
directRet=0x0
Ep=FFFFC38A741C84C0
DirectFn=FFFFF804764168D0 (GT[0x42BC]=0x764168D0)
```

`DirectFn = base + 0x168D0`，与原始活体 dump 的 `GT[0x42BC]` **完全一致**——
即驱动侧已经是 1:1 忠实复现。而该地址对应的 ntoskrnl 导出是
**`KeCancelTimer`**，不是任何终止函数；`KeCancelTimer(EPROCESS)` 返回 0，
进程继续存活（实测 `timeout.exe` 在调用前后都在）。

即：**原始驱动在 `build >= 0x1DB0`（Win10+）上走的就是这一支，同样不会终止进程。**
0xA2 在这条路径上对 Win10 是空操作。（`build < 0x1DB0` 的 legacy 分支需要
`GT[0x29C]`/`GT[0x29F]` 非零，而原始活体 dump 里这两个槽本身就是 0，
所以那条分支在实机上也不可达。）

## 二十二、补齐 ZeroProcessMemoryPages：0x28 真正能终止进程了（2026-10-21 08:40）

第二十一节定位到 `ZeroProcessMemoryPages`（0x28 路径）是**骨架实现**：
做完几个地址校验后直接 `Result = 1`，注释写着"清零页面的物理地址需要通过
PTE 遍历实现"。本轮逆向原始 `0x14007F138` 并补齐。

### 22.1 原始算法（逐条对应反汇编）

| 槽 | 反汇编立即数 | 反查出的导出 | 用途 |
| --- | --- | --- | --- |
| `GtUserVaMaxPtr` | `0x14007F16C` `mov ecx,43A3h` | `&MmUserProbeAddress` | 解引用得用户态 VA 上限 |
| `GtQuerySystemInfoFunc` | `0x14007F17E` `mov ecx,41DEh` | `NtQuerySystemInformation` | 取页大小/物理页数 |
| `GtReadMemoryFunc` | `0x14007F18B` `mov ecx,41E4h` | `MmGetPhysicalAddress` | VA → 物理帧 |
| `GtPhysToVaFunc` | `0x14007F198` `mov ecx,41E1h` | `MmGetVirtualForPhysical` | 物理帧 → VA（回代校验） |
| `GtSdstServiceCount` | `0x14007F1AA` `mov ecx,27h` | KTHREAD.PreviousMode 偏移 | 临时清 PreviousMode |
| `GtObjectTypeCheckFlag` | `0x14007F1B7` `mov ecx,41DBh` | `MmIsAddressValid` | 作为参数传给恒真桩 |
| `GtEprocessField32` | `0x14007F28F` `mov ecx,2Ah` | EPROCESS 用户空间基址偏移 | 起点地址 |

流程：
1. 七个非零前置 + `ValidateProcessObject(PROCESS,0)==1`；
2. `NtQuerySystemInformation(0=SystemBasicInformation, buf, 0x40)`，调用前后把当前
   线程的 PreviousMode 字节临时清 0（把 Nt* 调用伪装成内核态发起）；
3. `MinPageCount = min(info[3], info[5])`（**无符号** `cmova`），
   `MaxAddressLimit = (int)info[2] * (int)MinPageCount`（**有符号** `imul`）——
   即物理内存字节上限；
4. `ReferenceObjectSafe(PROCESS)`；起点 `0x1000`（若 `*(&MmUserProbeAddress) >= 4GB`
   则改用 `*(QWORD*)(PROCESS + GT[0x2A])`）；终点 `= *(&MmUserProbeAddress)`，
   且与起点相差不超过 4GB；
5. `KeStackAttachProcess` 后逐页（步长 0x1000）：
   - `PageFrame = MmGetPhysicalAddress(CurrentAddress)`；
   - 要求 `PageFrame` 非零、`(int64)PageFrame < MaxAddressLimit`（**有符号** `jge`）、
     `CmdStubAlwaysTrue(MmIsAddressValid地址, PageFrame) == 1`（作者把地址有效性检查
     伪装成一次恒真桩调用，参数被忽略）、
     `CurrentAddress == MmGetVirtualForPhysical(PageFrame)`；
   - 满足则 `DisableCr0WriteProtect(&saved)` → `memset(CurrentAddress, 0, 0x1000)`
     → `RestoreCr0WriteProtect(&saved)`；
6. `KeUnstackDetachProcess`；`IsReferenced==1` 则 `DereferenceObjectSafe`。

### 22.2 顺带修掉：DisableCr0WriteProtect 的签名与语义

旧实现是无参 `void DisableCr0WriteProtect(void)`，直接 `__writecr0(cr0 & ~0x10000)`，
**丢掉了"把旧 CR0 存进调用方缓冲"**这一步。原始 `0x1400015A8` 只有 5 条指令：

```
mov rax, cr0          ; 读当前 CR0
mov [rcx], rax        ; 旧值写入 *pOldCr0
and rax, 0FFFFFFFFFFFEFFFFh
mov cr0, rax
retn                  ; 返回新 CR0
```

配套 `RestoreCr0WriteProtect(*pOldCr0)`（0x1400015B8，`mov rax,[rcx] / mov cr0,rax`）。
二者必须配对，否则在并发/嵌套场景下会把写保护永久打开。已按原始改写
（调用点只有新加的这一处，改动安全）。

`build/audit/kill_diag3.txt`（0xA2 与 0x28 对照）与
`build/audit/kill28c.txt`、`build/audit/kill28d.txt`：

### 22.4 客户端返回值语义修正

0x28 处理器的返回字节按设计可能就是 0（校准文档已归类为"result==0 但处理器确实
执行"），所以 `FeKillProcess` 不再用结果字节判成功，改为**按效果判定**：
调用后重新枚举进程列表，PID 消失才算成功。

注意要**有限重试**：清零用户空间只是让进程无法继续运行，EPROCESS 真正从
`PsActiveProcessHead` 摘链、进程退出要等目标线程被调度后由内核完成，有可观测延迟。
实现为 25 次 × 200ms（`FeProcessPidGone`）。

前端 GUI 的 Kill 按钮本来就调 `FeKillProcess(..., ByEprocess=FALSE)` 即 0x28，
所以无需改动；`--kill-cli <pid>`（0xA2）与 `--kill28-cli <pid>`（0x28）
两个 CLI 入口都保留，供对照实验。


`REJECTED=85` 不变（仍是那 85 条未实现的空槽），协议级拒绝 1..10 全 0，
