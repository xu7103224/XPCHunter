# GT 槽号审计：方法、结果与遗留（2026-10-21）

## 一、为什么做这件事

0xA2 的排查中发现了一个**缺陷类**：本移植把原驱动里的**单一立即数**改写成了
"猜测式 OR 表达式"，算出来的槽号偏了一位。

- 原始 `0x140054609` 是 `mov ecx, 42BCh`；
- 本移植写成 `GtUninstallHookSyscallPeOffset | GtEprocessField138`
  = `0x4228 | 0x8A` = **0x42AA**（少 0x12）；
- 后果：0xA2 调用的是 `PsGetCurrentThreadId` 而不是 118 组的函数，
  "终止进程"变成读了一下当前线程号（详见 `Process页落地_2026-10-21.md` 第 21 节）。

这类错误**不会崩溃、不会报错**，只是行为静默错误，靠实机观察极难发现。
所以需要一次系统性的槽号比对。

## 二、方法（`tools/gt_index_audit_cs.py`）

1. **取原驱动全部 GT 访问点**：`xref_query` 对 `GtRead`(0x140029EFC) 与
   `GtWrite`(0x140029FF4) 取全部 code xref，得到 **6084** 个调用点
   （3624 读 + 2460 写）。
2. **取整段 .text 字节**：`get_bytes` 读 0x140001000 起 0x8C000 字节。
3. **用 capstone 线性反汇编**（147346 条指令），对每个调用点**向前回溯**，
   找到最后一次写 `ecx/rcx` 的指令；若为 `mov ecx, imm` / `mov rcx, imm` /
   `lea ecx,[reg+disp]` / `xor ecx,ecx`，取出其立即数。
   解出 **5004 / 6084**（82%）；未解出的 1080 个是经寄存器中转或跨基本块传递的索引。
4. **校验解码器**：用 IDA 已标注 `Index` 注释的 500 条样本比对，
   `OK=11 BAD=0`（其中 463 条操作数是寄存器，属预期跳过）。
5. **求值我方表达式**：解析 `xpc_gt_enum.h`（含 `#define` 别名）得到枚举值，
   把我方源码里每个 `GtRead/GtWrite(expr)` 求值（含 `|` 组合），
   与"原驱动用过的索引集合"（1265 个不同值）比对。
6. 排除两类**已知的非缺陷差异**：
   - `0x4E00-0x4FFF`：本移植新增的诊断槽（命令统计/环境导出），原始当然没有；
   - `0x4158-0x447C`：`BuildHookTable` 用**循环变量**写的 `[hash,rva,va]` 三元组，
     原驱动同样用循环写，因此不会以字面量形式出现在调用点里。

## 四、已确认并修复的两处（`QueryProcessModuleFilePath`）

我方 `ModuleMgmt.c:4079` 起，对应原始 `0x140057AEC`。原始逐条立即数：

```
0x140057B0F  mov ecx, 415Ah    ; pValidateFunc
0x140057B1B  mov ecx, 4223h    ; pCloseFunc
0x140057B28  mov ecx, 41C3h    ; pOpenHandleFunc
0x140057B35  mov ecx, 4166h    ; pTypeValue
0x140057B42  mov ecx, 4334h    ; pFreeFunc
0x140057B4F  mov ebx, 28Fh     ; pEnumModuleFunc
```

| 项 | 我方旧值 | 原始立即数 | 判定 |
| --- | --- | --- | --- |
| pValidateFunc | `GtValidateObjectTypeFunc` = 0x415A | 0x415A | ✓ |
| pCloseFunc | `GtCloseHandleFunc` = 0x4223 | 0x4223 | ✓ |
| pOpenHandleFunc | `GtEprocessField54` = **64** | **0x41C3** | ✗ 漏了 OR 基数 |
| pTypeValue | `GtTotalSize` = **0x4000** | **0x4166** | ✗ 用错常量 |
| pFreeFunc | `GtExFreePoolFunc` = 0x4334 | 0x4334 | ✓ |
| pEnumModuleFunc | `GtKernelDataField03` = 0x28F | 0x28F | ✓ |

已修正为 `GtNtDuplicateObjectPeSectionOffset | GtEprocessField54`（= 0x41C3）
与 `GtObjectTypeQueryFunc2`（= 0x4166）。

注意 `GtTotalSize`(0x4000) 的用法：头文件注释已写明它只是**OR 的基数**
（`GtTotalSize|GtEprocessField79|0x100 == 0x4159`），单独拿它当索引是错的。

## 五、已确认的一处**实现分歧**（不是槽号问题）

我方 `MiniFilterNotifyRoutine`（`Minifilter.c:383`）与原始 `0x140019AD8` 的
机制完全不同：

| | 原始 0x140019AD8 | 我方 |
| --- | --- | --- |
| 同步 | `KeWaitForSingleObject(g_Mutex)`（全局互斥量 0x1400CD3E0） | 无 |
| 去重 | `MiniFilterQueryFileName(Name)` 遍历通知链表 | 无 |
| 存储 | `ExAllocatePool` + 插入链表 | 写入 `GtRead(0x3C74)` 指向的"通知缓冲区" |
| GT 访问 | **一次都没有** | 读 `GT[0x3C74]`（三重 OR，值可疑） |

原始函数前 30 条指令里没有任何 `GtRead`，我方却读了一个三重 OR 出来的槽
（`GtEprocessModuleListOffset | GtPspExitThreadAddr | 0x3400` = 0x3C74）。
这是早期会话在缺少反汇编依据时的**推测实现**，需要按原始重写（互斥量 + 链表）。
未在本轮实施，记入遗留。

## 六、方法的局限

1. **只能发现"原驱动从未用过的值"，不能发现"用在了错误位置"**。
   例如 `GtEprocessField54`(64) → `0x41C3` 这一处，64 本身在别处是合法索引，
   所以审计不会报它；是逐条比对原始立即数才发现的。
2. **1080 个未解码调用点**会带来假阳性，需要人工确认。
3. **我方 1028 处索引含变量/加法**（循环变量、`+ 偏移`）无法静态求值，未参与比对。

因此本审计的定位是**分诊清单**，不是最终判据：它把 5000 处引用收敛到 42 处待核，
再配合"我方函数头部的原始地址注释 → 读原始立即数"逐点确认。

## 七、附带发现：驱动卸载后 minifilter 回调仍被触发 → BSOD 0x50

审计收尾时 VM 关机又启动，启动过程中出现一次蓝屏。用 `kd_capture_fault` 取到的证据：

```
BugCheck 0x00000050 (PAGE_FAULT_IN_NONPAGED_AREA)
Arg1 = fffff804`7ed13c40   被引用的地址
Arg2 = 0000000000000010    (读)
Arg3 = fffff804`7ed13c40   引发访问的指令地址

faulting_instruction:
  <Unloaded_ViewPlusPlusNew.sys>+0x33c40

Unloaded modules:
  fffff804`7ece0000 fffff804`7edbe000   ViewPlusPlusNew.sys
  fffff804`7edc0000 fffff804`7ee9e000   ViewPlusPlusNew.sys
  fffff804`7ece0000 fffff804`7edbe000   ViewPlusPlusNew.sys
```

`0xfffff8047ed13c40 - 0xfffff8047ece0000 = 0x33C40`。查我方的 map 文件
（`build/bin/Release/x64/XPCHunterDrv.map`）：

```
0x140033C40  MiniFilterCommPortReplyDone
```

**结论：故障指令在 `MiniFilterCommPortReplyDone`（一个 minifilter 回调），
而该模块已被卸载**（Unloaded modules 里 `ViewPlusPlusNew.sys` 出现 3 次，
对应本次会话内 3 次加载/卸载）。即：驱动卸载后，仍有 minifilter 回调被
FltMgr 触发，执行了已释放/已解除映射的代码页 → 0x50。

### 7.1 卸载路径的缺口

我方 `DriverUnload`（`DriverEntry.c:296`，对应原始 `0x140081480`）确实调用了
`CleanupMiniFilter()`，但：

```c
LONG CleanupMiniFilter(void)
{
    KeWaitForSingleObject(&g_Mutex, Executive, 0, 0, 0);
    CurrentEntry = (_QWORD *)g_Pointer;
    while (CurrentEntry) { NextEntry = *CurrentEntry; ExFreePoolWithTag(CurrentEntry, 0); CurrentEntry = NextEntry; }
    g_Pointer = 0;
    return KeReleaseMutex(&g_Mutex, 0);
}
```

**它只释放通知链表，从不调用 `FltUnregisterFilter`。** 全仓库 grep 的结果：
`FltUnregisterFilter` 只出现在 `ResolveFltUnregisterFilter`（把导出地址解析进
GT）以及 `Minifilter.c:4292` 处 `ContextListHead = GtRead(GtFltUnregisterFilterAddr)`
—— 后者把 **FltUnregisterFilter 的函数地址当成链表头**使用，本身就可疑。
没有任何一处真正调用它。

本移植的 minifilter 子系统（`FindKernelDataSectionForDeviceIoControl`、
`EnumMiniFilterContextList`、`MiniFilterCommPort*` 等）看起来是**直接读写
FltMgr 内部数据结构**，而不是走 `FltRegisterFilter`/`FltUnregisterFilter` 这对
正式 API。若如此，注销就不在 FltMgr 的引用计数里，驱动能卸载成功，但
FltMgr 侧仍持有回调指针 → 卸载后回调 → 崩溃。

### 7.2 影响与优先级

- **严重**：任何 `sc stop` 之后（或系统关机/重启过程中）都可能随机蓝屏，
  这使驱动不具备"可反复加载/卸载"的可用性，是复刻前端功能的前提条件之一。
- 与本次改动**无关**：本轮的改动是 `GetExportDirSize`、`BuildHookTable` 计数、
  `TerminateProcessByEProcessOperation` 的槽号与 trace、`ZeroProcessMemoryPages`、
  `DisableCr0WriteProtect` 签名，都不涉及 minifilter 的注册/注销。
  该缺陷为既有问题。
- 验证方式：`sc start` 我方驱动 → `sc stop` → 等待若干分钟（或重启），
  观察是否 0x50；或直接在 kd 里对 `MiniFilterCommPortReplyDone` 下断，
  看卸载后是否仍被调用。

### 7.3 下一步

1. 反汇编原始 `DriverUnload`（`0x140081480`）与 `InitMiniFilterDriver`（`0x140011F6C`），
   确认原始到底是"走正式 FltMgr API"还是"直接改 FltMgr 内部表"，
   以及它在卸载时如何撤销注册；
2. 若为前者，我方需要补 `FltRegisterFilter`/`FltUnregisterFilter` 的成对调用；
   若为后者，需要复刻其"撤销"步骤（把改过的内部表项恢复）；
3. 在此之前，测试流程应避免频繁 `sc stop`（用 `snap_revert` 回滚而不是反复装卸）。
