`XPCHunterDrv.sys` 上各跑一遍 235 条命令（0x20..0x10F），逐行比对
`InSize / OutSize / result / 输出 hex`：

| 项 | 数值 |
|---|---|

| 完全一致 | **233 条** |
| 存在差异 | **2 条**（0x20、0x27） |
| 修复后仍存差异 | **0 条真实行为差异** |

矩阵基线：`build/audit/m_o1.txt`（原版）· `build/audit/m_mine_full.txt`（我方修复前）
· `build/audit/m_reg.txt`（我方修复后回归）。

## 1. 命令 0x27 · `CmdCheckProcessAccess`（真实缺陷，已修）

### 1.1 现象

| | 原版 | 我方（修复前） |
|---|---|---|
| InSize=0 | `result=0` REJ | `result=1` **OK** |

### 1.2 根因

我方实现是：

```c
__int64 CmdCheckProcessAccess(...)
{
    return CheckProcessAccess();          /* 完全忽略 InputBuffer / InputSize */
}
```

`CheckProcessAccess()`（原版 `0x1400812B0`）是**分发器内部门禁** —— 判断
"当前进程是否有权访问驱动"，无参，与本命令的语义不是一回事。

原版 `CmdCheckProcessAccess`（`0x1400800C0`，0x12C 字节）的语义是
"给定 PID/EPROCESS，判断该目标进程是否受保护"：

```
InSize == 16 且 输入指针与指针+16 都在用户态范围
→ ProbeForRead(0x10, 8)
→ ProcessId = Input[0]，TargetProcess = Input[1]
→ PsLookupProcessByProcessId(ProcessId, &Process)
→ TargetProcess 为 0 时用查到的 Process 回填
→ 目标 == GT[0x185]                     → 1
→ GT[GtObjectTypeInfoPtr] 解引用 == 目标 → 1
→ 否则 ValidateProcessObject(目标,0) != 1 || ProcessOperationWithAttach(目标)
→ Status >= 0 时 ObfDereferenceObject
```

### 1.3 修复

按 `0x1400800C0` 逐条重写（`XPCHunterDrv/src/services/IoctlDispatch.c`）。

### 1.4 实机验证（双向）

| 调用 | 原版 | 我方 |
|---|---|---|
| `--raw 0x27`（InSize=0） | REJ / result=0 | **REJ / result=0** |
| `--raw 0x27 64 --rawin 16 4`（PID=4） | OK / result=1 | **OK / result=1** |

两条路径都一致，不再是「恒放行」的假实现。

## 2. 命令 0x20 · `CmdReadProcessMemory`（非缺陷）

原版 `result=136`，我方 `result=0`。

**不是行为差异**。原版 `CmdReadProcessMemory`（`0x14007F384`，77 条指令）的
Hex-Rays 签名是 `void`，反汇编确认 `retn` 之前**从未写过 `eax/rax`**：

- 最后一次写 rax 是 `mov rax, cs:MmUserProbeAddress`
- 之后全是 `call`，rax 由被调函数残留决定
- 所以 136 是**未初始化返回值**，每次调用都可能不同

我方返回 0 是确定性行为。这一条不计入差异。

## 3. 顺带确认：0xE1 `CmdEnumProcessListEx`（逐字节一致）

原版前端 Network 页的 NDIS handler 视图走的是
`sub_14009B1E0` → `sub_1400250D0`，后者发 **命令 0xE1、OutSize=0x400000（4MB）**：

```c
InBuffer[0] = 0xE100000000;      /* cmd = 0xE1 */
InBuffer[4] = 0x40000000000000;  /* outSize = 4MB */
```

handler 名称来自前端两张**静态字符串表**（不是驱动返回的）：

- `off_1406D49F0` — 24 项：`OpenAdapterCompleteHandler` / `CloseAdapterCompleteHandler`
  / `(Wan)SendCompleteHandler` / `(Wan)TransferDataCompleteHandler` / `ResetCompleteHandler`
  / `RequestCompleteHandler` / `(Wan)ReceiveHandler` / `ReceiveCompleteHandler`
  / `StatusHandler` / `StatusCompleteHandler` / `ReceivePacketHandler`
  / `BindAdapterHandler` / `UnbindAdapterHandler` / `PnPEventHandler` / `UnloadHandler`
  / `ReservedHandlers[0..3]` / `CoSendCompleteHandler` / `CoStatusHandler`
  / `CoReceivePacketHandler`
- `off_1406D5050` — 30 项：`(Wan)SendHandler` / `TransferDataHandler` / … /
  `InitiateOffloadCompleteHandler` / `TerminateOffloadCompleteHandler` /
  `UpdateOffloadCompleteHandler` / `InvalidateOffloadCompleteHandler`

**实测**：0xE1 在原版与我方都返回 `result=1`，把 4MB 输出在
`+0x58 / +0xD8 / +0x400` 三个区间逐 qword 对比，**完全一致**
（`+0x58` 起是 8/14/22/24 的小整数对 + 两个相同的 64 位值，
说明本机没有 NDIS miniport handler 被填充，属正确结果）。

## 4. 命令 0xEA · `CmdQuerySsdtDetails`（非环境问题，原版同样 REJ）

清单此前记 0xEA「卡在环境」——**结论订正**：

0xEA = `Table[202] = CmdQuerySsdtDetails`（`0x140067428`），要求
`OutSize == 176` 且 `GT[0x384..0x38D]` 十个槽全部非零。

**实机决定性对照**：

| 驱动 | `--raw 0xEA 176` |
|---|---|
| 原版 `View++ByLinxer` | **REJECTED / result=0** |
| 我方 `XPCHunterDrv` | **REJECTED / result=0** |

原版在**同一台机器同一个会话**下也返回 REJ，所以这不是我方缺陷、也不是
"环境"缺陷，而是该命令在本机（18362 + 无 NDIS offload handler 注册）
的真实行为。前端 `NdisTcpOffloadHandlers` 显示「0xEA query failed」与原版一致。

### 4.1 顺带修掉的实现缺陷（虽然本机仍不触发）

`ParseNtKernelDataOffsets`（`0x140061E08`）我方原实现有四处错误：

1. `SectionChar` / `SectionAlignment` / `Value`(=EntrySize) / `EntryCumulSize`
   四个变量**从未赋值**（恒 0），于是
   `SectionType == 1298 && SectionAlignment == 0x40000` 恒不成立 → 永远返回 0。
2. 首轮用**未解码的描述符**去推进读指针 → 读指针立即越界。
3. `GT[0x385..0x38D]` 的基址写成 `OffloadOffset`，原版是 **`SectionBase`**
   （`GT[0x361]`）。
4. GT 累计写入项 `GT[0x387]` 的公式与顺序不对。

修正后按原版语义：
先解码 → `SectionOffset = ReadPtr + desc[0xF0]` → `ReadPtr += desc[0xF0]` → 判类型。
字段取 `desc+0x50`（SectionChar）、`desc+0x88`（SectionAlignment）、
`desc+0x78`（EntrySize）、`desc+0xF0`（消耗量）、`desc+0x118`（SectionDataPtr）。

## 5. 环境事故：错误 127 与 C1001

本轮踩到两个与代码无关的环境坑，记录以免重犯：

### 5.1 `sc start` 报 127（ERROR_PROC_NOT_FOUND）

现象：**我方驱动与原版驱动同时都报 127**，`wevtutil` 只重复同一句话。

排查过程：
1. 解析 guest 的 `ntoskrnl.exe` 导出表 → 我方 83 个导入**全部存在**（含 `IoGetCurrentProcess`）
2. 解析 `fltmgr.sys`（8 个）与 `hal.dll`（3 个）导出 → 全部存在
3. `AuthenticodeSignature` 显示 `UnknownError`（证书链不受信）→ 导入证书到 Root/TrustedPublisher
   → 变成 `Valid`，**127 依旧**
4. 换回 git 基线的驱动源码重建 → **同样 127**

决定性判据：**原版驱动也 127** → 不是代码问题。

`vm_state probe=true` 显示 `guest_reachable=false`、`host_cpu_percent=0.0` ——
guest 内核已卡死（此前多次 kd_break/kd_go 与一次 0x109 崩溃的累积）。
硬重启后一切恢复，**同一个二进制正常加载**。

**教训**：`sc start` 返回 127 且原版驱动也同样失败时，先 `vm_state probe=true`
看 `guest_reachable` / `host_cpu_percent`，不要继续改代码。

### 5.2 编译 C1001（内部编译器错误）

`msbuild /t:ClCompile` 并行编译时，`mspdbsrv.exe` 残留会让 C1001 在**随机不同文件**
出现（ThreadMgmt.c / MemoryOps.c / ObjectMgmt.c 都中过）。

`build/build.bat` 已加 `/m:1` 强制单线程编译，并在每次构建前
`taskkill /F /IM mspdbsrv.exe`。

## 8. 追加（同日稍晚）：0x42 `CmdQuerySsdtInfo` 的 BSOD 与 0x27 复测

### 8.1 0x42 触发 BSOD 0x3B（我方与原版**都**崩）

`--ssdtinfo` 用合法 24 字节入参调 0x42：

```
+0  BYTE  Flags = 0
+8  PVOID OutputBuffer（用户态，0x40000）
+16 ULONG BufferSize
```

驱动走 `CmdQuerySsdtInfo → CmdEnumDriverObjects → EnumerateDriverFiles`。

**我方修复前**：BSOD 0x3B，崩在
`XPCHunterDrv+0x41DD6` = `EnumerateDriverFiles+0x4E6`，
指令 `cmp word ptr [r9],0`（r9=0，空指针解引用）。

**原版实测**：`View++ByLinxer` 上跑同一条命令，**同样 BSOD 0x3B**
（`0xFFFFF80589430280`）。所以这不是我方引入的缺陷，原版这条路径本来就会崩。

### 8.2 根因

`EnumerateDriverFiles` 的"无反斜杠分支"里：

```c
WStringConcat(pTempBuffer, (WORD *)GtRead(GtPathBuffer00), 255 - StrLen2);
```

`GtPathBuffer00`（GT[4]）是 `InitSdstTable` 写入的**内联字符**：

```c
GtWrite(GtPathBuffer00, 0x7300790053005CLL);   /* L"\Sys" 的前 4 个 wchar */
```

它是字符数据，**不是指针**。GT[4] 一旦被别的路径改写成 0，
`WStringConcat` 就会对 NULL 做 `cmp word ptr [r9],0` → 0x3B。

原版 `0x14003CAFF` 用的是 `qword_14008CA70`，而该地址处正是
`5C 00 00 00` —— 一个双字节字面量 `L"\"`，语义是"补一个反斜杠"。

### 8.3 修复

```c
/* 【2026-10-25 修正】原写 GtRead(GtPathBuffer00) 是内联字符而非指针 */
WStringConcat(pTempBuffer, (WORD *)L"\\", 255 - StrLen2);
```

**修复后实测**：
```
=== 0x42 CmdQuerySsdtInfo -> OK result=1 ===
  entry count @+0 = 194
```

不再 BSOD，返回 194 个驱动条目。**我方比原版更健壮**（原版在这条路径上
会崩），这是有意的偏离：修掉一处必然的空指针解引用，对外行为只会更好。

## 9. View HotKey（0x33 / GT[0x2E4]）深度定位

### 9.1 前端不是「无输出」，是**卡住**

`--hotkeys-cli <pid>` 表现为零输出，实际排查：

```
tasklist 显示 4 个 xpch_frontend.exe 进程滞留（Services 会话）
驱动 sc query XPCHunterDrv → RUNNING（未崩）
```

真正原因：**`xpch_frontend.exe` 是 GUI 子系统（`/SUBSYSTEM:WINDOWS`，
PE Subsystem=2），而 `xpch_probe.exe` 是控制台子系统（=3）**。
GUI 子系统程序在被 `(cmd) > file` 重定向时 stdout 行为与 console 子系统
不同，`printf` 的输出会丢。这是**前端 CLI 输出通道**的问题，
不是驱动或功能问题 —— 用 probe（console）验证同一条命令即可拿到结果。

### 9.2 0x33 的真实数据链条（已用 probe 逐环核实）

probe 发 `--xdump 0x33 2097152 0 6`（OutSize=2MB，与原版 `sub_14004D560` 一致）：

```
=== xdump 0x33 outSize=0x200000 off=0x0 count=6 -> REJECTED result=0 ===
```

不是 OutSize 太小，也不是对象表指针为空。kd 逐槽核对：

| GT 槽 | 含义 | 实测值 |
|---|---|---|
| `GT[0x2E4]` | 对象表指针（`GtCallbackField22`） | `0xFFFFEA3FF4931B70` **非空** |
| `GT[0x41DB]` | 校验函数（`GtObjectTypeCheckFlag`） | `0xFFFFF80132AC22F0` **非空** |
| `GT[55]` | `GtProcessEprocess`（EPROCESS 字段偏移） | `0x29E000` **非空** |
| `GT[56]` | `GtProcessOffset`（GrantedAccess 偏移） | `0xFFFFF8013275D000` **非空** |
| `GT[60]` | `GtProcessCreateTime`（句柄表偏移） | **0** ← 断点 |

`EnumObjectLinkedListWin8`（我方 `ObjectMgmt.c:3771`，原版 `0x140037058`）
的入口守卫是：

```c
if (pCallbackFunc && EprocessOffset != -1 && HandleTableOffset &&
    GrantedAccessOffsetVal != -1 && pTable)
```

`HandleTableOffset` 取自 `GT[60]`，**为 0 时整函数直接返回**，一个条目都不写，
于是 `CmdEnumObjectsEx` 的 `return *pOutputBuffer != 0` 得到 0 → REJ。

### 9.3 GT[60] 为什么是 0

`GT[60]` 由 `InitEprocessFieldOffsets`（`DriverEntry.c:1830`）写入：

```c
Offset2 = (ULONG)GtRead(GtProcessEprocess);   /* GT[55]，实测 0x29E000 */
GtWrite(GtProcessCreateTime, Offset2 + 8);    /* 应得 0x29E008 */
```

但该函数只在 `Success == 1` 时被调用（`DriverEntry.c:1742`），而 `Success`
是前面一长串 `HookSyscall*` / `InstallHookSyscall` / `EnableHookProtection`
的返回值。**我方驱动不装这些 hook**，`Success` 保持 0，
`InitEprocessFieldOffsets` 从未执行 → `GT[60]` 保持 0。

### 9.4 结论与待办

- 我方的 `EnumObjectLinkedListWin8` 与原版 `0x140037058` **逐条一致**
  （同一守卫、同样 127 桶、同样 7 qword 输出布局），不是实现错误。
- 断点是**初始化链路缺失**：因为不装 syscall hook，`InitEprocessFieldOffsets`
  被跳过，连带 `GT[39]`（`Offset1+8`）、`GT[60]`（`Offset2+8`）、
  以及 `GT[GtKiFastCallEntryAddr|GtNtoskrnlImageSize]` 三处收尾写入都没发生。
- **修复方向**：把 `InitEprocessFieldOffsets` 的调用从 `if (Success == 1)`
  里摘出来，或在其内部补一层「GT[60] 为 0 时用 `GT[55]+8` 兜底」。
  这不改变任何 hook 行为，只是让字段偏移表在任何情况下都完整。

### 9.5 最终定性（2026-10-25 收尾）

**`--hotkeys-cli` 无输出的问题已解决**：根因是 `xpch_frontend.exe` 为 GUI
子系统，默认无 stdout。修复后 CLI 模式会先探测 `GetStdHandle(STD_OUTPUT_HANDLE)`，
仅在拿不到句柄时才 `AttachConsole` / `AllocConsole`（避免抢走 cmd 已绑定的
重定向文件），并关闭缓冲。

实机输出（修复后）：

```
$ xpch_frontend.exe --hotkeys-cli 1924
enum hotkeys failed, GetLastError=31
  (driver rejected cmd 0x33: the win32k hotkey table pointer
   GT[0x2E4] is null or points into session space that is not
   mapped in this process context; the original driver returns
   REJECTED here too)
```

**双边 kd 数据结构对照**：

| | 原版 `View++ByLinxer` | 我方 `XPCHunterDrv` |
|---|---|---|
| `GT[0x2E4]` 对象表指针 | **0** | `0xFFFF9D5925731B70` |
| `!pte` 该地址 | —（指针本身就是 0） | **not valid** |
| `GT[0x41DB]` 校验函数 | `nt!MmIsAddressValid` | `nt!MmIsAddressValid` |
| 0x33 结果 | **REJECTED / result=0** | **REJECTED / result=0** |

原版的对象表指针直接就是 0；我方的非零但指向 win32k 会话空间，
`sesssion 0` 上下文里页表为空，`MmIsAddressValid` 返回 0。

**结论**：`View HotKey` 在本机没有可用数据源，原版与我方行为完全一致。
条目按"已实现 + 实机定性"勾选 —— 前端加载器、CLI、诊断提示全部到位，
拒绝理由如实呈现，不编造数据。

### 9.6 附带修好的初始化缺陷

`InitEprocessFieldOffsets` 原被 `if (Success == 1)` 包住，而 `Success` 取决于
一长串 syscall hook 安装结果（我方不装 hook，恒 0），导致整个 EPROCESS
字段偏移表（`GT[39]` / `GT[60]` 等）从不初始化。

已改为**无条件调用**（用独立变量接返回值，hook 门槛仍只看原 `Success`）。
实测 `GT[60]` 已从 0 变为 `0x29E008`（= `GT[55] 0x29E000` + 8），与原版公式一致。
这为其它依赖句柄表偏移的命令打好了基础。
