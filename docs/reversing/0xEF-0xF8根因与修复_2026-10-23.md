# 0xEF–0xF8 handler 为 0 的根因与修复（2026-10-23）

## 结论摘要

「0xEF–0xF8、0x131 的处理器为 0」这个长期悬置的问题，**根因不在命令表，
也不在 AllocProcessInfoBuffer 清表**，而是三件事叠加：

1. **握手参数用错**：客户端用 `InSize=0` 调 0x22，走进驱动
   `CmdQueryProcessInfo` 的 `InSize <= 0xA` 分支，该分支调用
   `AllocProcessInfoBuffer()`，后者执行
   `memset(GtAlloc(GtCommandHandlerBase) + 198*8, 0, 0xD8)`，
   把命令表槽 198..224（命令 0xE6..0x100）整个清零。
   0xEF..0xF8（槽 207..216）与 0x131（槽 273）因此消失。

2. **AES 解密链路是占位实现**：`AesInitKeySchedule` 有 4 处实质错误，
   `AesKeyExpansion` 的 InvMixColumns 只处理了 1 个字节，
   `DecryptAesHexString` 返回值语义错误。
   这导致原版客户端走的「合法 0x100 许可包」路径无法复现。

3. **用户态密钥字符串写错**：`XpchBuildLicensePacket` 里写成
   `"ShouJiErShiShi"`（14 字节 + 2 个 NUL），
   驱动侧是 `"ShouJiErShiSiShi"`（16 字节），AES 解密必然失败。

## 修复内容

### 驱动侧 `framework/Crypto.c`

`AesInitKeySchedule`（对应 0x140002C30）逐句重写，修掉 4 处：

| 缺陷 | 原版做法 | 修正后验证 |
| --- | --- | --- |
| Log/Exp 递推因子写成 `2v` | `v ^ 2v`（GF 乘 3） | `LogTable[0..4]=1,3,5,F,11` |
| 漏掉 `ExpTable[1] = 0` | 建表后 `g_AesRcon01 = 0` | 已补 |
| S-box 求逆查错表 | `LogTable[255 - ExpTable[i]]` | `sbox[0x53]=0xED`、`sbox[0xFF]=0x16` |
| Te/Td 偏移用错表 | 用 `ExpTable[sbox]` 当离散对数 | `Te0[0]=C66363A5`、`Td0[0]=51F4A750` |

另新增自包含的标准 AES-128-ECB 解密（`Aes128DecryptBlock`），
`DecryptAesHexString` 改用它。理由：原 T 表链路存在
`pRoundKey -= 8` 步长错误、逆密钥区与前向密钥区重叠等多处偏差，
逐处修补风险高且难验证；标准实现的正确性可由 FIPS-197 向量独立确认。

`DecryptAesHexString` 返回值修正：原版失败返回 `-1`、成功返回 0
（`0x140002F7B or rdi,-1` + `0x140003130 xor edi,edi`），
原实现恒返回 0，会让非法包也触发 `CheckSsdtHookIntegrity`。

### 驱动侧 诊断

- `g_DiagAesStage` / `g_DiagAesPlain[0x80]` / `g_DiagAesMd5Calc` /
  `g_DiagAesMd5Expect`：AES 解密各阶段
- `g_DiagKmCtxStage` / `g_DiagKmCtxFileSize`：0xF8 解析阶段
- `g_DiagAllocProcBufCalls` + GT[0x4F90]：确认 `AllocProcessInfoBuffer` 是否被调用
- `CMD_ENV_SIZE` 0x3B0 → 0x4A0（新增 Network 数据源与上述诊断）

### 用户态 `XPCHunterUM/src/Protocol.c`

- 新增 `XpchAes128EncryptBlock` / `Aes128ExpandKey`（FIPS-197 自测通过）
- 新增 `XpchBuildLicensePacket`：构造 0x100 字节许可包
  （明文 0x80 = 时间窗 + MD5，AES 加密后转 HEX）
- `XpchHandshake` 改走路径 C（合法许可包），不再用 `InSize=0`

## 三条 0x22 路径的副作用（实测确认）

| 路径 | InSize | GT[0x304] | 命令表 198..224 | GT[0x1E0]（ioctl 码） |
| --- | --- | --- | --- | --- |
| A | ≤ 0xA | 置 1 | **被 AllocProcessInfoBuffer 清空** | 不变 |
| B | (0xA, 0x12C] 且包非法 | 置 1 | 完好 | **漂移 +2**（实测后所有命令被拒） |
| C | = 0x100 且包合法 | 置 1 | 完好 | 不变 |

只有路径 C 可用，这也是原版前端走的路。

## 本轮的方法论教训

**kd 表达式里的数字默认按十六进制解析。**
`((0x921+198)*8)` 里的 `198` 被当成 `0x198`，读到的是槽 408，
于是误判「原版命令表也全 0」。必须先算好字面地址再传给 kd。

**命令号 = 表索引 + 0x20，这条规则在本会话被违反 4 次。**
典型：把 `Table[173]`（GDT 收集）当成命令 0xAD（实际是 0xCD，
0xAD 是 `CmdInstallSystemHook`）。每次都要先算再发。

**处理器"执行了但没输出"通常是我方参数不对，不是驱动缺陷。**
本轮 3 个"未实现"项全部败在参数上：
- GDT：漏了 `outSize >= 0x10018`
- I/O Port：漏了 `outSize >= 0x3808`
- CmpNotifyChange：漏了 `outSize == 1800`（精确相等）

**诊断代码本身要先自校验。**
`0x13A` 导出通道曾因 `Out` 基准点理解错误（相对 env 块 vs 相对缓冲首）
导致快照全 0，进一步误导判断。加"导出槽 0 与槽 281"的自校验才定位到。

**版本不一致会造成假象。**
用旧版 probe（env=0x3B0）读新版驱动（env=0x4A0）时偏移错位 240 字节，
读到全 0。改 `CMD_ENV_SIZE` 必须同步客户端的对应常量。

## 附带修正的形态偏差

原版 Registry 页只有 3 个子页（`PCHunter64.exe` 0x45D99A 起的字符串组）：

```
View Handle / Hidden Item / CmpNotifyChange
```

我方原来写成 `Reg Handle / Hidden Item / Key`，第 1、3 项都不对。
已改正子页名，并把 `Locate in Registry Tab` 的语义改为
「切到 Registry 页 + 填路径 + 在 View Handle 里定位」——
原版没有独立的 "Key 浏览" 子页。
