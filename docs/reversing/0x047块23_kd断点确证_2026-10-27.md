# 0x047 块 2/3：EnumerateProcessCallbackContext 确认被调用（2026-10-27）

## 本轮确证（kd 断点，确定性证据）

### 1. 函数确实被调用
在 `EnumerateProcessCallbackContext` 入口（map RVA **0x3CA70**）下 `bp`，
触发 `0x047` 后**断点命中**，kd 记录 `event: breakpoint`。

调用栈（`kb 6`）：
```
XPCHunterDrv+0x3ca70                        <- EnumerateProcessCallbackContext
XPCHunterDrv+0x819c7                        <- KernelMemoryOperationDispatch（调用者）
XPCHunterDrv+0x10efe                        <- DispatchDeviceControl
nt!IofCallDriver / IopSynchronousServiceTail / IopXxxControlFile
```
入口寄存器现场：
```
rcx=fffff801498db060   rdx=0x5a000   rsi=0x2000   rdi=0x5a000
r8 =fffff801498bfd2c   r9 =ffff818f1effe500
r14=0xab2000（= GT[0x21] 镜像大小）   r15=0x2000
```
多次触发均命中 → **不是"没被调用"**。

### 2. 因此 GT[0x2B8] 为 0 的原因在函数内部
即第一段扫描（≤0xC8 轮）没有命中 `类型==0x512 && +0x50==0x40 &&
+0x58==2 && +0x90==4` 后紧跟的 `+0x58==1 && +0x88==0x40000`。

### 3. 已经排除的假设
| 假设 | 结论 |

| 函数没被调用 | **已排除**（本轮 bp 证明） |

| 缺 kd 链路 | 已恢复 |

### 4. 下一步唯一可行方向
问题在**扫描输入**：`GT[0x42D0]`(CurrentOffset)、`GT[0x43A8]`(SectionBase)
这两个槽决定从内核镜像的哪个位置开始扫描节区描述符。
原版这两个槽由 `InitKernelMemoryContext`(0x14006BF2C) 填充。

**验证方法（一次即可）**：
```
dq XPCHunterDrv+0xab060+8*0x42d0 L1
dq XPCHunterDrv+0xab060+8*0x43a8 L1
```
与原版 `OGT` 的同槽值对比。若复刻为 0 或明显不同 →
根因在 `InitKernelMemoryContext`，与块 2/3 的遍历代码无关。

### 5. kd 操作备忘（本轮踩坑）
- 新部署 sys 后**必须 `.reload`**，否则 `lm m` 空、按名寻址失败
- `bp <addr> "kb 2; g"` 是自恢复断点，可在 `kd_log_tail` 里读多次命中
- `kd_exec` 里不能放 `g`（会被拒绝），用 `kd_go` / `kd_break`
- 偏移落在指令中间会得到 `???`，务必用 `u` 先确认对齐
