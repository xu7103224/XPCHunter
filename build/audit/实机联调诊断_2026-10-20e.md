# 实机联调诊断（2026-10-20 第五轮）：崩溃已消除，剩下加载失败

## 本轮的确定性进展

### 1. `ObpLookupObjectName` 崩溃已消除

修正 `DriverEntry` 用**拼接缓冲区**构造 `UNICODE_STRING`（与原始驱动一致），
不再用硬编码字面量：

```c
DestStr.Length        = DevNameIdx * sizeof(WCHAR);
DestStr.MaximumLength = (DevNameIdx + 1) * sizeof(WCHAR);
DestStr.Buffer        = g_DeviceNameBuffer;

SymStr.Length         = SymNameIdx * sizeof(WCHAR);
SymStr.MaximumLength  = (SymNameIdx + 1) * sizeof(WCHAR);
SymStr.Buffer         = g_SymlinkNameBuffer;
```

**验证结果**（RTZ70，端到端一次跑完，guest 未崩溃）：

```
sc create RTZ70 → 成功
sc start  RTZ70 → START_EXIT=0, STATE: 4 RUNNING
xpch_probe --live --open-only：
  Stage 1 全部 PASS
  Stage 2 open device failed, GetLastError=2 (ERROR_FILE_NOT_FOUND)
  PROBE_EXIT=1，进程正常退出
```

对比之前：探针一跑 guest 就挂死、cmd 连输出文件都写不出来。
**现在探针能正常跑完并返回干净的错误码** —— 这是实质进展。

### 2. 当前剩余问题：驱动没有真正驻留

`lm m RTZ70` 显示模块**不在内核模块列表**，但 `sc query` 报 RUNNING，
且 `\\.\View++ByLinxer` 与 `\\.\RTZ70` 都打不开（GetLastError=2）。

判断：`DriverEntry` 在创建设备之前就失败返回，SCM 短暂显示 RUNNING 后
驱动被卸载。最可能的失败点在：

```c
if (InitSdstTable() != 1 || ReadNtoskrnlFile() != 1) goto Cleanup1;
```

- `ReadNtoskrnlFile()` 需要读取 `ntoskrnl.exe`（依赖 `\SystemRoot\` 路径
  与 Zw* 文件操作），在驱动上下文里较易失败
- `InitSdstTable()` 依赖 PE 解析与内存布局

### 3. 新发现的第三个缺陷（本轮已修）

`DriverEntry` 里 `g_DeviceNameBuffer` / `g_SymlinkNameBuffer` 已经拼好，
却从未用于构造 `UNICODE_STRING`，实际用的仍是硬编码字面量。
一旦驱动以其它服务名加载，设备名/链接名与用户态按固定名打开的目标就不一致。

原始驱动的做法正是「拼好缓冲区 → 用实际长度构造 UNICODE_STRING」。

## 关键洞察：设备名由驱动文件名派生

原始用户态 `sub_140048FE0` 用的是 `\\.\%s`，`%s` 取自驱动文件名去 `.sys`；
驱动侧同样从 `RegistryPath` 最后一段（服务名）派生。

因此**要 1:1 复现 PCHunter64 的行为，驱动文件必须以服务名
`View++ByLinxer` 加载**（`sc create View++ByLinxer binPath= ...View++ByLinxer.sys`）。
本轮一直用 `RTZ70` 这类临时服务名，导致设备名变成 `\Device\RTZ70`，
用户态按 `View++ByLinxer` 打开自然找不到。

这一点此前一直被忽略，是「设备打不开」的直接原因之一。

## 下一步

1. **用服务名 `View++ByLinxer` 加载**，再跑 `--open-only`，
   确认设备名派生与打开是否恢复正常。
2. 若仍失败，用 kd 在 `InitSdstTable` / `ReadNtoskrnlFile` 的返回点下断，
   确定 `DriverEntry` 具体在哪一步失败。
3. 确认 `Cleanup1` 现在是否正确返回 `STATUS_UNSUCCESSFUL`
   （已改，但 SCM 仍报 0，需要核实时机）。
