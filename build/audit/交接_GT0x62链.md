## 剩余单一条件

`FindSyscallNumbers` 在 `.rdata` 中扫描：
```
找 dword[p] == AdjustRva(裸) 且 dword[p + (ST2-ST1)] == AllocRva(裸)
```
**要求 `ST2 - ST1 == 472`（dwords）**，其中
`ST1 = FindKernelPESectionByType(0x41D1)`、`ST2 = FindKernelPESectionByType(0x41D4)`。

### 离线已确证的事实（用真实 ntoskrnl.exe 核算）

```
真实 ntoskrnl.exe: 27 节，.rdata va=0x36b000 raw=0x368400 vsz=0xb5fd0
NtAdjustPrivilegesToken -> 裸 RVA 0x675140
NtAllocateVirtualMemory -> 裸 RVA 0x6788B0
.rdata 中：0x675140 @ rva 0x3D131C，0x6788B0 @ rva 0x3D1A7C
间距 = 0x960 字节 = 2400... 实测 0x3D1A7C-0x3D131C = 0x760 = 1888 字节 = 472 dwords ✓
```
即唯一候选的存在性已确认；只要 stride 给到 472 就必然命中。

### 待核对（两处之一）

1. **`FindKernelPESectionByType` 的返回值**
   - 原始返回 `[rsp+0x100]` = `Entry[0x70]`（描述符 +0x70）。
   - 我方 `return ReadEntry[28]`（28*4=0x70）✓ 偏移一致。
   - 匹配条件：`Entry[0x118]+6 == 0x53C(1340)` 且 `Entry[0x88] & 0x800000` 且 `Entry[0x74] == 0`。
     我方三条件一致，但需实测其返回值是否正好差 472。

2. **`FindPESectionByName` 的「取最小」语义**
   - 原始 0x140005C90 用 `cmovb` 在**多个匹配节**中取最小的 `PointerToRawData`；
     我方 `return` 首个匹配。真实 ntoskrnl 的 `.rdata` 只出现 1 次，
     所以这条**大概率不是**本机失败原因，但为忠实原文仍应改。

## 注意（本会话踩过的坑）

- kd 停住时 guest 冻结，vmrun 全部超时 → 先 `kd_go` 再操作。
- `u <模块名>+off` 对新模块会 wedge → 先 `.sympath cache*C:\symbols`，
  或用 `!drvobj <服务名> 2` 拿 DriverUnload 反推基址后用绝对地址。
- **`bp` 是绝对地址**：若中途 `sc stop/start` 重载了模块，旧 bp 失效且会误判
  「函数未被调用」。要判断调用，用 `sxe ld:<模块名>` 在**加载时**停下再设 bp。
- `.writemem` 写在宿主机（kd 所在机器）。

## 2026-10-18 追加：离线+活体取证的关键结论

### 已用**活体内存**确证的事实（kd 直读 RTZ15 的 PE 缓冲）

```
GT[0x20] = ffffe687`8fc00000   ← PE 文件缓冲（MZ 头 + 27 节表，与磁盘 ntoskrnl.exe 一致）
GT[0x21] = 0xAB2000            ← 缓冲大小（= SizeOfImage）
GT[0x41D1] = 0x1B9600          ← FindKernelPESectionByType 的扫描起始偏移
GT[0x41D4] = 0x1B90E0
.rdata 节头（活体读）：vsZ=0xB5FD0 va=0x36B000 raw=0xB6000 ptr=0x368400
```

**两个扫描锚点确认存在**（活体直读）：
```
PE + 0x3D131C = 0x00675140   ← == AdjustRva（NtAdjustPrivilegesToken 裸 RVA）
PE + 0x3D1A7C = 0x006788B0   ← == AllocRva（NtAllocateVirtualMemory 裸 RVA）
两者相距 1888 字节 = 472 dwords
```
→ 扫描**具备命中的一切物理条件**；`ScanPtr` 从 `PE+0x368400` 起步走 0x68F1C 即到锚点。

### 但 stride 对不上（这是当前唯一卡点）

原始 `FindSyscallNumbers` 0x1400531AD：
```
mov eax, r14d ; sub eax, esi   ; stride = ST2 - ST1（使其为正，见 0x14005310D 的交换）
lea rcx, [rdx + rax*4]
cmp dword ptr [rcx], r11d      ; 检查 dword[p + stride] == AllocRva
```
**需要 stride == 472**，但离线在**原始函数**（0x14007A6B8）上模拟得到：
```
FindKernelPESectionByType(0x41D1) -> Entry[0x70] = 0x81
FindKernelPESectionByType(0x41D4) -> Entry[0x70] = 0x58
stride = 0x29 = 41   （≠ 472）
```
返回字段已核对无误：原始 0x14007A7C3 是 `mov ebp,[rsp+0x100]`，
而 SectionInfo = `rsp+0x90`（0x14007A76D 的 `lea rdx,[rsp+0x90]`），
故 0x100-0x90 = **0x70**，`Entry[0x70]` 就是返回值 —— 与我方一致。

### 结论与下一步

**同一份离线环境里，原始函数也匹配不上**（`FindSyscallNumbers` 返回 0、无 GT[0x62] 写入），
说明我的离线模型缺少真实环境的一个要素。差异最可能在：
1. 真实 guest 的 `GT[0x20]` 缓冲可能是**已加载/已修补**的内核映像，
   而非纯磁盘文件（虽然节表与 `.rdata` 锚点均已核对为磁盘形态）；
2. `GT[0x41D1]`/`GT[0x41D4]` 在真实 guest 里可能被后续流程改写（本会话读到的是
   dump 时刻的值，不等于 `FindSyscallNumbers` 运行时刻的值）。

**下一步（未做）**：在 `FindSyscallNumbers` 内部对 0x1400531A8/0x1400531AD 设断点，
直接读运行时的 `r10d`/`r11d`/`rdx`/`r14d`/`esi`，与离线值比对 —— 这是唯一能
确证 stride 真实取值的方法。注意用 `sxe ld:RTZ16` 在**加载时**下断（绝对 bp 会因重载失效）。
