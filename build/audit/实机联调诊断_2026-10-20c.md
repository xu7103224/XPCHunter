# 实机联调诊断（2026-10-20 第三轮）

## 本轮用 kd 断点拿到的确定性证据

### 1. `IoCreateSymbolicLink` 的参数完全正确

断点 `bp nt!IoCreateSymbolicLink` 实测：

```
rcx = ffff88097c1fe768  → "\DosDevices\View++ByLinxer"
                          Length=0x34  MaximumLength=0x36  Buffer 有效
rdx = ffff88097c1fe758  → "\Device\View++ByLinxer"
                          Length=0x2c  MaximumLength=0x2e  Buffer 有效
```

之前用 `kb` 看到的 `rcx=0x0E` 是**参数显示错位**，不是真实参数。这纠正了一个误判。

### 2. 设备对象创建成功

`DriverObject->DeviceObject`（`DriverObject+8`）非零，指向有效设备对象。

### 3. 崩溃点是符号链接悬挂

探针 `CreateFile` 时崩溃在 `nt!ObpLookupObjectName+0xea`
（`0x3B` / `0xC0000005`），这是**符号链接指向的目标设备对象已失效**的典型症状。

### 4. 触发条件：驱动在探针打开设备期间被卸载

`restart68.bat` 里先 `sc stop/delete` 再 `create/start`。探针恰好撞上
`DriverUnload` 的执行窗口，因此拿到了失效的设备句柄。

## 关键发现：`DriverUnload` 会永久挂起

```c
Result = (UCHAR)RegisterFormatNameCallback();
Result = RegisterFormatPathCallback() & Result;
Result = MiniFilterCommPortRecv() & Result;
Result = MiniFilterCommPortDisconnect() & Result;
if (!((UCHAR)MiniFilterActiveRoutine() & Result))
{
    while (1)
    {
        Interval.QuadPart = -1000000;
        KeDelayExecutionThread(KernelMode, TRUE, &Interval);
    }
}
```

这是原始驱动的**反调试设计**：一旦 `MiniFilterActiveRoutine()` 返回假，
`DriverUnload` 就永久睡眠，`sc stop` 永不返回，拉长「符号链接已删/设备未删」
或反之的不一致窗口，导致后续任何 `CreateFile` 崩溃。

## 修正过的误判链条

本轮之前把问题归因为「guest 挂起 / 不可达」，实际是三层原因叠加：

| 层 | 现象 | 真实原因 | 状态 |
| --- | --- | --- | --- |
| 1 | `sc start` 报 RUNNING 但设备不可用 | `Cleanup1` 返回 `STATUS_SUCCESS` | 已修 |
| 2 | 探针启动即消失、trace 只有一行 | `L()` 对同一 `va_list` 调用两次 `va_start` | 已修 |
| 3 | `CreateFile` 崩溃 `ObpLookupObjectName` | 驱动在联调窗口内被卸载 | **本轮定位** |

## 下一步（明确）

1. **固定驱动再测**：只做 `sc create` + `sc start`，**不做** `sc stop/delete`，
   然后跑 `xpch_probe --live --open-only`，确认 `CreateFile` 能否成功。
2. 若仍崩溃，则在 `IoDeleteSymbolicLink` / `IoDeleteDevice` 上下断点，
   确认是谁在触发卸载。
3. `DriverUnload` 的 `while(1)` 是否符合原始语义需要单独核对
   （原始 0x140081480 的反汇编），否则 `sc stop` 会一直卡住，
   导致联调环境反复进入不一致状态。
