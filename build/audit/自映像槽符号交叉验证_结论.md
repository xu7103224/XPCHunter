# 自映像槽符号交叉验证：结果与真缺陷

## 方法

同会话对比得到的 248 个"自映像指针"槽（GT 0x921..0xA3A）存的是驱动内部函数地址。
因为两次加载模块基址不同、且 LTCG 会重排，绝对地址和 RVA 都不同，所以判据不是
"RVA 相等"，而是**各自解析成函数名后语义等价**。

- 原始侧：`_orig_funcs_ida.json`（IDA 导出的 1516 条）
- 我方侧：`XPCHunterDrv.map`（link.exe 导出）
- 取 "≤ RVA 的最近符号" + 偏移

工具：`build/audit/verify_selfptr_symbols.py`

## 发现的真缺陷：ICF / COMDAT 折叠

### 现象

第一轮比对有 32 个槽"名字不同"，其中 9 个指向**完全不同的函数**。逐个追查后发现
根因不是源码写错，而是**链接器把不同函数合并了**：

```
00000001400232c0 : CmdThreadMonitor, CmdThreadOperation
0000000140026e10 : CmdEnumObjectTypes, CmdEnumObjectTypeInfo
0000000140028360 : CmdSetProcessContextWin8, CmdSetProcessContextWin10
```

这三组函数的区别只是**一个常量参数**（例如 `PrepareFileForPageTableScan(Thread, 0)`
vs `(Thread, 1)`），LTCG 之后目标代码完全相同，链接器用 COMDAT 折叠（ICF）把它们
合并成同一个地址。

后果：命令表 `Table[29]` 和 `Table[30]` 指向同一份实现，于是
**`CmdThreadMonitor` 实际拿到的是 `CmdThreadOperation` 的常量 0 而不是 1**——
功能错误，仅在 `sc start` 不报错的层面被掩盖。

原始驱动**没有**做 ICF：`0x1400807F0`（CmdThreadMonitor）与 `0x1400809CC`
（CmdThreadOperation）是两个不同地址，首 16 字节相同但函数体不同。

### 修复

1. `build/build.bat` 的 link 命令行加 `/OPT:NOICF`
2. `XPCHunterDrv/XPCHunterDrv.vcxproj` 的 `EnableCOMDATFolding` 改 `false`（两处配置）

效果（我方 `.map` 中"同地址多符号"的组数）：

| | 修复前 | 修复后 |
| --- | --- | --- |
| 折叠组数 | **12** | **1** |

仅剩 `memcpy`/`memmove`（本来就是同一份实现，保留折叠是对的）。

### 实机验证（RTZ58）

| 槽 | 修复前我方 | 修复后我方 | 原始 |
| --- | --- | --- | --- |
| GT[0x93F] | CmdThreadOperation | **CmdThreadMonitor** | CmdThreadMonitor |
| GT[0x9D5] | CmdEnumObjectTypeInfo | **CmdEnumObjectTypes** | CmdEnumObjectTypes |
| GT[0xA21] | CmdSetProcessContextWin10 | **CmdSetProcessContextWin8** | CmdSetProcessContextWin8 |

`sc start` → `STATE: 4 RUNNING`。

## 另一类"差异"：符号快照过期导致的假阳性

`_orig_funcs_ida.json` 是 2026-09-29 之前导出的旧快照，而 IDB 里的函数名已在
命名审计中更新过。用旧快照比对，会把"我方已按审计结论改名"的函数误判为
"指向不同函数"。

已用 `build/audit/refresh_orig_funcs.py` 从 IDA 当前符号表重建快照，共有 **30 个
函数名变化**，包括：

```
0x1400129CC  MiniFilterInstanceSetup  → CmdOpenFilterVolumeFile
0x1400152D4  MiniFilterPreClose       → FindKernelObjectFieldOffsetsWin10
0x14001A030  MiniFilterFormatFileName → RegisterFormatNameCallback
0x14001C274  MiniFilterAcquireForSectionSync → CmdCollectAllCpuGdtEntries
...
```

重建后重新比对：名字+偏移完全相同 219 / 仅命名差异 22 / 指向不同 7。

## 剩余 7 个：命名历史冲突（非功能缺陷）

| 槽 | 旧快照名（IDA） | 我方源码名 | 说明 |
| --- | --- | --- | --- |
| 0x92A | CmdHandleStreamProcessInput | CmdMiniFilterStreamHandle | 我方两个名字都存在 |
| 0x9C8 | CmdSetCallbackFlagTrue | MiniFilterClientContext | |
| 0x9C9 | CmdSetCallbackFlagFalse | MiniFilterServerContext | |
| 0x9E0 | CmdOpenFilterVolumeFile | MiniFilterInstanceSetup | |
| 0x9E1 | CmdRemoveFilterContextNode | MiniFilterInstanceQuery | |
| 0x9F2 | CmdInitFwpsDispatchTables2 | MiniFilterAcquireForModWrite | |
| 0xA13 | CmdEnumAleEndpointLayers | MiniFilterPreFastIo | |

这 7 对是**同一函数的两个名字**，历史上两批命名审计给出了相反结论：

- 2026-09-29 的审计（IDB 注释）说：`MiniFilter*` 与实物不符，改名为 `Cmd*`
- 2026-10-08 的记录（源码注释）说：`Cmd*` 与实物不符，改名为 `MiniFilter*`

两者只能有一个正确。这属于**命名一致性问题，不影响功能**：地址指向的函数体
相同（偏移都是 +0x0），只是叫法不同。

处理建议：以一次实际的函数体复核为准，统一成一套名字，然后同步 IDB 与源码。

## 复跑方法

```bash
# 1) 同会话采集两份 GT（见 GT同会话严格对比_rtz56.md）
# 2) 交叉验证
python build/audit/verify_selfptr_symbols.py \
    build/audit/gt_orig_samesession.bin build/audit/gt_mine_rtz58.bin \
    0xFFFFF806420F0000 0xFFFFF8037F3E0000
# 3) 若 IDB 改过名，先刷新快照
python build/audit/refresh_orig_funcs.py <entity_query 导出.json>
```

> 注意：GT RVA 会随链接选项变化。关闭 ICF 后我方 `g_GlobalTable` 从 0xa1060
> 变成 **0xa3060**，dump 前务必从 `.map` 重新读取。
