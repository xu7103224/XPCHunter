# 结论：GT[0x62] 链真凶——解码器读错字段（+0x24 → +0x08）

**日期**：2026-10-18
**状态**：根因已定位、已修、已由离线差分 oracle 逐轮证实与原始一致

## 一句话结论

`FindKernelPESectionByType` 永不命中的真因**不是 stride=472**（那是被错误前提误导），
而是**解码器把「地址大小」读成了「操作数大小」**：
`DecodeReadSizeDependentImmediate` / `CalcPESectionFieldSize` / `CalcPESectionFieldSizeAlt`
三个函数读的是描述符 **+0x24（DEC_CTX_OPERAND_SIZE，init=3）**，
而原始读的是 **+0x08（DEC_CTX_ADDR_SIZE）**。

## 链条（逐环）

```
FindSyscallNumbers
  └─ FindKernelPESectionByType(GT[0x41D1]) / (GT[0x41D4])   ← 返回扫描锚点的 syscall 号
       └─ ReadPESectionEntry → 各操作码 handler（解码指令流）
            └─ 命中判据：Entry[0x88] & 0x800000   ← **op1 标志**
                 └─ 该标志由 DecodeReadSizeDependentImmediate 按「立即数宽度」置位：
                      宽度 4 → 置 0x800000（bit 23）
                      宽度 2 → 置 0x200000（bit 21）
                      宽度 8 → 置 0x2000000（bit 25）
```

## 活体+离线双重取证（同一份真实镜像布局缓冲）

轨 8 的指令是 `B8 41 00 00 00`（`mov eax, 0x41`，位于 buf+0x1B9614）：

| | 读的字段 | 值 | 选的宽度 | op1 标志 | 消耗字节 | 命中 |
| --- | --- | --- | --- | --- | --- | --- |
| ORIG | +0x08 | 1 | imm32 | `0x800000` | 5 | ✅ 返回 0x41 |
| MINE（修前） | +0x24 | 3 | imm16 | `0x200000` | 3 | ❌ 返回默认 0x1000000 |
| MINE（修后） | +0x08 | 1 | imm32 | `0x800000` | 5 | ✅ 返回 0x41 |

修前 MINE 只吃掉 `B8 41 00` 3 字节 → 后续每一轮都错位 → 16 轮扫描全部走偏 →
`FindKernelPESectionByType` 返回默认值 → `FindSyscallNumbers` 的
`SectionType1 >= ServiceCount` 判据成立即 return → **GT[0x62] 永不写入** →
`ResolveSyscallToAddress` 拿不到表 → **GT[0x16E..0x180] 整簇恒 0**。

## 修复内容

`XPCHunterDrv/src/framework/PEDecoder.c`：

1. `DecodeReadSizeDependentImmediate`（对应 sub_14008C0F8）
   - `CTX_D(DecodeCtx, DEC_CTX_OPERAND_SIZE)` → `DEC_CTX_ADDR_SIZE`
   - 原始 0x14008C100 = `mov eax,[r9+8]`（r9 = Context[4] = 描述符）
2. `CalcPESectionFieldSize`（对应 sub_14008A844）
   - 同上；原始 0x14008A84B = `mov ecx,[rax+8]`
3. `CalcPESectionFieldSizeAlt`（对应 sub_14008A9E8）
   - 同上；原始 0x14008A9EC = `mov edx,[rax+8]`
4. `ReadPESectionField`（对应 sub_14008A87C）64 位分支
   - `(ULONG64)*(ULONG *)BufferBase` → `(ULONG64)(LONG64)*(INT *)BufferBase`
   - 原始 0x14008A8B1 = `movsxd rcx,dword [rax]`（**符号扩展**）

## 为什么之前一直误判为「stride 必须 472」

旧 offline oracle 把 ntoskrnl **按磁盘文件布局**映射，
而驱动 `GT[0x20]` 指向的是**内存镜像布局**（活体已核对：
`live[0x1B9600] == image[0x1B9600] != disk[0x1B9600]`，差 0x800）。
于是旧 oracle 在错位字节上跑，得到 stride=41（假象），
又因为 `.rdata` 里恰好存在一对相距 472 dwords 的锚点，
就错误地把「stride==472」当成命中条件。

**正确口径**：`GT[0x41D1]/GT[0x41D4]` 是**系统调用号**（0x41/0x18），
差值 0x29=41 就是 stride；`.rdata` 里 `AllocRva@0x420600` 与
`AdjustRva@0x4206A4` 恰好相距 41 dwords，正是要匹配的那一对。
