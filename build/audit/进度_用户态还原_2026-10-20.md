### 密钥与 IOCTL 码（关键发现）

IOCTL 码**不是任意值**，而是由设备名派生，结果恰好等于驱动侧 `GT[0x1E0]`：

```
Destination = L"\\\\.\\" + Name
n = wcslen(Destination)

edi = 0x20
for i in 0..n-4:
    w = *(WORD*)(DestBytes + 8 + i*2)
    edi = w ^ (w + edi)

ioctl   = 4 * (DestBytes[8] | (edi << 14))      // DestBytes[8] = Name[0] 低字节
keyByte = 0x20
for c in DestBytes[8 .. 2n]:
    c ? keyByte ^= c : keyByte = (keyByte>>4) + 16*keyByte
```

**交叉验证（双向独立复算，结果完全一致）**：

| | ioctl | keyByte |
| --- | --- | --- |
| 用户态 `_um_keycalc.py` 复算 | `0x05E00158` | `0xCF` |
| 驱动侧实机 `GT[0x1E0]` / `GT[0x1E1]` | `0x05E00158` | `0xCF` |

### 加密（自反）

```c
for (i = 0; i < 0x30; i++) buf[i] = ~(buf[i] ^ keyByte);
```


## 三、本轮定位并修复的驱动侧真缺陷（3 个）

### 1. `DispatchDeviceControl` 是自创协议（RTZ59 全部返回 87）

旧实现读 `Irp->AssociatedIrp.MasterIrp` 并要求 `Type == 0x20202020`，原始驱动**从不**看
`MasterIrp`。已按原始 0x1400823EC 完整重写：`InputBufferLength==0x30` → 校验
`IoControlCode == GT[0x1E0]` → 解密 → Magic → MD5 校验 → 命令表分派 → 重入锁。

### 2. `DecryptInputBuffer` 变换错误

旧实现是 `buf[i] ^= key` **再加**前 4 字节额外异或 `GT[0x1E0]` 的四个字节。
原始 0x1400813C0 只有一条变换：`buf[i] = ~(buf[i] ^ GT[0x1E1])`，自反。

### 3. `EnumerateProcessCallbackContext` 完全是虚构实现（RTZ59 蓝屏 0x3B）

旧实现假设存在 `DecodeUnicodeChar` 字符解码器，并用 `TokenType = *pTokenType`
（`pTokenType` 从未赋值 → 未初始化栈指针）。实机在 `mov r15,[r15+0x30]` 处
0xC0000005 蓝屏。

原始 0x14003EAA8 是**PE 节区扫描**（`InitPESectionReadContext` + `ReadPESectionEntry`），
已按反汇编完整重写（两段循环、类型 0x512/0x545/0x4B1/0x175/0x472、写 GT[0x2B8]/[0x2BA]）。

### 4. 描述符 +0x118 的 32 位截断（RTZ61/62 蓝屏 0x3B）

`SectionEntry[0x118 >> 2]` 把 `ULONG[]` 数组按 32 位读，内核指针
`0xFFFFF807_xxxx4EE01` 被截断成 `0x4EE01`，解引用即崩溃（实机 `rax=0x4EE01` 已证实）。

已修复 4 处（`PeSectionParse.c` 1 处、`ContextMgmt.c` 1 处、`SyscallTable.c` 2 处），
全部改为 `*(ULONG64 *)((PUCHAR)Entry + 0x118)`。

### 5. 读指针推进时机（RTZ60）

原始在 `ReadPESectionEntry` **之后**才 `add [ctx+0x08], entry[0xF0]`。我方有 64 处把推进
放在解码之前，首轮读到未初始化数据。已修 `FindKernelDataSectionOffsetWin8`，
其余 63 处同类写法待逐个核对原始地址后统一修正。

## 四、剩余崩溃（RTZ62，进行中）

RTZ62 已 RUNNING（前两类崩溃已消除），但执行命令时在
`FreeListAllocation+0x10`（`mov rbx,[rcx+0x20]`）蓝屏 —— 链表节点指针无效。

`FreeListAllocation` 本身与原始 0x1400575A0 逐字节一致，问题在**上游链表构造**：
`CmdEnumDriverObjects` → `EnumerateDriverList` 等函数产出的链表，节点 +0x20 存下一个
节点。需要逐个核对这条链的构造逻辑。
