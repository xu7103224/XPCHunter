## 九、`SendWriteMemoryIoControl` 的实参映射（2026-09-29，用于精确转写）

调用方 `CmdWriteProcessMemoryEx`(0x1400749A0) **可反编译**，其伪代码第 76 行给出：

```c
v7 = SendWriteMemoryIoControl((int)&v39, Address[2], v9, v8, v5, v29, Address[4], v10);
//                           OutFlag(&v39) ProcessId  PageIdx AddrField pOutBuf OutSize ResultBuf Flag
```

由此确定 8 个形参（也解决了 `arg_XX` 槽位命名）：

| 形参 | 调用点实参 | 函数体内对应 |
|---|---|---|
| 1 OutFlag | `&v39` | `*(BYTE*)rcx = 1`（序言）；`arg_0` 即此槽 |
| 2 ProcessId | `Address[2]` | 作 IOCTL 句柄传 `SendDeviceIoControlWithRetry` |
| 3 PageIndex | `v9` | 循环里 `cmp PageIndex, 1`（`arg_18`） |
| 4 AddressField | `v8` | `cmp r9d,2; ja 失败`；作类型传子调用（`arg_10`） |
| 5 pOutputBuffer | `v5` | 作子调用第 6 实参（`arg_20` → rsi 初值） |
| 6 OutputSize | `v29` | **`arg_28` → r15d**（剩余量初值，每轮递减） |
| 7 ResultBuffer | `Address[4]` | 游标基址（`arg_30`） |
| 8 Flag | `v10` | `cmp Flag, 1`（`arg_38`） |

> 与读版对照：读版第 5/6/11 实参是 `v5/a4/v35`，本版是 `v5/v29/Address[4]` ——
> 说明写版把"结果缓冲"（`Address[4]`）与"输出缓冲"（`v5`）**分开传**，
> 而读版是合一的。这是两版的实质差异之一。

## 十、`SendWriteMemoryIoControl` 实参映射最终定案（2026-09-29）

**裁判 = 调用点反汇编**（0x140074A60–0x140074AD3，`CmdWriteProcessMemoryEx` 内），
不经任何推断：

140074A9B  mov  edx, 4 / mov r8d,edx / call ProbeForWrite    ; 校验结果缓冲可写
140074AA9  mov  [rsp+0B8h+var_80], r12b      ; ← 第 8 实参槽 (rsp+0x38)  = char
140074AAE  mov  rax, [r13+20h]
140074AB2  mov  [rsp+0B8h+var_88], rax       ; ← 第 7 实参槽 (rsp+0x30)  = [r13+0x20]
140074AB7  mov  dword ptr [rsp+0B8h+var_90], r14d ; ← 第 6 实参槽 (rsp+0x28) = dword
140074ABC  mov  [rsp+0B8h+var_98], rsi       ; ← 第 5 实参槽 (rsp+0x20)  = void*

**结论（形参表）**：

**⚠ 据此更正两处此前的错误结论**：
1. 我先前按"IDA `arg_XX` 显示名 = 形参序号"推断，得出 `arg_28`=OutputSize —— **错位一格**。
   函数体内：`arg_18`=第4实参(AddressField??)… 以本表为准（下文实现时逐条对齐）。
2. 我先前从调用方**伪代码变量名**（`v29`/`Address[4]`）推断"第 7 = ResultBuffer、第 8 = Flag"，
   与反汇编一致 ✓；但从伪代码无法得知**宽度**（第 6 是 dword、第 8 是 char），
   只有反汇编能给出 —— 再次印证"**以反汇编为最终裁判**"。

### 十·补：槽位↔形参的严格映射 与 一个待解矛盾

**严格映射**（推导：`lea rbp,[rax-3Fh]` 且 `rax`=entry_rsp，故 `[rbp+37h+arg_N]` = `entry_rsp + N - 8`；
x64 下形参 k 位于 `entry_rsp + 8*(k-1)`，参数 1..4 占 shadow space）：

| IDA 显示名 | entry_rsp 偏移 | 形参序号 |
|---|---|---|
| `arg_10` | +0x08 | **1** |
| `arg_18` | +0x10 | **2** |
| `arg_20` | +0x18 | **3** |
| `arg_28` | +0x20 | **4** |
| `arg_30` | +0x28 | **5** |
| `arg_38` | +0x30 | **6** |
| `arg_40` | +0x38 | **7** |
| `arg_48` | +0x40 | **8** |

**序言 home 写入自证**（编译器生成，必然正确）：`mov [rax+8],rcx`(形参1→arg_10)、
`mov [rax+18h],r8d`(形参3→arg_20)、`mov [rax+20h],r9d`(形参4→arg_28) —— **与上表逐项吻合** ✓

**待解矛盾（阻碍忠实实现）**：

| 位置 | 函数体用法 | 调用点传参 | 矛盾 |
|---|---|---|---|
| 形参 3（`arg_20`） | `mov rsi,[arg_20]` —— 按 **8 字节指针**读 | `mov r8d, ebx` —— 32 位整数 | 宽度不符 |
| 形参 6（`arg_38`） | `cmp [arg_38], r8b` —— 与 1 作**字节**比较 | `mov dword [var_90], r14d` —— dword | 宽度不符 |
| 形参 2（`arg_18`） | `cmp [arg_18], 1` —— dword 比较 | `mov rdx,[r13+10h]` —— 指针/句柄 | 语义不符（句柄与 1 比较） |

**三种可能解释**（下一轮需先排除）：
1. 调用点 0x140074AD3 的栈槽与我的分配差 8 字节（即 `[rsp+0x20]` 实为形参 6 而非 5）；
   —— 可验证方式：对 `CmdWriteProcessMemoryEx` 用 `_dump2` 取**其自身的序言 home**，反推其 `entry_rsp`，
   再算调用点各 `[rsp+X]` 的真实形参序号；
2. `SendWriteMemoryIoControl` 的形参声明本就不含"结果缓冲"（我按读版类比引入的假设有误），
   其真实签名更接近读版（参数更少）；
3. IDA 对 `arg_XX` 的命名在本函数里与 `entry_rsp` 基准不符（已知 IDA 在个别函数上会如此）。

**结论**：`SendWriteMemoryIoControl` 的实现**必须先做上述验证 1**（取调用方序言 home），
在矛盾消除前不写第三版 —— 前两版均因该处失真而主动废弃（未提交）。

### 十·最终更正：`arg_N` 基准 = entry_rsp（此前推导有误）

**决定性证据**：调用方 `CmdWriteProcessMemoryEx` 的序言
```
1400749A0 mov [rsp+arg_18], r9d   ; 第4形参 a4
1400749A5 mov [rsp+arg_10], r8    ; 第3形参 a3
1400749AA..9B3 push rbx/rsi/rdi/r12/r13/r14/r15   ; 7 push = 0x38
1400749B5 sub rsp, 80h
```
而调用点用 `[rsp+0B8h+arg_N]` → `0xB8 = 0x38 + 0x80` ✓（即 arg 基准就是**入口 rsp**）。
故 **`arg_N` 偏移 = 入口 rsp + N**（我上一条"`N - 8`"的推导**错误**，源于我把 callee 的
`lea rbp,[rax-3Fh]` 与 caller 的基准混用）。

**修正后的槽位↔形参映射（本函数 `SendWriteMemoryIoControl`）**：

| IDA 名 | 偏移 | 形参 | 实参（调用点定案） |
|---|---|---|---|
| `arg_10` | +0x10 | 3 | PageIndex（`mov r8d,ebx` 的 home） |
| `arg_18` | +0x18 | 4 | AddressField（`mov r9d,r15d` 的 home） |
| `arg_20` | +0x20 | **5** | **pOutputBuffer**（void*，`mov rsi,[arg_20]` ✓） |
| `arg_28` | +0x28 | **6** | **OutputSize**（`mov r15d,[arg_28]` ✓） |
| `arg_30` | +0x30 | **7** | **ResultBuffer** |
| `arg_38` | +0x38 | **8** | **Flag**（`cmp [arg_38],1` 按字节 ✓） |

**矛盾全部消除**（三处宽度/语义不符均得到解释）：
- `mov rsi,[arg_20]` 8 字节 = 形参 5 输出缓冲（指针）✓
- `cmp [arg_38],r8b` 字节 = 形参 8 标志 ✓
- `cmp [arg_18],1` = 形参 4 地址字段（调用方传 `r15d`）✓

**方法论教训（第三次同类）**：我三次在"`arg_XX` 基准"上出错，根因都是**混用 caller 与 callee 的
rsp 基准**，且**没有优先去看 caller 的序言**（那里有编译器生成的 home 写入，
是确定基准的最硬证据）。**今后凡遇 `arg_XX` 歧义，第一步就看调用方序言的 home 写入。**

### 十·第二次停手：`SendWriteMemoryIoControl` 剩余的**具体**未知点

修正映射后我又逐条核了三条路径，**已确证**的部分：

**循环状态变量（已确证）**：
- `rsi` = **当前游标**（初值来自 `mov rsi,[arg_20]` = pOutputBuffer，即形参 5），每轮 `rsi += Step`
- `r14` = **上一轮游标位置**（`mov r14,rsi` 在推进前保存；循环内 `mov [r14],r12d` 写它）
- `r15d` = 剩余量（初值 `[arg_28]` = OutputSize，每轮 `-= Step`）
- `r12d` = 累计计数（循环内 `+= 1`）；`var_8C` = 另一计数
- `Step`：描述符 `[+8]`，若为 `0xFFFFFFFF` 则改用 `[+0x10] + 0x14`；收尾条件 `Remaining <= Step+4`

**路径 C 的 7 实参（与 `SendIoControlWithQuotaBufferEx` 的 7 形参完全吻合 ✓）**：
```
rcx=[var_60]  rdx=[var_88]  r8d=PageIndex  r9d=AddressField
[rsp+20h]=rsi(游标)  [rsp+28h]=r15d(Remaining)  [rsp+30h]=ResultBuffer
```
→ 即 (HandlerFunc, Arg2, Arg3=PageIndex, Arg4=AddressField, Dst=游标, NumberOfBytes=Remaining, pOutSize=ResultBuffer)

**仍未确证的一点**：`var_60` 与 `var_88` 的**语义**
- `var_88`：由 `0x140072FD2` 附近的 IOCTL 结果写入（`mov [var_88],...`），疑为"发送 IOCTL 后取得的目标句柄"
- `var_60`：由 `0x140072F40 mov [var_60],rax` 写入（`rax` 来自 GT 0x179 的读取）
- 这两者哪个对应 `SendIoControlWithQuotaBufferEx` 的 `HandlerFunc`、哪个对应 `Arg2`，
  **需通过 `SendIoControlWithQuotaBufferEx` 自身的实现或调用点来确定**（尚未做）。

**路径 A（`AllocBufferAndSendIoControl`）**：4 个寄存器 + 4 个栈槽 =
`rcx=Value198  rdx=游标  r8=Handle88  r9d=AddressField`，
栈槽 `[rsp+20h]=?、[rsp+28h]=?、[rsp+30h]=?、[rsp+38h]=?`
—— 其中 `[rsp+38h]` 由 `mov [rsp+38h],rax(=ResultBuffer)` 写入（**已确证**），
另三个的归属待定（`rsi`/`r15d`/`r9d` 的组合方式需与 9 形参签名逐一对齐）。

**结论**：`SendWriteMemoryIoControl` 的可转写程度约 **85%**（循环、状态变量、条件分支、
收尾、路径 C 全确证），剩余 **15%** 集中于"路径 A/B 的栈实参归属"与"`var_60`/`var_88` 语义"。
**下一轮只需解决两点**（`SendIoControlWithQuotaBufferEx` 的调用点/实现 + 9 形参对齐），
