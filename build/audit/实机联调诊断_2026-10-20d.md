# 实机联调诊断（2026-10-20 第四轮）：修正第三轮的结论

## 第三轮结论被推翻

第三轮判断「崩溃源于驱动被卸载（`sc stop/delete` 撞上 `DriverUnload`）」，
本轮用**最干净的流程**证伪了它：

```
重启 guest
  → sc create RTZ69 （只创建，不 delete）
  → sc start RTZ69  → START_EXIT=0, STATE: 4 RUNNING
  → 立即运行 xpch_probe --live --open-only
  → vmrun 超时 143
  → guest 挂死：host_cpu_percent=0.0, guest_reachable=false
  → 连 open69.txt 都没生成（cmd.exe 都没跑完）
```

整个流程里**没有任何 stop/delete**，`DriverUnload` 不可能被调用。
所以崩溃与卸载无关。

## 修正后的结论

**探针执行 `CreateFileW(L"\\\\.\\View++ByLinxer")` 会让 guest 崩溃。**

崩溃点（前几轮重复出现）：
```
nt!ObpLookupObjectName+0xea
bugcheck 0x3B / 0xC0000005
```

`ObpLookupObjectName` 在解析符号链接时读取目标对象。它在 `+0xea` 崩溃，
说明**符号链接的 Target 字符串或目标对象头无效**。

而 `IoCreateSymbolicLink` 断点实测的参数是正确的（见第三轮文档）。

因此嫌疑集中在：**符号链接创建后，其 Target 字符串所在的内存被覆盖**。

## 可能的根因（待验证）

`RtlInitUnicodeString(&SymStr, L"\\DosDevices\\View++ByLinxer")` 让
`SymStr.Buffer` 指向**字面量 `L"\\DosDevices\\View++ByLinxer"`**。

但 `IoCreateSymbolicLink` 并**不复制**目标字符串 —— 它保存的是指针。
如果那个字面量位于**可丢弃的初始化段**（`.rdata` 中若被标记为
`INIT`/discardable），驱动初始化完成后该内存被释放，符号链接就指向
已释放内存，任何 `CreateFile` 都会在 `ObpLookupObjectName` 崩溃。

我方驱动很可能把字符串放在 `.rdata` 且使用了 `#pragma section` 或
`/Gy` 等设置导致该段被标记为可丢弃。这需要检查 PE 段的 Characteristics。

原始驱动显然避开了这个问题（它用 `wcsncat` 把名字拼到全局缓冲区
`g_SymlinkNameBuffer` 里，再基于该缓冲区构造 UNICODE_STRING）。

**注意我方代码里已经有 `g_SymlinkNameBuffer` 的拼装，但后面却
`RtlInitUnicodeString(&SymStr, L"...")` 又用回了字面量** ——
拼装结果完全没被使用。这很可能就是缺陷所在。

## 下一步（具体）

1. 把 `RtlInitUnicodeString(&SymStr, L"\\DosDevices\\View++ByLinxer")`
   改为基于 `g_SymlinkNameBuffer`（堆/全局缓冲区）构造 UNICODE_STRING，
   与原始驱动一致：`SymStr.Length = SymNameIdx * sizeof(WCHAR)`；
   `SymStr.Buffer = g_SymlinkNameBuffer`。
2. `DestStr`（`\Device\View++ByLinxer`）同理，改用 `g_DeviceNameBuffer`。
3. 检查 PE 段 Characteristics，确认 `L"\\DosDevices\\..."` 字面量所在段
   是否被标记为 discardable。
4. 改完后重新实机验证 `--open-only`。
