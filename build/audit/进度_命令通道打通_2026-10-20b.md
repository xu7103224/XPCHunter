# 进度：命令通道打通中，已修 3 个新缺陷（2026-10-20 第二轮）

## 本轮修复（承接第一轮的 5 个）

### 6. `InitRegNotify` 的链表索引写错（RTZ62 蓝屏）

原始 `0x14000C213` 是 `mov ecx,16Dh`，我方写成 `GT[0x415F]`。
`0x415F` 在原始驱动中**从未被引用**，是凭空捏造的索引。

后果：真正的链表没被释放（泄漏），而 `GT[0x415F]` 若被别处写入非链表数据，
`FreeListAllocation` 就把任意值当链表头 → `mov rbx,[rcx+0x20]` 解引用野指针
→ 0x3B/0xC0000005 蓝屏。

已改为 `GT[0x16D]`，并补齐原始里的 `GT[0x6B]` / `GT[0x6C]` / `GT[0x354]` 三段。

### 7. `ReadWriteVirtualMemory` 两个索引凭空捏造

原始 `0x14007173C` / `0x140071749` 依次是 `GT[0x41C3]` / `GT[0x4166]`；
我方写成 `16735`（0x415F）/ `16748`（0x416C）—— 这两个槽同样从未被原始引用。

已改为 `0x41C3` / `0x4166`。

### 8. `MmUserProbeAddress` 被多解引用一次（RTZ63/64 蓝屏）

这是本轮最隐蔽的一个。`MmUserProbeAddress` 在内核里是 **`ULONG64` 变量**，
不是指针。实机 `dq MmUserProbeAddress` 得到：

```
fffff807`1ed7d558  00007fff`ffff0000
```

即它的值就是用户地址上界 `0x7FFFFFFF0000`。

原始驱动 `0x140019357`：
```
mov rax, cs:MmUserProbeAddress     ; rax = &变量
mov rcx, [rax]                     ; rcx = 变量的值（上界）
```
只有**一次**解引用。

我方源码写成 `*(ULONG64 *)MmUserProbeAddress` —— 把上界值 `0x7FFFFFFF0000`
当地址再读了一次，得到垃圾值（实测 `rdx = 0x8A`），随后
`cmp r8, rcx` / `ProbeForWrite` 全部失效。

共 5 处（都在 `Minifilter.c` 的 `ProbeLimit = ...` 赋值行），已全部去掉多余解引用。
修复后我方生成代码与原始逐指令一致：

```
mov  rax,[rip+...]      ; &MmUserProbeAddress
mov  rcx,[rax]          ; 上界
cmp  r8,rcx
```

## 附带修复：`MiniFilterCommPortReply` 的参数映射

原始 `0x14001934E` 是 `mov rdi,r8` —— 输出缓冲取**第 3 个参数 r8**。
命令分派约定是 `(rcx=ContextPointer, rdx=OutputSize, r8=ExtraPointer, r9d=ContextSize)`，
所以正确签名是 `(Unused1, Unused2, Output, OutputSize)`。
旧签名 `(Address, Length, Output, OutputSize)` 把 Address 放在 rcx，走错了分支。

| 工具 | 用途 |
| --- | --- |
| `audit_gt_literal_indices.py` | 逐个函数比对源码里的 `GtRead/GtWrite` 字面量索引与原始反汇编中该函数的真实立即数，报出「源码有、原始没有」的索引 |
| `audit_cmdtable_signatures.py` | 从原始驱动提取命令表 248 个函数各自对 rcx/rdx/r8/r9 的**首次用法**，给出参数角色 |

两个工具都踩过同一个坑并已修正：**必须从函数入口开始线性解码**，
否则会从指令中间起解、落到非法指令上，产生大量误报（第一版误报 71 处，
修正后降到 42 处，剩余的多数是条件分支差异，需人工判断）。

## 关键教训

这一轮 3 个缺陷都属于同一族：**索引/指针的取值方式与原始不符**，而且
都不会在 `sc start` 阶段暴露——驱动能 RUNNING，只有真正发命令才崩。
所以「驱动能加载」远不等于「功能可用」。
