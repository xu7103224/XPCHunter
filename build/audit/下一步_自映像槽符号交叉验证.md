# 下一步：用符号名交叉验证 248 个自映像槽（已发现 8 个真缺陷）

## 方法

同会话对比得到 248 个"自映像指针"槽（GT 0x921..0xA3A），它们存的是驱动内部
函数的地址。因为两次加载的模块基址不同、且 LTCG 会重排函数顺序，绝对地址（甚至
RVA）都不同，所以之前只做了"LTCG 重排"的定性判断。

但真正的判据是**语义等价**：把两边的地址各自解析成函数名，名字应当一致。

- 原始侧：`_orig_funcs_ida.json`（1516 条，IDA 导出）
- 我方侧：`XPCHunterDrv.map`（1169 条，link.exe 导出）
- 各自取 "≤ RVA 的最近符号" + 偏移

## 结果

| 类别 | 数量 |
| --- | --- |
| 函数名完全相同（含偏移 0） | **216** |
| 名字不同 | 32 |
| 无法解析 | 0 |

216/248 = **87% 精确对齐**，这是比"RVA 不同"强得多的证据。

## 为什么静态引用表（gt_writesites.py）查不到这 8 个槽

`gt_writesites.py` 只识别 `mov ecx, <立即数>` 形式的索引。这 8 个槽的写入方用了
**动态索引**——驱动里存在大量

```
cmp eax, 0xa28        ; 0xA28 = 2600 = 全局表槽数
```

的循环边界（原始驱动中出现 **34 次**），说明有一族函数按"表下标"遍历整张 GT 并逐项
登记函数指针。这类写入的索引来自寄存器，静态扫描看不到。

这正是 `BuildHookTable` 那次（`0x4474`/`0x4475`）的同一模式。

## 下一步的具体动作

1. **定位写入者**：在原始驱动上对这 8 个 GT 地址下**硬件写断点**
   （`ba w8 <GT基址 + idx*8>`），在 guest 里加载原始驱动，抓调用栈，得到
   写入函数与其原始索引表达式。
2. **对照我方实现**：同一索引在我方写入的是哪个函数，是"填错了位置"还是
   "函数本身被写成了另一个功能"。
3. **逐槽修正**：按原始语义改正，再用 `gt_samesession_diff.py` 复验 216 → 240+。
4. **补齐 oracle**：为这 8 个函数各建一个离线差分，防止回归。

其中 0xA21（`Win8` vs `Win10`）和 0x93F（`Monitor` vs `Operation`）最可能是
**索引写错**（把相邻槽的内容写串了），其余 6 个更像是**实现内容本身不匹配**，
需要读原始反汇编确认。
