# 无界循环验证（18 处 `for(;;)`）

## 结论

`XPCHunterDrv/src/` 共 18 处 `for(;;)`，**全部有可达退出路径**，且退出条件与原始
反汇编一一对应（原始本身就是寄存器级无条件回跳 + 内部条件退出，不是 bug）。

## 自动化检查

`python build/audit/check_unbounded_loops.py` → **for(;;) 循环总数: 18，无退出路径: 0**

脚本按花括号配平取出循环体，剥掉注释与字符串后搜索 `break|return|goto`。

## 终止性的真正保证：解码器自带 End 边界

绝大多数循环以 `ReadPESectionEntry(...) != 0` 作为退出条件。该函数在
`PEDecoder.c` 的**每条**取值路径前都检查 `CTX_OFF_END_PTR`（+0x10）：

```
PEDecoder.c:222   if (BufferPos >= (PUCHAR)CTX_Q(Context, DEC_CTX_BUFFER_END))
PEDecoder.c:312   if (BufferPos >= (PUCHAR)CTX_Q(Context, DEC_CTX_BUFFER_END))
PEDecoder.c:352   CTX_Q(Context, DEC_CTX_BUFFER_END),
```

而 `InitPESectionReadContext` 把 `+0x10` 设为 `Base + Size`（同文件 159 行）。
每轮循环都会把读指针推进 `Entry[0xF0]`，因此读指针单调递增、必然触达 End，
`ReadPESectionEntry` 返回非零 → 循环退出。

## 特别说明：`SsdtHook.c:5451` 的"无轮次上限"是有意为之

原始 `HookSyscallNtDeleteKey` 的循环（`0x14001FFFC jne → 收尾`）**确实没有**轮次计数，
只靠 `ReadPESectionEntry` 的解码失败退出。此前为"防挂起"加过 `LoopIndex < N` 的上限，
反而偏离了原始语义（会导致扫描提前中断、漏写 GT[0x34E]）。现已改回 `for(;;)`
并加 `__declspec(noinline)`，实机 `sc start` 稳定 RUNNING。

## 实机佐证

RTZ19..RTZ56 共 30+ 次实机加载，全部：

```
sc start <svc>   → START_EXIT=0
sc query <svc>   → STATE: 4 RUNNING
```

若任一扫描器存在真实死循环，`DriverEntry` 会挂死在初始化阶段，`sc start`
将超时失败而非返回 RUNNING。
