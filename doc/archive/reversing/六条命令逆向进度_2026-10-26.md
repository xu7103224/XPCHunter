## 二、已修复：`0x0D5` 的 `pOutputEntry[24]` 被无条件覆盖

原版 `CmdEnumKernelObjectTable` 按构建号分四条字段布局分支，其中
`pOutputEntry[24]` 只在两条分支里被赋值（经 `LABEL_18`）：

| 构建号 | `pOutputEntry[24]` |
|---|---|
| `< 0xA28` | `= pObjectHeader[7]` |
| `< 0x23F0` | `= pObjectHeader[8]` |
| `> 0x2580` | `= 0`（显式，**跳过** LABEL_18） |
| 其余 | `= 0`（显式，**跳过** LABEL_18） |

我方原实现在四条分支之后多了一行 `pOutputEntry[24] = FieldValue;`，
用**未初始化的** `FieldValue` 覆盖了后两条分支刚写的 0。

本机构建号 18362（`0x47BA`）走 `> 0x2580` 分支，因此每个条目的这一字段
都被写成了垃圾值。已改为在各分支内赋值，实测 `0x0D5` 的字节差
**961 → 952**，A/B 状态保持 28 OK 无退化。

## 三、`0x0D4` 发现错误接线（已回滚，待配套条件）

### 3.1 错误本身

我方 `Table[180] = CmdEnumObjectTypes`，但该函数的实现是：

```c
return ((PCOMMAND_HANDLER)EnumObjectTypeInfoOperation)(...);
```

`EnumObjectTypeInfoOperation` 是**另一条命令**（槽 200 / `CmdEnumObjectTypeInfo`
@ `0x14007EDC8`）的实现。这解释了实测的布局差异：

```
原版 0x0D4: +0x00 = 0x26 (条目数 38)，+0x08 起为 (指针,大小) 交替
我方 0x0D4: +0x00 = 0x05，+0x04 = 0x05，+0x08 = 0x02，+0x10 起 指针 + ASCII 名
```

### 3.2 原版的正确实现（已完整逆出）

```
*OutputBuffer = 0;
MaxEntries = ((BufferSize - 40) >> 5) + 1;        // 条目步长 0x20
if (build >= 0x23F0) {
    if (build > 0x2580)  ScanProcessVadForObjectTypes(Out+2, Out, MaxEntries);
    else                 DispatchEnumObjectTypes(Out+2, Out, MaxEntries);
} else {
    pTypeTable = GT[0x31A];
    if (!pTypeTable) { FindWin32kSectionByType(); pTypeTable = GT[0x31A]; }
    if (pTypeTable) EnumProcessObjectTypes(pTypeTable, 3, Out+2, Out, MaxEntries);
}
return *OutputBuffer != 0;
```

本机 18362 > 0x2580，走 `ScanProcessVadForObjectTypes`。
三个辅助函数在我方**均已存在**（`MemoryOps.c` 的 3074 / 3536 / 3743 行），
签名与调用点全部匹配。

### 3.3 为什么按正确实现写完却返回 REJ

`ScanProcessVadForObjectTypes` 的入口门限（原版 `0x14008A278` 反汇编确认）：

```
14008a29a: mov ecx, 41DBh ; GT[0x41DB] —— 对象类型检查函数
14008a2a7: test rax, rax
14008a2aa: jz   返回          ← 为 0 直接退出
14008a2b0: mov ecx, 4265h ; GT[0x4265] —— 对象类型信息指针
```

运行时实测这两个槽**都是 0**：

```
GT[0x41DB] = 0
GT[0x4265] = 0
```

它们的唯一写入者是 `InitObjectCallbackEntries`（原版 `0x1400100A4`），
调用链经反汇编 xref 确认是：

```
命令 0x6B (EnableObjectCallback, 0x14000FB88)
  → InitObjectCallbackFiles (0x14000F8E4)
      → InitObjectCallbackEntries(文件句柄)   ← 参数是 CreateFileWithPath 返回的 HANDLE
```

而 `0x6B` 在 A/B 扫描里被列入 `g_AbDangerous` 有意跳过，所以两个驱动
在扫描时 `GT[0x41DB]` 都应恒为 0。

### 3.4 未解的矛盾（下一步的关键）

原版在**同样跳过 0x6B** 的前提下，`0x0D4` 两次采集都返回了数据
（`0x26`=38 条 / `0x15`=21 条）。这与 3.3 的推理矛盾，说明原版还有
一条**尚未定位的**填充路径把 `GT[0x41DB]` 置成了非 0。

已排除：
- 不是 `InitCommandHandlerTable` 里的间接调用（`EnableObjectCallback` 的
  code xref 只有命令表一处）
- 不是 `CmdEnumObjectTypes` 自己填充（它只读）

**下一步**：在 IDB 里对 `0x140010153` / `0x1400104A3`（`InitObjectCallbackEntries`
内两处引用 `0x41DB` 的位置）确认哪一处是写；再对 `GT[0x41DB]` 下**写入断点**
（kdBp 或 `.writemem` 观测）跑一次原版的 `0x0D4`，直接从运行时抓出写入者。
定位后再把 3.2 的实现正式启用。

当前为免引入未验证的状态回归（正确实现下 `0x0D4` 会 OK→REJ），
`Table[180]` 暂时保留原转调，正确实现与上述分析已完整记在本文件。

## 四、`0x0D5` / `0x0FF` / `0x0D4` 共用同一条对象类型数据源

`0x0D5` 的计数来自 `GT[0x337]`（对象类型链表头），`0x0FF` 的条目来自
`GT[0x...]` 同一族对象类型表，`0x0D4` 依赖 `GT[0x41DB]`/`GT[0x4265]`。

三者都由对象类型初始化链填充。因此：

- `0x0D5` 条目数 26 vs 原版 27–30
- `0x0FF` 条目数 93 vs 原版 136（少 43 种）
- `0x0D4` 布局完全不同（见第三节）

**这三条应作为一组一起修**，根因在初始化链而非各自的枚举逻辑。

## 五、`0x108` 的阻塞点（已精确到函数内）

### 5.1 已确认正确的部分

`CmdEnumProcessorInfo`（`0x14002FDD4`）我方实现与原版逐行一致；
其七个前置槽用正确的十六进制槽号复测**全部正常**：

```
GT[0x4B] = 0x820 = 2080    GtObjectTypeCount
GT[0x37] = 0x648 = 1608    GtProcessEprocess
GT[0x38] = 0x220 = 544     GtProcessOffset
GT[0x35] = 0x420 = 1056    GtEprocessField43
GT[0x1CF]= 0x28  = 40      ObjectTypeOffset
GT[0x873]= 0x190 = 400     ImageFileOffsetVal
GT[0x4265]= 有效指针        SectionBase
```

并用诊断确认 `InitEprocessFieldOffsets` 被调用、进入
`BuildNumber == 18362` 分支、返回后 `GtObjectTypeCount` 确为 2080。
`ExAlloc(PagedPool, 0x44610)` 也成功（返回有效池指针，Tag 正常，`PagedPool`=1）。

### 5.2 原版那 33 字节不是"处理器上下文"

反推确认：原版 `0x108` 的 33 字节是**进程枚举的部分写入**——
`+0x10` 是 EPROCESS 指针、`+0x18` 是基优先级字段、`+0x20` 是对象表字段，
而计数停在 0 是因为随后那道 `EprocessAddr` 校验失败。
`ReadThreadContext`（`0x14002FB54`）此路径未写任何条目。

### 5.3 真正的阻塞：`EnumerateProcessList` 返回 0

诊断实测 `EnumRet = 0`、`pProcessBuffer[4]`（计数，位于 `OutputBuffer+0x10`）= 0。

`EnumerateProcessList`（`0x14004FF98`）我方与原版逐行一致，它返回
`*(DWORD*)(OutputBuffer+16) != 0`。计数为 0 说明两个子函数都没加条目：

```
DispatchProcessHandleTableEnum(...)   // 其结果不被使用
EnumerateProcessInformation(0, Out, Size)
```

`EnumerateProcessInformation`（`0x14004FAC4`，0x412 字节）的 9 个前置槽
反汇编确认与我方索引完全一致，且运行时全部有效。**失败在其内部校验链**：

```
memset(Dst, 0, 0x40)
Thread = gs:[188h];  saved = Thread[GT[0x27]];  Thread[GT[0x27]] = 0
call GT[0x41DE]                                   // 查询函数
GetKernelVirtualAddressRange(&Src, &end)
循环每个 0x1000 页:
  call GT[0x41DB]                 必须返回 1      ← 第一道
  call CallRegisteredCallback     必须返回 1      ← 第二道
  call GT[0x41E4]                 必须非 0 且 < rdi
  call CmdStubAlwaysTrue          恒 1
  call ValidateEnumerationResult  必须返回 1      ← 最后一道
```

**注意第一道又是 `GT[0x41DB]`** —— 与第三节同源。

### 5.4 因此 `0x108` 与 `0x0D4` 共享同一根因

两者都卡在 `GT[0x41DB]`。定位该槽的真实填充路径，
**同时**能解开 `0x0D4` 与 `0x108`。

## 七、测试覆盖缺口（本轮发现，影响所有结论的置信度）

A/B 只覆盖 **126 / 283 条**命令（`0x20`–`0x13A`），**157 条从未被测**。

其中 `0x6B`（`EnableObjectCallback`）被列入 `g_AbDangerous` 有意跳过，
而它正是对象回调初始化链的入口。凡依赖该链的命令在 A/B 里都会
"看起来失败"，与真实前端调用顺序下的行为不同。

`g_SkipCommands` 的注释已记录同一现象：

> calls GT[0x4226] ... GT[0x42A6] through EnumProcessInformationWorker.
> Those slots are filled by InitObjectCallbackEntries / object enumeration,
> which no caller has run yet at sweep time.

**建议**：A/B 在正式扫描前先补一轮"真实前端的初始化前置命令"
（至少 `0x6B`），否则对象类命令的结论不可靠。
