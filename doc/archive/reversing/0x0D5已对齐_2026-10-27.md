|---|---|---|

**条目集合逐项比对：`only mine = []`、`only orig = []`** —— 完全一致。

## 此前「多 1–2 条」的真相

此前记录为「原版 29 / 复刻 30，多出 `0xBEE0BEE0` 已释放池节点」，
判断是实现缺陷。**该判断错误。**

实际原因是**测量方法**：每次都是先跑复刻、再切驱动跑原版，两次之间相隔
十几秒，而内核对象类型链表在这段时间里会随进程/驱动创建销毁而变化。
因此差异是**系统状态漂移**，不是实现差异。

正确做法（本次采用）：在**同一驱动状态下连续测量**，并与原版自比对照。
原版自比两次结果完全相同（29/5776），复刻也是 29/5776 且集合相等 →
**0x0D5 无需修改，已对齐**。

## 复核方法（可复现）
```
# 1) 原版连跑两次，确认自稳定
xpch_probe --live --handshake --ab --ab-lo 0x0D5 --ab-hi 0x0D5 --ab-out ...
# 2) 切到复刻，跑一次
# 3) 按 0xC8 步长解析条目集合，比较 set(entries)
```
条目布局：`+0x00 DWORD 构建号`、`+0x04 DWORD 条目数`，之后每 0xC8 字节一条，
条目 `+0x00` 是对象地址。

### 28 与 26 的再确认
过程中曾出现原版首次枚举 28 条的情形。对称对照实验（两个驱动都做
「删服务 → 重建 → 启动 → 首次探测」）显示两者首次均为 26 条，说明 28 是
