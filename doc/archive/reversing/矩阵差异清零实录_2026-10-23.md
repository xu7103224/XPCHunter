# 全命令矩阵差异清零实录（2026-10-23 夜）

本轮把全命令 I/O 差分矩阵的差异从 **10 条压到 1 条**（且最后 1 条经查证是原版
未定义返回值，不是功能缺口）。以下每条都给出了：症状 → 定位手段 → 根因 →
修复 → 同开机对照证据。

工具链与约束沿用前几轮：IDA Pro MCP（原版 IDB `origdrvG`）+ kd 双机调试
（KDNET，VM `win10dev`）+ `xpch_probe.exe` 的 `--live --cmd` / `--matrix`。

## 二、0x0C4 `CmdFixProcessEProcess`：状态常量写错

### 症状
`FixProcessEProcessOperation` 恒返回 0。诊断槽 `0x4FF0 = 1`，
即 `QueryObjectTypeDirectoryPath()` 返回的目录指针为 0。

### 定位
给 `QueryObjectTypeDirectoryPath` 加分级诊断（0x4FF5 阶段码 / 0x4FF6 状态 /
0x4FF7-0x4FFD 遍历细节）。实测：

```
0x4FF5 = 6      → 主循环走完没找到目标
0x4FF6 = 0      → ObReferenceObjectByName 成功
0x4FF7/F8 非零  → DriverObject / 首个 DeviceObject 正常
0x4FF9 = 1      → 只遍历了 1 个设备
0x4FFA = 1      → 类型/标志命中 1 次
0x4FFB = 0      → **第一次 ObQueryNameString 没返回期望值**
```

### 根因
原版 `0x1400797A7` 是 `cmp eax, 0C0000004h`（`STATUS_INFO_LENGTH_MISMATCH`），
我方写成了 `STATUS_BUFFER_TOO_SMALL`（0xC0000023）。
`ObQueryNameString(DevObj, NULL, 0, &len)` 在缓冲区传 NULL 时返回的正是
`0xC0000004`，所以这个判断在旧代码里**恒不成立**，整个函数必然返回 0。

### 修复
`XPCHunterDrv/src/kernel/ObjectMgmt.c`：

```c
if (ObQueryName(DeviceObject, NULL, 0, &ReturnLength) == (NTSTATUS)0xC0000004L
    && ReturnLength)
```

### 证据
修复后 `command 0xC4 -> OK, result=1`。

## 三、0x0F8 `CmdInitKernelMemoryContext`：整个函数没实现

### 症状
命令恒返回 0，我方 `IoctlDispatch.c` 里该函数只有一行注释 + 转调别的函数。

### 定位
IDA 反汇编原版 `0x1400681DC`：42 条指令的实函数，不是转调。

### 语义（逐条转写）
```
0x1400681F4  GT[0x7D0]（NsiDeregister 数据节）；为 0 才调 InitKernelMemoryContext
0x140068205  rdi = GT[0x7D0]（重读）
0x140068212  rsi = GT[0x7CF]（要调用的函数指针）
0x14006821A  !rdi → 失败
0x140068226  rdi <= MmSystemRangeStart → 失败
0x14006822B  !rsi → 失败
0x140068235  CheckMemoryValid(rdi) != 1 → 失败
0x14006823E  rcx = *rdi；为 0 直接成功
0x140068246  call rsi(rcx)；返回值 < 0 → 失败
```

### 修复
按上述流程完整重写（`XPCHunterDrv/src/services/IoctlDispatch.c`）。实测
`command 0xF8 -> OK, result=1`。

## 四、0x0FB `CmdWriteKernelMemoryRange`：三处偏移 + 一处漏参

### 4.1 第一层：描述符偏移错（导致 GT[0x7BA] 恒为 0）

`ScanKernelDataPartitionSection`（对应原版 `0x140069504`）是两阶段匹配。
按**本函数自己的栈帧**换算（描述符基址 `var_160 = rbp-0x60`）：

| 原版引用 | 真实偏移 | 旧代码 |
|---|---|---|
| `mov eax,[rbp+100h+Value]` | desc+**0x78** | +0x40 |
| `mov r13d,[rbp+100h+var_108]` | desc+**0x58** | +0x8C |
| `cmp r13d,[rbp+100h+var_D0]` | desc+**0x90** | +0x8C |

诊断槽 0x5000 起的实测描述符证实：两条类型 `0x510` 的记录其 `+0x78` 才是
非零的候选字段，`+0x48` 恒为 0 —— 与旧代码用 +0x40/+0x48 读的结果完全对不上。

**教训**：`listed_offset - 0x100` 才是真实 rbp 偏移。IDA 的 `stack_frame`
offset 字段是 `var_XXX` 相对 `rbp+0x100` 的编号，不能直接当字节偏移用。

### 4.2 第二层：`AllocateNtHandleEntry` 漏传实参 → 蓝屏 0x3B

修好偏移后扫描成功（`GT[0x7BA]=fffff80460437560`、`GT[0x7BB]=0x380`），
但紧接着 BSOD 0x3B（0xC0000005），栈顶：

```
nt!ObfDereferenceObject+0x26
ViewPlusPlusByLinxer+0x1f8e7   → AllocateNtHandleEntry + 0xb7
ViewPlusPlusByLinxer+0x2d50f   → CmdWriteKernelMemoryRange + 0x6f
```

原版 `0x14006C401 call rdi` 时 `rcx` 仍是 `Handle`（`FILE_OBJECT`），
我方写成了无参调用 `CloseHandleFunc()`，rcx 是上一条指令残留的垃圾值。

修复：函数指针类型改为 `void (__fastcall *)(__int64)` 并显式传入 `Handle`。

### 证据
`command 0xFB -> OK, result=1`。

## 五、0x026 `CmdEnumHandles`：宏覆盖 + Fiber 语义

### 5.1 第一层：宏覆盖读错 GT 槽

`GetProcessVirtualizationContextFallback` 在 build 18362 上走回退分支。
原版 `0x140049D05` 是 `mov ecx, 18Eh` —— 读 **GT[0x18E]**。

我方写的是 `GtRead(GtEprocessField132 | 0x100)`，而 `xpc_gt_enum.h` 的
「兼容旧名称」宏把 `GtEprocessField132` 覆盖成
`GtEprocessField122 → GtEprocessField112 → GtPeDataSectionVa2(112)`，
于是 `112|0x100 = 0x170` —— **读错了槽**，0x170 为 0 使函数第一步就返回。

这是本轮第二次踩同类坑（第一次是 `GtFwpsDispatchTableBase` 被 `#define` 成 0x910）。

修复：改用显式常量 `GtRead((GLOBAL_TABLE_INDEX)0x18E)`。

### 5.2 第二层：`GetCurrentFiber` 语义不同

原版 `0x140049CF3` 调 `j_GetCurrentFiber`，其实现是
`mov rax, gs:[20h]`（`0x140001584`），即 **KPCR/KPRCB 基址**；
`mov rsi, [rax+18h]` 取的才是 `PRCB->CurrentThread`。

我方旧代码用 `KeGetCurrentThread()` 再取 `[3]`（`ETHREAD+0x18`），语义完全不同，
后续 `CheckFunc` 判定必然失败。

修复：改用项目里已有的 `GetCurrentFiber()`（`Utility.c`，实现正是 `__readgsqword(0x20)`）。

### 证据
`command 0x26 -> OK, result=1`（原版同为 `OK(1)`）。

## 六、0x0E1 `CmdEnumProcessListEx`：阈值写小导致误放行

### 症状
矩阵里**原版 REJ、我方 OK** —— 方向与其他条目相反。

### 根因
原版 `0x140062F63` 是 `cmp esi, 3C0h / jb → 失败`，最小缓冲区阈值 **0x3C0**。
我方旧代码写成 `>= 0x1E0`（0x1E0 是单条输出记录长度，不是最小要求）。
probe 矩阵对该命令给的 OutSize 落在 `[0x1E0, 0x3C0)` 区间，于是
我方放行、原版拒绝。

### 修复
`XPCHunterDrv/src/services/Operation.c`：

```c
if ((unsigned int)RemainingSize >= 0x3C0)   /* 原为 0x1E0 */
```

### 证据
修复后 `command 0xE1 -> REJECTED`，与原版一致。

## 七、0x10B `MiniFilterPreAcquire`：三层缺陷（含新发现的通用 bug）

### 7.1 第一层：描述符偏移

`ScanFltMgrExportTable`（原版 `0x1400172AC`），描述符基址 `var_148 = rsp+0x90`：

| 原版引用 | 真实偏移 | 旧代码 |
|---|---|---|
| `mov eax,[rsp+1D8h+var_D0]` | desc+**0x78** | +0x40 |
| `cmp [rsp+1D8h+var_C0],40000h` | desc+0x88 | 正确 |
| `cmp [rsp+1D8h+var_F8],40h` | desc+0x50 | 正确 |

### 7.2 第二层：RVA 公式错（导致写出非法指针）

原版 `0x1400173C0`：
```
mov ebx, eax        ; eax = desc+0x78
sub ebx, esi        ; esi = ExportBase 低 32 位
add ebx, ecx        ; ecx = **推进后的绝对读指针**
```
即 `RVA = 描述符字段 - ExportBase + 绝对读指针`。

旧代码用「累计消耗量」代替读指针、又额外减了 `ExportBase`，把 RVA 算成负数回绕，
最终 `GT[0x885]` 被写成非法地址 `fffff80425ce8ec0` —— 0x10B 在其上解引用即 BSOD 0x50。

修复：引入 `NewReadPtr = (ULONG)ReadContext.ReadPtr`（推进后），公式照抄原版。

### 7.3 第三层：`MmSystemRangeStart` 双重解引用（**跨文件 6 处**）

修好前两层后仍 BSOD 0x50，故障地址 `ffff8000_00000000` —— 正是
`MmSystemRangeStart` 的**值**。根因：

```c
/* 错 */
if ((ULONG64)NameArray <= *(ULONG64 *)MmSystemRangeStart)
```

WDK 把 `MmSystemRangeStart` 声明为 `extern PVOID`，变量**本身的值**就是
`ffff8000_00000000`；再写 `*(ULONG64 *)x` 等于去解引用这个地址，必然页错误。

原版 `mov rax, cs:MmSystemRangeStart; cmp rcx, [rax]` 是**汇编层面的取变量地址**，
C 里对应的就是直接用 `MmSystemRangeStart`。

**全仓排查后共 6 处同型 bug，全部修复：**

| 文件 | 行 | 上下文 |
|---|---|---|
| `features/ModuleEnum.c` | 65 | 遍历节点边界 |
| `framework/MemoryOps.c` | 2828 | `base` 取值 |
| `framework/MemoryOps.c` | 2846 | `base` 取值 |
| `kernel/Minifilter.c` | 2708 | `MiniFilterPreAcquire` 名字链表 |
| `kernel/Minifilter.c` | 2899 | `MiniFilterPreHardLink` 边界 |
| `kernel/Minifilter.c` | 2909 | `MiniFilterPreHardLink` 边界 |

统一改为 `(ULONG64)MmSystemRangeStart`。

### 证据
`command 0x10B -> OK, result=1`。

## 八、保留差异：0x020 是原版未定义返回值

### 事实链

1. 原版对 0x020 稳定返回 `192 (0xC0)`，重复调用结果不变。
2. 我方返回 `0`。
3. IDA 反汇编 `0x14007F384 CmdReadProcessMemory` 的**返回类型是 `void`**
   —— 整个函数没有任何设置 `eax` 的路径。
4. 原版分派器 `0x1400825BC` 是 `mov r13b, al`，即把处理器返回时 `eax`
   的**残留值**当结果字节写回用户缓冲。
5. `0xC0` 恰好是 `RtlCopyMemory` 一类的残留值，与功能语义无关。

### 结论
这条不是功能缺口，而是**原版自身的未定义行为**。原版前端不依赖这个字节
（真正的数据走 OutputBuffer）。复刻它需要刻意写一个返回 `0xC0` 的空壳，
属于「假装成功」，违反项目约束，因此**保留差异并在文档记录**。

## 九、0x027：状态相关，两边一致

矩阵里原版 REJ / 我方 OK。逐个变量对照（同开机、同 `GT[0x304]=1` 条件）：

```
原版   GT[0x185]=0  GT[0x353]=1  GT[0x355]=0  GT[0x928]≠0
我方   GT[0x185]=0  GT[0x353]=1  GT[0x355]=0  GT[0x928]≠0
```

完全一致。差异来自**矩阵执行顺序**：0x020 会写 `GT[0x185]`
（= 当前 EPROCESS），后续 0x027 的 `CheckProcessAccess` 于是走
`ValidateProcessObject` 分支并失败。

**验证**：先跑 0x20 再跑 0x27，我方也变成 REJ：

```
command 0x20 -> REJECTED, result=0
command 0x27 -> REJECTED, result=0
```

与原版矩阵中的表现一致。

## 十、本轮新增/复用的排查手法

1. **分级诊断槽**：在关键函数内把每一步的结果写进未占用的 GT 槽
   （本轮新增 0x4FF0-0x4FFD、0x5000-0x502F、0x5100-0x511E、0x5200-0x5205、
   0x5300-0x531F），然后 `kd_break` + `dq` 读数。
   **注意槽位冲突**：`0x4F60` 曾被 `ScanWfpDeviceObjectSection` 占用，
   导致读数错位，换到 0x5000 区间才看清。
2. **kd 表达式数字一律按十六进制**：`+0x921*8+235*8` 里的 `235` 是
   0x235 而非十进制 235，必须写 `0xEB*8`。
3. **同开机对照**：跨重启比对的 VA 类字段必然不同，只能同一次引导内采样。
4. **原版需要 `GT[0x304]=1` 才响应命令**：`sc start` 后立刻 `kd` 置位，
   中途不能重启驱动。
