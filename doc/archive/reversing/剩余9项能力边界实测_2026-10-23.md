# 剩余 9 项能力边界实测（2026-10-23）

清单里除 Network 外的 9 个未勾选项，本轮逐条做了技术勘察。
判据一律是「驱动侧到底有没有能拿到该数据的原语」，而不是推断。

| # | 项目 | 能否完成 | 依据 |
|---|---|---|---|
| 1 | Dump Kernel Memory | **部分可做，已实现** | 无任意内核 VA 读，但 0x131 的真实内核代码可转储 |
| 2 | View CmpNotifyChange | **不可做** | 0x127 实测返回 Npfs 文件系统上下文，非 CmRegisterCallback 链 |

## 二、「有没有任意内核 VA 读」的完整排查

这是决定 5 项能否实现的核心问题。逐个候选命令查实：

### 0xF7 / 0xF9：定点读，不接收地址

```c
/* MemoryOperation.c — ReadKernelMemoryToUserBufferOperation */
pKernelMemCtx = GtRead(GtEprocessExtField58 | GtEprocessField54 | 0x400);
if (pKernelMemCtx && ... && CheckMemoryValid(pKernelMemCtx) == 1) {
    *pOutputBuffer = *pKernelMemCtx;      /* 固定指针，只读 8 字节 */
```

`0xF9`（`ReadKernelMemoryRangeOperation`）同构：
`*pOutputBuffer = *pMacShimData;`。**两者都不看 InputBuffer。**

### 0x3A：接受地址，但两个读函数槽都是 0

`ReadProcessMemoryString`（framework/Utility.c）确实在
`InputBuffer+8` 处接受任意地址，看起来正是所需原语。但：

```c
ReadFunc = GtRead(GtReadMemoryFunc);          /* = GT[0x41E4] */
if (ReadFunc && (unsigned int)GtRead(39) != -1) { ...主路径... }
else {
    AltReadFunc = GtRead(0x4189 | 0x100);     /* GT[0x4289] */
    ...
}
```

kd 实测本机：

```
(ViewPlusPlusByLinxer+a7060)+0x41E4*8 L1  →  00000000`00000000
(ViewPlusPlusByLinxer+a7060)+0x4189*8 L1  →  00000000`00000000
```

两个槽都是 0，命令返回 0。

而且 `GT[0x41E4]` 的语义不是「通用读」——`TailHelpers.c:3978` 的
注释明确写着 `0x41E4 = MmGetPhysicalAddress`，同族代码
（HandleMgmt.c / ModuleMgmt.c / ProcessMgmt.c）也都按
`MmGetPhysicalAddress` 使用它。所以即使该槽非 0，也只能做
虚拟→物理转换，不能按任意 VA 拷贝字节。

### 0x20 / 0x25：只做进程附加

`CmdReadProcessMemory` 的返回值恒为 0，且只调
`ReadProcessMemoryWithAttach`（做 `KeStackAttachProcess`），
不把数据拷回用户缓冲。

### 0x2B：读固定 GT 指针

`CmdReadProcessMemoryBlock` → `ReadProcessMemoryBlock(TargetProcess, ...)`，
地址来自 GT，不是 InputBuffer。

**结论：本驱动不存在「按调用方给的任意内核虚拟地址读取」的能力。**

## 三、各项的独立依据

### Dump Kernel Memory —— 已实现（在能力范围内）

`probe --dump-kmem` 输出 0x131 已验证的 28 个内核回调目标：

```
=== Dump Kernel Memory ===
slot RVA        VA                 current            on-disk first 16 bytes
[ 0] 00001450   FFFFF80585AC1450   FFFFF80585AC1450   48 83 EC 28 33 C9 48 8B C2 89 4A 30 48 89 4A 38
[ 1] 00125D40   FFFFF80581F25D40   FFFFF80581F25D40   48 83 EC 28 48 8B CA C7 42 30 10 00 00 C0 33 D2
...
dumped 28 kernel callback targets (16 bytes each, read by the driver from
the on-disk ntoskrnl image)
```

这些字节是驱动从磁盘 ntoskrnl 镜像里读出来的真实机器码，
与内存中的值可比对（`current` 列即内存中的函数指针）。
**这不是「任意地址转储」**，所以原版那个「输入任意地址 + 大小」的
对话框无法照搬；提供的是同等真实的定点转储。

### CmpNotifyChange —— 0x127 的实测语义

`0x127` 返回 37 条（输出必须恰好 1800 字节），但用 kd `u` 核对回调
地址全部落在 `Npfs+0xb670` 这类命名管道文件系统模块 —— 是
**文件系统上下文表**，不是注册表回调。拿它冒充就是伪造。

### KiDebugRoutine / PTE Hook / ClassInitData

- kd `x nt!KiDebugRoutine` **无输出**；`x nt!KiDebug*` 只有
  `KiDebuggerOwner` / `KiDebugTrapOrFault` / `KiDebugServiceTrap` /
  `KiDebugTrapIndex`。该全局 Win8 起已移除。
- 后两项需要任意内核 VA 读，见第二节。

### View HotKey

热键表在 win32k 的会话空间。命令表 283 项全量核对无 HotKey/Timer
数据项（`View Timer` 能用是因为它走句柄枚举，热键没有对应句柄类型）。

> **2026-10-24 更正**：本节结论错误，已推翻。原版 `CProcessHotkeyDialog`
> 的 `RefreshList`（0x14015E0E0）经 `sub_14004D560` 发送**命令 0x33
> CmdEnumObjects**，以 0x200000 输出缓冲取回 win32k 热键链表（count@+0，
> 条目@+8 步长 0x38：桶指针 / 桶[8] / 修饰键 / VK / PID / EPROCESS / TID），
> 对话框按 EPROCESS 过滤并显示 7 列。该数据源从一开始就存在，不在命令表
> “HotKey” 名义项里，因此 10-23 的全量名义核对漏掉了它。前端
> `FeLoadProcessHotkeys`（0x33 + 过滤器 + 原版 VK 名表）已实现并编译通过。

### Forbid Injecting / Locking

`CmdCallbackControl`（原版 0x140070190）对入参 `+8` 的对象类型做
**固定 17 项清单**比对。kd 实测 `MmSectionObjectType = FFFFF8058236F478`，
不在清单内；`IoDesktopObjectType` 连符号都没有。不匹配只会返回 0。

### Restore / Restore All (SSDT)

`0xE7` 需要 `GT[0x80A]/[0x80B]`，其上游 `GT[0x802]` 的唯一写入者是
`InitProcessNotify` 里对 `L"td.sys"` 的模块名匹配 —— td.sys 是
Windows XP/2003 的 TDI 驱动。同一次枚举里 `tdx.sys` 命中
（`GT[0x322]=FFFFF80539BB0000`），`td.sys` 不命中（`GT[0x802]=0`），
证明遍历与比较逻辑本身正常。

同一台机器上装**原版驱动**实测 `--raw 0xE7 4096` → `result=0`，
与 ovf 方一致。

不把 0x802 改指 tdx.sys：两组槽用途不同，导出布局也不同，改指等于猜实现。

## 五、方法论

**「能不能做」的判据必须是「驱动侧有没有这个原语」，不是「我试了没成功」。**

本轮有两次差点误判：
1. 一度以为 `0x3A` 是通用读原语 —— 查到 `GT[0x41E4]` 的真实语义是
   `MmGetPhysicalAddress` 才纠正；
2. 一度以为 `0xF7/0xF9` 读的是不同结构 —— 读完实现才发现两者都是
   「读 GT 里那个固定指针的 8 字节」，只是槽不同。

相反，`Dump Kernel Memory` 虽然不能照搬原版的任意地址对话框，
但可以在「0x131 已跑通的真实内核代码」范围内提供实质功能 ——
这比只写一句「不可用」更接近复刻目标。
