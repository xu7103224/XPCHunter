## 二、本轮修复的 6 个真实缺陷

### 缺陷 1：GT 越界写导致驱动一加载就 BSOD 0x50

**症状**：`sc start` 后 guest 直接蓝屏，bugcheck 参数为
`0xfffff8065517c060 / 0x2 / 0xfffff806550af2ea`，faulting instruction
`mov qword ptr [rcx+rax*8], rdx`，模块 `ViewPlusPlusByLinxer+0x1f2ea`。

**根因**：我为了诊断在 `DriverEntry` 里写了 GT[0x9000..0x9005] 六个槽，
但 `GT_TABLE_CAPACITY` 只有 **0x5000**（`xpc_gt_enum.h:1334`）。
`GtAlloc`/`GtWrite` 只做数组下标运算，没有任何边界检查，于是
`GtWrite(0x9000, ...)` 写到 `g_GlobalTable + 0x48000`，
越过 `.data` 末尾落到非法页。

**修复**（`DriverEntry.c`）：
- 删除全部 0x9000..0x9005 的写入；
- 诊断改用本文件内的独立全局变量
  `g_DiagSdst / g_DiagNtoskrnl / g_DiagHookSubsys / g_DiagDevice /
   g_DiagSymlink / g_DiagCmdTable / g_DiagInitDone`，由 kd 直接读取；
- 同时把初始化控制流改回与原始完全一致
  （`0x1400810F9..0x140081111`：任一步失败即 `goto Cleanup`）。

**实机验证**：kd 读 `g_DiagSdst/Ntoskrnl/HookSubsys` = `01 01 01`，三步全部成功。

---

### 缺陷 2：请求头字段语义全错（数据缓冲根本不是 +0x08）

**症状**：所有命令都返回 `result=0`，包括本该最简单的 0x24。

**根因**：早期按「Output/Context/Extra」命名请求头，实际分派器
（`0x1400825AB..5BA`）的寄存器映射是：

```
0x1400825B7  mov rcx, r12    ; r12 = [buf+0x10]  → In
0x1400825B3  mov edx, [...]  ; edx = [buf+0x20]  → InSize
0x1400825B0  mov r8, r15     ; r15 = [buf+0x18]  → Out
0x1400825AB  mov r9d, [...]  ; r9d = [buf+0x24]  → OutSize
```

即处理器统一签名是 `char Handler(PVOID In, ULONG InSize, PVOID Out, ULONG OutSize)`。
**+0x08 不是数据缓冲**，它只是驱动写回 1 字节结果码的位置。

三个原始处理器交叉验证：

| 命令 | 原始处理器 | 参数用法 |
|---|---|---|
| 0x24 | `CmdGetModuleCount` | 要求 `Out!=NULL && OutSize==4`，把构建号写到 `Out` |
| 0x2A | `CmdEnumThreads` | 要求 `InSize==8 && OutSize==520`，读 `*In` 当 PID，写 520 字节路径到 `Out` |
| 0x20 | `CmdReadProcessMemory` | 要求 `InSize==8`，只读 `*In` |

**修复**：`XPCHunterUM.h` 重命名字段为
`ResultBytePtr / InPtr / OutPtr / InSize / OutSize`，
`Protocol.c` 的 `XpchInvoke` 改为 7 参数形式
`(Client, Command, In, InSize, Out, OutSize, Result)`。

---

### 缺陷 3：用 `IoStatus.Information` 判断成败（恒为 0）

**症状**：即使命令真正执行成功，`DeviceIoControl` 也被判为失败。

**根因**：原始分派器**从不写** `Irp->IoStatus.Information`，
反汇编 `0x140082603` 只有 `and dword ptr [r14],0`（r14 = `&IoStatus.Status`）。
所以 `lpBytesReturned` 恒为 0。真正的结果码是驱动写回
`ResultBytePtr` 的那 1 字节（1=成功，0=被拒）。

**修复**：`XpchInvoke` 改为读 `ResultByte`，返回 `ResultByte != 0`。

---

### 缺陷 4：结果字节写回缺失 + `IoStatus.Status` 语义不符

**根因**：我方 `DispatchDeviceControl` 在成功时返回 `STATUS_SUCCESS`、
失败时返回 `STATUS_INVALID_PARAMETER`，而原始实现**无条件**
把 `IoStatus.Status` 置 0（`0x140082603`），并且**无条件**
把结果字节写到用户输出缓冲（`0x1400825DE..5F4`）：

```
0x1400825DE  mov edx, 1
0x1400825E3  mov r8d, edx
0x1400825E6  mov rcx, [rdi+8]      ; ResultBytePtr
0x1400825EA  call ProbeForRead
0x1400825F0  mov rax, [rdi+8]
0x1400825F4  mov [rax], r13b       ; 写结果字节
```

`r13b` 在 `0x14008251E` 被清零，只有处理器真正执行后才赋成返回值低 8 位。

**修复**（`DriverEntry.c`）：按原始顺序重写整个
`DispatchDeviceControl`，补上
- `MmUserProbeAddress` 三指针校验（`0x1400824DD..4FD`）；
- `KeWaitForSingleObject(&g_Event, ..., NULL)` 串行化（`0x140082503..518`）；
- 统一出口写结果字节；
- 唯一例外：`InputBufferLength != 0x30 || SystemBuffer == NULL` 走
  `0x140082616` 出口，返回 `STATUS_UNSUCCESSFUL`。

---

### 缺陷 5：设备名被错改成「由服务名派生」

**根因**：原始 `DriverEntry` 里设备名/符号链接名都是**硬编码字面量**：

```
0x140081144  RtlInitUnicodeString(&DestinationString, L"\\Device\\View++ByLinxer")
0x1400811DF  RtlInitUnicodeString(&SymbolicLinkName, L"\\DosDevices\\View++ByLinxer")
```

`g_DeviceNameBuffer` 虽然被 `wcsncat` 拼过，但此后**从未被取地址**，
是纯死代码。我之前误以为要用拼接结果，导致设备名随服务名变化，
用户态按固定名 `\\.\View++ByLinxer` 打开时得到 `ERROR_FILE_NOT_FOUND(2)`。

**修复**：改回 `RtlInitUnicodeString` 字面量。

---

### 缺陷 6：`QueryObjectTypeDirectoryPath` 函数指针签名全错 → BSOD 0x3B

**症状**：扫描到某段命令时 guest 蓝屏 `0x3B (c0000005)`，
栈为
```
ViewPlusPlusByLinxer+0x4774A  →  ObReferenceObjectByName
nt!ObpLookupObjectName+0xea   →  nt!KiPageFault
```

**根因**：旧实现把 `GT[0x421A]` 当作 `IoCreateFile` 按 **7 参**调用，
还在栈上手工拼 `OBJECT_ATTRIBUTES`。原始实际是
`ObReferenceObjectByName`（**8 参**），真实映射为：

| GT 槽 | 真实函数 |
|---|---|
| `GT[0x421D]` | `RtlInitUnicodeString` |
| `GT[0x4160]` | **指向对象类型指针的地址**（`mov rax,[rbx]` 再解引用） |
| `GT[0x421A]` | `ObReferenceObjectByName` |
| `GT[0x4220]` | `ObQueryNameString` |
| `GT[0x4223]` | `ObfDereferenceObject`（不是 CloseHandle） |

原始流程（`0x140079654..0x1400798B0`）：
构造 `L"\\Driver\\Disk"` → `ObReferenceObjectByName(..., IoDriverObjectType,
KernelMode, ..., &DriverObject)` → 遍历 `DriverObject->DeviceObject`(+0x8)
与 `NextDevice`(+0x10)，要求 `DeviceType(+0x48)==7 &&
Flags(+0x30)&0x40` → `ObQueryNameString` 两次（先取长度，
`0xC0000004` 表示缓冲不足）→ 校验 `OBJECT_NAME_INFORMATION` 名字内联在
+0x10 → `WStringFindLastChar(name,'\\')` 后 3 字符满足
`(c0&~0x20)=='D'`、`(c1&~0x20)=='R'`、`c2=='0'` → `ExFree` →
`ObfDereferenceObject(DriverObject)`。

错误签名下第 5 个参数本应是 `IoDriverObjectType`，旧实现传了 `&Handle`，
内核把它当对象类型指针解引用 → `ObpLookupObjectName` 内页错误。

**修复**（`ObjectMgmt.c`）：按原始逐条重写，含
- `MmIsAddressValid` + 二次解引用取 `IoDriverObjectType`；
- 正确的 8 参 `ObReferenceObjectByName` 调用；
- 设备链表遍历、`ObQueryNameString` 两段式、`\DR0` 名字判定；
- 结尾 `ObfDereferenceObject`。

**实机验证**：修复前扫描 0x61–0x68 必崩；修复后该段正常返回。

## 四、扫描方法论

一次性给所有命令传 0x1000 字节输出缓冲会导致部分不校验 `OutSize`
的处理器越界写内核栈（观察到 BSOD 0x139）。因此扫描器改为：

- 已知形状的命令按真实形状调用（`g_Shapes` 表）；
- 未登记的命令只给 **1 字节**输出缓冲 —— 足够接收结果码字节，
  且让不校验长度的处理器尽早失败而不是破坏内存；
- 每 6 条命令一段，逐段用 `vmrun runProgramInGuest` 执行，
  崩溃时可精确定位到段；段内再二分。

用「1 字节探测」跑完全部 283 条命令，**零崩溃**，证明命令通道本身稳定。

## 五、最终扫描结果（2026-10-20）

```
accepted=21  rejected=257  skipped=5   total=283
```

分段记录见 `build/audit/FINAL_SCAN.txt`。

- **accepted (21)**：处理器真正执行并返回 1。包括 0x22（就绪标志）、
  0x24（构建号 18362）、0x7F（恒真桩）、0xD1/0xD2 等。
- **rejected (257)**：处理器执行到尺寸/参数校验即返回 0。
  这不是通道问题 —— 每条处理器都要求精确的 InSize/OutSize 与
  合法的内核对象指针，而扫描器只提供了安全的最小值。
- **skipped (5)**：见下表。这些命令在缺少前置状态时会解引用
  未初始化的内核指针，因此自动扫描不发送它们。

### 跳过清单（附原始依据）

| 命令 | 处理器 | 缺失的前置条件 |
|---|---|---|
| 0x25 | `CmdEnumKernelDrivers` | `GT[0x4226]`（对象类型引用函数）、`GT[0x4271]`（驱动对象链表）、`GT[0x42A6]` 由 `InitObjectCallbackEntries` 等填充，扫描时尚未运行 |
| 0x28 | `CmdProcessOperation` | 输入 16 字节被解释为 `{EPROCESS, PID}`，需真实进程句柄 |
| 0x30 | `CmdRegistryProtect` | 输入被解释为注册表键对象指针 |
| 0x56 | `CmdEnumObjectAllTypes` | 遍历对象类型链表，表头来自未初始化的 GT 槽 |
| 0x115 | `CmdCallSystemRoutine` | 原始 `0x1400776D8` 把 `GT[0x27]`（服务计数 562）当 `_KTHREAD` 字节偏移写 0，仅在 `GT[0x4298]` 非 0 时触发 —— 原始前端从不触发，裸调用会破坏线程状态 |

## 六、本轮之后修掉的同族缺陷（节区扫描族）

`InitKernelDataSectionTable` / `InitTdiExportAndRelocTable` 会在命令
首次调用时被间接拉起，它们调用的 20 个 PE 节区扫描函数里有大量
「描述符字段声明成独立局部、恒为 0、再拿去做解引用」的写法：

```c
__int64 SectionInfoPtr = 0;
...
__int16 t = *(_WORD *)(SectionInfoPtr + 6);   // 解引用 NULL+6 → BSOD 0x3B
```

`ReadPESectionEntry` 的输出是 **0x120 字节描述符**，字段必须按偏移读：

| 含义 | 偏移 | 宏 |
|---|---|---|
| 本次消费字节数 | +0xF0 | `PE_DESC_SECTION_SIZE` |
| 字段值 | +0x50 | `PE_DESC_FIELD_VALUE` |
| 字段大小 | +0x78 | `PE_DESC_FIELD_SIZE` |
| 字段值 2 | +0x88 | `PE_DESC_FIELD_VALUE2` |
| 类型结构体指针 | +0x118 | `PE_DESC_SECTION_DATA` |

本轮按此模板重写了：

- `ParseKernelDataSectionRelocs`（`SsdtHook.c`）—— 修掉 0xD4 崩溃
- `ScanTextSectionPattern` —— 修掉 0xE1 崩溃
- `ScanInitSectionPattern` —— 同上
- `ScanPageSectionPattern`
- `ParseNtKernelDataSections`（原有 `goto` 跨变量声明的破损结构）
- `ScanDataSectionPattern`
- `FindNdisExportsBySectionScan` / `...BySectionScanV2`
- `ScanFltMgrExportTable`（`Minifilter.c`）—— 修掉 0x10B 崩溃
  （旧代码把类型指针当 `SectionEntry[14]` = +0x38，实际在 +0x118）

## 七、部署注意

guest 的**测试签名模式在冷启动后会失效**。每次部署顺序必须是：

1. `build\build.bat` 编译
2. `build\sign\host_sign.bat` 用 `xpch_test.pfx` 签名
3. 推送 `build/sign/XPCHunterDrv_signed.sys`（**不是** `bin` 里的未签名产物）
4. `deploy_test.bat`：复制到 `drivers\ViewPlusPlusByLinxer.sys` 并
   `sc create/start View++ByLinxer`

跳步会得到 `StartService 失败 577`（签名无法验证）。
