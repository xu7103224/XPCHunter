# Network 页数据链路与能力边界（2026-10-23 实测）

## 一、推翻旧结论：驱动里**有** Network 命令

`100%完成度定义与验收清单.md` 此前写「驱动命令表里没有 Network 相关命令」，
这个结论**是错的**。用原版前端 IDB（`PCHunter64.exe.i64`）反查到了完整链路。

### 1. 原版前端的 Network 页结构

`CNetworkDialog`（构造 0x14013F8C0）是一个 9 子视图容器：

```
+352    CTabCtrl
+576    sub_140141060(a1+576, 0)
+1440   sub_14011C910(a1+1440, 5)
+2432   sub_14011C910(a1+2432, 6)
+3424   sub_14011C910(a1+3424, 7)
+4416   CNdisProtocolFunDialog     ← WiFi / 协议相关
+5280   CNetworkOtherDialog        ← 「其它网络回调」，TreeCtrl 承载 21 项
+6432   sub_140134750
+7328   sub_14013B040
+8200   sub_1401433E0
+9064   sub_140133880
```

### 2. 真正的数据入口

`CNetworkOtherDialog` 的刷新函数 `sub_1400A01E0` 里有一个
`switch (a6)`，按子视图索引分发到六个薄封装：

| 视图 | 封装函数 | 命令号 | 驱动处理器 | 语义 |
|---|---|---|---|---|
| 0 | `sub_1400262E0` | **0xF1** | `Table[209] MiniFilterAcquireForModWrite` | Fwps 修改写分发表 |
| 1 | `sub_140026340` | **0xF2** | `Table[210] CmdInitFwpsDispatchTables` | Fwps 分发表（Win8） |
| 2 | `sub_1400263A0` | **0xF3** | `Table[211] CmdCopyKernelArrayToUserBuffer` | 内核数组 → 用户 |
| 3 | `sub_140026400` | **0xF6** | `Table[214] CmdCopyKernelDualArrayToUserBuffer` | 双数组变体 |
| 4 | `sub_140026590` | **0xF7** | `Table[215] CmdReadKernelMemoryToUserBuffer` | 单个内核指针 |
| 5 | `sub_140026650` | **0xF9** | `Table[217] CmdReadKernelMemoryRange` | 另一内核指针 |

六个封装的结构完全一样（93/97 字节）：
在栈上填一个 0x30 字节的 IOCTL 描述符（`[0]=0`、`[1]=命令号`、
`+0x10=输出缓冲`、`[+0x20]=输出大小`、`[+0x30]=结果字节`），
调用 `sub_14004DD40` 下发。

**准确的语义（不要过度解读）**：`0xF7`/`0xF9` 都是
「读 GT 里存的**那个**内核指针所指向的 8 字节」，**不接收用户指定的地址**：

```c
pKernelMemCtx = GtRead(GtEprocessExtField58 | GtEprocessField54 | 0x400);
if (pKernelMemCtx && ... && CheckMemoryValid(pKernelMemCtx) == 1) {
    *pOutputBuffer = *pKernelMemCtx;      /* 固定指针，只读 8 字节 */
```

所以它们是**按子系统的定点读**（该指针由 `InitKernelMemoryContext`
解析 NDIS/WFP 结构后写入 GT），不是通用的「任意内核 VA 读」。
Network 页能用它们，是因为前端要的就是这几个固定位置的值；
而 `Dump Kernel Memory` 需要按用户给的任意地址读，这两条命令办不到。
先前清单里对 Dump Kernel Memory 的「无法实现」判定因此**依然成立**，
但理由要改成「只有定点读、没有任意地址读」，而不是「两个命令语义相同」。

## 二、这台虚拟机上原版自己也拿不到数据

在同一台 Win10_Dev（build 18362）上，把**原版驱动**装进去逐条实测：

| 命令 | 原版返回 | GT 支撑槽 |
|---|---|---|
| 0xF1 | result=0 | GT[0x7FC] |
| 0xF2 | result=0 | GT[0x800] |
| 0xF3 | result=0 | — |
| 0xF6 | result=0 | — |
| 0xF7 | result=0 | GT[0x7E0 区] |
| 0xF9 | result=0 | GT[0x7E1 区] |

kd 读原版驱动自身的 GT：

```
(ViewPlusPlusByLinxer+a84f0)+0x7F8*8 :
  fffff805`8972c4b0  fffff805`86670000 00000000`0007a000   ← GT[0x7F8]=fwpkclnt 基址, GT[0x7F9]=0x7A000
  fffff805`8972c4c0  00000000`00000000 00000000`00000000   ← GT[0x7FA]=0     GT[0x7FB]=0
  fffff805`8972c4d0  00000000`00000000 00000000`00000000   ← GT[0x7FC]=0     GT[0x7FD]=0
```

即：`fwpkclnt.sys` **加载了**（基址 0xFFFFF80586670000，大小 0x7A000），
但四个 `FindFwps*` 一个都没命中，四张表全为空。

## 三、结论与定性

- **不是实现缺陷**：我方与原版在这台机器上逐条行为一致（都返回 0）。
- **是环境限制**：本虚拟机没有安装/激活 WFP 过滤驱动（wfplwfs.sys 等），
  也没有第三方网络过滤组件，因此 fwpkclnt.sys 里根本没有可解析的
  `Fwps*` 分发表实例。Network 页那 21 项在这样的环境里天然为空。
- **我方已实现的对照项**：Network 页的 `netio.sys` 解析（0xF8
  `InitKernelMemoryContext`）已经跑通，20 个槽里 11 个有真实地址，
  这部分数据是真的（见 `Network页落地_2026-10-22` 及 `--network-cli`）。

因此清单里这 21 项的正确状态是：
**「链路已复刻，本环境无数据；需在装有 WFP 过滤驱动的机器上才能取到值」**，
而不是「未实现」也不是「无能力」。

## 四、本轮另修的实质缺陷

`FindFwpsTcpIpDispatchTable`（0x14001B990）与
`FindFwpsDispatchTableWin8`（0x14001B72C）的 Win10 分支
（`build > 0x23F0`）里，读指针推进写在了 `ReadPESectionEntry` **之前**：

```c
/* 错误 */
*(ULONG64 *)((PUCHAR)&ReadContext + 0x08) += *(unsigned int *)((PUCHAR)SectionEntry + 0xF0);
if (ReadPESectionEntry(...)) break;     /* 首轮用未初始化值，其后整体错位一条 */
```

与 0x131 的 `ParseNtExportSectionsV3` / `ScanKernelModulePESections`
是同一类缺陷。已改为「先解码 → 再推进」，两个分支现在一致。

虽然本机仍取不到数据（环境原因），但这个错位在**有 WFP 的机器上**
一定会导致解析失败，属于必须修的实质 bug。

## 五、方法论记录

**先验证「原版在同样条件下是否也失败」，再断言「我方实现有 bug」。**

这次靠这一步避免了又一轮无效的深度调试：
如果我只看我方 GT 全 0 就一路追解码器，会花很久去"修"一个在
当前环境下根本无法产生结果的东西。原版驱动是唯一的判据——
它在同一台机器上的行为，定义了这个环境下"正确"的边界。
