### 块 2 数值一致性证明

两个驱动运行在不同 VM 会话，ntoskrnl 重定位基址不同（本方 `0xfffff8043d000000`、
原版 `0xfffff8023d000000`，相差 `0x49E0000`）。把第二个指针减去各自 nt 基址后：

```
[0] mine RVA=0x747e960   orig RVA=0x2bee960   差值恒为 0x49E0000
[1] mine RVA=0x749ce40   orig RVA=0x2c0ce40   差值恒为 0x49E0000
[2] mine RVA=0xa771060   orig RVA=0x5c21060   差值恒为 0x49E0000
[3] mine RVA=0xa629fc0   orig RVA=0x49e9fc0   差值恒为 0x49E0000
[4] mine RVA=0xa62a060   orig RVA=0x49ea060   差值恒为 0x49E0000
```

差值恒定 ⇒ 指向同一批 nt 函数，块 2 内容等价。
块 3 同理（3 条，第二个指针同样只差基址）。

## 二、本轮修掉的三处结构性缺陷

三处都是同一类问题：**反编译产物里的判据字段被写成"声明后从不赋值"的独立局部变量**，
以致每条判据恒假，函数永远不产出结果。

### 1. `EnumerateProcessCallbackContext`（Minifilter.c，原版 0x14003EAA8）

按反汇编 `0x14003EAD0..0x14003ED8C` 逐条还原后，修正 6 处：

| 项 | 旧（错误） | 新（原版） | 依据 |
|---|---|---|---|
| 扫描窗口 Base | `GT[0x43A8] + GT[0x42D0]` | `GT[0x42D0] + GT[0x20]` | `0x14003EBBA add rcx,r12`（r12=GT[0x20]）|
| 窗口长度 | `GT[0x20] - base + GT[0x21]` | `(ULONG)GT[0x20] - (ULONG)Base + GT[0x21]` | `0x14003EBBD sub edx,ecx` / `0x14003EBBF add edx,edi` |
| 守卫 3/4 | 判 `GT[0x20]` | 判 `GT[0x43A8]`（ebx） | `0x14003EB60..6A cmp ebx,edi` |
| 第一段读取次数 | 2 次 | **3 次**（第三次判类型 `0x558`） | `0x14003EC85..ECAA cmp cx,[rax+6]`（cx=0x558）|
| 累加器 | 独立 `Cumul`（从 0 起） | `ctx+0x08`（即读指针） | `InitPESectionReadContext` 把 Base 写入 `+0x08` |
| 第二段字段 | `+0x28` bit2 / `+0x70` | `+0x20` 单字节 bit2 / `+0x40` | `0x14003ED4C test [rbp+..],4` / `0x14003ED5C mov eax,[var_140]` |

`GT[0x43A8]` 在原版里只参与守卫，**不参与寻址**。旧实现把它当 Base，算出
`0x83B850` 这种用户态伪地址，正是此前 `ReadPESectionEntry+0xB9` 野指针崩溃的来源。

### 2. `ResolveSsdtTablePointer`（SyscallTable.c，原版 0x1400401DC）

旧实现的 8 个判据字段（`SectionEntrySize` / `RootTableOffsetAccum` / `TableFieldFlags` /
`FieldFlags` / `FieldFileOffset` / `FieldCount` / `FieldValue` / `FieldFlagsByte`）
全部是未赋值空壳。改为直接读 0x120 字节描述符：

| 原版栈变量 | 描述符偏移 | 语义 |
|---|---|---|
| var_80 | +0xF0 | 本条消耗长度 |
| var_58 | +0x118 | 类型结构体指针（+6 为类型号）|
| var_E8 | +0x88 | QWORD 段标志（与 0x40000 / 0x400000000 比较）|
| var_F8 | +0x78 | ULONG 表 RVA 基值 |
| var_120 | +0x50 | QWORD 段特性（与 0x40 比较）|
| var_100 | +0x70 | ULONG 计数 |
| var_130 | +0x40 | ULONG 偏移 RVA 基值 |
| var_150 | +0x20 | UCHAR 标志字节（bit2）|

描述符基址 `rbp-0x60`（`0x1400402A2 lea rdx,[rbp-0x60]`）。
RVA 公式 = `字段 - GT[0x20] + ctx+0x08`。

### 3. `ResolveSsdtTablePointerEx`（SyscallTable.c，原版 0x1400403B4）

同类空壳，且**累加器 `RootOffsetAccum` 与解码上下文是同一个栈槽**：

原版 `SectionReadContext` 在 `[rsp+50h]`、`RootOffsetAccum` 在 `[rsp+58h]`，
即 `ctx+0x08`。`InitPESectionReadContext` 会把它置为 Base（绝对 VA），**不是 0**。
旧实现初始化为 0，导致 `ComputedOffset + SubCount - NtImageBase` 算出巨大负数，
第一级 `SubSectionRva < NtImageSize` 永不成立 ⇒ 块 2 恒 0。

改为 `SectionReadContext.ReadPtr` 后块 2 立刻产出 5 条。

## 三、顺带修正

- `ParseNtSectionsForShadowSsdt`（原版 0x140040C14）：匹配段改用真实偏移
  `+0x50==0x40000`、`+0x90==1`、`+0x40==0x40`，RVA = `(+0x40) - GT[0x20] + ctx+0x08`。
- `FindSsdtServiceTableV1/V2/V3`：扫描窗口基点统一为 `GT[0x20]`/`GT[0x21]`
  （PE 文件映射量纲），不再用 `GT[32]`/`GT[33]`（内核镜像量纲）。
  依据：`0x1400409DE add rdi,r14`、`0x140040B5E add rsi,r15`、`0x140040E4B`，
  三处的 r14/r15/rbp 都来自 `GtRead(0x20)`。
- `EnumProcessPeExportDataByIndex`（原版 0x14003F7D0）：`SectionAlignedSize` /
  `FieldFlags` / `FieldValueSize` / `SectionDataSize` / `SectionFileOffset`
  五个空壳改为读 `+0x40` / `+0x50` / `+0x88` 与 `ctx+0x08`。

## 四、剩余块（5/6/9/10/11/12）的卡点

### 块 5（类型 5，原版 3 条）

调用链：dispatch 读 `GT[0x2BB]`（`mov esi,2BBh` @ `0x14004122A`）→ 若为 0 则调
`EnumProcessPeExportDataByIndex` → 再读 `GT[0x2BB]` → 当 LIST_ENTRY 头遍历。

`EnumProcessPeExportDataByIndex` 的前提是 `GT[0x42DF]` 非零。实测：

- 副本 `GT[0x42DF] = 0`
- 原版 IDB 里 `0x42DF` 只有一处引用（读点 `0x14003F82B`），**没有显式写入者**
- `0x42DF = 0x4158 + 3*130 + 1` ⇒ 它是 `BuildHookTable` 的 **k=130 组 RVA 槽**
  （与 `GT[0x42D0]` 同型）
- 对应哈希槽 `GT[0x42DE]` 已由 `InitSyscallNumberTable` 写入 `0x992020AA`
- 但 `LookupExportFuncAddr(0x992020AA)` 未命中 ⇒ RVA 未写

**下一步**：查 `BuildHookTable` 里 `LookupExportFuncAddr` 对哈希 `0x992020AA`
（以及其余未命中的哈希）的匹配逻辑，确认是否导出名表/序号表读取有偏差。
这是块 5/6 的共同前置。

### 块 6（类型 6，原版 215 条）

源为 `GT[0x2BC]`（`ReadWriteKernelMemory`，原版 0x14003F998）。该函数同样是
`SectionAlignedSize` 一类的空壳铺满，需要按反汇编整体重写。

### 块 9/10/11/12

分别是 `GT[95]`（`EnumProcessPeExportData`）、`GT[0x2CF]`（`ScanKernelPeExportSection`）、
`GT[0x338]`（`EnumProcessPeExportDataEx`）、`GT[0x33D]`（`ScanKernelPeExportData`）。
其中 `EnumProcessPeExportDataEx` 是两级匹配（先 Type 0x53C~0x543 打标记，
再 Type 0x512 命中），已从反汇编 `0x14003F5E0` 取到完整控制流，尚未落地。

## 五、复现命令

```bat

copy /y C:\Users\Public\XPCHunterDrv_new.sys C:\Windows\System32\drivers\XPCHunterDrv.sys
sc stop XPCHunterDrv & ping -n 3 127.0.0.1 >nul & sc start XPCHunterDrv
C:\Users\Public\xpch_probe.exe --live --cmd 0x047 --dump 8192 > C:\Users\Public\p047.txt
```

块解析脚本（宿主机）：

```python
import re
def blocks(path):
    data = {}
    for line in open(path, encoding='utf-8', errors='replace'):
        m = re.match(r'\s+([0-9A-F]{4}):\s+((?:[0-9A-F]{2}\s*)+)$', line)
        if m:
            data[int(m.group(1), 16)] = bytes(int(x, 16) for x in m.group(2).split())
    buf = bytearray()
    for o in sorted(data):
        if o > len(buf): buf.extend(b'\0' * (o - len(buf)))
        buf[o:o+len(data[o])] = data[o]
    return bytes(buf)

b, off = blocks('p047.txt'), 0
while off + 0x28 <= len(b):
    t = int.from_bytes(b[off:off+4], 'little')
    c = int.from_bytes(b[off+0x10:off+0x14], 'little')
    print(f'type={t} count={c}')
    if t == 0: break
    off += 0x18 + c * 0x10
```

## 六、踩过的坑（避免重复）

1. **过期 `g_GlobalTable` RVA 会伪造"槽为 0"的结论**。本轮曾误判 `GT[0x42D0] = 0`，
   实际是用了旧构建的 RVA `0xab060`，正确值 `0xac060`。每次重新部署后必须从
   `build/bin/Release/x64/XPCHunterDrv.map` 重取 `g_GlobalTable` 地址。
2. **VMware Tools 在 kd 停在 `kd>` 时会失去响应**，`vmrun` 全部失败。
   `kd_go` 之后 Tools 才会恢复；若 Tools 已崩，需 `vm_reboot mode=hard`。
3. **`taskkill` ntdrived 会让 MCP 工具层与 daemon 失联**（daemon 重启后 pid 变了）。
   重启 daemon 可恢复，但会断掉 kd 会话，且此后 `kd_attach` 需 guest 重新启动才能连上。
4. **map 文件的第三列是完整 VA**（`0x14007DCF0`），RVA 要减 `0x140000000`；
   但 LTCG 会重排函数顺序，不能靠 map 相邻关系推断代码位置。
