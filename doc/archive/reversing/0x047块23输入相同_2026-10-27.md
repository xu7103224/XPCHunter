# 0x047 块 2/3：扫描输入完全一致，问题在解码结果（2026-10-27）

## 决定性对比：四个输入槽逐字节相同

跑完 `0x047` 后，原版 `OGT` 与复刻 `XPCHunterDrv` 的同槽值：

| 槽 | 含义 | 原版 OGT | 复刻 | 判定 |
|---|---|---|---|---|
| `GT[0x42D0]` | CurrentOffset | `0x00823260` | `0x00823260` | **相同** |
| `GT[0x43A8]` | SectionBase | `0x000185F0` | `0x000185F0` | **相同** |
| `GT[0x20]` | SectionSize(指针) | `0xFFFFC00314400000` | `0xFFFFC00314400000` | **相同** |
| `GT[0x21]` | 镜像大小 | `0x00AB2000` | `0x00AB2000` | **相同** |

`InitPESectionReadContext` 的入参因此完全相同：
```
Base = GT[0x43A8] + GT[0x42D0] = 0x185F0 + 0x823260
Size = GT[0x21]     - GT[0x42D0] = 0xAB2000 - 0x823260
Mode = 2, Param5 = 0, Extra = -1, Param6 = 0, Param7 = 0
```

## 因此根因锁定在 ReadPESectionEntry 的解码结果

同一份 `Base/Size/Mode`、同一份内核内存，原版能命中
`类型==0x512 && +0x50==0x40 && +0x58==2 && +0x90==4` 与随后的
`+0x58==1 && +0x88==0x40000`，而复刻不能。

这说明**两个驱动的 `ReadPESectionEntry` 对同一字节流产出的描述符不同**
—— 即审计项 **P0-1（0x120 描述符布局）** 的实际影响：

`PEDecoder.c:185` 头的自述：
```c
// 注意：原始驱动把这三个值分别写入描述符的 +0x110/+0x10/+0x18，本重建的目标
// 偏移尚未按原始布局改正（见审计报告 P0-1 的 0x120 描述符布局表）。
```

已知：
- 外层字段（`+0xF0`、`+0x38`、`+0x118`）是对的 —— 所以 `0x0FF` 能逐字节对齐、
  `FindSsdtTableAddresses` 外层能命中 1368；
- 内层/深层字段（`+0x50`、`+0x58`、`+0x88`、`+0x90`、`+0x70`、`+0x78`）在我方
  移植里落在错误位置 —— 所以这里读到的永远是垃圾，条件永不成立。

**这与 §7.5 的记录互相印证**：`FindSsdtTableAddresses` 里我实测到
`AlignmentValue=0x500BE9`（条件要求 0x40000）、`SizeFieldValue=0xC2C00000`
（要求 64）—— 同一族字段、同一个缺陷。

## 结论：修 PEDecoder.c，不要再动别的

块 2/3、块 6、块 9/10、以及 `0x0F4/0x0F6/0x10B` 全部依赖这套描述符解码。
正确顺序：

1. 按原版 `ReadPESectionEntry`（0x14008A54C）把 `PEDecoder.c` 中
   `ExtraField/Param6/Param7` 及各子解码器的**目标偏移**改正（审计 P0-1 的布局表）；
2. 用 `0x0FF`（当前 7384B/0 差异）做回归 —— 它只用外层字段，改完应仍然一致；
3. 验证 `GT[0x2B8]/[0x2BA]/[0x2BB]` 非 0；
4. 块 2/3 的遍历代码**保持不动**（已照原版写好）。
