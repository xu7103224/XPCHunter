## 二、0x117 输出的完整结构（本轮解出）

### 2.1 头部（12 字节）

```
+0x00 DWORD  WindowsBuildNumber
+0x04 DWORD  Count1        第一张表条目数（GT[0x8B7]）
+0x08 DWORD  Count2        第二张表条目数（GT[0x8BA]）
+0x10 起     条目数组，每条 40 字节，先 Count1 条再 Count2 条
```

### 2.2 条目（40 字节，基址 = 0x10 + 40*index）

| 偏移 | 大小 | 内容 | 写入者（原始反汇编） |
| --- | --- | --- | --- |
| +0x00 | BYTE | flagAddrChanged：表项当前值 ≠ 磁盘原始值 | `ValidateHookEntries`：`*CurrentEntry != CurrentEntry[1]` |
| +0x01 | BYTE | flagBytesChanged：内存前 16 字节 ≠ 磁盘 16 字节 | 同上：`MemoryCompare(*EntryPtr, ..., 0x10)` |
| +0x04 | DWORD | 索引 | `CopyHookEntryArray`：`*(DWORD*)(Dest + 4 + 40*Index) = Index` |
| +0x08 | QWORD | 当前地址 | `FilterActiveHookEntries`：`*pDst = *pSrc` |
| +0x10 | QWORD | 磁盘原始地址 | `CopyHookEntryArray`：`*(QWORD*)(Dest + 16 + 40*Index) = pSourceArray[Index]` |
| +0x18 | 16B | 磁盘原始指令前 16 字节 | `CollectTwoSyscallTables`：`*(_OWORD*)(pEntry + 3) = *(_OWORD*)(Rva + File)` |

**上一轮我把它记成「+0x00 = 索引」，是错的**：`CopyHookEntryArray` 写的是 `Dest + 4 + 40*Index`，
即索引在 +0x04；+0x00/+0x01 是 `ValidateHookEntries` 后续写入的两个标志字节。
本机实测 454 条的两个标志**全为 0**，说明当前没有任何条目被改写。

### 2.3 缓冲大小要求（关键）

```c
BufferSize >= 40 * (Count1 - 1) + 56
```

Count1 = 454 时 = **18176 字节**。给 0x2000（8192）会让条目拷贝判定失败、
`EnumHookInfoOperation` 返回 0。前端固定申请 `0x20000`。

## 三、这两张表究竟是什么（纠正上一轮的误判）

上一轮文档把 GT[0x8B7] / GT[0x8BA] 称作 SSDT / Shadow SSDT。**本轮证明这是错的。**

证据链：

1. `ParseSyscallTableExportDir`(0x1400865C8) 的起点是 `GtRead(0x8AE)`（反汇编 `mov ecx, 8AEh`）。
2. `InitThreadNotify`(0x14001F8E4) 里写 GT[0x8AE] 的那个分支，
   前置换算为**长度 0x18（12 个宽字符）**，且拼出的字符串是：

   ```
   var_A0:  0057h 'W'  0064h 'd'  0030h '0'  0031h '1'
   var_9C:  0030h '0'  0030h '0'  002Eh '.'  0073h 's'
   var_90:  0079h 'y'  0073h 's'  → "Wdf01000.sys"
   ```

3. `ReadWdfLibraryModule`(0x140086EA4) 里的 20 个 DWORD 编码路径同样是 `\??\C:\Windows\System32\drivers\Wdf01000.sys`。
4. 实机用 WinDbg 核对：454 条地址全部落在 `Wdf01000` 模块区间
   （本次开机 `fffff806077a0000 - fffff80607875000`）。

**结论**：0x117 枚举的是 **Wdf01000.sys 内部的两处函数指针表**，并逐条与磁盘文件比对，
用于发现「WDF 框架被 inline hook / 表项被改写」。这正是 Ring0 Hooks 页要的东西 ——
原版 Ring0 Hooks 页展示的就是「哪些内核函数被改了」，WDF 例程表是其中一批。

**它和内核 SSDT 无关。** 前端已据此把列名改为 `HookTable1 (GT[0x8B7])` /
`HookTable2 (GT[0x8BA])`，不再冒称 SSDT。

## 四、Kernel→SSDT / Shadow SSDT 的正确数据源

| 子页 | 命令 | 处理器 | OutSize | 实测 |
| --- | --- | --- | --- | --- |
| SSDT | 0x8C | `CmdEnumSyscallEntries` → `EnumSyscallTable7` | **必须 1352** | 返回 0 |
| Shadow SSDT | 0x8E | `CmdEnumShadowSyscallEntries` | **必须 1352** | 返回 0 |

两条命令都先把 `GT[0x...|0x100]` 就绪位取出，为 0 则调 `InitDiskQueryExportTable()` 再取。
返回 0 说明这条导出表链条仍未打通 —— 界面如实显示 `driver returned 0`，不伪造数据。

另外记录一个**命名陷阱**：表 34（0x42）`CmdQuerySsdtInfo` 名字叫 SSDT，
原始实现（0x14003B0A0）却只是校验入参后转调 `CmdEnumDriverObjects` 枚举驱动对象，
与 SSDT 完全无关。**不能拿它当 SSDT 数据源**。

## 五、本轮修掉的两个 G5 缺陷

### 5.1 `ReadWdfLoaderModule`（原 0x140087E80，292 字节）

**修复前**：

```c
bool ReadWdfLoaderModule(_QWORD *pBuffer, unsigned int *pBufferSize)
{
    if (!pBuffer || !pBufferSize) return 0;
    return 0;                       // ← 静默失败型空壳
}
```

**修复后**：按原始逐字还原 —— 20 个 DWORD 编码出 `wdfldr.sys` 路径，
`ReadFileRawData` 读文件，`ReadNtFileToBuffer` 展开成 PE 缓冲，`ExFree` 原始数据。

这是 `InitDriverModuleParsing`（0x140087D80）的唯一被调用方，
而 `InitDriverModuleParsing` 是 `EnumSsdtHooks`（0x118）的前置。空壳直接导致 0x118 恒返回 0。

### 5.2 `MiniFilterNotifyRoutine`（原 0x140019AD8）

**修复前**（推测实现）：把文件名 memcpy 进 `GT[0x...|0x3400]` 缓冲区「通知用户态」。

**原版真实语义**（Hex-Rays 伪代码可读）：

```c
KeWaitForSingleObject(&g_Mutex, ...);
if (!MiniFilterQueryFileName(FileName)) {
    Pool = ExAllocatePool(PagedPool, 2*LengthChars + 16);
    if (Pool) {
        *Pool = 0;                               // +0x00 next
        *((_DWORD*)Pool + 2) = LengthChars;      // +0x08 字符数
        memmove((char*)Pool + 12, FileName, 2*LengthChars);  // +0x0C 名字
        *((_WORD*)PoolEntry + LengthChars + 6) = 0;          // 尾随 NUL
        *PoolEntry = g_Pointer;                  // 头插单链表
        g_Pointer = PoolEntry;
    }
}
KeReleaseMutex(&g_Mutex, 0);
```

即「文件名去重链表」，既不碰 GT 也不通知用户态。已按此重写。
