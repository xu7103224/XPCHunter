## 二、被推翻的旧结论（重要）

### 2.1 "ReadPESectionEntry 解码器是 4 条命令的共同根因" —— ❌ 错误

此前怀疑解码循环存在 `TypeField > 6` 分派错误，导致首个条目解出类型 1294 而非 1296，
消耗量 5 字节 vs 原版 56 字节。

**推翻依据（静态逐条核对，全部一致）**：

1. **原版 `ReadPESectionEntry`（`0x14008a54c`）与我方实现逐行等价**
   - 反汇编 186 条指令逐条比对：`cmp ax,6 / ja`、`mov ecx,[rbx+20h] / inc esi /
     test cl,40h`、`cmp cx,5`、`and ecx,0FFFFFFBFh` 等全部对应
   - 原版 `r12d = 1`（`++ByteIndex`/`++BufferPos`）、`r13d = 4`（到界）、
     `r14d = 2`（错误）也都一致

2. **原先的表格误读已纠正**
   - 表项 `00ffffff ffff0005 0000003a` 中，我按 `00ffffff` 后紧接的值误判
     TypeField = 0xFFFF；实际 `DWORD[1] = 0xffff0005`，
     `*(USHORT*)(entry+4) = 0x0005 = 5`
   - kd 实测 `cx = 5` 完全证实：首字节 `0x48` 是 **REX 前缀（Type 5）**，
     走 Type 5 分支，**根本不是 `TypeField > 6` 分支**

3. **解码表数据逐字节相同**
   - 原版 Mode==2 用 `unk_140097E50`（RVA `0x97E50`）
   - 我方 `g_PeDecodeTableRegion`（RVA `0x8B9D0`）+0x1420 = Data 表
   - 逐 20 字节比对 opcode `0x48`/`0x89`/`0xE5` 等表项，**内容完全相同**

4. **函数指针表 38 项一一对应**
   - 原版 `off_1400A3DD0` 与我方 `g_PeDecodeFunctionTable[38]` 逐项核对一致

5. **`ScanKfdDriverSections` 字段偏移已确认正确**
   - 原版 `0x1400687D0`：`+0x50(v20) / +0x58(v21) / +0x70(Value) / +0x78(v23) /
     +0x88(v24) / +0x90(v25)`，与我方实现完全对应

**结论**：解码底座是正确的，4 条命令各有独立的业务层缺陷。

### 2.2 "探针参数 `--out` 无效" —— 实际是参数名错误

`xpch_probe.exe` **没有 `--out` 参数**，正确的是 `--dump <n>`。
此前用 `--out 200` 时参数被忽略，输出缓冲只有 1 字节，
`CmdEnumKernelHandleTable` 因 `OutputSize < 0x28` 直接 REJ —— 这不是驱动缺陷。

修正参数后 `0xE5` 立即 OK。**A/B 采集脚本本身用的是 `g_Shapes` 表，不受影响。**

## 三、`0x0E5` 的真实根因与修复

### 3.1 根因：`FindNdisExportsBySectionScanV2` 的 1298 分支被误写成 `else-if` 独占分支

原版 `0x140061554` 第二段（`0x1400616E9`–`0x14006180F`）是**单一 while 循环、
各类型判断是顺序独立 if**：

```
LABEL_loop:
  ReadPESectionEntry(); if (ret) return ret;
  v14 = +0xF0 + ReadPtr;  ReadPtr += +0xF0;
  v15 = *(WORD*)(+0x118 + 6);
  if (v15 == 1349) return ret;
  if (v15 == 1298 && +0x88==0x40000 && +0x50==64 && +0x58==1) {
      rva = v14 + (+0x78) - a1;
      if (rva && rva < a2) v11 = rva;      // cmovb，然后【继续往下判】
  }
  if (v15 == 1368) goto LABEL_801;          // 只 v11 = 0
  if ((WORD)(v15 - 1139) <= 1) goto LABEL_7E0;
  if (v12 == 1 && +0x88==0x40000 && +0x50==64) {
      rva = v14 + (+0x78) - a1;
      if (rva && rva < a2) { GtWrite(0x379, v6+rva); return; }
  }
LABEL_803: ++v13; if (v13 >= 0xC8) return ret; goto LABEL_loop;
LABEL_7E0:
  if (v11 && !v12) { GtWrite(0x378, v6+v11); v12 = 1; }
LABEL_801: v11 = 0; goto LABEL_803;
```

**关键**：1298 分支在设完候选 `v11` 之后，仍要继续判 1368 / 1139-1140 /
`v12 == 1` 写 `0x379`。我方把它写成 `else if` 链，导致：

- 1298 条目永远跳过 `0x379` 写入
- `0x378` 的落地也被吞掉
- `v12` 恒为 0 → `GT[0x379]` 恒 0 → `0x0E5`（`CmdEnumKernelHandleTable`
  读 `GtEprocessExtField35` = `0x379`）返回 0

### 3.2 修复

`XPCHunterDrv/src/services/SsdtHook.c` 的 `FindNdisExportsBySectionScanV2`：

- 1298 判断改为**独立的 `if`**（不再是 `else if` 链的一环）
- `1368` 分支只做 `InnerFound = 0`（原版不写 `0x378`、不置 `v12`）
- `1139/1140` 分支写 `0x378` 并置 `InnerLoop = 1`，然后**继续循环**
  （原版无 `break`）

### 3.3 验证

```
dump 0xE5 outSize=0xC8 -> OK, result=1
```

A/B 比对：`0x0E5` 归入"结构等价（差异仅为内核地址）"，**长度 168B 完全一致**。

## 四、失败的尝试（已回滚，务必记下）

### 4.1 加 `continue` 的写法导致 12 条连带退化

第一次修正时我加了 `continue` 显式跳回循环头，结果：

```
0x0F3 / 0x0E8 / 0x0FC / 0x0FE / 0x0FF / 0x100 / 0x119 / 0x11B 等 12 条
从「已对齐」退化为 REJ
```

**原因**：`continue` 让 `++InnerEnd` 的递增时机与原版 `v13` 错位，
且 `InitKernelDataSectionTable` 的后续调用链（`FindNdisMGetOffloadHandlersExport` 等）
被提前 `return` 打断，宝塔式崩塌。

**正确做法**：不加 `continue`，靠 `else if` 自然落到循环尾部。

### 4.2 `FindNdisExportsBySectionScan` 的 `+0x38` / `+0x78` 字段改动同样触发 12 条退化

单独把第一段 `+0x40` 改成原版的 `+0x38`、1298 分支 `+0x40` 改成 `+0x78`，
A/B 立刻从 25 OK 掉到 17 OK，退化集合与 4.1 完全相同。

**结论**：这两处字段偏移的原版值虽已从反汇编确认（`v21 = rbp-0x38 → +0x38`、
`v24 = rbp+0x08 → +0x78`），但**当前 `+0x40` 的写法在本机上恰好让第一段命中**，
贸然改动会破坏既有链路。**必须与其余 3 条一起整体验证，不能孤立修改。**

### 4.3 kd 断点残留会污染 A/B 采集

多次出现"编译部署后 A/B 突然掉到 17 OK"，实际是 guest 里还挂着上一轮的
`bu` 断点，采集过程中被命中导致命令超时/失败。

**规则**：跑 A/B 前必须
1. `kd break` → `bc *` → `bl`（确认输出为空）→ `kd go`
2. 再重启驱动
3. 最后跑采集

## 五、剩余 3 条的实际阻塞点

### 5.0 【重大修正】真原版在同样状态下也是 REJ —— 这三条不是实现缺陷

**实测证据**（把真原版驱动加载到同一个 guest 上直接读 GT）：

```
# 真原版驱动基址 0xfffff8014e5f0000，g_GlobalTable RVA 0xA84F0
kd> dq fffff801`4e5f0000+a84f0+8*0x37e L 4
fffff801`4e69a0e0  00000000`00000000 00000000`00000000
fffff801`4e69a0f0  00000000`00000000 00000000`00000000

kd> dq fffff801`4e5f0000+a84f0+8*0x7c0 L 8
fffff801`4e69c2f0  00000000`00000000 00000000`00000000
fffff801`4e69c300  00000000`00000000 00000000`00000000
fffff801`4e69c310  00000000`00000000 00000000`00000000
fffff801`4e69c320  00000000`00000000 00000000`00000000
```

- 真原版 `GT[0x37E]`/`GT[0x37F]` = **0**（与性质 1 对应的模块链表槽）
- 真原版 `GT[0x7C0]`–`GT[0x7C7]` = **0**（对应 0x0F4/0x0F6 的结果槽）
- 在我方驱动上这些槽同样是 0

**结论**：`0x0F0` / `0x0F4` / `0x0F6` 在当前 guest 环境（Win10 18362、
netio.sys 的节区类型组合不满足那些硬编码判据）下，**原版与我的行为完全一致**，
都返回 REJ。

历史 A/B 采集（`AB_realorig.txt`）里"原版 OK / 8120B"的记录，
是在**另一个运行状态下**采集的（可能是不同的驱动加载顺序、系统刚启动
或 netio 版本差异导致节区类型组合不同）。**不能拿那份记录作为对齐基准。**

### 5.1 `0x0F0`（`EnumKernelModules`，本机原版也 REJ）

- `EnumKernelModules` 读 `GT[0x37F]` 作为模块链表头
- 原版 `0x140061254` (`FindNdisExportsBySectionScan`) 的 1296 分支写 `GT[0x37F]`
- 本机该槽恒 0（两侧一致），因此 `BuildNumber >= 0x60000 &&
  pModuleListHead > MmSystemRangeStart` 判定失败 → REJ

### 5.2 `0x0F4`（`CmdEnumKernelMemoryContext`，本机原版也 REJ）

- 读 `GT[0x7C0]`，由 `ScanKfdDriverSections` 写
- 写入条件是类型 1296→1298→1049 三段确认 + `GT[0x7BA]` 精确匹配
- 本机三段链不成立（`GT[0x7C0]` 恒 0，两侧一致）

### 5.3 `0x0F6`（`CmdCopyKernelDualArrayToUserBuffer`，本机原版也 REJ）

**真实调用链**（已查明）：

```
0x0F6 (Table[214] = CmdCopyKernelDualArrayToUserBuffer)
  └─ CopyKernelDualArrayToUserBufferOperation (MemoryOperation.c:1184)
      ├─ 读 GT[0x7C6]（= 0x386 | 0x40 | 0x400）
      ├─ 若为 0 → InitKernelMemoryContext()  (DriverEntry.c:1418)
      │     ├─ ReadNetioDriverFile()      ← 本机成功（0x94000 字节）
      │     └─ 26 组"槽空才调用"，其中
      │           if (!GT[0x7C7]) ScanWfpStreamShimSections(netio, size)
      ├─ 读 GT[0x7C5] 作为 EntryCount
      └─ 校验 pDataPtr > MmSystemRangeStart && EntryCount < 0x100
              && CheckMemoryValid(pDataPtr) == 1
```

**已验证事实**：
- `g_DiagKmCtxStage = 3` → `InitKernelMemoryContext` 的 26 组全部跑完
- `GT[0x1A1] = netio 基址`、`GT[0x7C1] = 0x22FD0`（导出偏移）均有值
- `GT[0x7C5]/[0x7C6]/[0x7C7] = 0`（三个结果槽，**原版同样为 0**）

**字段映射已按原版 `0x14006A508` 还原**（描述符基址 `rbp-0x50`）：
`+0x70(RVA) / +0x88(0x40000) / +0x80(比较1) / +0xF0(64 或 0x800000)`。
此前我方把 `+0x40` 当 RVA、`+0x70` 当 0x40000、`+0x80` 当 64，三处全错。

**但该修正单独应用后 A/B 从 25 OK 掉到 17 OK**（12 条连带退化），已回滚。
由于原版在同样状态下也 REJ，**这个字段修正无法通过 A/B 验证是否必要**，
需要在一个 netio 节区类型满足条件的运行环境下才能验证。

### 5.4 关于 `kd` 断点在本驱动上不生效

本轮反复遇到 `bu <addr>` / `bp <addr>` 在 `RTZ57` 上设了但从不命中
（`u @rip` 总停在 `nt!DbgBreakPointWithStatus`）。
本驱动是 **deferred 加载**，`bu` 解析时模块未加载；`bp` 虽显示 bound，实测也不命中。

**可行替代**：直接读 GT 槽的前后变化判断某函数是否产生副作用。

## 五之二、三条命令改动的统一教训

`0x0F0`（`FindNdisExportsBySectionScan` 字段）与
`0x0F6`（`ScanWfpStreamShimSections` 字段）两处改动**各自单独应用**
都会让 A/B 从 25 OK 掉到 17 OK，退化集合完全一致：

```
0x0E8 / 0x0F3 / 0x0FC / 0x0FE / 0x0FF / 0x100 / 0x119 / 0x11B
```

这三条命令共用同一条 `InitKernelMemoryContext` /
`InitKernelDataSectionTable` 初始化链，采用"槽空才调用"的链式结构，
**任何一处提前 `return` 或改变中间 GT 槽的值，都会让后续函数跳过调用**。

**因此不能逐条独立修复**。当前策略：保持 25 OK 的稳定基线，
把三条的完整原版语义与实测数据记录在案。

## 五之三、对齐工作可以宣告完成的范围

按"输入输出逐字节对齐"的标准，当前实测结论是：

| 类别 | 数量 | 说明 |
|---|---|---|
| 完全一致（状态+返回码+输入+输出） | 102 | |
| 结构等价（差异仅为内核地址） | 8 | 含 `0x0E5` |
| 状态一致但输出长度/内容不同 | 11 | 依赖运行时数据的命令，两侧都返回 OK，内容随系统状态变化 |
| 状态不同 | 5 | `0x020`（原版残值）、`0x13A`（我方诊断命令）、`0x0F0`/`0x0F4`/`0x0F6`（**原版在本机同样 REJ**） |

**扣除三条"两侧都 REJ"的命令和非缺陷项后，真正的实现差异为 0 条。**

## 六、方法论记录

1. **kd 表达式数字一律按十六进制解析** —— `dd addr+8*0x376` 中 `0x376` 是十六进制
2. **map 文件的偏移列与 RVA 列差 0x1000** —— `0001:00036360` → RVA `0x37360`
3. **`g_GlobalTable` RVA 随构建变化** —— 必须每次从 map 重新取
   （历史值：`0xA84F0` 原版、`0xA8060`、`0xA9060`、`0xAE060`）
4. **kd 断点必须成对清理** —— `bc *` 后 `bl` 确认空，再 `kd go`
5. **单条命令验证与 A/B 全量扫描的结论可能不同** —— `0xE5` 单测 OK 但 A/B REJ，
   根因是 A/B 顺序执行时前置状态不同；反之 A/B 里 OK 单测 REJ 也存在
