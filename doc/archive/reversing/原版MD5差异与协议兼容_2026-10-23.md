# 原版 MD5 与标准 MD5 的差异（2026-10-23）

## 结论

原版驱动的 MD5 实现与标准 MD5 **只有一个常量的差别**：

```
第 34 步（K[33]）：原版 0x8771F683    标准 0x8771F681
```

就这一个 +2 的笔误，导致原版驱动算出的摘要与标准 MD5 完全不同。

必须**照抄这个笔误**，否则：

- 我方驱动会拒绝原版前端（PCHunter64.exe 算的是原版 MD5，我方按标准算）
- 我方前端也驱动不了原版驱动（验证原版行为时的最大障碍）

两侧都已改为 `0x8771F683`：

- `XPCHunterDrv/src/framework/Crypto.c` 的 `Md5_K[33]`
- `XPCHunterUM/src/Protocol.c` 里 `MD5STEP(F3, d, a, b, c, in[8] + 0x8771f683, 11)`

## 定位过程（可复现）

1. **用 kd 抓原版的实际输入与输出。**
   在 `ViewOrig64+0x824B6`（`Md5Final` 之后、`cmp eax,[rdi+0x28]` 之前）
   下断点，同一次命中里 dump：
   - `db @rdi L40`（解密后的请求前 0x28 字节）
   - `dd @rsp+0xb0 L4`（摘要）

   拿到的样例：请求 `10 08 24 20 24 ...`，摘要 `2987975d 6e2fa9ce 072d5992 dfd9d303`。

2. **确认输入是标准的。**
   在 `ViewOrig64+0x59CEC`（`Md5Transform2` 入口）下断点，
   dump `dd @rcx L4`（状态）与 `db @rdx L64`（块）：

   ```
   状态: 67452301 efcdab89 98badcfe 10325476     ← 标准 IV
   块  : 10 08 24 20 24 ... 80 00 ... 40 01 ...  ← 标准填充（长度 0x140 位）
   ```

   `Md5Init`(0x140059CB4)、`Md5Update`(0x14005A50C)、`Md5Final`(0x140059C14)
   逐个核对指令，布局与逻辑都是标准的（State@0x00 / Buffer@0x10 / Count@0x50，
   长度写到 Buffer+0x38/+0x3C）。

3. **逐句转写 64 步并逐步对比。**
   把 `Md5Transform2` 的反编译结果机械转写成 Python，
   与标准 MD5 在同一块上逐步比对：

   ```
   前 33 步完全一致
   step 34  seq=e49086ad  std=e49076ad  DIFF
   ```

4. **穷举定位差异量。**
   固定前 33 步的状态，对第 34 步穷举 `H 三元组 / X 索引 / 旋转量 / 常量偏移`：

   ```
   命中: ('b^c^d', 8, 11, 'K+2')
   ```

   即只把常量 +2 就能解释。

5. **端到端验证。**
   标准实现把 `K[33]` 改成 `0x8771F683` 后：

   ```
   标准       : 13bdbaf5 80754b08 fba1c2c7 85e6a657
   K[33]+2    : 2987975d 6e2fa9ce 072d5992 dfd9d303
   驱动实测   : 2987975d 6e2fa9ce 072d5992 dfd9d303   ← 逐字节吻合
   ```

## 实机验证

改完后，**不经任何调试器补丁**就能驱动原版驱动：

```
$ xpch_probe.exe --live --raw 0x24 4
  handshake 0x24 -> OK, result=1, build=18362 (0x47BA)
=== raw 0x24 outSize=0x4 -> OK result=1 ===
  0000: BA 47 00 00
```

在此之前，同样请求被原版的 MD5 关卡拒绝（`cmp eax,[rdi+0x28]` 的 ZF=0）。

## 方法论意义

这个缺陷存在了很久没被发现，原因是之前的验证都是「我方驱动 + 我方前端」
自洽测试 —— 两侧用同一套标准 MD5，永远自洽，永远发现不了与原版的差异。

发现它靠的是**把原版驱动当参照系**：加载原版、用调试器补齐它的前置状态
（`GT[0x304]=1`、`GT[0x17B]=0`）、直接发命令、在关键路径下断点比对。
同样的方法还能继续用于逐条命令的差分对照。
