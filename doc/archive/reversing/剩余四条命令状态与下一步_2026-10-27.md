# 剩余 4 条命令的状态与下一步（2026-10-27）

目标：`CmdKernelMemoryOperation`(0x047)、`CmdEnumProcessListWin10`(0x0E4)、
`CmdEnumObjectTypeTable`(0x0FF)、`CmdEnumKernelObjectTable`(0x0D5) 与原版对齐。

已对齐、**不要再动**的两条：`0x0D4`（52 条目/1658 B，字段逐项一致）、
`0x108`（34 B 逐字节相同）。它们的实现路径（`ValidateKernelObject` 重写、
`DecodeObjectPointerFromHandleEntry` 的算术右移、24 字节枚举上下文）是所有
相关命令的公共基础，改动前务必先跑这两条回归。

## 1. `0x047 CmdKernelMemoryOperation`（当前 265 B / 块头正确 / 条目全 0）

### 已修复
- **参数映射**：原版 `0x1400410AE/B1` 是 `mov r14d,r9d`（长度=第 4 参）+
  `mov rbx,r8`（缓冲=第 3 参）。已改为
  `KernelMemoryOperationDispatch((void*)pOutputBuffer, OutputSize)`。
  修复前恒为 0 字节。
- **`FindSsdtTableAddresses` 外层子节区 RVA 量纲**（`SyscallTable.c`）：
  ```c
  SubSectionRva = SubSectionAddress + *(ULONG64*)(ReadContext+0x08) - (UINT)NtImageBase;
  InitPESectionReadContext(NtImageBase + SubSectionRva,
                           (ULONG)(SectionEnd - (NtImageBase + SubSectionRva)), ...);
  ```
  **实测有效**：`g_DiagEpiB = 0x0074A522`（合法 RVA）、`g_DiagEpiA = 12`
  （30 条外层描述符里 12 条命中 1368–1370）。
- `FindSsdtTableAddresses` 里 9 个原本未赋值的局部变量已按原版偏移补全：
  `+0xF0` 条目长度、`+0x38` SubSectionAddress、`+0x20` DecodedFlags、
  `+0x50` SizeFieldValue、`+0x88` AlignmentValue、`+0x78` AddressFieldValue、
  `+0x70` TypeFieldValue、`+0x40` OffsetFieldValue、`+0x118` 类型指针。

### 仍未解决
`GT[0x5A]`/`GT[0x5B]` 仍为 0 → 块 1 空；其余块同理。

### 2026-10-27 第二次尝试（失败，已回滚）
外层 `SubSectionRva` 修好后，单独重试内层 `TableRva`/`OffsetRva` 改用
`*(ULONG64*)(ReadContext+0x08)` —— **仍然 BSOD 0x3B**（AV @ 驱动 RVA `0x81C4A`）。
结论：`0x14003FF86` 的 `add eax,ecx` 里 `ecx` **不是** `ctx+0x08` 的读指针。
必须先把 `0x14003FF3E..0x14003FF89` 这段（26 条指令）完整 dump，
逐条跟踪 `ecx` 的赋值，再改；不要再用"和外层一样"的推断。

当前已回滚为相对偏移写法，实测 `0x047` 回到 265 B 且不崩。

### 2026-10-27 第三次尝试（失败）
按"`var_1B8` 是外层运行指针的局部副本"实现（在内层 `InitPESectionReadContext`
之前保存 `OuterReadPtr`，内层 RVA 用 `AddressFieldValue + OuterReadPtr - NtImageBase`）
—— **guest 仍然崩溃**（这次的 bugcheck 没被 kd 捕获，因为 kd 当时是 detached）。

三次失败说明这条公式**不是** 0x047 的阻塞点，或者还有其它前置条件没满足。
**下一步必须换方法**：不要再改公式，而是
1. `kd_attach` → 触发 0x047 → `kd_wait_event` 捕获 bugcheck →
   `kd_capture_fault` 拿到真实 RIP 所属函数与调用栈；
2. 先确认崩溃到底发生在 `FindSsdtTableAddresses` 内还是后续使用
   `GT[0x5A]` 的函数里（`KernelMemoryOperationDispatch` 会把 GT[0x5A]
   当表指针用），再决定改哪里。

另外诊断变量被多轮探针复用、语义已混乱（`g_DiagFilC/FilD` 既当过计数器也当过
探针槽），继续用它们判断会导致误读；下一步应改用一组**全新的** `g_Diag*`。

### 2026-10-27 第四轮：原版目标值已拿到 + 决定性发现

**原版真值**（OGT 运行、跑完 0x047 后读 GT）：
```
GT[0x5A] = 0xFFFFF80603F00D60   GT[0x5B] = 0xFFFFF806043AB938
GT[3](nt 基址) = 0xFFFFF80603A00000   GT[0x20](展开镜像) = 0xFFFF8A0EC2C00000 / 0xAB2000
GT[0x41A7] = 0x74A400
→ TableRva_orig = 0x500D60    OffsetRva_orig = 0x9AB938
```

**我方候选值**（非侵入式诊断，不写 GT，guest 不崩）：
```
OuterReadPtr = 镜像+0x74A412（= 导出目录起点+0x12，量纲正确）
新公式 TableRva = 0x500BE9（差 0x177）   新公式 OffsetRva = 0x9AB78C（差 0xAC）
```
→ **公式结构正确、数值接近**，说明方向对但运行指针/字段有细微偏差。

**决定性发现（矛盾数据）**：在 1298 分支内捕获
`AlignmentValue = 0x500BE9`（测试要求 ==0x40000）、
`SizeFieldValue = 0xC2C00000`（测试要求 ==64）、
`AddressFieldValue = 0xFFDB67D7`（负数）、最后一个内层 Base RVA = `0xFFC40B22`（越界）。
分支测试通过但捕获值不满足测试条件 → **我方 `ReadPESectionEntry` 移植
向 SectionInfo 写出的字段布局与原版不一致**（至少对 0x047 扫描到的
这批描述符而言）。这也解释了为什么三次"改公式"都会崩：字段值本身就是垃圾，
任何公式都算不出正确 RVA，而一旦 GT[0x5A] 被写入，下游块 1 的无保护解引用就崩。

**下一步（精确）**：
1. 对照原版 `ReadPESectionEntry`（0x14008A54C）逐字段核对我方移植
   （`PeParse.c` / `PEDecoder.c`）写出的字段偏移——重点验证
   `+0x50 / +0x78 / +0x88` 这三个内层字段是否真的由该解码器填写。
2. 用一组全新的 `g_Diag*`（不复用旧槽），在**单次调用内**记录
   第一个 1298 命中的完整 0x120 字节 SectionInfo 原始内容。
3. 修正字段布局后再回到 RVA 公式（此时公式已验证正确）。

### 2026-10-27 第五轮：最终根因确认（我方代码注释自证）

`PEDecoder.c:185` 的 `ReadPESectionEntry` 移植头部有如下自述：
```c
// 注意：原始驱动把这三个值分别写入描述符的 +0x110/+0x10/+0x18，本重建的目标
// 偏移尚未按原始布局改正（见审计报告 P0-1 的 0x120 描述符布局表）。
```
即 **0x120 字节描述符的字段布局从未按原版改正**（审计项 P0-1）。这统一解释了：
- 外层字段（+0xF0 长度、+0x38 SubSectionAddress、+0x118 类型指针）恰好正确
  → 0x0FF 能逐字节对齐、0x047 外层能命中 1368；
- 内层字段（+0x50 SizeFieldValue / +0x78 AddressFieldValue / +0x88 AlignmentValue /
  +0x40 OffsetFieldValue / +0x70 TypeFieldValue / +0x20 DecodedFlags）位置不对
  → 读到的全是垃圾 → 任何 RVA 公式都失败；
- 一旦把（错误但"看起来合法"的）GT[0x5A] 写进去，下游块 1 的
  `*(QWORD*)(表项 & ~0xF + 8)` 无保护解引用就 BSOD —— 三次崩溃全部由此而来。

**修复路径**：按原版 `ReadPESectionEntry`（0x14008A54C）+ 审计报告 P0-1 的
描述符布局表，把 `PEDecoder.c` 中 ExtraField/Param6/Param7 及各子解码器的
目标偏移全部改正；修正后 0x047 的 RVA 公式用已验证的
`字段 + 运行指针 - NtImageBase` 即可。此项工作量集中且独立，
建议单开一轮完成，完成后顺带回归 0x0FF/0x0D4/0x108/0x0E4。

### 关键教训（勿重蹈）
把**内层** `TableRva`/`OffsetRva` 里的 `ComputedOffset2` 改成
`*(ULONG64*)(ReadContext+0x08)` 会 **BSOD 0x3B**（AV @ 驱动 RVA 0x818CA），
已回滚。说明内层 `0x14003FF86` 处的 `ecx` 与外层 `0x14003FEDF` 的 `edx`
**来源不同**，不能类推。

### 下一步
1. 完整 dump 原版 `0x14003FF54..0x14003FF8B`（约 14 条指令），确认
   `0x14003FF86` 之前 `ecx` 由哪条指令赋值（此前只看片段，连错两次）。
2. 再按该来源改内层两处 RVA，**同时**改配套长度参数（外层那次 BSOD 就是
   只改 RVA 没改长度）。
3. 块 1 通了之后，其余块逐个按同样方法核对（每块都有独立的懒加载子系统）。

## 2. `0x0E4 CmdEnumProcessListWin10` —— ✅ 已对齐（2026-10-27）

**实测与原版逐字节一致：608 B，0 处差异。**

### 根因（两个，均已修正）
1. **`+0x08` 写进程名**：原版条目 `+0x08..+0x4F` 从不写入（保持 memset 的 0），
   我方却把 `EPROCESS.ImageFileName` 写到 `+0x08`。
2. **枚举对象不对**：旧实现用 `PsGetCurrentProcess` 兜底遍历真实 EPROCESS，
   而原版就是 `v11 = *GT[0x36C]`、后继取 `v11[481]`（+0x1E90，一个远大于
   EPROCESS 的私有结构）。实机核对两个驱动的
   `GT[0x36C] = 0xFFFFF8011D8E6648`、`GT[0x363] = 0x60053` **完全相同**，
   `*GT[0x36C] = 0xFFFF888B9C16E1A0` 正是原版输出的首条 `+0x00`。

### 实现（`Operation.c`，`EnumProcessListWin10Operation`）
NDIS 版本 `GT[0x363] >= 0x60053` 时走忠实实现：
条目 664 字节、后继 `Object[481]`、"有后继"标记写在上一条 `+656`、
48 个字段的 `{Dst, Src}` 表按原版 `sub_14005E354` 最内层分支逐项照抄。
其它 NDIS 版本仍走旧路径（未改动，避免未核对的行为回归）。

## 3. `0x0FF CmdEnumObjectTypeTable`（93 条 vs 原版 136 条）

### 已知差异
- 原版首块：`88000000`（136）+ `58000000`（0x58=88 条目步长）+ `02000000`
- 复刻首块：`5D000000`（93）+ `58000000` + `02000000`
条目步长一致（0x58），**只是条目数少 43 条**。

### 2026-10-27 进展：已定位到"子条目判据过宽"

处理函数：`CmdEnumObjectTypeTable` → `EnumObjectTypeTableOperation`（`Operation.c:1009`），
原版 `sub_14006B0AC`。头部槽两者都是 **`GT[0x7CD]`**（原版 `mov edi,7CDh` 逐字节核对），
头指针与首块内容完全一致。

把两侧输出按"块"解析（块头 `+0x00=块长度`、`+0x04=子条目数`，块长 = 40n+8）：

| | 头部计数 | 解析块数 | 子条目总数 | 前几块 (长度,子条目) |
|---|---|---|---|---|
| 原版 | 136 | 136 | **32** | (88,2) 然后全是 (48,0) |
| 复刻 | 93 | 93 | **186** | (88,2) (88,2) (88,2)… |

即：**首块完全相同**，但从第 2 块起，原版几乎收不到子条目（48 字节空块），
我方每块都收到 2 个 → 每块 88 字节 → 缓冲区更快填满 → 块数反而更少（93 < 136）。

子条目判据（原版 `v23` 循环）：
```c
while (v23 && v23 != v18 && v23 > MmSystemRangeStart && v22 && v24 <= 0x10000) {
    if (CheckMemoryValid(v23) == 1 && v23[3]) { 收录 }
    v24 = ++v29; v23 = (_QWORD *)*v23;
}
```
我方代码文本与之逐字相同，所以差异只能来自 **`v23` 的起点或 `v18` 的取值**：
`v18 = v11[8] + 24*entryIndex`，`v23 = *v18`。

### 已排除
- 头部槽：两侧都是 `GT[0x7CD]`（原版 `mov edi,7CDh`），实机读值相同
  `0xFFFFF8011D767630`、`*head = 0xFFFFF8011D767188`。
- `CheckMemoryValid`：就是 `MmIsAddressValid`（+ 几个 GtRead 副作用），与原版一致。
- 循环源码：逐行比对 `v9/pEntry`、块头写入、`LABEL_47` 记账、`v16/v30` 索引恢复，
  与原版完全一致。

### 尚未确定
逐块子条目计数：原版 `[2,0,0,0,...]`，复刻 `[2,2,2,2,...]`，**第 0 块相同、第 1 块起分歧**。
原版共 136 块（多数 48 字节空块，总子条目 32），复刻 93 块（每块 88 字节，总子条目 186）；
复刻 93×88 = 8184 正好填满输出缓冲而停，原版是节点枚举自然结束（136 个 v18）。

因第 0 块完全一致，说明 `v11[5]/v11[8]/v18` 的**取值方式**没错，
分歧只能出现在第 1 个 `v18` 之后的某个状态量上。下一步需要在 >= 0x47BA 分支里
对前 3 个 `v18` 记录 `v18`、`*v18`、`(*v18)[3]`、`(*v18)[0]` 到 `g_Diag*` 槽读回，
与 kd 直接读同一内存的结果对照，定位是"读到的 v18 不同"还是"判据不同"。

## 6. 2026-10-27 重大进展：0x047 块 1 已与原版逐字节对齐

### 6.1 崩溃现场（kd_capture_fault 一次拿到）
```
Bugcheck 0x3B (c0000005)
XPCHunterDrv+0x81cda (= KernelMemoryOperationDispatch+0xb0a)
    mov qword ptr [rbx+rax*4], rdx     ← 写，AV
```
崩溃**不在** `FindSsdtTableAddresses`，而在块 1 的条目写入。

### 6.2 两个独立缺陷（都已修）

**缺陷 A：`GT[0x5A]` 的 RVA 公式（已从前几轮验证）**
原版 `0x14003FF86` `sub eax,r12d; add eax,ecx`，`ecx` = 内层推进后的读指针
（`var_1B8` 就是 `ctx+0x08`，内外层共用同一上下文）。实测：
```
AddressFieldValue = 0xFFDB67D7   推进后读指针 = 镜像 + 0x74A589
→ TableRva = 0x500D60，与原版 GT[0x5A] − GT[3] 完全一致
```
公式正确后 `GT[0x5A]/GT[0x5B]` 被写入，块 1 才有数据。

**缺陷 B：块 1 的条目寻址（本轮 kd 现场定位）**
原版块布局（`r13` = 块基址）：
```
r13+0x00                      DWORD  块类型 (=1)
r13+0x10                      DWORD  条目计数 count（初值 0，每收一条 +1）
r13+0x18 + count*0x10         QWORD  第 count 条的表项（完整指针，含低位标记）
r13+0x20 + count*0x10         QWORD  第 count 条的解引用值
```
对应指令：`0x14004142E mov eax,[r13+0x10]; add rax,rax; mov [r13+rax*8+18h],rcx`
→ `0x14004144E ... add rax,2; add rax,rax; mov [r13+rax*8+0],rcx`
→ `0x14004145E add [r13+0x10],esi`。

旧实现写 `pOutput[4 * pOutput[4] + 6]`，而 `pOutput` 已推进到 `+0x18`，
所以 `pOutput[4]` 读的是 **`+0x28`（恒 0）**而不是 `+0x10` 的计数 →
下标恒为 6、计数永不增长 → 块内"只有一条、count=0"，
且 `pOutput += 4` 与 `RemainingSize -= 16` 双重推进 → 越界写（AV）。

### 6.3 对齐实测
```
orig 4816 B   mine 441 B
块 1：orig type=1 count=11 len=200  |  mine type=1 count=11 len=200
块 1 内容：前 216 字节**完全相同**（含全部 11 条 SSDT 表项的 key/value）
```
块 2–11 结构正确（type 2..10、长度 24）但 count 全为 0 —— 它们各自依赖的
懒加载子系统仍未产出（与原版块 2=5、3=3、6=215、9=12/2、10=30、11=1 相比为空）。

### 6.4 下一步
按块逐个补齐数据源，优先级：
1. 块 2/3（SSDT2/SSDT3 表）：同块 1 的懒加载模式（`FindSsdtServiceTableV2/V3`）；
2. 块 6（原版 215 条，最大）：PE 导出索引；
3. 块 9/10（进程 DeviceMap）；
4. 块 4/5/7/8/11。

回归：`0x0FF` 7384、`0x0E4` 608、`0x0D4` 3450、`0x108` 33 全部正常，无退化。

## 7. 0x047 块 2/3 的原版语义（2026-10-27 逆向完成，待实现）

### 7.1 关键纠正：块 2/3 **不是** SSDT2/SSDT3 表
我方现有实现把块 2/3 当作"遍历 SSDT2/SSDT3 服务表数组"（用
`GT[GtEprocessField78]` / `GT[EprocessField82]`）。**与原版完全不同**。

原版块 2/3 是**遍历链表**，数据源分别是：

| 块 | 头指针来源 | 大小/长度槽 | 元素结构 |
|---|---|---|---|
| 块 2 | `var_B0 = GT[0x2B8]`（`GtKernelDataField38`） | `var_90 = GT[0x2BA]`（`GtKernelDataField40`） | 每 8 字节一项，`[+0]=完整指针` |
| 块 3 | `var_68 = GT[0x2BB]`（`GtKernelDataField41`） | — | 链表，`r15=[r15]` 沿 Flink |

懒加载：`GT[0x2B8]` 为 0 时调用 `CmdEnumFileSystemCallback()`（`0x14004120A`）
后重读。这与块 1 的"槽空则先初始化"是同一模式。

### 7.2 块 2 的两条分支（原版 0x14004166D / 0x140041789）

```
if (build == 0xA28 || build == 0xECE)  →  0x140041789（数组模式）
else (build >= 0x1771)                 →  0x14004166D（链表模式）
```
**18362 走链表模式**，即：
```
r13 = var_B0 (链表头)
count = 0
循环:
  if (r13 == NULL) break
  if (var_90 == 0) break                      ; 大小槽非零检查
  if (!MmIsAddressValid(r13)) break
  r13 = [r13]                                  ; 沿 Flink
  if (r13 == 链表头) break                      ; 回到表头 → 结束
  if ((ULONG64)r13 <= MmSystemRangeStart) break
  if (!MmIsAddressValid(r13)) break
  count++; if (count > 0x10000) break
  ; 写入（与块 1 完全同一套寻址）：
  ;   [r13+0x10] = count
  ;   条目 slot = 块基址 + 0x18 + count*0x10
  ;   slot[0] = 完整指针, slot[8] = 解引用值
```

注意块 2 首次 `r13 = [链表头]`（**先取一次 Flink**），块 3 是
`r15 = 链表头` 然后循环体内 `r15 = [r15]` —— 两者起始语义差一步，
实现时必须区分。

### 7.3 块 3（原版 0x140041830）
```
[rbx+0x10] = 0                ; 清计数
edi -= 0x18                   ; 剩余空间 -= 24
rbx += 0x18                   ; 游标推进到条目区
r15 = var_68 = GT[0x2BB]
if (!r15) break
if (!MmIsAddressValid(r15)) break
count = 0
loop:
  r15 = [r15]
  if (r15 == GT[0x2BB]) break   ; 回表头
  if (r15 <= MmSystemRangeStart) break
  if (!MmIsAddressValid(r15)) break
  count++; if (count > 0x1000) break     ; ← 注意上限是 0x1000，不是 0x10000
  ...写入同块 1 寻址...
```

### 7.4 实现注意
- 块基址游标 `rbx` 是**单指针**（每收一条 `+= 0x10`），与块 1 的修正一致；
- 计数在 `块基址+0x10`，写入用 `块基址 + 0x18 + count*0x10`；
- 块 2 上限 0x10000、块 3 上限 0x1000（原版立即数不同，勿混用）；
- 块 3 的 `edi -= 0x18` + `rbx += 0x18` 说明块头 24 字节，与块 1 一致。

## 8. 0x047 块 2/3 的真正根因（2026-10-27，kd 实测确认）

### 8.1 原版/复刻槽值对比（跑完 0x047 后）

| 槽 | 原版 OGT | 复刻 XPCHunterDrv |
|---|---|---|
| GT[0x2B8] | 0xFFFFF80144460920 | **0** |
| GT[0x2B9] | 0 | 0 |
| GT[0x2BA] | 0xFFFFF80144464E6C | **0** |
| GT[0x2BB] | 0xFFFFF8014444AA70 | **0** |

原版这些槽在懒加载后都有值；复刻全 0，于是块 2 一进入
`if (List2 && Size2)` 就失败退出。

### 8.2 槽的真实含义（kd 符号解析）
```
GT[0x2BA] = 0xFFFFF80144464E6C = nt!CmpCallBackCount   <- 注册表回调计数
GT[0x2B8] -> [0xFFFFC0030A91D7A0, 0xFFFFC0030A91D7A0]  <- 空链表头（Flink==Blink）
GT[0x2BB] -> 另一个链表头（Flink/Blink 均有效）
```
即 **块 2 = 注册表回调、块 3 = 另一个回调链表**，与 SSDT 无关。

### 8.3 为什么复刻是 0（与 §6 同一根因）
GT[0x2B8] 的唯一写入者是 `Minifilter.c:8589`
（`EnumerateProcessCallbackContext`，原 0x14003EAA8），
其筛选条件读的正是**同一套 0x120 描述符字段**：
```
+0x50 == 0x40      +0x58 == 1        +0x88 == 0x40000
+0x78 -> RVA 基值   +0xF0 -> 条目长度  +0x118 -> 类型指针（+6 必须 0x558）
```
这与 `FindSsdtTableAddresses` 用的是同一族字段。§6 已确认
**0x120 描述符布局从未按原版改正**（PEDecoder.c 注释自证，审计 P0-1）。
`FindSsdtTableAddresses` 我用"实测 + 运行指针"绕过了，
但 `EnumerateProcessCallbackContext` 没有绕过，所以 GT[0x2B8] 一直是 0。

### 8.4 因此块 2/3 的正确修法
**不是**改链表遍历代码（那部分照原版写的，方向没错；两次 BSOD 是因为
GT[0x2B8] 为 0 时走到了不安全的兜底路径）。真正要做的是
**让 GT[0x2B8] 被正确写入**：按原版 0x14003EAA8 + P0-1 布局表修正
`Minifilter.c` 的 `EnumerateProcessCallbackContext` 中那 6 个字段偏移，
使其能命中类型 0x558 的三层 PE 节区并算出 RVA。

### 8.5 实施顺序（下一轮）
1. 先修 §8.4 的字段偏移 —— 这同时会修复 0x0F6/0x0F4/0x10B 等
   依赖同族扫描的命令；
2. 验证 GT[0x2B8]/[0x2BA]/[0x2BB] 非 0；
3. 块 2/3 的遍历代码保持不动（方向正确），只需保证 GT[0x2B8] 为 0 时
   不要误入危险路径（`Size2` 与 `MmIsAddressValid` 前置判断已在现码里）。
