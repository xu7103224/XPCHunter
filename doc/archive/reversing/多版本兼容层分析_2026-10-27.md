# 目标驱动的多版本兼容层分析（2026-10-27）

对标对象：`View++_Driver64.sys`（PCHunter 2024.09.02）
测试环境：Windows 10 18362 x64（仅覆盖其中一条路径）

本文回答一个问题：**这套驱动到底靠什么适配不同 Windows 版本，我们该照什么实现。**
结论是它没有散落的一堆 if，而是「**一个总闸 + 11 张按版本分派的偏移表 + 若干独立编译期表**」，
其中只有 18362 这一条能在当前 VM 里动态验证，其余必须靠静态比对。

---

## 一、版本号从哪来

1. `DriverEntry` 读 `nt!NtBuildNumber`（内核导出数据符号，不是函数），
   经 `GetWindowsBuildNumber()` 拿到 `dwBuildNumber`。
2. 写入全局表 **`GT[0x914]`（`GtWindowsBuildNumber`）**。
3. 之后全驱动统一用 `GtRead(GtWindowsBuildNumber)` 取版本，**不缓存到寄存器**。

原版二进制里对 `0x914` 这个立即数的引用有 **421 处**，说明版本判断是深度嵌入各子系统的，
不是只在入口做一次。

---

## 二、总闸：`InitEprocessFieldOffsets`（0x14002131C）

这是唯一按版本分派到不同偏移表的函数。原文逻辑（已与我们的实现逐字对齐）：

| 构建号范围 | 十进制 | 对应系统 | 分派函数 |
|---|---|---|---|
| `0x1770`–`0x1772` | 6000–6002 | Vista RTM/SP1/SP2 | `InitEprocessOffsetsWin7` ※ |
| `0x1DB0`–`0x1DB1` | 7600–7601 | Win7 / Win7 SP1 | `InitEprocessOffsetsWin81_Update` ※ |
| `== 9200` | 9200 | Win8 | `InitEprocessOffsetsWin8` |
| `== 9600` | 9600 | Win8.1 | `InitEprocessOffsetsWin81` |
| `== 10240 / 10586` | 10240/10586 | Win10 1507 / 1511 | `InitEprocessOffsetsWin10_10240` |
| `== 14393` | 14393 | Win10 1607 | `InitEprocessOffsetsWin10_14393` |
| `== 15063 / 16299` | 15063/16299 | Win10 1703 / 1709 | `InitEprocessOffsetsWin10_15063` |
| `== 17134 / 17763` | 17134/17763 | Win10 1803 / 1809 | `InitEprocessOffsetsWin10_17134` |
| `== 18362 / 18363` | 18362/18363 | Win10 1903 / 1909 | `InitEprocessOffsetsWin10_18362` |
| `0x4A61`–`0x4A65` | 19041–19045 | Win10 2004 … 22H2 | `InitEprocessOffsetsWin10_19041` |
| `== 20348` | 20348 | Server 2022 | `InitEprocessOffsetsWin11` |
| `== 22000 / 22621 / 22631` | 22000/22621/22631 | Win11 21H2 / 22H2 / 23H2 | `InitEprocessOffsetsWin11` |
| **其它一切** | — | 含 **26100（24H2）** | **`return 0`，初始化失败** |

※ **函数名与范围是错位的**：`InitEprocessOffsetsWin7` 实际服务 6000–6002（Vista），
`InitEprocessOffsetsWin81_Update` 实际服务 7600–7601（Win7）。这是历史命名问题，
**以构建号范围为准**，不要按函数名推断系统。

分派完成后还有三行收尾写入（`GT[GtEprocessField39] = GT[GtEprocessField30] + 8`、
`GT[GtProcessCreateTime] = GT[GtProcessEprocess] + 8`、
`GT[GtEprocessField201] = GT[GtEprocessField202] - 8`）。

### 两个必须知道的边界

- **低于 6000 不支持**：XP(2600)/2003(3790) 会走到 `return 0`，EPROCESS 偏移表不建立。
  XP 时代只支持了 SSDT 服务计数（见第三节）。
- **高于 22631 不支持**：原版不认 26100（Win11 24H2）。我们与之一致也是 `return 0`。
  这不是我们的缺陷，是**原版的能力边界**；若将来要支持 24H2，必须自己补表。

## 三、独立于总闸的第二张版本表：`InitSdstServiceCount`（0x140021004）

写 `GT[0x27]`（`GtSdstServiceCount`），是 SSDT 服务计数：

| 构建号 | 系统 | 计数 |
|---|---|---|
| 2195 | Windows 2000 | 308 |
| 2600 | XP | 320 |
| 3790 | Server 2003 | **SP2 → 215，非 SP2 → 277** |
| 6000–6002 | Vista | 231 |
| 7600–7601 | Win7 | 502 |
| 9200/9600/≥10240 | Win8 及以后 | 562 |

3790 的 SP2 判定由 `CheckWin2k3Sp2`（0x1400210F4）完成：

```c
// 原版 0x1400210F4
CurrentProcess = IoGetCurrentProcess();
return *((_DWORD*)CurrentProcess + 38) > 0x80000000;   // EPROCESS+0x98，严格大于
```

### 本轮发现并修复的两处缺陷

| 位置 | 原版 | 我方（修复前） | 影响 |
|---|---|---|---|
| `CheckWin2k3Sp2` | `Value > 0x80000000` | `Value == 0x80000000` | 除恰好 0x80000000 外全部漏判 |
| `InitSdstServiceCount` 的 3790 分支 | `SP2 ? 215 : 277` | 写死 `277` | Server 2003 SP2 上 SSDT 计数错 62 |

两处都在 XP/2003 路径上，Win10 永远走不到，因此动态测试发现不了 —— 正是本文要防的盲区。

## 四、其它与版本相关的独立编译期开关（已确认）

| 位置 | 门限 | 行为 |
|---|---|---|
| `HookSyscallNtLoadDriver` 0x140020E0F | `< 0x3FAB`（16363） | 只有低于 16363 才做两阶段 PE 节区扫描去找 NtLoadDriver；新版直接跳过并清零相关 GT 槽 |
| `ScanKernelPeExportData` 0x14003F232 | 由 `GT[0x435D]` 起始偏移决定 | 见 0x047 块 11 的修复记录 |
| `MemoryCleanup` 条目数 | `< 0x3FAB ? 8 : 32` | 扫描条目上限随版本变化 |
| `GtEprocessFieldOffsets` 收尾 | 无 | 三行派生偏移（见第二节） |

另有按 `构建号 == 0x3FAB` 或 `>= 0x4F7C` 选择 `GT[0x4450]` 低位取值的分支
（`DriverEntry.c:6041`，对应原版 `0x14006E053`）。

## 六、我方当前状态

- 11 个 `InitEprocessOffsetsWin*` 与 `InitEprocessFieldOffsets` 总闸：**已全部实现，总闸逻辑逐字一致**。
- `InitSdstServiceCount` / `CheckWin2k3Sp2`：本轮修掉两处偏差（第三节）。
- 常量层面：原版使用的构建号常量我方差一个 `16363`（`0x3FAB`），
  但它以十六进制形式存在于 `MemoryCleanup.c`、`DriverEntry.c`，**不是缺口**。
- 构建 0 警告 0 错误。

### 尚未做的验证（重要）

**只有 18362 这一条路径被动态验证过**（0x047 / 0x0D5 逐字节一致、GT 槽逐项相同）。
其余 10 张偏移表（约 1000+ 条槽位赋值）**只做了结构对照，没有逐值比对**。

## 七、怎么补上其余版本的验证

### 方法 A：静态逐值比对（无需其它系统）

对每个 `InitEprocessOffsetsWin*`：

1. IDA 里拿到原版函数（地址见第二节表格）的 `GtWrite(slot, value)` 序列；
2. 从 `DriverEntry.c` 抽取我方同名函数的 `GtWrite(符号, 常量)` 序列；
3. 两边把符号解析成数字槽位后，**按顺序 diff**。

已知规模：18362 表 524 条指令 / 182 个常量；Win8.1 表 169 次调用；Win11 表 0xD7A 字节。
这是一项纯机械工作，可以脚本化，但**必须逐表做完才算真正对标**。

### 方法 B：动态验证（需要对应系统）

在目标系统上分别加载原版与我方，用 kd dump 全局表 `GT[0 .. 0x920]`
（偏移表最高用到 2304 = 0x900），逐槽 diff。
这是唯一能覆盖「偏移表 + 所有散落版本门限」的方法。
注意 GT 里含内核指针，两侧同一会话内才会相同；跨会话只能比较"非指针槽"。

### 方法 C：廉价回归（推荐先做）

即便没有其它系统，也可以把 `GT[0x914]` **临时改成目标构建号**再跑一次回归
（只改版本号、不改真实系统），观察各子系统是否走对分支、是否崩。
这能覆盖"分支选择正确性"，但覆盖不了"偏移值是否与该系统真实结构匹配"。

## 八、给后续实现的三条硬约束

1. **不要按函数名推断系统版本**。`InitEprocessOffsetsWin7` 服务的是 Vista，
   `InitEprocessOffsetsWin81_Update` 服务的是 Win7。以构建号范围为准。
2. **不要给不支持的构建号"兜底"**。原版对 <6000 和 >22631 一律 `return 0`，
   我们若擅自加默认表，会产生原版没有的行为，破坏对标。
3. **改动任何 `InitEprocessOffsetsWin*` 后必须回归 0x047 / 0x0D5 / 0x0D4 / 0x0FF / 0x0E4**。
   这些命令的条目数直接依赖偏移表（例如 `GtCallbackField101` = EPROCESS 对象类型索引偏移，
   `GtObjectTypeCount` = 2080，`GtEprocessModuleListOffset` 等）。

## 九、逐值对拍结果（2026-10-27 收尾）：11/11 张表完全对齐

### 方法

原版侧不再用线性反汇编扫描——它在**分支合并处会取错槽位**（实测产生过两类假阳性，
详见第十节）。最终改用 **CFG 感知的常量传播**（`build/audit/gt_cfg_extract.py`）：
按跳转目标切基本块，前向传播寄存器常量，多前驱取交集，在 `call/jmp GtWrite` 处读取
`ecx`/`rdx`。11 张表共 1438 条 `GtWrite`，**槽位未解析数 = 0**。

我方侧不用正则猜符号——把源码里 `GtWrite` 的第一个实参交给 C 编译器求值
（`build/audit/cmp_gt_cfg.py` 生成探针程序 + clang 编译执行），得到与编译产物一致的槽号。
这条很关键：`xpc_gt_enum.h` 里同一符号既有枚举值又有后置 `#define` 别名，
手工解析必然出错。

### 结果

| 表 | 原版条目 | 我方条目 | 对齐 | 值不同 | 仅原版 | 仅我方 |
|---|---|---|---|---|---|---|
| Win7 | 144 | 144 | 144 | 0 | 0 | 0 |
| Win8 | 133 | 133 | 133 | 0 | 0 | 0 |
| Win81 | 135 | 135 | 135 | 0 | 0 | 0 |
| Win81_Update | 133 | 133 | 133 | 0 | 0 | 0 |
| Win10_10240 | 140 | 140 | 140 | 0 | 0 | 0 |
| Win10_14393 | 134 | 134 | 134 | 0 | 0 | 0 |
| Win10_15063 | 148 | 148 | 148 | 0 | 0 | 0 |
| Win10_17134 | 147 | 147 | 147 | 0 | 0 | 0 |
| Win10_18362 | 134 | 134 | 134 | 0 | 0 | 0 |
| Win10_19041 | 134 | 134 | 134 | 0 | 0 | 0 |
| Win11 | 180 | 180 | 180 | 0 | 0 | 0 |

`(槽位, 值)` 序列逐项相同，包含所有带构建号分支的写入（如
`GtWrite(GtEprocessField34, build == 10240 ? 1648 : 1656)` 这类）。

复现：`python build/audit/cmp_gt_cfg.py`

### 本轮真正修掉的三处

1. **`GtEprocessField131/132 | 0x100` 槽号错误（11 张表全部受影响）**。
   这两个表达式经编译器求值得到 `0x183`/`0x170`，而原版对应写的是
   `0x18D`/`0x18E`。已改为显式槽号。
2. **`InitEprocessOffsetsWin10_18362` 尾部 5 条重复写入**。
   早先为补"GT[0x18B..0x18E] 恒 0"追加了一段补丁，但上述槽号修好后前段已正确写入，
   补丁变成重复（原版这些槽只写一次）。已删除。
3. **`CheckWin2k3Sp2` 比较运算符 + `InitSdstServiceCount` 的 3790 SP2 分支**（见第三节）。

### 实机回归

改完后重新构建（0 警告 0 错误）、部署到 Win10 18362 验证：

- 驱动正常加载（`sc start` 返回 0，STATE RUNNING）；
- `0x047` 与原版基线**逐字节一致**（`diffbytes=0`），说明偏移表改动没有引入回归；
- `0x0D5` 计数 29（原版同条件下 26/28）属已定性的"服务刚删除后对象滞留"瞬态；
- `0x0D4` 仍是独立缺陷（我方条目数为原版约 2 倍），与本轮偏移表改动无关。

## 十、为什么必须用 CFG 提取（两个实测假阳性）

线性扫描在两处把**不该配对的槽位和值配到了一起**，如果据此改代码会引入真实错误：

**假阳性 1：`0x140025233`（10240 表）**
```
140025202  lea ecx, [rbx-0Ch]
140025205  cmp eax, ebp
140025207  jnz  loc_14002522E      ; 走 else 时 ecx 仍是 rbx-0Ch
140025221  lea ecx, [rbx-0Ah]      ; 这是 then 路径才执行的
14002522E: mov edx, 164h
140025233  call GtWrite            ; else 路径实际用 rbx-0Ch
```
线性扫描看到最近的 `lea ecx` 是 `rbx-0Ah`，误判为 `0x1DA`；实际 else 路径是
`rbx-0Ch` = `0x1D8`，与我方一致。

**假阳性 2：`0x140021BA1`（Win7 表）** 类似，条件跳转目标里的 `lea ecx` 被误当成前驱。

**假阳性 3：0x18B=0（Win81 / Win81_Update）** 三分支各写一次同一槽，线性扫描在
`xor edx,edx` 分支上丢失了 `ecx`。

结论：**在这类"多分支写同一批槽位"的代码上，必须做 CFG/数据流分析，
线性反汇编不可作为改码依据。**
