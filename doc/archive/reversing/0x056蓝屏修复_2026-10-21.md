# 0x056 蓝屏根因定位与修复（G2 卡点解除）

## 一、结论

`0x056 CmdEnumObjectAllTypes` 现在 **`result=1`，两个缓冲尺寸都不再蓝屏**，
输出是真实的设备对象枚举数据。

| 缓冲 | 结果 | 条目 |
| --- | --- | --- |
| 0x2000（可容 3 条） | `OK result=1` | 3 条，正好填满，无越界 |
| 0x20000（可容 50 条） | `OK result=1` | 6 条 |

修复后紧接着调 `0x117` 仍 `OK`，证明 guest 存活、未蓝屏。
证据：`evidence/0x056_fixed_2026-10-21.txt`

## 二、两处独立缺陷（都已用 WinDbg 调用栈实证）

### 缺陷 1：64 位内核指针被截断成 32 位

`EnumDeviceObjects`（RVA 0x682a0）里：

```c
ULONG InitResult;                                   /* ← 32 位，装不下指针 */
InitResult = (ULONG)(ULONG_PTR)InitSystemPath();
...
((WORD *)PathBuffer)[4] = *(WORD *)(ULONG_PTR)InitResult;   /* ← 解引用截断值 */
```

`InitSystemPath()` 返回 `ffffc30a`0d132b30`，截断后变 `0x0d132b30`（用户态垃圾），
解引用即 0xC0000005。

**WinDbg 实证**（`VPChainG`，bugcheck arg1=c0000005）：

```
VPChainG+0x68382  call  VPChainG+0x7c550        ; InitSystemPath
VPChainG+0x6838f  mov   ecx,eax                 ; ← 把 64 位返回值截成 32 位
VPChainG+0x68391  movzx eax,word ptr [rcx]      ; ← 崩溃点
```
bugcheck **Arg3 = ffffc30a`0d132b30**，与截断前的原指针完全吻合。

**修复**：`ULONG64 InitResult`，并去掉多余的 `(ULONG_PTR)` 强转。

### 缺陷 2：`CloseHandleFunc()` 无参数调用，但它是 `ObfDereferenceObject`

`QueryDriverObjectByPath`（RVA 0x684f0）里：

```c
void (*CloseHandleFunc)(void) = (void (*)(void))GtRead(GtCloseHandleFunc);
...
CloseHandleFunc();          /* ← 不传参 */
```

`GT[0x4223]` 实际是 `ObDereferenceObject`，它把 `rcx` 当 OBJECT_HEADER 指针做
`lock xadd qword ptr [rcx-30h], rbx`。不传参 → rcx 是上一条指令的残留值 → 崩。

**WinDbg 实证**（`VPChainH`，bugcheck arg1=c0000005）：

```
nt!ObfDereferenceObject+0x26     lock xadd [rsi-30h],rbx   ← rsi 无效
VPChainH+0x68616                 ← 本函数内 (0x684f0+0x126)
VPChainH+0x25a9b                 ← CmdEnumObjectAllTypes 内
VPChainH+0x1184e                 ← 命令分派
nt!IofCallDriver
nt!NtDeviceIoControlFile
```

**修复**：改为 `void (*)(__int64)`，调用处 `CloseHandleFunc(FileHandle);`
（原版 0x1400084D9 正是 `mov rcx,[rsp+88h+var_48]` 后才 call）。

### 附带修正：OBJECT_ATTRIBUTES / UNICODE_STRING 的栈布局

`EnumDeviceObjects` 里 `RtlInitUnicodeString` 会写满 16 字节，而原代码把目标
存在 `__int64 ResultInfo`（8 字节）里，溢出冲掉相邻局部；
`OBJECT_ATTRIBUTES` 又由 4 个独立变量拼成，字段不保证连续。

**修复**：改用真正的 `UNICODE_STRING` / `OBJECT_ATTRIBUTES` / `IO_STATUS_BLOCK`，
并按原版填 `Length=0x30`、`Attributes=0x240`、`ObjectName=&DeviceName`。

## 三、修复前后对照

| 版本 | 症状 |
| --- | --- |
| 修复前 | 0x2000 缓冲即蓝屏 0x3B，崩溃点 `VPChainG+0x68391`（指针截断） |
| 仅修 MaxEntries 下溢 | 仍蓝屏，崩溃点漂到 `VPChainB+0x68391`（同一处，说明下溢不是主因） |
| 修指针截断后 | 崩溃点变到 `nt!ObfDereferenceObject`，栈指向 `QueryDriverObjectByPath` |
| 再修 CloseHandle 传参 | **通过**：两个尺寸都 `result=1`，数据有效 |

> 「MaxEntries 下溢」那条改动保留 —— 它是真实的防御缺口（枚举器返回数可能大于
> 剩余量），只是不是本机这次崩溃的主因。

## 四、对验收门的影响

**G2（驱动零崩溃）** 的直接卡点解除。此前每次 `--scan` 之外的 0x056 手工测试都会
打挂 VM；现在 0x2000 与 0x20000 两个尺寸均正常返回。

仍然待做的崩溃排查：`0x2A`（挂死，非蓝屏）、`0x25`/`0x3C`（早期记录会崩，
本轮未复测）。
