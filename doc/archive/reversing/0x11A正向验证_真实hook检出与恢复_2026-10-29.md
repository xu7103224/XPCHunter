# 0x11A 正向验证：真实 hook 检出与自动恢复（2026-10-29）

## 0. 结论

**`0x11A QueryHookStatus` 的正向路径已验证通过。**
用 KD 修改系统调用入口首字节制造真实 inline hook，
检测返回 1，并且驱动**自动恢复了原始字节**，再次检测返回 0。

这是此前唯一缺失的验证项（之前只测了干净系统返回 0）。

## 2. 目标入口点的真实身份

用 `0x119` 取基线第 0 项：

```
[00] +0x00008 = 0xFFFFF8063EE2F3D0   ← 当前地址
[01] +0x00010 = 0xFFFFF8063EE2F3D0   ← 原始地址（相同）
[02] +0x00018 = 0x013657E828EC8348   ← 原始字节
[03] +0x00020 = 0xCCCCC328C4834800
```

用 KD 查这个地址：

```
kd> ln 0xFFFFF8063EE2F3D0
(fffff806`3ee2f3d0)  Wdf01000!LibraryCommission

kd> u 0xFFFFF8063EE2F3D0 L3
Wdf01000!LibraryCommission:
fffff806`3ee2f3d0 4883ec28   sub  rsp,28h
fffff806`3ee2f3d4 e857360100 call Wdf01000!FxLibraryCommonCommission
fffff806`3ee2f3d9 4883c428   add  rsp,28h
```

**重要发现**：`0x117`/`0x118`/`0x119`/`0x11A` 这套接口检测的
**不是内核 SSDT 入口点，而是 wdf01000.sys 内部的 Hook 表**。
这与 `HookViews.c` 里已有的说明一致（「这两张表是 Wdf01000.sys 内部的
Hook 表，属 Ring0 Hooks 页」）。

这解释了为什么 `0x117` 返回的 908 条看起来像普通函数——
它们是 wdf01000.sys 的导出函数地址表。

## 3. 正向验证（三步闭环）

### 3.1 制造 hook

```
kd> eb 0xFFFFF8063EE2F3D0 49
kd> db 0xFFFFF8063EE2F3D0 L8
fffff806`3ee2f3d0  49 83 ec 28 e8 57 36 01     I..(.W6.
```

首字节 `48` → `49`（`sub rsp,28h` 的 REX 前缀被改）。

### 3.2 检测 → 返回 1

```
kd> g     (让系统跑起来)
```

```
> xpch_probe.exe --live --raw 0x11A 0x10 --inhex 0000000000000000D0F3E23E06F8FFFF
=== raw 0x11A outSize=0x10 -> OK result=1 ===
```

**`result=1`——检测到了钩子。** 这是此前从未观察到的正向结果。

### 3.3 自动恢复（驱动的副作用）

紧接着再调用一次：

```
> xpch_probe.exe --live --raw 0x11A 0x10 --inhex ...同上...
=== raw 0x11A outSize=0x10 -> REJECTED result=0 ===
```

返回 0 说明 hook 已经不在了。用 KD 确认：

```
kd> db 0xFFFFF8063EE2F3D0 L8
fffff806`3ee2f3d0  48 83 ec 28 e8 57 36 01     H..(.W6.
```

**我没有任何恢复操作，字节自己回到了 `48`。**

这是 `QuerySyscallHookStatus` 里 `WritePhysicalMemoryBuffer(addr, 基线字节, 16, 0, 0)`
的作用——原版的「检测即恢复」行为，被我按原样转写了。

## 4. 一次调用内的完整时序

| 时刻 | 内存字节 | `0x11A` 返回 | 说明 |
|---|---|---|---|
| T0 | `48 83 ec 28 ...` | 0 | 干净 |
| T1 | `49 83 ec 28 ...` | — | KD 注入 hook |
| T2 | `49 83 ec 28 ...` | **1** | 检出，并写回基线 |
| T3 | `48 83 ec 28 ...` | 0 | 已被 T2 恢复 |

**三段证据齐全**：检出（0→1）、恢复（字节回退）、复检（1→0）。

## 6. 发现的一个真实缺陷（原版也有）

验证过程中观察到：**`0x11A` 检测一次后，`0x119` 会失效**（返回 0）。

现象：

```
T2: 0x11A → 1   (检出并恢复)
T2: 0x119 → 0   (原本返回 1，现在失败)
sc stop/start XPCHunterDrv
T3: 0x119 → 1   (重载驱动后恢复)
```

根因：`QuerySyscallHookStatus` 恢复时写回的是
`GT[0x8B5]` 指向的表项（`SyscallTable + index + 1`），
而 `GetHookEntryInfo` 用的是 `GT[0x895]` 的表。两个槽指向同一块内存区域，
所以 `0x11A` 的写操作破坏了 `0x119` 依赖的 `CheckMemoryValid(pTableCopy + 55)` 前提。

**这是原版行为，我忠实转写了。** 实际使用中不会连调这两条命令
（`0x119` 用于取详情，`0x11A` 用于检测/恢复），所以不影响原版功能。
但如果将来要做「刷新 UI 时同时调两条」，需要注意这个耦合。

可选的改进（需决策）：把 `0x11A` 的恢复动作拆出去，只保留检测，
恢复交给 `0x118`（`RestoreSyscallHookByIndex`，本来就有完整恢复逻辑）。
这样 `0x11A` 变成真正无副作用的查询接口。但会偏离原版语义。

## 7. 验证方法（可复现）

```batch
:: 前提：主机放开 kd.exe 防火墙、确认 50000 端口无残留进程
netstat -ano | findstr ":50000"        :: 若有 kd.exe 残留则 Stop-Process

kd_attach(wait_for_target=false)
vm_reboot(reattach_kd=true)
kd_exec "vertarget"                    :: 确认 Windows 10 Kernel Version 18362

:: 装载我方驱动
sc start XPCHunterDrv

:: 取基线
xpch_probe.exe --live --xdump 0x119 0xB0 8 4

:: 制造 hook（首字节 48 → 49）
kd_exec "eb 0xFFFFF8063EE2F3D0 49"
kd_exec "g"

:: 检测（应为 1）
xpch_probe.exe --live --raw 0x11A 0x10 --inhex 0000000000000000D0F3E23E06F8FFFF

:: 确认自动恢复后为 0
xpch_probe.exe --live --raw 0x11A 0x10 --inhex ...同上...
kd_exec "db 0xFFFFF8063EE2F3D0 L8"     :: 应回到 48 83 ec 28

:: 健康检查
xpch_frontend.exe --ring0-cli
xpch_frontend.exe --devobj-cli
```

> 地址 `0xFFFFF8063EE2F3D0` 是本次会话的值，每次启动会变，
> 需先用 `0x119` 取当前基线地址。字节内容 `48 83 ec 28` 是稳定的。
