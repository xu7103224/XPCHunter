# 第二步增量 4：Process 页双击下钻（2026-10-28）

范围：双击进程行 → 按**当前子 Tab** 重查该 PID 的数据源并填入详情区，
焦点移到详情列表。复用既有 `FeLoadXxx`，不新增任何查询路径。

## 一、实现内容

### 1.1 `FeProcPageDrillDown()`（FeProcPage.c）

```
读选中行 → 取 PID → 读当前子 Tab（越界归 0）
       → g_DetailTab = -1（强制重建列集/列宽，不残留上一个 PID 的状态）
       → DoRefreshDetail()（既有函数，内部按 tab 选 FeLoadXxx）
       → SetFocus(g_hDetail) + 选中首行
       → 状态栏回报 "Drill-down: PID N, <View> - M rows (focus in detail)"
```

- **强制重建列**是关键：`DoRefreshDetail` 原本只在 `tab != g_DetailTab` 时重建列。
  下钻时把 `g_DetailTab` 置 -1，确保详情区一定是"当前 Tab + 当前 PID"的确定
  状态，不会沿用上一个进程的列宽。
- 七个子视图全部支持：Modules / Threads / Windows / Handles / Memory /
  Timer / HotKey（`FeLoadProcessModules` / `FeLoadProcessThreads` /
  `FeLoadProcessWindows` / `FeLoadProcessHandles` / `FeLoadProcessMemory` …）。
- 无选中行时状态栏提示 `Double-click a process row to drill down`，不静默失败。

### 1.2 接线（frontend.c）

```c
if (nm->idFrom == IDC_PROCLIST && nm->code == NM_DBLCLK) {
    FeProcPageDrillDown();
    return 0;
}
```

### 1.3 自动化入口

- `--drill-test N`：启动 → 选第 N 行 → 走**同一个** `FeProcPageDrillDown`
  → 打印 `ok/tab/detail_rows` → 退出。与双击事件完全同路径。
- `--selftest-drill-cli PID`：在进程内对指定 PID 分别调 Threads / Modules
  数据源，验证下钻的承重部分是"按 PID + 子视图调 FeLoadXxx"这条链路可用。
  断言 Threads > 0（任何存活进程至少 1 个线程）；Modules 对 System 类进程
  返回 0 属正常，仅作信息输出。

## 二、验收

### 2.1 数据链路（`--selftest-drill-cli`）

```
# PID 4 (System)
drill selftest: pid=4
  threads=138 OK
  modules: unavailable for this PID (expected for System)
drill selftest: PASSED

# PID 4008 (explorer.exe)，连跑两次结果一致
drill selftest: pid=4008
  threads=42 OK
  modules=240 (informational)
drill selftest: PASSED
```

### 2.2 子 Tab 切换（`--drill-test N --tab K`）

```
--- tab0 Modules, pick 0 ---
drill-test: procs=10 pick=0
drill-test: ok=1 tab=0 detail_rows=0
--- tab1 Threads, pick 0 ---
drill-test: ok=1 tab=1 detail_rows=0
--- tab1 Threads, pick 5 ---
drill-test: ok=1 tab=1 detail_rows=0
--- tab3 Handles, pick 0 ---
drill-test: ok=1 tab=3 detail_rows=0
```

`ok=1` 且 `tab` 随 `--tab` 正确切换 ⇒ 下钻动作本身成功。
`detail_rows=0` 的原因见 §3：本 guest 进程列表的 PID 全是同一个无效值，
`FeLoadXxx` 自然查不到数据。**这是既有驱动行为，不是下钻的缺陷**——
§2.1 已用真实 PID 证明同一批 `FeLoadXxx` 能取到 42 线程 / 240 模块。

### 2.3 CLI 防回归（同 boot 背靠背双客户端）

| 分类 | 条数 |
|---|---|
| 逐字节一致 | **39 / 45** |
| 已知天然时变 | 6（gdt 落核漂移 / exam / fireeye / filever / handles / threads） |

**0 条代码回归。**

## 三、已知环境限制（与增量2/3 同源）

本 guest 的 `0x0E4`（CmdEnumProcessListWin10）返回 10 条记录，PID 全部是
`458383552`（无效值）、Name 为空、Path 为空。已记录在
`docs/reversing/剩余四条命令状态与下一步_2026-10-27.md` §2：原版该命令的
条目 `+0x08` 起就是 0，我们按原版对齐后同样如此。因此：

- 进程列表只能按 PID 列/状态列筛选（增量2 已如此验证）；
- 双击下钻到 Modules/Threads 时 `FeLoadXxx(无效PID)` 返回空。

在真实 Windows 上（0x0E4 正常返回真实 PID）下钻会直接出数据；
按 PID 4 / 4008 的自检已证明数据链路本身完好。
